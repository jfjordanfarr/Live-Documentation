## What works, and what a newcomer has to learn

The product already makes useful answers tangible. The small estate is the clearest introduction: recognizable systems, a visible chain, then the routes, configuration and files behind a piece ([17](17-estate-world.png), [18](18-estate-evidence.png)). The file reader’s Purpose answers a different and necessary question from the wires ([14](14-evidence.png)). Knowledge Sources is unusually candid about files that were not read and the limits of reachability. A question and its evidence survive sharing into a fresh context ([16](16-shared-fresh.png)). These are substantial foundations for release. The estate’s 36 generated file docs all have pending authored Purpose sections, so its useful system-level explanation does not depend on the extensive prose this repository has accumulated.

The newcomer still has to learn several distinctions through trial: view versus representation; inspect versus pin versus centre; a source reference versus a directory containment line; a current file versus a historical identity; a static snapshot versus a live project. Each distinction is useful. The work is to make their consequences clear where they matter, without turning the canvas into a tutorial.

## The distance to release

The gap is a set of unfinished journeys rather than a defensible percentage or date. The map and evidence model are considerably further along than obtaining the tool, making one’s own first map, composing an estate and handing it to somebody else.

1. **A useful cold start on someone else’s folder.** The getting-started guide begins by cloning this development repository, then runs repository npm scripts; it never completes the transition to the reader’s own project. It describes the generic `.live-documentation/source/` default even though the shown repository command passes this repository’s `.mdmd` configuration. Its path example names files that do not exist in the checkout. The CLI package is private version 0.0.0, its dependencies are sibling `file:` references, and its entry point launches TypeScript scripts from the monorepo. The shipping work is real: finish the package-first delivery already selected on October 10 ([the World Map decision](../../../.mdmd/layer-3/world-map.mdmd.md#open-questions)), settle its remaining scan-root/configuration behavior, preserve useful unannotated output, and test a complete first-run guide. Improving the guide alone would not make the package distributable.
2. **An exploration that explains itself.** Finish the accepted Local Map repairs, recoverable framing, readable direction, useful disclosure, and the relationship between inspecting, retaining and navigating. The history panel is a small, concrete example: let a person keep the timeline and hide the details. Broader system/file transitions and Structure choices still require design. Tuning should remain available without being a prerequisite for comprehension.
3. **The World Map people can make and trade.** The estate viewer shows why this matters. Creating a board, adding systems/snapshots, joining evidence and declarations, saving it, and exchanging it remain substantial product work. Saving positions from an existing board is only part of authoring. The portable, self-contained file and the scan/delivery choices in owner direction need completing in their intended order; no new packaging choice is made by this review.
4. **A clear promise about what the map knows.** Publish a concrete support contract by project shape and kind of relationship, backed by independent oracles and real unfamiliar projects. Keep unsupported files, unresolved references, dynamic relationships and declared facts understandable. Ruby’s missing oracle and unresolved discovery/asset cases remain real gaps, but “all languages and all frameworks” would be an unbounded release criterion. Explain snapshot provenance and history sampling as well as graph counts. The current separation of unread from unreachable is a strong starting point.
5. **A dependable artifact people can keep using.** Verify the selected installation, supported platforms and browsers, useful keyboard and small-screen operation, repeatable regeneration, preserved authored notes, update/migration behavior, and an exported map reopened elsewhere. Decide what compatibility is promised for markdown, boards, history and shared addresses. Give the distributable output a clear boundary: today’s reused `dist/explorer/` also held an obsolete easing page and about 67 MiB of Structure comparisons. The comparisons explicitly remain available until the owner judges them, so they are useful local work rather than a release deliverable. A publishable bundle should not silently inherit experiment pages from its output directory. This is the point at which the owner’s transition to PRs protects people relying on the product’s contract.

A useful release rehearsal would give a person unfamiliar with this repository a supported project and no private instructions. They obtain the tool, generate a useful map without writing Purpose sections first, find an entry point, trace a relationship, verify its evidence, recognize one blind spot, share the result with a second person, change the code and regenerate without losing authored work. The second person can open and understand the result without this development checkout. Repeat across a small, deliberately different set of project shapes. That exercises a proposed release bar; it does not silently declare the unfinished broader vision out of scope.

My suggested order is to finish the already accepted Explorer comprehension work, then exercise the cold-start journey through the selected package-first delivery and resolve the remaining scan choices, then complete World Map authoring and portable exchange. Keep the history panel as the next small repair: independent detail visibility, created/deleted wording, and an intelligible indication when the selected file is outside the displayed time. Each of those next changes should be designed with the owner before enlarging implementation scope.

Discovery’s existing lockfile rule was missing the Dev Containers names. The [session record](../../ChatHistory/2026/10/2026-10-26.1.record.md#verification-finding-and-repair-scope) records the provenance, official format references and repair. Default discovery and explicit inclusion tests first reproduced the fault while preserving ordinary configuration and similarly named source files. The screenshots above retain the pre-repair 878-file bundle as observed; removing the unintended generated lockfile doc will change today’s inventory, not these historical observations. The actual lockfile is preserved.

Output cleanup: the retained Structure comparison is still justified by its [probe record](../../Probes/2026-10-24/structure-sizing/README.md), which explicitly keeps those local pages until the owner judges them, so it was preserved. The obsolete `dist/explorer/probes/easing/` page (HTML, compiled JS and source map, about 11 MiB) had no source/test consumers; its [probe’s October 21 outcome](../../Probes/2026-10-19/easing/README.md#outcome-2026-10-21) records the selected motion and links the production captures. Those ignored disposable build artifacts were removed; all committed probe evidence and findings remain.

Final verification: `npm run safe:commit -- --e2e` passed in full after the discovery repair and correction of this review’s initial bad heading link: 1,406 unit tests, 113 integration tests and 206 browser cases (29.6 minutes), with lint, builds, type checks and all documentation audits. The actual feature lock remains; the generated corpus is now 877 files. The 646-commit historical sequence has not been recomputed under the changed discovery lens.
