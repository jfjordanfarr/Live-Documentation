## The MDMD convention, as it stands

The four-layer convention this repository keeps under `.mdmd/` is the owner's, and it changed shape through the archive. The trail, dated, so that no agent mines it again:

- **2025-10-19.** "Membrane Design MarkDown": four layers from most public to most internal, vision (1), requirements and roadmap (2), architecture and solution components (3), one implementation doc per source file, "somewhat like a more human-readable C Header file" (4), each layer linking to the next and layer 4 to code. They authored layer 4 first and implemented against it.
- **2025-10-30.** "MDMD is a convenient convention -- a structure emergent of good configuration of our available tooling -- not a constant in the VS Code Extension we're building itself." Restated on 2026-02-15 ("a _workspace_ convention that is totally tangential to Live Documentation") and enforced on 2026-02-23 by removing code that expected it.
- **2025-11-08 to 11-16.** Layer 4 became the generated base layer of Live Documentation, and configuration put it back under `.mdmd/layer-4/` with the `.mdmd.md` extension: "I am okay if we want to configure the name for our output Live Documentation to something which fits into the big ol' stack of MDMD."
- **2025-11-10.** The layers above: "there shouldn't be a need to link _beyond_ one layer up or down (and preferably just down). The design for the layers should be such that each can somewhat comfortably tame the chaos beneath it, and itself be chaos to be tamed for the layer above it." "layer 4 can easily be programmatically determined, almost in full, from code, and layer 3 can be almost entirely programmatically determined from layer 4. Layer 2 cannot be programmatically determined from layer 3. Nor layer 1." Generated sections for layers 1 and 2 were "extremely far fetched". The numbers stayed, for Kahneman's reason: "we don't have precise English words that _exactly_ match the _full_ description of what these _things_ actually _are_."
- **2025-11-19 to 2025-12-12.** The generated system layer, layer 3 derived from layer 4 by clustering, produced "difficult-to-read statistical artifacts"; the layer-3 docs became "heavily edited versions of the materialized system views"; the rule that layer 3 link every layer-4 doc was disabled, and the closure of layer 2 into layer 1 with it: "That was a really wonderful _idea_, but messy in _practice_... what remained was only the guarantee of the 'Base Layer' ('layer 4' in our convention of MDMD) matching (via markdown link) to each implementation, test, or asset file." Layers 1 and 2 are authored only. "It is both acceptable and accurate to imply that Layer 3 is not yet figured out." On whether layer 3 never needs a generated section again: "I'm not confident that the statement is 'forever true'."
- **2026-09-27.** The system layer and its clustering deleted, "so the new layer is not shaped by the old code"; the layer-1 vision rewritten; layer 3 holds the authored architecture docs and the decisions log; layer 4 is the base layer under the strict grammar.
- **2026-09-28, open.** Asked where the facts the World Map needs should grow "with respect to the 'MDMD' convention", the owner wondered whether "that's a layer 3 concern". The agent's proposal, not yet answered: the observed facts (how an edge is known, openings, manifests, a folder's kind) grow the base layer's grammar; what a person declares about an estate is a system-scale doc with the same shape as a file's, a generated region for what the scans found and an authored region for the rest, placed by configuration, which this repository would put in layer 3.

## Theses they have flagged for later

- **Common sense in, common sense out.** "I am using a common sense engine (LLMs) to solve a common sense problem (software architecture understanding)." They hope that once semantic intent is codified, "the same rough shape must always result from it. (Not just because it is idiomatic or sensible but because it is correct)." They call this self-healing and says the old chats show them reaching for it. "A heady topic for later perhaps."
- **Measuring correctness may be circular.** "My best tools for discovering the shape of a program are the tools I would use to evaluate my success in evaluating the shape of a program. This is totally unsolved in my opinion." (2026-09-26) Compiler resolution is the current answer, and they asked that the vision not sound "unnecessarily reactionary" about self-grading once the cleanup is done.
- **Prose rots between links.** Links are checked; the words between them are not. They loved the problem: "I wonder if we could use Live Documentation or VSCode to try to locate these putative symbol/file references and enforce them in markdown." See [ideas.md](ideas.md).

**Two dimensions, or the browser?** (2026-10-07, [Turn 19](../ChatHistory/2026/10/2026-10-06.1.record.md#turn-19)). On seeing the wider space buy only a percent or two: "I still admit maybe a smidgeon of surprise that adding more levers to tune, more forces to contend with, more scores' dimensions to optimize, that we couldn't get a _little_ more optimal. Perhaps we're smacking into the limits of what a 2D diagram can do, and perhaps we're smacking into the limits of what deterministic layouts in a browser will allow (i.e. membrane overlap an _impossibility_, etc.)." And from dimensionality reduction: "allowing _juuuust a little non-orthogonality_ in things like PCA can wildly improve the ability of the reduced-dimensional representation to capture the true variation in high-dimensional space. ... To you, is improvement more constrainted by two dimensions, or by the browser?" The agent's answer that day: by neither, but by the layout's own rules (left-to-right flow, membranes that never interleave, cards wires do not pass, one column per rank), none of them the browser's; the browser measures text and paints. The owner's "little non-orthogonality" is a rule made a lever of the lab and swept, which is the open path.
