### Option 2: Configuration/Resource Archetype

**Current State:**
- Current archetypes: `implementation`, `test`, `asset`
- Config files (`.json`, `.xml`, Web.config, appsettings.json) fall into **asset** archetype
- Assets don't get `Public Symbols` or `Dependencies` sections — they get `Consumers` (who references them)

**Conceptual Challenge:**
Configuration files DO expose "public symbols" in a sense:
- Web.config has `<appSettings>` keys like `EnableWidget`, `ClientConfig`
- appsettings.json has keys like `Telemetry.Endpoint`, `Telemetry.InstrumentationKey`
- `.env-template` has environment variable names

But the **semantics differ** from code symbols:
- Code symbols: `function doThing(x)` — callable, has signature, has documentation
- Config "symbols": `"ConnectionString"` — a **key** that code **reads**, not **calls**

**Potential Design:**
```markdown
## Metadata
- Archetype: configuration (or "resource")
- Format: XML | JSON | YAML | INI | ENV
- Keys Exposed: ConnectionString, EnableWidget, Telemetry.Endpoint

## Dependencies
- Schema: AppSettings.xsd (if present)
- Transforms: Web.Release.config (config transforms)

## Consumers
- [DatabaseService.cs](./DatabaseService.cs.mdmd.md) (reads `ConnectionString`)
```

**Technical Challenges:**
1. **No standard format**: XML/JSON/YAML/INI/ENV all differ
2. **No standard key extraction**: JSON keys vs XML attributes vs dotted paths
3. **No way to detect "who reads this key"** without code analysis (grep for key names)
4. **Key names are often magic strings** that analyzers can't trace

**Value Assessment:**
- This is **exploratory research** territory
- Would require:
  - New archetype definition
  - Format-specific key extractors (JSON path walker, XML XPath extractor)
  - Heuristic detection of key usage in code (grep for string literals matching keys)
- High reward for **configuration-heavy projects** (ASP.NET, Spring Boot, etc.)
- Lower reward for this repository (we don't have many config files)
