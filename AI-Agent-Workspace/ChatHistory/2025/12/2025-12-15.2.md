## The Network-Free CI Test: What Happened

### What I Wanted To Do (The Ideal)

The gold standard for proving "our software never needs internet" is to run tests in a Docker container with `--network none`. This is the **definitive proof** — if tests pass with no network stack at all, the software genuinely doesn't call out to the internet.

I initially added this to the CI workflow:

```yaml
network-isolation-test:
  runs-on: ubuntu-latest
  needs: ci-check
  timeout-minutes: 15

  container:
    image: node:22-slim
    options: --network none   # <-- This is the key: no network at all

  steps:
    - name: Checkout
      uses: actions/checkout@v4

    - name: Download build artifacts
      uses: actions/download-artifact@v4
      with:
        name: build-artifacts
        path: .

    - name: Run unit tests (network isolated)
      run: npm run test:unit
```

The idea was:
1. First job (`ci-check`) runs normally with network — installs deps, builds, runs full tests
2. First job uploads built artifacts (node_modules, dist/) 
3. Second job (`network-isolation-test`) runs in `--network none` container
4. Second job downloads the pre-built artifacts
5. Second job runs unit tests in complete network isolation

This would **prove** that our unit tests don't need network at runtime.

### Why It Doesn't Work

When I looked at this more carefully, I realized a fundamental problem:

**GitHub Actions itself needs network to function.**

- `actions/checkout@v4` — Needs to clone the repo from GitHub (network)
- `actions/download-artifact@v4` — Needs to download from GitHub's artifact storage (network)

If you set `--network none` on the container, those actions can't even run. The container starts with no network, so:
1. Checkout fails immediately (can't reach github.com)
2. Artifact download fails (can't reach GitHub's storage)
3. We never even get to run the tests

### Alternative Approaches I Considered

**Option A: Self-hosted runner with Docker-in-Docker**
- Run a self-hosted runner that has Docker
- In the job, spin up a `docker run --network none` container manually
- Copy files in, run tests, copy results out
- **Problem**: Requires self-hosted infrastructure, complex to maintain

**Option B: Two-stage job with artifact mounting**
- First job builds and uploads artifacts
- Second job runs on bare `ubuntu-latest` (not in container)
- Second job downloads artifacts, then spawns `docker run --network none` with a volume mount
- **Problem**: Still complex, requires docker permissions in GitHub Actions

**Option C: iptables firewall rules**
- Run tests normally but add iptables rules blocking all outbound except localhost
- **Problem**: Requires root/sudo, might interfere with GitHub Actions' own telemetry

**Option D: Accept a weaker but practical proof**
- Static analysis audit (Layer 1) proves no unaccounted network calls in code
- Runtime wrapper (Layer 2) blocks non-localhost at the API level
- CI runs the audit on every commit (Layer 3)
- The combination provides strong evidence without true network isolation

### What I Settled On

I chose **Option D** because:
1. It's actually implementable within GitHub Actions constraints
2. The static audit catches any new network code immediately
3. The `safeFetch` wrapper provides runtime enforcement
4. Together, these provide auditable evidence that satisfies the "hard evidence" requirement

The CI now runs:
```yaml
- name: Run network usage audit
  run: npm run audit:network

- name: Run unit tests (simulated network isolation)
  run: npm run test:unit
  env:
    http_proxy: ""
    https_proxy: ""
    # ... (clear all proxy vars)
```

### What Would Be Needed For True `--network none` Testing

If we really wanted the definitive `--network none` proof, we'd need to:

1. **Create a custom GitHub Action** that:
   - Runs before the container starts
   - Copies the repo and built artifacts into a volume
   - Then spawns `docker run --network none -v /artifacts:/app node:22 npm test`

2. **Or use a self-hosted runner** where we control the Docker environment

3. **Or run the test locally** as part of a release checklist:
   ```bash
   # On developer machine:
   docker build -t ld-test .
   docker run --network none ld-test npm run test:unit
   ```
   And document this in SECURITY.md as a manual verification step.

### The Honest Assessment

What we have now is **strong circumstantial evidence** but not **absolute proof**:

| Layer | What It Proves | Limitation |
|-------|---------------|------------|
| Static audit | Code doesn't contain unaccounted network calls | Doesn't prove runtime behavior |
| safeFetch wrapper | Our fetch calls are localhost-only | Doesn't cover dependencies' internal calls |
| CI audit | New code is checked on every commit | Audit could have false negatives |

For true air-gapped/PCI-DSS environments, a security team would probably want the `docker --network none` test. We could add that as a documented manual step in SECURITY.md, noting that it can be run locally but not in standard GitHub Actions CI.

## 1. CLI Package Structure (What It Looks Like)

A new `packages/cli/` would contain:

```
packages/cli/
├── package.json          # non-private, has "bin" entries
├── tsconfig.json         # extends base, targets dist/
├── src/
│   ├── index.ts          # thin CLI entry: parses args, dispatches to subcommands

│   │   ├── generate.ts   # imports logic from @live-documentation/shared or scripts
│   │   ├── lint.ts
│   │   ├── inspect.ts
│   │   └── visualize.ts
│   └── ...

```

The package.json would declare:

```json
{
  "name": "live-documentation",
  "bin": {
    "live-docs": "./dist/index.js"
  },
  "files": ["dist"],
  "dependencies": {
    "@live-documentation/shared": "..."
  }
}
```

**What changes today vs. later:**
- **Today (prep)**: Create the folder structure, wire up the entry point, add it to the npm workspace, verify it builds.
- **Later (publish)**: Flip `private: false`, set a real version, run `npm publish`.

This gives you a working CLI during development (`npx tsx index.ts generate`) while keeping the publish trigger entirely manual.

## 2. When Does Removing `private: true` Cause a Publish?

**Never automatically.** Removing `private: true` only *allows* publish — it doesn't trigger it.

The actual publish happens only when you run:
```bash
npm publish
```

You can safely:
1. Remove `private: true`
2. Add all the metadata (license, `repository`, etc.)
3. Set `version: "0.1.0"`
4. Run `npm pack --dry-run` to see exactly what would be published
5. Even run `npm pack` (creates a `.tgz` tarball locally) and inspect it

**None of this publishes anything.** The tarball only goes to the registry when you explicitly `npm publish`.

Additionally, you can add a `.npmrc` or CI guard that requires `--dry-run` by default, or use `npm publish --access public` with 2FA prompts as a final gate.

## 4. Single Package vs. Scoped Monorepo — Pros & Cons

### Option A: Single `live-documentation` package

**Pros:**
- Simplest for consumers: `npm install -g live-documentation` → done
- One version to track, one changelog
- No internal dependency version coordination
- Easier for first-time contributors

**Cons:**
- Larger install footprint (includes everything even if you only want the CLI)
- Can't version shared/server/cli independently
- If server has a bug, CLI users get a new version too

### Option B: Scoped `@live-documentation/{shared,server,cli}`

**Pros:**
- Consumers can install only what they need
- Independent versioning (shared can be stable at 1.x while CLI iterates at 0.x)
- Cleaner dependency graph for advanced users
- More "professional" monorepo pattern

**Cons:**
- More complex publish workflow (need `lerna`, `changesets`, or manual coordination)
- Scoped packages require npm org setup
- Version mismatches between packages can cause confusion
- Overkill if the packages are always used together

### My Recommendation

**Start with Option A (single package)** for MVP. Reasons:

1. You're the only contributor — coordination overhead is zero benefit.
2. The CLI, server, and shared code are tightly coupled and versioned together in practice.
3. You can always split later if adoption grows and use cases diverge.
4. Simpler onboarding for outside eyes reviewing the project.

If you later find that people want just the analyzer library without the CLI, *that's* when scoped packages earn their keep.
