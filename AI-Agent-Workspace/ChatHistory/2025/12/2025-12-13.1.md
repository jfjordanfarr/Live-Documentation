## Workflow-by-Workflow Breakdown

### 1. ci.yml

**Purpose:** Runs the full `npm run ci-check` gate on every PR and push to `main` — the GitHub Actions equivalent of "can I commit this?"

**How it works:**
- Triggers on `pull_request` and `push` to `main`
- Uses `ubuntu-latest` runner, Node 22, npm caching
- Caches .vscode-test to avoid re-downloading VS Code each run
- Installs `xvfb` (virtual framebuffer) so the VS Code integration tests can run headlessly
- Runs `xvfb-run -a npm run ci-check` (the CI-mode safe-to-commit, which skips git-status summary)

**Cost profile:**
- ~5–10 minutes per run based on local timing
- Runs on every PR + every push to main (typically 1–3 runs/day in our linear workflow)
- Free for public repos (GitHub gives unlimited Actions minutes)

**Safety:**
- 45-minute timeout prevents runaway jobs
- No secrets exposed; read-only checkout
- `xvfb` is the standard pattern for headless Electron tests

---

### 2. pages.yml

**Purpose:** Builds and deploys the static Live Documentation Explorer to GitHub Pages on every push to `main`.

**How it works:**
- Triggers on `push` to `main` + manual `workflow_dispatch`
- Two jobs: `build` → `deploy`
- Build job runs `npm run live-docs:visualize:static -- --commit $SHA --ref $REF`, outputting to explorer
- Adds `.nojekyll` to prevent GitHub Pages from processing markdown files
- Uses `upload-pages-artifact` + `deploy-pages` actions (official GitHub Pages v2 deployment pattern)
- Concurrency group prevents overlapping deploys

**Cost profile:**
- ~3–5 minutes per deploy
- Only runs on main pushes (not PRs), so low frequency
- Pages hosting is free for public repos

**Safety:**
- `id-token: write` permission is required by the deploy action but scoped only to Pages
- `concurrency.cancel-in-progress: true` prevents queue buildup
- No secrets beyond the auto-generated GITHUB_TOKEN

**Potential refinement needed:**

### 3. codeql.yml

**Purpose:** Static Application Security Testing (SAST) — scans TypeScript/JavaScript for security vulnerabilities and code quality issues.

**How it works:**
- Triggers on PRs, pushes to main, and weekly schedule (Mondays 3:30 AM UTC)
- Initializes CodeQL with `javascript-typescript` language pack
- Builds the project (`npm run build`) so CodeQL can analyze compiled output
- Runs the analysis and uploads results to GitHub Security tab

**Cost profile:**
- ~10–15 minutes per run (CodeQL is compute-heavy)
- Runs on every PR + main push + once weekly
- Free for public repos

**Safety:**
- `security-events: write` is required to upload findings
- Weekly schedule ensures we catch issues even during quiet periods
- Results appear in Security → Code scanning alerts (not Issues)

**Why CodeQL vs Dependabot:**
- **CodeQL** = analyzes *your code* for security bugs (SQL injection patterns, XSS, etc.)
- **Dependabot** = analyzes *your dependencies* for known CVEs and opens update PRs

### 4. npm-audit.yml

**Purpose:** Scheduled/manual `npm audit` to catch dependency vulnerabilities.

**How it works:**
- Triggers weekly (Mondays 4:00 AM UTC) + manual dispatch
- Runs `npm audit --audit-level=high --json` and captures exit code
- Uploads the JSON report as an artifact regardless of pass/fail
- Fails the workflow if high+ vulnerabilities are found

**Cost profile:**
- ~2 minutes per run
- Once weekly + on-demand
- Minimal compute

**Safety:**
- Only alerts on `high` or `critical` (not `moderate` or `low`) to avoid noise
- Artifacts are retained for download/inspection
- Does NOT open Issues or PRs — purely a gate + artifact

**Why separate from Dependabot:**
- Dependabot focuses on *updating* dependencies and opening PRs
- `npm audit` gives us a weekly "are we currently vulnerable?" checkpoint
- Both are complementary, not redundant
