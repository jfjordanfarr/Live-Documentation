## **The Story of Live Documentation**

### **Genesis: Link-Aware Diagnostics (October 2024)**

This project began as **"Link-Aware Diagnostics"** — a VS Code extension + Language Server architecture that aimed to answer one deceptively simple question:

> *"For any given change in any given file, what other files will be impacted?"*

The initial vision was to build a system that could deterministically trace the ripple effects of code changes across a workspace. The foundation was laid through TypeScript/Node.js tooling with a SQLite-backed graph store, leveraging the VS Code Language Server Protocol.

### **The Benchmark Foundation (Late October – Early November)**

The project adopted a **falsifiability-first** approach — any claim the system makes about code relationships had to be provable and testable. This led to an extensive benchmark infrastructure:

1. **Fixture-based Testing**: Synthetic and real-world fixtures (Ky, libuv, psf/requests, rust-lang/log, square/okhttp, dotnet/roslyn) were onboarded to establish ground-truth relationship graphs.

2. **Polyglot Oracles**: Compiler-backed oracles for TypeScript, Python, C, Rust, Java, Ruby, and C# were built to generate deterministic `expected.json` files from actual AST analysis, preventing hallucinated edges.

3. **Benchmark Automation**: The `npm run safe:commit --benchmarks` pipeline became the heartbeat of development — no code ships without green tests, audits, and benchmark stability.

### **The Live Documentation Pivot (November 2024)**

Around Dev Day 17-18, a profound realization crystallized: instead of building a proprietary knowledge graph, **why not use markdown as the AST?**

This led to the **Live Documentation** system:
- **One `.md` file per tracked artifact** (code, test, config, asset)
- **Authored sections** (`## Purpose`, `## Notes`) for human context
- **Generated sections** (`## Public Symbols`, `## Dependencies`) for deterministic machine data
- **Relative markdown links** as the graph edges — parseable, versionable, and publishable

The key insight: *markdown header sections and relative links can be treated as a lightweight AST which can be parsed, analyzed, and linked to code artifacts.*

### **Four-Layer Architecture (Mid-November)**

The documentation crystallized into a **four-layer pyramid**:

| Layer | Name | Nature | Content |
|-------|------|--------|---------|
| **Layer 1** | Capability | Authored | Vision, Features, User Stories |
| **Layer 2** | Commitment | Authored | Requirements, Work Items, Tasks |
| **Layer 3** | System | Generated/Ephemeral | Architecture diagrams, topology views |
| **Layer 4** | Implementation | Unit-level | Per-file Live Docs with symbols/deps |

Layer 3 became **materialized views** — generated on-demand via CLI rather than committed artifacts. Layer 4 is the persistent, deterministic spine.

### **Polyglot Docstring Bridging (Nov 12-14)**

Live Docs needed to capture not just code structure but **developer intent** from docstrings. Adapters were built for:
- **C#**: XML documentation (`<summary>`, `<param>`, `<returns>`)
- **Java**: Javadoc blocks
- **Python**: reST, Google, and NumPy docstring styles
- **Rust**: `///` doc comments
- **Ruby**: YARD comments
- **C**: Doxygen
- **TypeScript**: JSDoc
- **PowerShell**: Comment-based help (`.SYNOPSIS`, `.PARAMETER`)

Each adapter extracts structured documentation into the `Public Symbols` section.

### **The LD-402 Pathfinder (Nov 17)**

A pivotal CLI tool emerged: `npm run live-docs:inspect` — the "Oracle of Bacon" for code relationships.

```bash
npm run live-docs:inspect -- --from packages/shared/src/index.ts --to some/deep/module.ts
```

This traces dependency paths through the Live Doc graph, enabling fearless change analysis. When you modify a module, you can now answer: *"What's the actual chain of dependencies that leads to the user-facing surface?"*

### **Visualization Command Center (Nov 19-Dec)**

Starting with a Gemini Antigravity experiment, a **3D force-graph visualizer** was prototyped. This evolved into a three-view system:

1. **Circuit Board**: Hierarchical treemap of the entire workspace, directories nested recursively
2. **Local Map**: Focus view showing one artifact with its direct dependencies (inputs left, outputs right) and symbol-level connector routing
3. **Force Graph**: Physics-based layout for exploratory navigation

Key innovations during December 2024:
- **Symbol-level pin connections**: Lines route to specific function/class pins, not just file cards
- **"Alchemy" pins**: Multi-connection symbols glow to indicate high fan-in
- **Blue-to-green routing**: Output (blue, right) → Input (green, left) for consistent directionality
- **Test-backed styling**: Files with observed test evidence get a distinctive visual treatment
- **CSS modularization**: `styles.css` split into domain files to stay under the 1000-line LLM edit threshold

### **Current State (December 2024)**

The workspace is stable and battle-tested:
- **252+ unit tests**, **41+ integration tests**
- **95%+ precision/recall** on AST benchmarks across 6+ languages
- **Full Live Doc coverage** with authored Purpose/Notes for all permanent fixtures
- **Working visualization** at `localhost:3000` with Circuit Board, Local Map, and Force Graph views

### **What's Next**

## Polyglot Type Reference Extraction: A Counterfactual Analysis

### The Core Question

Can we build a **language-agnostic** mechanism for extracting type references from symbols and linking them to other Live Documentation artifacts?

### Current Sources of Type Information by Language

| Language | Static Signatures | Docstrings | Reliability |
|----------|-------------------|------------|-------------|
| **TypeScript** | ✅ Full AST access (return types, params, generics, extends/implements) | JSDoc `@returns`, `@param {Type}` | **High** — AST is authoritative |
| **C#** | ✅ Regex-based extraction of return types, parameters | XML `<see cref="">`, `<returns>` | **High** — XML is rich |
| **Java** | ✅ Return types via regex | Javadoc `@return`, `@link` | **Medium** — imports lack paths |
| **Python** | ❌ Type hints optional (PEP 484) | `:rtype:`, Google `Returns:`, NumPy | **Low** — runtime duck typing |
| **Rust** | ✅ Signature visible via regex | Markdown doc comments | **Medium** — no formal `@returns` |
| **Ruby** | ❌ No static types | YARD `@return`, `@param` | **Low** — purely docstring |
| **C** | ✅ Regex for return types | Doxygen `@return`, `\returns` | **Medium** — headers can be complex |

### The Sweet Spot: What's Commonly Extractable

**Universally available from docstrings:**
1. **`@return` / `@returns` / `Returns:`** — Present in all major doc conventions
2. **`@param {Type} name`** — Typed parameters where conventions support it
3. **`@see` / `@link` / `cref`** — Explicit cross-references to other symbols

**Available from static signatures (most languages):**
1. **Return type** — `function foo(): Widget` or `public Widget Foo()`
2. **Parameter types** — `(widget: Widget)` or `Widget widget`
3. **Inheritance** — `extends Base`, `implements Interface`, `: IBase`

### The Failure Points (Counterfactuals)

#### 1. **Duck-Typed Languages (Python, Ruby, JavaScript)**

```python
def process(widget):
    """Process a widget.
    
    Args:
        widget: The widget to process  # No type hint!
    
    Returns:
        The processed result  # What type?!
    """
    return widget.value * 2
```

**Failure mode**: Without type annotations or docstring type hints, we **cannot** determine that `widget` should link to `Widget.mdmd.md`.

**Mitigation**: 
- Require type hints for linkable symbols (`widget: Widget`)
- Parse Google/NumPy/reST type hints from docstrings (`:param widget: Widget`)
- Accept graceful degradation — untyped params simply don't link

#### 2. **Unresolvable External Types**

```typescript
export function parse(input: string): cheerio.CheerioAPI
```

**Failure mode**: `cheerio.CheerioAPI` is from `node_modules`, not the workspace. We cannot generate a Live Doc link.

**Mitigation**:
- Only link types that resolve to workspace files
- Display external types as plain `code` without links
- Possibly annotate: `cheerio.CheerioAPI (external)`

#### 3. **Generic Type Parameters**

```typescript
export function filter<T extends Widget>(items: T[]): T[]
```

**Failure mode**: `T` is a generic, not a concrete type. `Widget` is the constraint.

**Mitigation**:
- Extract the constraint type (`Widget`) as the linkable reference
- Display as: `T extends [Widget](./widget.ts.mdmd.md)`
- Ignore unbound generics (`T` alone → no link)

#### 4. **Union/Intersection Types**

```typescript
export function resolve(input: Widget | Error | null): Promise<Result>
```

**Failure mode**: Multiple types. Which one links where?

**Mitigation**:
- Extract ALL type names from unions/intersections
- Link each one separately if resolvable
- Display: `[Widget](./widget.ts.mdmd.md) | [Error](./error.ts.mdmd.md) | null`

#### 5. **Qualified/Nested Type Names**

```csharp
public Diagnostics.Models.FormattedReport Process(Diagnostics.Data.Record record)
```

**Failure mode**: Fully-qualified names require namespace → file resolution.

**Mitigation**:
- Use existing `symbolTargets` mapping from dependency resolution
- Build a workspace-wide type → file index
- Accept that some qualified names won't resolve without a proper compiler

#### 6. **Docstring Type References That Don't Match Symbol Names**

```python
def get_widget() -> "Widget":
    """Get the active widget.
    
    Returns:
        Widget: The currently active widget instance.
    """
```

vs.

```python
# In widget.py
class ActiveWidget:  # Symbol name differs from docstring!
    pass
```

**Failure mode**: Docstring says `Widget`, but the actual class is `ActiveWidget`.

**Mitigation**:
- Match against a **symbol index** built from all Live Docs
- Use fuzzy matching with confidence thresholds
- Prefer exact matches; flag ambiguous matches for human review

#### 7. **Implicit Inheritance (Python MRO, Ruby Mixins)**

```ruby
class WidgetProcessor
  include Processable  # Mixin - is this a "type reference"?
  extend ClassMethods
end
```

**Failure mode**: Mixins and module inclusion blur the line between "type" and "behavior".

**Mitigation**:
- Treat `include`/`extend` as dependency edges (already captured)
- Don't promise type-level linking for these cases
- Document the limitation

#### 8. **C's Header-Only Type Visibility**

```c
// In processor.c
#include "widget.h"

widget_t* create_widget(int seed);  // widget_t is in widget.h
```

**Failure mode**: Type `widget_t` is defined in a header, not a `.c` file.

**Mitigation**:
- Already support headers as tracked artifacts
- Link to header Live Docs: `[widget_t](./widget.h.mdmd.md#symbol-widget_t)`
- C is fundamentally "header + implementation" paired

#### Phase 2: Docstring-Based Fallback (Medium Confidence)

For non-TS languages, extract type names from docstrings:
- Python: Parse `:rtype: Widget`, `Returns: Widget:`, Google/NumPy formats
- Java: Parse `@return Widget`, `@link Widget`
- Rust: Parse `# Returns` section (heuristic)
- C#: Parse `<see cref="Widget"/>`, `<returns>Widget</returns>`

- C: Parse `@return widget_t*`

These become **unresolved** type references that need a second pass to link.

```typescript

```

Then resolve unlinked type references against this index.

## The Answer: **100% from Function Definitions, Zero Docstrings Required!**

The type reference linking is extracted **entirely from the TypeScript AST** (function signatures, class declarations, type aliases), NOT from docstrings. Here's the proof:

### What's Happening Under the Hood

1. **`extractTypeReferencesFromTypeNode()`** - Recursively walks TS type nodes (`ts.TypeReferenceNode`, `ts.UnionTypeNode`, etc.)
2. **`collectTypeReferencesFromFunction()`** - Extracts from:
   - Parameter type annotations: `function foo(config: **LiveDocConfig**)` 
   - Return type annotations: `function foo(): **ParsedLiveDoc**`
   - Generic constraints: `<T extends **Widget**>`
3. **`collectTypeReferencesFromClass()`** - Extracts from:
   - `extends` clauses
   - `implements` clauses
   - Property type annotations

### This Means:

✅ **Free for all TypeScript code** - If you have type annotations in your function signatures, we extract and link them automatically  
✅ **No docstring authoring required** - The linking comes from the AST, not from `@param` or `@returns` JSDoc tags  
✅ **The docstring information is additive** - When docstrings exist, they provide *descriptions* of what those types mean, but the type *names* come from the code itself

### Your Idea About Generating Docstrings

Your insight is brilliant! The flow could be:

```
AST type extraction → Live Doc links → Generate @param/@returns JSDoc → Write back to source
```

However, you correctly identified the challenge: **line number shifts**. If we inject generated docstrings, every line number in the source file shifts, which would invalidate the `Source: [source](path#L32)` links in the Generated section until the next regeneration cycle.

This is solvable but would require either:
1. **Regenerate immediately after docstring injection** (two-pass generation)
2. **Track line numbers relative to function start** rather than absolute
3. **Accept stale line numbers until next full regeneration**

The current implementation gives you the type linking "for free" without any of that complexity!
