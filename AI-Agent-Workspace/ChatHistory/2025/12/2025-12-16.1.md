## The “layer between heuristics and compilers” (what it really is)

Conceptually, there are three ways to get “semantic truth” without “running compilers ourselves”:

1. **IDE indexes** (VS Code, language servers)
   - Pros: already running, user implicitly opted in, no extra build actions
   - Cons: not always complete, sometimes workspace-symbol-only (not full reference graph), varies by language

2. **Build-tool / compiler indexes** (SCIP/LSIF)
   - Pros: closest thing to “ground truth”; stable formats; rich cross-reference data
   - Cons: generating them may require build; may execute build steps; may not exist by default

3. **Pre-generated artifacts** (CI outputs, checked artifacts, SBOM-like “index bundles”)
   - Pros: safest for “don’t execute anything locally”; deterministic; can be produced in controlled environments
   - Cons: operational overhead; freshness concerns

The “middle layer” you’re circling is: **consume semantic indexes that are produced by something else, somewhere else**, and treat them as *authoritative edges* (or at least higher-tier evidence) when present.

Your current code already leans this way: feeds are *ingested*, not generated, via the server’s knowledge bridge (see discover/ingest flow in packages/server/src/features/knowledge/knowledgeGraphBridge.ts).

### 1) WebForms → JS → config: “show me the entire path”
This is the archetypal *value provenance* query. It needs multiple edge types:

- **Code-behind → rendered HTML** (server emits hidden field / script assignment)
- **JS reads DOM / global var** (frontend consumes)
- **Backend mapping layer** (e.g., `Globals.cs` exporting configuration)
- **Config symbol origin** (`<appSettings>` key in Web.config)

Heuristics alone can get you some of this (string literals, common patterns), but the durable win comes from combining:
- deterministic edges from language tooling (C# symbols, call graph-ish links, config key usage)
- heuristic edges for the messy glue (DOM ids, string keys, reflection-ish patterns)
- explicit “document/config symbol” modeling (Web.config keys as first-class nodes)

This is exactly where “feeds” help: not because they solve the Web.config part, but because they make the *C# graph portion* far less hand-wavy, which makes the remaining heuristic work smaller and more auditable.

This is a *boundary-crossing* query:
- WCF proxy types (generated) → mapping code → domain model types → serialization shape

Here, compiler-grade indexing is hugely valuable because the mapping often looks like:
- object initializers
- extension methods
- AutoMapper-ish patterns
- partial classes
- generated code

You can still support it without “turning compilers loose” by relying on:
- IDE indexes (when available)
- pre-generated indexes from CI for the solution(s)
- heuristics as the “gap filler” for the weird stuff (like BiDictionary usage and “UNSET” fallbacks)

The key is: **feeds don’t need to be universal**; they need to be *consumable when available*, and the UI should make it obvious what tier each edge came from.

- no “imports” in the normal sense
- dynamic SQL
- implicit dependencies (permissions, synonyms, linked servers)
- ORM layers, string-based invocation, and “magic parameter name” wiring

The realistic path is:
- Treat SQL as its own artifact graph with specific node types: `proc`, `param`, `table`, `column`, `view`

  - language server indexes (where mature)
  - heuristics on T-SQL text for `EXEC`, `sp_executesql`, and dependency views

  - string literal callsites
  - ORM metadata/config
  - query builder conventions
  - telemetry (future: runtime traces, but that’s a separate trust boundary)

- “This param likely comes from X” with evidence links
- fast narrowing of search space
- surfacing the 5 candidate paths you’d otherwise spend a day diffing
