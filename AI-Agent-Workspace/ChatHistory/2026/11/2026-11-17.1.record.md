- **What the web says, checked before designing** (sources below; none gives a tested recipe for this exact stack). Under WSL2 a container reaches the card through `/dev/dxg` and Microsoft's Direct3D 12 libraries in `/usr/lib/wsl/lib`; NVIDIA ships no OpenGL or Vulkan driver of its own for WSL2, so OpenGL comes from Mesa's `d3d12` driver. Chrome's own guidance for a headless browser on a card names `--use-angle` as the switch and says to verify by the renderer the page reports, not by the flag. The devcontainer specification's `hostRequirements.gpu: "optional"` is not detected by VS Code on Docker Desktop for Windows (the extension looks for an `nvidia` runtime in `docker info`, which Docker Desktop does not list); the reported ways round are `--gpus all` in `runArgs`, which breaks the container on a machine without a card, or the extension's own GPU setting on the user's machine.
  - [Chrome for Developers: testing with WebGL and WebGPU in headless Chrome](https://developer.chrome.com/blog/supercharge-web-ai-testing)
  - [vscode-remote-release issue 9385: `hostRequirements: gpu: optional` on Windows](https://github.com/microsoft/vscode-remote-release/issues/9385)
  - Search results read for the WSL2 path: [a Docker forum thread on headless Chrome with an NVIDIA card](https://forums.docker.com/t/hardware-acceleration-for-headless-chrome-with-nvidia-gpu/132557), [WSLg issue 1394](https://github.com/microsoft/wslg/issues/1394), [a note on WSLg with Docker](https://nes.is-a.dev/out/2025/wslgdocker.html).

#### The plan: prove it in a sibling container, then rebuild once

Root's decision, with its reason. Passing the card in means changing how the container is created, and a rebuild ends this session and deletes its log; a first attempt is unlikely to be the last (the device, the libraries, the browser's flags and the tests' own tolerance of a different renderer are four separate unknowns), and each further attempt would cost another rebuild and another startup read. So the recipe is proven first in two throwaway containers started beside this one from the Windows host, each created from this container's own image with this container's volumes (`--volumes-from`), so that they see the same repository and the same `node_modules`:

- `ld-gpu-a`: `--gpus all` and nothing else, the form the devcontainer specification can express portably.
- `ld-gpu-b`: `--device /dev/dxg` and `/usr/lib/wsl` mounted read-only, the form known from WSLg's own container notes.

Each runs `AI-Agent-Workspace/tmp/gpu-probe/loop.sh`, which executes the job scripts root drops into its inbox under that folder and keeps each job's output beside it; `AI-Agent-Workspace/tmp/gpu-probe/run` is root's side of it. It gives root nothing it does not already have in this container except the card. What is to be measured there, in order: what each form puts in the container; whether Mesa's `d3d12` driver reports the card (`eglinfo`); which launch flags make Playwright's Chromium report it as the WebGL renderer; the time and frames this repository's 3D picture of `generator.ts` takes to rest, in software and on the card, in the same container; then the slow 3D cases and the whole browser suite on the card. Only then is the devcontainer changed, the container rebuilt once, and the same cases run again in it.

**A consequence to put to the owner when the numbers are in, not before:** the cases they keep red on their clocks are red because the software renderer is slow. On the card they will probably pass, and that pressure goes away although a person's browser was never the slow thing. The frame counts beside those clocks (320 frames, 1,228 frames) do not depend on the renderer and would still say when a picture takes long to settle.
