  Where a new sphere is born

  Since October 28 a sphere entering the 3D picture is not born at the centre
  when anything it is wired to already stands. A file starts at the mean of its
  placed partners, pushed out one spring length in a direction seeded by its
  name. A directory hub starts at the centroid of its placed members. So your
  idea is already in, in a slightly better form than one partner, and it costs
  almost nothing: a handful of positions read per newcomer. No pushback needed.

  The gap is the other case. A sphere with no placed partner, which is every
  orphan and the first sphere of every island, is left to the library, which
  seats it on a tight spiral around the origin. For this repository that is at
  most 97 units out, while the main mass at rest reaches 1,300. The reveal
  enters the unconnected last, so each orphan is born inside an already settled
  mass and spends the settle pushing its way out. The fix is cheap and I
  recommend it: seat a partnerless newcomer on the outside of the picture, at
  the picture's current radius plus a spring length, in its seeded direction.

  ### What I built
  - **Engine** (`packages/engine/src/live-docs/pathfind.ts`):
    - `export function components(ids, neighbours): Component[]`, with
  `Component { seed; members }`.
      - The seed is the member with the most distinct neighbours; ties go to the
  lower id by code point. Members are sorted.
      - Components come largest first, then by seed.
      - It builds an undirected adjacency internally, so a link joins both ends
  whichever end names it. A one-way neighbour function therefore gives the same
  groups, whatever the input order. It reuses `walk`.
      - Neighbours outside the ids, and self-links, are ignored.
    - `export function fileGroups(graph): FileGroups`, with `FileGroups {
  groups: {seed,size,members}[]; alone: string[] }`.
      - This is the single computation that both the CLI and the panel call. Its
  object is the CLI's `--json` body and the panel's export alike.
    - For the client change: `componentLandmarks` counts isolates as landmarks.
  `components` returns them too, as components of one, so `components(ids, id =>
  beside.get(id))` maps directly.

● The symbol pin leaves out same-file references by construction. When a file is
  narrowed to one symbol, its card shows the rows some pin needs: the pinned
  row, plus the row at the far end of every cross-file connection that pin makes
  visible. Those connections are read from the bundle's link list, and that
  list holds no same-file reference at all, because the bundle drops a link
  whose two ends are one file. The references inside a file live with each
  symbol's type references instead. The 2D builder turns them into laces only
  after the rows have been chosen, and never feeds their other ends back into
  the rows. So walk, reachFrom and components were treated like any unrelated
  row: folded under the "+N symbols" reveal, or muted when the file is the
  subject, and with their rows gone the laces had nothing to end at. Hover shows
  them because the hover runs over the drawn edges, laces included. The rule
  dates from the symbol-pin grammar of 2026-10-15, which was written for
  cross-file connections only.

  A fix is underway. An Opus subagent at XHigh is building it in a worktree: a
  symbol pin discloses the rows joined to it by its own file's references, one
  hop, in both directions, with their laces, exactly as a cross-file connection
  discloses its far row. It writes the unit test and a browser spec. I review
  it, run the spec and the full gate once the browser is free, and commit.

  Walk in your list is a false light. The Walk interface does not use
  Neighbours; the walk function does. The client's name normaliser maps "walk
  (function)" and "Walk (interface)" to one key, "walk", and the doc's two
  anchors the same way, so the highlight for the function's edge lights the
  interface's row as well. The same happens to Reachability and reachability,
  and to FileGroups and fileGroups. The docs add the kind to such names
  precisely to tell them apart, and the client throws it away. The right fix
  keeps the kind in the key and has same-file references carry the doc's anchor
  instead of a bare type name. That touches every place the client matches a
  symbol: pins in links, search, the reader's anchors, the 3D map's symbol pins.
  I would send a second Opus at it; say the word.
