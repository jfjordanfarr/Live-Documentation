❯ While that runs, I'd like to hear you pontificate and ponder a bit longer
  with respect to a way in which we can marry the concepts of "dataset
  capture"/"measurement"/"multi-assertion tests" with the concepts of "robust
  to change in the codebase", "unlikely to add unnecessary fragility" in our
  e2e test suite (and tests in general which occupy considerable amounts of
  time and have become the bottleneck to development velocity).

● The short version: the fragility comes from where the expected values live,
  not from asserting many things at once. I'd split a test into three layers and
  let each be robust in its own way: the scenario, a captured reading of the
  page, and judgments over that reading.

  The three layers

  1. Scenario: a map and an address. The Explorer already puts its state in the
     link, so a scenario is a link we really opened. On a frozen map (Rosetta,
     the estate) literal names are safe, because nothing drifts. Tokens are
     needed in two places: where one scenario runs across the nine Rosetta
     languages, and on our own growing map, where a token is a description ("the
     file with the most consumers") resolved at run time.
  2. Reading: what the settled page says, captured as data. Not pixels and not a
     DOM dump. For each drawn thing it records what it is, its box, whether its
     text is whole, its wires and their sides, and its state; plus the address,
     console errors and network requests. This is your "dataset capture". One
     instrument produces it for any picture.
  3. Judgments: pure functions over a reading. They never touch the browser.
     This is the multi-assertion layer, and each judgment reports separately, so
     one scenario lists every promise it broke.

  Where robustness comes from: rank every check

  Kind of judgment: Law (an invariant)
  What it needs: Nothing
  Example here: Every card inside its directory; no name cut or colliding;
    uses enter on the left, offerings leave on the right
  Breaks when: The promise is broken
  ────────────────────────────────────────
  Kind of judgment: Relation between two readings of one run (testers call
    these metamorphic)
  What it needs: Nothing
  Example here: Reload gives the same reading; 2D → 3D → 2D keeps the same
    files; pin then unpin returns to the start
  Breaks when: The promise is broken
  ────────────────────────────────────────
  Kind of judgment: Oracle fact
  What it needs: An independent truth
  Example here: The wires shown for {processor} equal the Rosetta manifest's
    edges
  Breaks when: The product or the fixture's meaning changes
  ────────────────────────────────────────
  Kind of judgment: Baseline (a recorded measurement)
  What it needs: A stored number
  Example here: Crossings, frames to rest, picture size
  Breaks when: Anything moves it

  The rule is to push each check as high up that table as it will go. A literal
  written into a spec ("328 hidden files in 10 shells") is a baseline pretending
  to be a law, and that is where most of our fragility sits today.

  Baselines still earn their place for things with no law and no oracle, such as
  how good a layout is. I'd treat them as measurements:
  - one-sided bounds ("no more crossings than recorded");
  - an explicit re-approval step that shows what moved and by how much.

  A deliberate layout change then costs one reviewed update, not forty
  hand-edited expectations.

  What the split buys beyond speed

  - Judgments can be tested without a browser. Each one gets a hand-made bad
    reading that it must reject, which is our rule that a test which cannot fail
    proves nothing.
  - Readings can be kept. A new promise can run against yesterday's readings in
    milliseconds. Kept over time they are also the measurement you mention:
    today's surprise, that the same search went from about 25 s to about 60 s in
    a month, would have been a visible curve.
  - Failures read as a table of scenarios against promises. A whole row red
    means that scenario cannot load. A whole column red means one promise is
    broken everywhere, or the check is wrong. A single cell is an edge case.
  - Rosetta gives a relation nobody else has. The same scenario in nine
    languages should draw the same shape, within the two documented tiers. That
    checks the adapters through the UI with no expected data at all.

  Where it can go wrong

  - Laws pass on an empty page. Each scenario needs a floor: the pinned thing is
    drawn, and at least one wire exists.
  - The reading instrument can lie. It must stay small, and a screenshot is
    saved beside each reading so an eye can confirm that it means what it says.
  - Re-approval can become a rubber stamp. Diffs must be small and explained.
  - Conversion can silently drop coverage. I'd keep a ledger mapping each of
    today's 488 cases to the judgment that replaces it, and for a sample, break
    the product the way the old case guarded against and confirm the table goes
    red.
  - Sequences and motion do not fit a single reading. Journeys become a path of
    readings with the same laws at every step. Motion is judged from the
    product's own counters, read at rest. A handful of clock alarms run alone.

  Our own map and slow tests in general

  Our own map keeps a seat, but only for laws and relations on a few
  token-resolved scenarios. Those need no literals, so the repository can grow
  without breaking them.

  The same split applies to the slow unit and integration tests: run the
  expensive producer once per scenario, keep its output, and judge it many
  times.

  The first slice after the rebuild would be the instrument, about a dozen laws
  and relations, and Rosetta, measured against the cases it replaces. The gate's
  rerun is still going; the hand-over follows when it ends.

● Ubuntu would ask almost nothing of you once it is installed. The one lasting
  thing to know is that it would hold the only working copy, so pushing to

  Why another Windows folder won't help

  The slowness is not the D: drive. The container runs in Linux, and every file
  it opens on any Windows drive is a request sent across to Windows and back, 4
  to 6 ms each. A folder on C: is reached through the same crossing. Docker's
  guidance (https://docs.docker.com/desktop/features/wsl/best-practices/) says
  the same: "Performance is much higher when files are bind-mounted from the
  Linux filesystem."

  So "somewhere else" has to be on the Linux side, and there are only two such
  places: a Linux install's disk (Ubuntu), or Docker's own disk.

  What Ubuntu asks of you over time

  - Nothing to run or keep up. It is a disk with our folder on it. The tools,
    dependencies and tests stay in the container, as now. Updating Ubuntu is
    optional, because nothing we do depends on it.
  - No second virtual machine. It runs inside the one Docker already uses, so
    installing it needs no restart.
  - A username and password, chosen once at install. The password is only for
    administrator commands, which our steps rarely need. If you forget it, it
    can be reset from PowerShell.
  - A new place to open the project from. VS Code's recent list will hold it,
    and the D:\ entry retires.
  - About 6 GB on C:, in one disk file that Windows keeps for Ubuntu.
  - Know what deletes it. Removing Ubuntu (uninstalling it, or wsl --unregister
    Ubuntu) deletes the working copy with it. Push as you do now, and always
    before removing Ubuntu.

  You can still browse the files from Windows: File Explorer → Linux → Ubuntu →
  home → your name → src.

  The way without Ubuntu

  The working copy can go into a Docker volume, which is Docker's own disk,
  where your chats and the dependencies already live. VS Code documents this
  (https://code.visualstudio.com/remote/advancedcontainers/improve-performance)
  too.

  - Nothing to install. Your part would be one "Rebuild Container".
  - More exposed to deletion. Docker Desktop's "Clean / Purge data", a factory
    reset or an uninstall deletes it, and those are the usual advice when Docker
    misbehaves. One such loss would take the chats and the working copy
    together.
  - File Explorer cannot open it.
  - Not prepared yet. I would add set-up steps to the container's configuration
    first. The Ubuntu copy script is already written and tried.

  Neither way's container start can be tried from inside this container, so each
  has one untested step on your side.
