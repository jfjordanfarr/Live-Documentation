● Both records are committed (3dd4560b, and 5793c37f for your export of this
  chat). Here are the forks, from the ground up.

  Where this comes from. reachable is the vision's step 4: start at a system's
  entry points, follow the references, and see what is reached. It is the dual
  of "what does my change touch". The docs today record every import and type
  reference between files, and nothing else. So the Knowledge Sources panel can
  list the files nothing references, but it cannot tell an entry from an orphan,
  because a script npm runs, a main, a route a browser calls and a dead file
  all look the same: no inbound reference. On October 8 you asked for a
  dead-code sweep. I measured the graph against a hand reading of this
  repository, and the graph had missed no import. Of the implementation files it
  called unreferenced, nearly all were entries or tooling inputs, one was dead
  and one redundant. That sweep named where entries come from. Yesterday the
  walk itself landed in the engine, under the destination field and inspect
  --reachable. What remains is the fact "this file is an entry, and here is
  why", written into the docs so every reader can use it. The forks are where
  that fact comes from, where it is written, and what gets reported from it.

  Fork 1: what counts as an entry declaration

  An entry is a file that something outside the code starts. Six kinds exist,
  and each needs its own reading:

  1. A manifest's commands. In package.json, the scripts that name a path, and
     bin and main. This repository has about twenty such scripts, and the CLI
     package's bin points at a built file that maps back to its source through
     tsconfig. Other ecosystems declare the same thing differently: a .csproj
     with an executable output type, a web project, Cargo's bin targets,
     pyproject's scripts, a gemspec's executables. Adapters exist today only for
     package.json and .csproj. Cargo, pom, pyproject and go.mod have no Live
     Docs at all yet.
  2. The language's own main. C, Go, Rust, Java, C# and Python each have one. No
     adapter marks any of them today, and in Go and Rust main is not even
     public, so it is absent from the docs.
  3. An opening served. A route, an address, a procedure, a table. These are
     already symbols with kinds in the docs since the September openings work. A
     file that serves one is an entry by definition, because its caller is
     outside. This costs nothing new. The one gap is WebForms pages, whose docs
     carry no route.
  4. Tests. A runner starts them. Either trust the test archetype the generator
     already assigns by naming convention, or read the runner configurations'
     include globs. The sweep found the globs matched all but two test files,
     and those two were tooling inputs. Reading the globs means evaluating
     TypeScript config files, which I would rather not build as a special case.
  5. Tooling inputs. Manifests and compiler or runner configurations are roots
     by their kind, never orphans. A rule by file kind.
  6. What no rule can infer. The bundler entry named by a path string inside
     code, and the stylesheet the page template links. For these, a declared
     list in the configuration file, which is the fallback you accepted on
     October 8.

  One more thing the sweep found that is not an entry but an adapter miss: a
  dynamic import("./file") with a literal path is not recorded as an edge. The
  compiler oracle records it, so it is measurable.

  My recommendation: read all six kinds, but limit the manifest reading to the
  two adapters that exist, add main marks to every language adapter we ship,
  take openings as they are, take tests by archetype, and add the declared list.
  New manifest adapters for the other ecosystems are a later pass.

  Fork 2: how the fact is written into the docs

  The rule is that markdown is canonical and consumers read the derived graph,
  so a fact the picture needs has to live in the docs. Two shapes fit:

  - An edge on the declarer. The manifest's doc gains a dependency line linking
    to each script, with the existing (configuration) qualifier, meaning "this
    manifest runs that file". The walk then starts at manifests, and the Local
    Map draws package.json wired to twenty scripts. This matches how a served
    route and its caller are already written. Its weakness is that a language
    main has no declarer other than its own file, so this shape cannot carry it,
    and a runner config's doc would gain over a hundred lines.
  - A mark on the entry. The entry file's own doc says it, in its Metadata
    block, with the reason and a link to the declarer: a script name and its
    manifest, main, a route, a test runner, or "declared". The precedent is the
    Archetype: line, which the generator also decides from configuration and
    naming rather than from the file's text. One line, one vocabulary, and every
    reader finds "is this an entry and why" on the file itself.

  A hybrid is possible, edges where a declarer exists and marks where the file
  declares itself, but that is three mechanisms for one fact. I recommend the
  mark. The manifest's wires can be added later if you want them in the picture.

  Fork 3: what is reported, and where the Explorer lands

  - The panel. An "Entry points" section grouped by how each is known, and
    "Unreachable from any entry" in place of today's "Nothing references these".
    The difference matters: a file referenced only by an orphan is unreachable,
    and the one-hop list cannot see that. "Reached only from tests" stays. I
    would replace the one-hop list rather than keep both.
  - The CLI. inspect --reachable with no --from would mean "from the entries",
    in text and JSON, computed by the same engine function the panel's JSON
    export uses. The alternative is a new command. I recommend the option.
  - The landing. Today a filename-scoring heuristic picks the rosetta sample's
    main file. Options: the entry with the largest reach, the manifest's main or
    bin, the root landing built yesterday with nothing pinned, or the heuristic
    kept. I recommend: when the scan declares exactly one entry outside the
    sample roots, land on it; otherwise land on the root with the entries listed
    in the panel. The configuration already names the sample roots, so
    excluding them fixes the rosetta landing on its own.

  How we would know it is right. Three oracles, none of them the analyzer
  grading itself: the October 8 hand table of this repository's unreferenced

  as the entry role in eight languages, so each variant's main must come out an
  entry and nothing else in it; and the estate sample's served openings, the
  Portal's page and controller, the Gateway's routes, the Hub's address, the
  service's procedure and tables.

  The file plan

  The grammar and the model. A doc's Metadata block gains zero or more - Entry:
  lines between Code Path and Generated At, each a reason and its evidence:
  program (the file holds the language's entry point, naming the symbol when
  there is one), command (a manifest script or bin runs it, naming the script
  and linking the manifest's doc), module (a manifest's main names it as the
  package's entry), opening (one line per route, address, procedure or table the
  file serves, linking the symbol), tooling (a manifest or a compiler or runner
  configuration a tool reads) and declared (the configuration names it). Tests
  are not written as entries: Archetype: test already says a runner starts the
  file, and the index treats that archetype as an entry. document.ts renders and
  parses the lines and the round-trip test over the whole corpus proves them;
  the LiveDoc and GraphFile types carry entries.

  Where each reason comes from. program: each language adapter reports it from
  its own syntax, as a new entries field on the analysis result. C's int main,
  Go's func main in package main, Rust's fn main in src/main.rs or under
  src/bin, Java's public static void main, C#'s static Main or top-level
  statements, Python's __main__ guard, Ruby's __FILE__ guard, and every
  PowerShell .ps1 file. command and module: the JSON adapter's package.json
  branch reads scripts, bin and main, resolves the paths a command names against
  the file index, and maps a built path through the package's tsconfig outDir
  and rootDir back to its source. Those are declarations about other files, so
  the generator's first pass, which already runs every adapter to build the
  symbol index, also builds an entry index from them, and the second pass writes
  each file's lines from its own analysis plus that index. opening is composed
  from the file's symbol kinds. tooling is a rule by kind: the manifest symbol
  kinds, packages.config, tsconfig*.json, *.config.*, Web.config and App.config.
  declared comes from a new entryPoints list in the configuration, paths or
  globs like archetypeOverrides; this repository's lists the Explorer's bundler
  entry and its stylesheet. The dynamic import() with a literal path becomes an
  import edge in the TypeScript dependency reader, measured on the oracle.

  The walk. pathfind.ts gains reachability(graph, from?): the entries with their
  reasons, every file reached with its hops, the files no entry reaches by
  archetype, and the files only test entries reach. One function, used by the
  CLI and the panel.

  The CLI. inspect --reachable with no --from walks from the entries and prints
  them, the reached files nearest first and the unreachable ones, in text and
  JSON; the guides and the README say so.

  The Explorer. The bundle's data gains the configuration's sample roots. The
  panel's "Nothing references these" becomes "Entry points" grouped by reason,
  with sample programs' entries grouped under their root, then "Unreachable from
  any entry" by archetype, "Reached only from tests", the field and the copy
  action; the JSON export carries the same shape the CLI prints. The landing:
  exactly one entry outside the sample roots lands on it; several land on the
  root with nothing pinned; none falls back to the guess.

  Tests and the oracle. Unit tests for the grammar, the walk, the JSON adapter's
  mapping, each adapter's program mark, the composition rules and the panel's
  facts. Integration: a small fixture workspace with scripts, a tsconfig and a
  declared file; the rosetta parity test asserting each variant's main carries
  program and nothing else in it does; the estate test asserting the served
  openings' files; the CLI test for the new form; and
  tests/integration/live-docs/expected/repository-entries.json, this
  repository's entries written by hand with a reason each, compared against the
  committed docs. Playwright: the panel's sections and field under the design
  audit, and the landing. Pictures under today's folder.

  Docs. The pipeline and openings docs for the new line, the Explorer design's
  Knowledge Sources section, the CLI guides, a decisions-log entry quoting you,
  the vision's step 4, and the authored notes of every changed module. Several
  dozen Live Docs gain a line when regenerated.

  I would land it as two commits, each after the full gate: the engine,
  generator and CLI with the oracle tests first, then the Explorer with its
  pictures. Say yes, or strike or rename anything above, and I build.

● Short answer: REA and Live Documentation share an instinct and not a subject,
  and neither is a layer over the other. The survey is committed as 5a45cfd7 at
  2026-10-15-rea-reverse-engineer-anything.md
  (AI-Agent-Workspace/Research/2026-10-15-rea-reverse-engineer-anything.md),

  What REA is. A local CLI and MCP server, MIT and TypeScript, by one author,
  created in April and published to npm in July. It connects a coding agent to
  reverse-engineering engines you bring yourself (Hopper, Ghidra, IDA, JADX) and
  to its own static readers for JavaScript and Electron bundles, .NET
  assemblies, Go and Rust binaries, captures and firmware. Its pitch is a
  feature in someone else's app: "See a feature you like. Understand how it
  works, down to the binary level," then "build a version for your project." Its
  showcases are two game-function reconstructions and one trace of Notion's
  clipboard path. The GitHub API gave it 266,742 stars today, most of them from
  this month; the week's headlines disagree with each other by the day they were
  read.

  Related? By subject, no. REA reads what a build produced; Live Documentation
  reads what a person wrote. REA's own skill, the instructions it installs into
  the agent, says it in one line: "For ordinary analysis of a complete source
  repository, use normal repository tools and do not run REA." By instinct, yes,
  and closely. Every edge REA records carries an authority, an epistemic state
  (observed, inferred, unknown, unavailable), a bounded confidence, a location,
  coverage and limitations, under the rule that "absence of evidence cannot
  silently become evidence of absence." That is the same instinct as the
  vision's "where an edge is inferred rather than observed, the map says so,"
  the basis on every cross-process edge, and today's Entry line with its reason
  and declarer. REA states it more completely, on every edge, with "unavailable"
  as a value a reader can see.

  A layer of abstraction outside it? Neither above nor below. They are two maps
  of the same kind of thing from different inputs, and neither contains the
  other. REA has no durable, person-facing, reviewable record: its evidence is a
  session ledger, hundreds of megabytes for a real application, projected into
  summary views for the agent, and the human-facing result is whatever the agent
  writes. Live Documentation has no reading of an artifact. If they ever met it
  would be on the World Map, at a piece whose source is not in hand, a vendor's
  DLL or a database whose schema is not in source control, described from its
  artifact instead of declared by hand. A possible adapter someday, not a plan.

  ## 2. Frontmatter fields

  All fields are optional, and the docs recommend only `description`. Unknown
  fields are ignored without an error. The opening `---` must be the file's
  first line. If the YAML does not parse, the skill loads with no fields;
  `--debug` shows the error, and `claude plugin validate .claude/skills` finds
  unparseable files (v2.1.233 or later).

  | Field | Meaning | Default |
  |---|---|---|
  | `name` | Command name in the `/` menu | Directory name. Claude Code accepts
  another value; the spec requires the folder name to match |
  | `description` | What the skill does and when to use it; Claude uses it to
  decide when to apply the skill | First non-empty body line if omitted |
  | `when_to_use` | Trigger phrases or example requests; appended to
  `description` | None; counts toward the 1,536-character cap |
  | `argument-hint` | Autocomplete hint, e.g. `[issue-number]` | None |
  | `arguments` | Named positional arguments for `$name` substitution | None |
  | `disable-model-invocation` | `true`: Claude does not load it automatically;
  it stays out of context | `false` |
  | `user-invocable` | `false`: hidden from the `/` menu; only Claude invokes it
  | `true` |
  | `allowed-tools` | Tools usable without prompts during the invoking turn; the
  grant clears at your next message; it does not restrict other tools. Space-
  or comma-separated string, or YAML list | None |
  | `disallowed-tools` | Removes tools from the pool while the skill is active |
  None |
  | `model` | Model for the turn; accepts `/model` values or `inherit` | Session
  model |
  | `effort` | `low`, `medium`, `high`, `xhigh`, `max` | Effort resolution order
  |
  | `context` | `fork` runs the skill in a subagent | Inline |
  | `agent` | Subagent type when `context: fork` | `general-purpose` |
  | `background` | With `context: fork`: `false` waits for the result in the
  invoking turn | `true` |
  | `hooks` | Hooks registered on invocation, active for the rest of the session
  | None |
  | `paths` | Glob patterns; the skill auto-loads only for matching files | No
  path limit |
  | `shell` | `bash` or `powershell` for `` !`cmd` `` blocks | `bash` |
  | `metadata` | Free-form map for your own tooling; Claude Code ignores it |
  None |
  | `license`, `compatibility` | Spec fields; accepted, not acted on.
  `compatibility` is up to 500 characters | None |

  Spec `name` rule (https://agentskills.io/specification): 1 to 64 characters,
  lowercase letters, digits, and hyphens; no leading, trailing, or doubled
  hyphen; must match the parent directory name.

  ## 3. Invocation and description

  - User: `/name` at the start of a message runs the skill directly. A name
  placed after plain text gives Claude permission to run it but does not run it.
  - Model: by default "Claude can load it automatically when relevant to your
  conversation." `disable-model-invocation: true` turns that off. Descriptions
  are always in context; the body loads only when invoked.
  - Good descriptions (docs guidance; the docs describe no scoring rule): say
  what the skill does and when to use it; put the key use case first; include
  the words users would naturally say; put trigger phrases or example requests
  in `when_to_use`; narrow it if it fires too often. Docs example: "Summarizes
  uncommitted changes and flags anything risky. Use when the user asks what
  changed, wants a commit message, or asks to review their diff." Spec's poor
  example: "Helps with PDFs."
  - Limits:
    - Claude Code: `description` plus `when_to_use` is truncated at 1,536
  characters in the skill listing.
    - Claude Code: the listing budget is 1% of the model's context window. Tune
  with `skillListingBudgetFraction`, `SLASH_COMMAND_TOOL_CHAR_BUDGET`, or
  `skillListingMaxDescChars`.
    - Claude Code: "Keep SKILL.md under 500 lines" (a tip, not a hard limit).
    - Claude Code: after compaction, the first 5,000 tokens of each invoked
  skill are kept, and re-attached skills share a 25,000-token budget. Put key
  instructions near the top.
    - Spec: `description` 1 to 1024 characters; main SKILL.md under 500 lines;
  instructions under about 5,000 tokens recommended.

  ## 4. Supporting files

  Yes. The docs' layout is `SKILL.md` plus `reference.md`, `examples.md`, and
  `scripts/helper.py` ("executed, not loaded").

  - Refer to them from SKILL.md with relative Markdown links and say when to
  load each: "For complete API details, see [reference.md](reference.md)."
  - `${CLAUDE_SKILL_DIR}` expands to the directory containing SKILL.md. It works
  in the body and in `allowed-tools` Bash rules, e.g. `allowed-tools:
  Bash(${CLAUDE_SKILL_DIR}/scripts/render.sh *)`. `${CLAUDE_PROJECT_DIR}` also
  exists. For `!` command blocks, which run in the session's current directory,
  use these variables for paths.
  - Spec: paths are relative to the skill root and one level deep. `scripts/`,
  `references/`, and `assets/` are recommended conventions, not requirements.

  The four families of edges, and the sidecars

  Every file-to-file reference the survey found falls into one of four families,
  by how the referring file names the referred one.

  1. By path. HTML's src, CSS's url(), markdown's link, C's #include "…", Rust's
     mod to a file, PHP's include, Ruby's require_relative, Kustomize's
     resources, Terraform's ./modules, Compose's context, Godot's res://. The
     referring file alone says where the other file is, up to a search list (-I
     directories, $LOAD_PATH, sys.path). This is the family the adapters read
     today; the include rule chosen last night is the search-list half of it.
  2. By name through a convention. Java's import a.b.C reaches a/b/C.java; Go's
     package path reaches a directory; Python's module path walks sys.path;
     PSR-4 maps a namespace to a directory; Rails maps a constant to a file. The
     referring file names a symbol and the ecosystem's rule turns it into a
     path. The compiler-backed adapters already do this; it is the other half of
     what makes an import edge.
  3. By an opaque identifier through a sidecar or a database. Unity's scenes
     point at a script by a GUID that lives in the script's .meta file; Godot's
     uid:// lives in the .import or .uid sidecar; Android's R.drawable.icon is
     derived from a file name by the build; DVC's .dvc pointer stands for a data
     file. The referring file cannot be read alone. A first pass over the
     workspace must collect the identifiers, exactly as the generator's first
     pass collects symbols and entries today. The sidecar is content, since
     deleting it breaks the edge, and a Unity script's doc would say "referenced
     by scene X through GUID", with the .meta as the evidence.
  4. By a name resolved at build or run time. An Xcode asset set, a Helm chart
     name, an Unreal module, a Swift target, a Unity Resources path in a string,
     a Terraform registry source, uses: owner/repo@ref. The manifest or a
     registry decides what the name means; some are external by nature and stay
     external dependencies.

  What the grammar has today is one notion of how an edge is known within a
  folder (an import or type reference) and three bases across a process boundary
  (contract, configuration, declared). Families three and four would each want
  a basis of their own written on the edge, with the sidecar or manifest that
  carried it as the evidence, and the Explorer would draw them as it draws every
  wire. The second family's rule and the third's first pass are mechanism we
  already own in other forms. None of this is proposed for building now. It is
  what the archetypes design step opens, and a text-serialized Unity project is
  the natural first sample: its edges are legible YAML and its GUIDs sit in
  sidecars we can read.

  So it is not the browser's layout. Forty milliseconds of each frame is
  JavaScript: drawConnections measures about 900 rectangles, builds a fresh SVG
  of some 2,500 elements (a path and a five-element gradient per wire, the
  laces, the bundle runs), diffs it against the previous frame's elements by
  key, reparents every kept element and removes the rest. The diff loop alone is
  the largest bucket in the whole profile.

  What we can do: route once, tween the geometry. Every input of a wire's shape
  during a move is already known without asking the page. The cards' places are
  the tweened pose. A pin's place on its card is the rows' measurement the
  search already prices from (rowsOf, pinFor), plus the sliding row's offset the
  move already computes. The lanes' slots and the columns' extents follow the
  pose. The routing itself (curveTo, threadedRoute, the laces) is pure. So a
  move would build its wire elements once, at its start, and each frame write
  each wire's d and its gradient's four numbers onto elements that already
  exist, reading nothing. The last frame stays what it is today, drawn exactly
  from the page, so the picture at rest is identical by construction. Expected:
  a few milliseconds of JavaScript per frame against the browser's own 13, which
  is near 60 frames a second on the chain scope and at it on smaller ones. The
  motion spec's promises hold (wires keep their elements, follow their pins,
  fade in with entering cards).

  The alternatives I would not take: routing every other frame (half the cost,
  visible stutter); hiding the wires during motion (against the motion you asked
  for on October 7 and its spec); CSS-animated d (the browser interpolates only
  paths of the same shape, so a wire that changes lanes would jump, and
  Safari's support is uncertain); canvas (loses the DOM that hover and the tests
  read).

● Honest answer: two of the three I proposed carry real debt, and one of my own
  details was the worst of it. Here is each, judged on your criteria.

  The search gate (1). The gate itself is a boolean: no step scheduled unless
  the Local Map is the view shown and the document visible, resumed on return.
  Structural, no model of anything. The debt was in my proposal, not the
  problem: the "input signature" I offered is a second list of what the renderer
  depends on, and every new lever anyone adds to the layout would have to
  remember it or the picture goes stale silently on return. The simpler complete
  form is a deferred-render flag: a render asked for while the map is hidden is
  noted and owed on return; if none was owed, the picture stands and the search
  resumes. Any caller that renders today keeps rendering; nothing new to keep
  in step. About thirty lines. Low-hanging, no drag on design iteration.

  The arithmetic wire frames (2). This is the one I would not build now, and I
  was wrong to lead with it. It is a second model of the page's geometry,
  sitting beside the page: a pin's place on its card reproduced from
  measurements, kept in step with every change to a card's CSS, a row's height,
  a badge, a pin's position. The layout lab already has one such model, and it
  needed fixing this week when the card's reveal count changed. You iterate on
  exactly the things that model would mirror, so yes, it would make the 2D
  design harder to change, and a drift shows as a snap at the end of every move.

  What is low-hanging in the same place is smaller and is a deletion: keep the
  wires' elements by key and write their attributes in place from the measured
  page, instead of building a fresh SVG every frame and diffing it against the
  last. By the profile's buckets the diff is 54% of the wire time and the
  element creation 15%; measuring the page, which is the truth, is 17% and
  stays. Roughly 40 ms of JavaScript a frame becomes 12 on the chain scope,
  which with the browser's own 13 is about 40 frames a second there and 60 on
  anything smaller, and the code that remains is less than today's. Same truth,
  fewer moving parts, no second model.

  The incremental simplex (3). Contained behind its interface, so it would not
  touch design iteration, but it is the subtle kind of code: the known
  implementations of the method took years to get the pivot bookkeeping right, a
  wrong pivot gives a plausible-looking picture, and it buys about a fifth of a
  click. Our solver is slow because it is obviously correct. I would keep it
  that way until the two changes above have been felt and a click still hurts.

  Something different. The handler's size is the number of starts solved before
  paint, and the tail's length is the search's seeds, patience and joins. Those
  are design choices you made on October 7 and the lab prices them; turning them
  is zero code and more effect than the solver. I am not recommending a value,
  only that it is a lever and not a defect.

  So: build the gate with the deferred flag, and the retained wire elements.
  Don't build the arithmetic frames or the incremental solver now. If that is
  right to you, say go.
