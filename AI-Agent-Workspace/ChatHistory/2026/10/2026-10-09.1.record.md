## What the code does today

I read the board grammar and its join, the generator's entry, the sample builder, the static builder, the World Map's model and the Explorer's landing rule, and your own words on this from every month of the record.

- The generator scans one folder per run. Files are known by their path inside that folder, so two folders would collide on a path like `src/index.ts`.
- A board names a thing by a `From` folder inside the scanned folder. A `From` outside it is reported and ignored. So "several systems" today means several subfolders of one scanned folder, named by a board. The estate sample is exactly that.
- A bundle carries one graph and at most one board, and lands on the World Map only when it carries a board.
- Wires between things are the docs' edges across things. Those edges are made while the docs are written: a call in one file is matched to the file that serves it, within the same scan. When nothing in the scan serves a call, the doc still writes it, unlinked, with its basis. So a folder scanned alone keeps every call it makes as a fact, even the ones that land in a folder it has never seen.

## The answer I propose, walked through the scenarios

A thing is a folder someone pointed the tool at. The board nobody wrote is derived: one thing per pointed folder, named for the folder, its kind from its manifest, no connections. It behaves like a written board until "save board" writes it out, and from then on you own it. Each folder is scanned alone with its docs beside it, so a folder's docs never change because another folder was open. The wires between two things are matched where the board meets the docs, from the calls one folder wrote unlinked against the openings the other serves, by the same rules the scan already uses inside one folder.

A parent and a child both pointed at are two things, with the child's files out of the parent's, which is the join's deepest-folder rule as it stands. A submodule is the same case.
