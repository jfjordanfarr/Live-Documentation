  Siblings, and what makes a thing

  You have just separated two boundaries that I had been letting blur, and the
  tool already has the mechanism that lets them differ.

  A scan's boundary is where the facts are whole. For your solution that is the
  solution root: every project reference between its four to sixteen projects
  resolves inside it, so nothing is dropped. Scan it once.

  A thing's boundary is where the deployment is: what runs as one process on one
  host. That is also where the wires change kind. Inside a deployment,
  references are project references and imports, what one piece stands on.
  Between deployments, references are routes, addresses and procedures, which
  are calls across a process boundary. The World Map already draws those two
  differently.

  The board is what lets the two boundaries differ. A written board can name
  several project folders of one scan as separate things. The join gives each
  its files by the deepest folder, and every edge the scan resolved survives as
  a wire between things, the stands-on wires and the calls alike. The estate
  sample does exactly this today: one scan, nine things. So for your solution:
  scan the root, and if the projects deploy together, leave it one thing; if
  they deploy apart, name each deployable project as a thing on the board.
  Nothing is rescanned and nothing is lost. The derived board gives one thing;
  carving it is your choice, by naming.

  And the wires answer the question you are unsure of. If two projects reach
  each other only by project reference, they are compiled together. If one
  reaches the other by a route or an address in its config, they are two
  processes. The kinds of the edges between two folders are the deployment
  boundary made visible. The tool could even suggest a carve where that is so,
  with you doing the creating by a click; I have written that in ideas.md as
  mine, not yours.

  Separate scans stay for folders with no practical common root, two
  repositories, or a Dev/ too large to scan whole. The project-reference fix
  belongs to that case and stays in the probe.

  Does this hold: scan where the facts are whole, carve where the deployment is,
  and the board is what lets the two differ?

  Detached, and whose map it is

  "Once detached for sharing, does it matter if they disagree?" Inside one
  detached bundle, no. The addresses are internal and the bundle agrees with
  itself. It matters in one place: when the same bundle is built again from
  somewhere else and the old links should still land. That is not a corner case;
  it is your CI developer. This repository's Pages site is built on a GitHub
  runner by live-docs:visualize, from the same committed mirror you have here.
  Under a disk-path address, the hosted site's addresses would differ from the
  ones you saw locally, and would change whenever the runner's path did. So an
  address must be built from names the bundle controls, the thing's name and the
  path inside it, never from where the folder sat on the machine that built it.
  That removes D for me. B or C remains yours.

  "Should each dev have the same world map?" No one needs to. There are three
  artifacts and each has a home. The docs live beside the code and travel with
  it through the repository, as the mirror does here. A board lives with its
  author, a file on a workstation, or in a repository when a team wants to share
  one, as this repository's board is. A bundle is published, detached, and
  complete in itself. A team shares a board through git when it is worth sharing
  and not before. One caution: a board's From lines are relative to the board,
  so a board shared across repositories assumes the checkouts sit where it
  expects, which a pipeline can arrange and a workstation may not.

  A shared bundle that takes in nothing live: yes, and for a plain reason. A
  published bundle has no sources, so it cannot scan. It can be explored,
  pinned, linked and exported as a copy. I would keep one door open in it:
  authoring without sources, an empty thing placed or a connection declared,
  because scenario 7 is a colleague marking up your map and sending it back.
  Detached constrains scanning, not authoring. The blank file is the viewer that
  can scan, because it sits where the sources are.
