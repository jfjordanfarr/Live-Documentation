  ## Sources (fetched 2026-10-16)

  **JEP 512, https://openjdk.org/jeps/512, "Instance main methods":**
  > "If the class declares or inherits a main method with a String[] parameter
  then the launcher chooses that method. Otherwise, if the class declares or
  inherits a main method with no parameters then the launcher chooses that
  method. Otherwise, the launcher reports an error and terminates. If the chosen
  method is static then the launcher invokes it. Otherwise, the chosen method
  is an instance main method. The class must have a non-private constructor with
  no parameters. The launcher invokes that constructor and then invokes the
  chosen main method of the resulting object. If there is no such constructor
  then the launcher reports an error and terminates."

  **The JEP does not state the "non-private" and "void" rules from the brief;
  the JLS does.** JLS SE 25 §12.1.4,
  https://docs.oracle.com/javase/specs/jls/se25/html/jls-12.html#jls-12.1.4:
  > "A main method declared in, or inherited by, a given class is a candidate
  main method if either: It has a single formal parameter (§8.4.1) whose
  declared type is an array of String, a void result, and public, protected or
  package access; or It has no formal parameters, a void result, and public,
  protected or package access. Note that a candidate main method may be either a
  static or an instance method. … The type of the single formal parameter may
  be given as either String[] or String... as they denote the same type."

  JLS SE 25 §7.3 (compact files): "A compact compilation unit implicitly
  declares a top level class (§7.6) whose members are the methods, fields,
  classes, and interfaces declared in the compact compilation unit."

  **Cargo, https://doc.rust-lang.org/cargo/reference/cargo-targets.html#target-a
  uto-discovery:**
  > "By default, Cargo automatically determines the targets to build based on
  the layout of the files on the filesystem. The target configuration tables,
  such as [lib], [[bin]], [[test]], [[bench]], or [[example]], can be used to
  add additional targets that don't follow the standard directory layout."

  That section names neither `examples/<name>.rs` nor the subdirectory form; the
  layout comes from these two pages:
  - Same page, "Examples": "By default, examples are executable binaries (with a
  main() function). You can specify the crate-type field to make an example be
  compiled as a library".
  - https://doc.rust-lang.org/cargo/guide/project-layout.html lists
  `examples/simple.rs` and `examples/multi-file-example/main.rs`, and says: "If
  a binary, example, bench, or integration test consists of multiple source
  files, place a main.rs file along with the extra modules within a subdirectory
  of the src/bin, examples, benches, or tests directory."

  ## Where the brief and the code or grammar disagreed
  1. **An old test conflicted with the brief.** "Leaves program absent when no
  main is public, static and void" asserted that `static void main()` and
  `public void main(String[] args)` do not count; under JEP 512 both do. I
  rewrote it as the new negative test and moved those two cases into the
  positive test. Your two named cases are kept: `public static String main(int)`
  does not count and `public static void main(String[])` does.
  2. **The brief's rule was incomplete in two places, and I followed the
  specs:**
     - an instance `main` counts only when its type can be made with `new T()`,
  which is the JEP's constructor clause;

  would have been marked.

  no-parameter form. Otherwise the first in the file wins, where the old code
  kept the last. In a compact file the implicit class's own `main` comes first.

  **What is new beyond the earlier survey:**
  - **Gource reads an event log, not snapshots.** Each line is
  `timestamp|user|A/M/D|path|colour`, and there is no rename type.
  - **Gource turns rename detection off on purpose.** It runs `git log
  --no-renames`; its ChangeLog says renames "don't display correctly". A renamed
  file therefore disappears and reappears, and a renamed directory empties out
  entirely (issue #61).
  - **A Gource seek rebuilds from scratch.** `seekTo` resets the whole scene and
  replays from a byte offset in the log; the tree as it stood on that date is
  never reconstructed.
  - **How Gource holds the tree still:** each directory is pulled toward its
  parent, pushed outward and repelled by its siblings, and a new directory
  starts next to its parent at an offset taken from a hash of its path. Files
  also vanish after 60 seconds untouched, and its documentation gives no limit
  for very long histories.
  - **Two earlier tools already animate a dependency graph rather than a file
  tree:**
    - Evolution Storyboards (Beyer and Hassan, 2006) seeds each panel's layout
  with the previous panel's positions and draws how far each node moved.
    - Repo Visualizer (Jany-M, created May 2026) is a d3-force import graph
  clustered by top-level directory, stepped commit by commit. It seeks backward
  by replaying from the start and also turns rename detection off.
  - **3d-force-graph keeps positions only by object identity.** Every
  `graphData` update reheats the whole simulation. Nodes passed back as the same
  objects keep their positions; new objects start in d3's default spiral
  (phyllotaxis) arrangement.
  - **The mental-map evidence is mixed.** Most comprehension experiments found
  no conclusive benefit, but orientation tasks were faster with fewer errors
  when positions were preserved. Small multiples beat animation for speed, while
  animation made fewer errors on "what was added in this step".
  - **Browser numbers with dates:**

    - IndexedDB quotas are large and left to each browser (MDN page last changed

  Change over time: the questions I would put to you

  Each with my recommendation, so you can answer by exception.

  1. One lens or the committed mirror? The mirror at a commit carries the
     generator of that day, and the adapters changed a lot since September 27,
     so a sequence read from the committed docs would mix the tool's growth with
     the code's. I recommend regenerating every commit with one generator
     version, which is what "through its own lens" asks; the mirror is a
     shortcut only where the generator is the same.
  2. What a step is. Every commit as the unit of truth, cheap as a delta; played
     at Gource's seconds-per-day with quiet stretches skipped; stepped one
     commit at a time by key.
  3. Renames. Trust git's inference as the identity signal, so a renamed file
     slides to its new hub and a renamed directory moves whole. A file below the
     similarity threshold is a death and a birth, shown as such rather than
     invented. Gource chose to drop renames and pays with vanishing directories.
  4. What holds still. The structure layout's hubs are the skeleton, as
     CodeCity's lots and Gource's branches are: a file is born at its hub, dies
     in place, slides on a rename; hub volumes breathe with exposed surface; no
     re-layout per step. The connections layout is not the timeline's first
     home, since every edge change would move everything.
  5. Where the sequence lives. A base graph plus per-commit deltas with interned
     ids, materialized one snapshot at a time, beside the bundle and inline in
     the single file, never in the Live Docs. Memory is a question of shape
     before place: a few megabytes of deltas before any IndexedDB, and never
     localStorage.
  6. Continuity in 3D. Feed the running simulation rather than restart it. A
     born file is placed at its hub before the update, as a new hub already is,
     so a step is a small reheat and not the hundred-tick warm-up that costs two
     to six seconds today.
  7. The control. A scrubber in the slider grammar with the date and the commit
     spoken; play and pause; beside the picture, what changed in the step, the
     commit message and the files and edges that came and went, since that is
     the one task animation measurably helps. The address carries the commit, so
     a link shares a moment.
  8. The headless twin and the oracle. A history command in the generator
     produces the sequence, reading the configuration as it stood at each
     commit; inspect answers "at commit X" and "between X and Y" in text and
     JSON; git itself is the oracle for births, deaths and renames, with this
     repository's September renames read by hand as the first expectation.
  9. How to proceed. A probe first: regenerate a sample of this repository's
     commits, a disposable page over the structure layout with a scrubber,
     pictures and a recording for your eye; then the design doc in layer 3 as
     the World Map's is, and the build in gated commits. Before the probe, the
     scenarios to walk on paper: September 26 to 28 here; one file's life; a
     directory renamed whole; a repository with ten thousand commits; one
     without a committed mirror, such as TH04; the 8 GB machine; the single
     file; a shallow clone, whose truncated history must be said; a link to a
     moment.
  10. Out of scope for now: TFS, whose history lives on a server and not in the
      folder; the 2D Local Map; the World Map's two-snapshot board; the flyover.

  ### The fork you need to decide

  The bundled `tree-sitter-powershell.wasm` (identical in
  `@vscode/tree-sitter-wasm` 0.3.0 and 0.3.1) fails on three things:
  - **Bare-word comma lists given to a command**, such as `Export-ModuleMember
  -Function A, B` or `Format-Table Name, Status`. The grammar's
  `_command_argument` has no rule for them. Its error recovery sometimes stays
  inside the command and sometimes swallows every following statement. My probes
  lost functions this way: a top-level `Import-Module Foo, Bar` followed by
  `function X {}`, and a `Format-Table Name, Status` followed by a nested
  function.
  - **Unquoted variable-led paths as an argument**, such as `Import-Module
  $PSScriptRoot\x.psm1`, and `${PSScriptRoot}/x.ps1` even as a dot-source
  target. `. $PSScriptRoot\x.ps1` itself parses.
  - **`using` statements.** The grammar has none, so `using module x` is read as
  a command, and a script's `[CmdletBinding()] param()` after it parses as an
  expression full of errors.

  The upstream npm package `tree-sitter-powershell` 0.26.4 has the same defects.
  Options:
  1. **Land as is.** It is better than the `pwsh` adapter on every measure. The
  risk is that in real estate code a comma list can still hide whatever follows
  it.
  2. **Fix the cause: build and ship our own patched grammar wasm, and offer the
  patch upstream.** In a scratch probe, one added rule removed every comma-list
  error with the native CLI:
     - `seq($.command_argument_sep, $.command_argument_list)` added to
  `_command_argument`
     - `command_argument_list: prec.left(seq($.generic_token, repeat1(seq(',',
  choice($.generic_token, $.unary_expression)))))`

     `using` and variable-led paths would need more rules. Building wasm needs
  Emscripten or Docker, and neither is in the devcontainer.
  3. **Read these two cmdlets' argument lists from the source text when the
  grammar errs.** That is a second reading of the same text, which the
  no-workarounds rule argues against.

  **A policy choice inside option 1:** an `Export-ModuleMember` the grammar
  cannot read in full narrows nothing. A misreading therefore shows private
  functions rather than hiding public ones. The alternative is to apply the
  partial list, which hides public functions.

  ### Defects in the Explorer's modules, met while reusing them
  1. **In the structure layout, reference wires drawn on demand are never
  positioned.**
     - Cause: `pullingLinkForce` hands d3 only the containment links, so only
  their endpoints become node objects. three-forcegraph then skips any line
  whose endpoints have no coordinates.
     - In the probe page: 0 of 791 references resolved; their line objects sat
  at the origin with length 1.
     - In the built Explorer (`dist/explorer`, built 14:52 today): hovering
  `.live-docs.config.json` gives two visible reference objects at (0,0,0) with
  length 1, and no wire on screen (`explorer-structure-hover.png`).
     - `tests/e2e/force-graph-directories.spec.ts` checks only each line's
  `visible` flag, so it passes while nothing is drawn.
  2. **Link colours are dimmed five-fold.** `forceGraphView.ts` writes alphas
  (0.35 / 0.5 / 0.2 / 0.025 …) but never sets `linkOpacity`, and the library
  multiplies them by its default of 0.2. Containment shows at 0.07 and a
  revealed wire at 0.1.
  3. **Every render rebuilds every line.** `spatialGraphOf` returns new link
  objects each time, and the library binds render objects to data-object
  identity. That is the 65–88 ms per step here with about 2,650 links.
  4. **The engine runs 15 s after every change.** The Explorer never sets
  `d3AlphaMin`, so the engine only stops at the library's 15-second cooldown,
  and `aria-busy` stays true that long.
  5. **`NODE_COLORS` is not exported and has no `asset` colour,** so assets fall
  back to grey.
  6. **The two cold-start filter defaults disagree:** `DEFAULT_SNAPSHOT` has
  `showAssets: true`, `getDefaultFilters` has `false`. I did not check which one
  governs.
  7. **Hub identity breaks over time.** A collapsed directory chain is
  identified by its deepest path, so a directory gaining or losing its only
  child changes hub ids (a birth and a death).
