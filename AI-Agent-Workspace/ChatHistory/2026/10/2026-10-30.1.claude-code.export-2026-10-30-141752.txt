  ## B. Search ranking

  **1. The rules** (`search/graph-search.ts:107-177`)
  - Words are the query lowercased and split on whitespace (`:102-104`).
  - Per word, a file's score is:
    - its **name** (`node.name`, which **includes the extension**): +100 exact,
  else +50 prefix, else +25 substring;
    - +10 if its path contains the word;
    - +15 if **any** public symbol contains the word (once per word, not per
  symbol).
  - A file is kept when its score is above 0. Files are sorted by score, then
  id, and only the top `FILE_LIMIT` = 12 are kept (`:76`).
  - A directory scores by the name of its last segment with the same name rule;
  the top 6 are offered (`:77`, `:149-154`).
  - `SYMBOL_CAP` = 5 matched symbols are listed per file, followed by an "N more
  symbols" fold (`:78`, `:166-174`).
  - **Score decides only which files make the cut.** Groups are then sorted
  **alphabetically by directory path** (`:176`), with the scan root `""` first.
  Inside a group, files keep their score order. A matched directory becomes a
  choosable heading row; an unmatched one becomes a plain `.search-group`
  heading (`search-field.ts:83-85`).
  - `SearchFile.matched` (whether the file's own name matched) is computed but
  **never rendered**.
  - In the subject field, files past the 12th are dropped silently.
  `SearchResult.files` drives the "N files match, but no path connects them"
  fold only in the destination field (`search-field.ts:95-98`).
  - The explorer doc's "five at a time with a fold that lists the rest" is true
  only of symbols.

  ## 1. Wires

  **Geometry.** There are three instanced batches
  (`forceGraphBatches.ts:67-71`):
  - **Spheres:** `SphereGeometry(1,12,12)` with a Lambert material that takes
  per-instance alpha.
  - **Wires:** one batch of three.js `LineMaterial`/`LineSegmentsGeometry`
  screen-space strokes with round caps, `renderOrder 10`, `depthWrite:false`.
  - **Arrows:** `ConeGeometry(.25,1,8)` with the same alpha Lambert material.

  Each wire's instance matrix holds its axis from the source sphere's centre to
  the target's (`:229-233`).

  **Base width** is set at `forceGraphView.ts:878-879`. It is `linkWidth`
  (default **1**, `persistence/local-storage.ts:81`) times a factor:
  - references: `min(3, 1+0.375·log2(count))`, so count 1→1, 4→1.75, 64 and
  above→3;
  - containment: 1;
  - related-doc and cited-by: 0.5.

  The result is rounded up to tenths (`forceGraphBatches.ts:127`).

  **Zoom resistance.** The shader takes a separate width at each endpoint:
  `linewidth·pow(pixelScale/clip.w, 1−wireResistance)` (`:374`; CPU culling
  `:309`, picking `forceGraphSizing.ts:278-279`). Default wire resistance is
  0.9.

  **Colour and alpha** are set per kind in `forceGraphView.ts:1036-1047`.
  "visible" means the wire is in the current attention (the rule is below the
  table).

  | Wire kind | Colour | Visible / faded alpha | Arrow |
  |---|---|---|---|
  | File reference, Connections | white `rgba(255,255,255,…)` | .16 / .025 |
  none |
  | File reference, Structure (on demand only, `:1048-1057`) | white | .5 / 0 |
  none |
  | Containment (Structure) | amber `233,152,77` (the directory hub colour) |
  .35 / .08 | none |
  | Related doc (file cites document) | violet `153,102,204` | .4 / .04 | length
  4 |
  | Cited by (document cites file) | light violet `214,178,240` | .55 / .06 |
  length 4 |

  - **Type references are not a distinct kind.** `fileConnections()` merges
  every reference kind for a file pair and keeps the first link's `kind`
  (`fileConnections.ts:10-20`), and every reference is drawn the same way.
  - **Path and hover have no emphasis colour or width.** "Visible" means the
  wire touches the hovered file, or lies on the path, or has both ends in the
  attention set (`forceGraphView.ts:1038-1039`). Everything else fades. A path
  wire in Connections therefore stays at the ordinary .16 white.
  - **Direction cue: none on references.** There is no gradient, arrowhead or
  motion.
    - The wire does taper, but the taper is depth, not direction: the nearer
  endpoint is wider (`:374`). A reader can mistake it for direction.
    - **Root cause:** the 3D data is undirected by construction.
  `fileConnections` sorts each pair's endpoints alphabetically and merges
  reciprocal references (`fileConnections.ts:9,13`; `forceGraphLayout.ts:28`
  says "One undirected file pair"). The payload itself is directed: `source` is
  the referencing file (the user) and `target` is the referenced file (the
  offerer) (`shared/graph.ts:...addLink(file.codePath, reference.targetId…)`).
  The hover text says only "N documented references" (`forceGraphView.ts:1102`).
    - `spatialGraphOf` is shared with the headless spatial command and the
  layout lab (`forceGraphData.ts:32-43`). Any change that keeps direction lands
  in both.
  - **Citation arrows** (`forceGraphBatches.ts:209-222`):
    - The cone's base sits back from the target by the target's *physical*
  radius plus the arrow length; its tip touches the physical sphere surface.
    - The arrow is scaled in world units (length 4, radius 1). It has no zoom
  resistance, while the spheres are drawn with resistance-adjusted radii
  (`:193`). So the tip sinks inside a sphere drawn larger than physical (zoomed
  out) and floats off one drawn smaller (zoomed in).
    - Arrow alpha is the wire's alpha ×3 (`:128`): visible arrows clamp to 1,
  faded ones are .12–.18.
    - Direction comes from the data: related-doc runs file→document and cited-by
  runs document→file (`forceGraphData.ts:62-64`).
  - **Palette.** `SPATIAL_NODE_STYLES` (`forceGraphAppearance.ts:2-12`) holds
  sphere colours only. Wire RGBA values are literals in
  `forceGraphView.ts:1042-1046`.
    - **Blue-offers / green-uses appears on no 3D wire.** In 3D, blue `#0091ff`
  (the same as 2D's offer blue and `--accent`, `theme.css:7,13`) is the
  *implementation* archetype, and green `#28a745` is the *test* archetype. 2D's
  "uses" colour is teal `0,211,170`.

  ## 2. Depth and occlusion

  - **Spheres** are transparent with base alpha .75
  (`forceGraphBatches.ts:126`), and they write depth (the Material default).
  Instances are re-sorted far to near on every update by the centre's NDC z
  (`:158-166`, `:195`).
  - **Faded spheres** use alpha `0x33`, about .2 × .75 ≈ .15
  (`forceGraphView.ts:1034`). They still write depth, so a nearly invisible near
  sphere cuts holes in bright wires behind it.
  - **Wires** are drawn after spheres and arrows (`renderOrder 10`),
  depth-tested against them, and write no depth (`forceGraphBatches.ts:68-69`).
    - The part of a wire behind a sphere's front face is hidden, including the
  stub from the surface to the centre.
    - A wire *in front of* a sphere paints across its face, which is the source
  of finding 7's "lines across faces".
    - Wires blend among themselves in far-to-near order of mean clip depth
  (`:204`).
  - **Arrows** share `renderOrder 0` with the spheres and write depth.
  - **Nothing else separates near from far:** no fog (the `Scene` has none), no
  distance-based alpha and no colour change.
    - Wires differ only by width: at resistance 0.9 the factor is
  `(px-per-unit)^0.1`, so a wire twice as near is only ~7% wider.
    - Spheres differ by resistance 0.3: radius in pixels ∝ `ppu^0.7` (`:193`;
  labels, framing and the action strip use the same scale,
  `forceGraphSizing.ts:245`).
    - Finding 6's broad strokes predate the October 24 resistance sliders.
  - **Doc vs code mismatch:** the layer-3 doc gives the defaults as "node 0.45,
  wire 0.9, thickness 0.9" (`live-documentation-explorer.mdmd.md:88`). The code
  defaults are node 0.3, wire 0.9, thickness 1 (`local-storage.ts:81`), and the
  template's initial values agree (`template.html:223,227,231`).

  ## 6. Sphere geometry and antialiasing

  - Spheres use 12 width × 12 height segments (`forceGraphBatches.ts:67`), the
  same as the old `nodeResolution(12)`. Picking raycasts the same tessellated
  mesh (`:81,244`).
  - Arrows use 8 radial segments (`:71`).
  - The renderer is `new WebGLRenderer({ antialias:true, alpha:true })` with
  `setPixelRatio(Math.min(2, devicePixelRatio))` and clear colour `0x000011`
  (`forceGraphRenderer.ts:21,43-44`).
  - Lighting is ambient `0xcccccc` at π plus directional at 0.6π (`:46`).
  - `LineMaterial` has no `alphaToCoverage` set
  (`forceGraphBatches.ts:334-382`), so wire edges rely on MSAA alone.
  - One line: a higher segment count, or an impostor or level-of-detail scheme,
  would add per-instance vertex cost at the 21,720-sphere scale measured on
  2026-10-27.

  # How the 2D Local Map frames its picture, and why it clips

  Short answer: every automatic 2D frame is drawn at exactly k = 1. Two rules
  then place the picture:
  - **Centre on a focus card, clamped.** The focus is the subject's card or,
  with no subject, the first card in the DOM. The clamp stops the picture being
  cut when it fits, and keeps the frame full when it does not.
  - **On a 3D→2D return, hold the subject still.** The subject's title is moved
  to where its sphere stood, and the 2D fit is thrown away.

  Both observed clippings follow from these rules, and I reproduced both in the
  built page (numbers in §6).

  I changed no tracked files. I ran one scratch Playwright probe against
  `dist/explorer`, which was built 2026-10-29 20:16, before the last commit.
  That commit touched only the 3D renderer. The probe served the bundle on port
  8947 and closed it afterwards. The probe is

  ## 1. The transform chosen on arrival, on a new subject, on opening a
  directory, after a pin

  **Where every render goes.** `render()` (controller.ts:356-388) calls
  `drawScene()` (391-452), which ends with:
  - `path ? fitMapToPath()`
  - `: !mapHasInitialFit ? fitMapToContent()`
  - `: updateMapTransform()` (448-450)

  When the fit is reset:
  - `mapHasInitialFit` is cleared whenever `!mapUserAdjusted` (426-429).
  - A changed subject clears it and also clears `mapUserAdjusted`, and sets
  `lastInteracted` (430-438).

  **The exploration fit.** `fitMapToContent` = `computeFitTransform(extents,
  frame, branches ? {minScale: 1} : undefined)` (controller.ts:1093-1096). Every
  scope goes through `renderBranches`, which sets `controller.branches`
  (branch-renderer.ts:215), so `minScale: 1` always applies.

  Inside `computeFitTransform` (layout-measure.ts:176-236):
  - Scale is `clamp(min(autoScale·0.96, 1), 1, 1.45)` (227), which is always
  exactly 1. The focus-plus-buffer "effective size" logic (196-226) is therefore
  dead in practice.
  - Position: the focus centre goes to the frame centre, then `keepVisible`
  (248-250) clamps it.
    - If the content fits, it is clamped so neither edge passes the padding.
    - If it does not fit, the frame is kept full.
  - Padding is `clamp(W·0.02, 8, 72)` and `clamp(H·0.025, 8, 72)` (187-188).
  - The focus is `.node-card.local-focus`, else `.local-column.center
  .node-card`, else `.node-card` (layout-measure.ts:142-145).
    - Every card wrapper is `.local-column.center` (branch-renderer.ts:162), so
  with no subject the focus is simply the first file card in DOM order.
    - Subject cards get `local-focus` at creation (card-factory.ts:80).

  **The path fit.** `computePathFitTransform` (layout-measure.ts:258-267) uses
  `scale = 1`. It is centred if the path fits; otherwise the first file goes at
  the left padding. Vertically it is always centred.

  **Reading size is k = 1** in CSS pixels. The "do not shrink text" rule
  (AGENTS.md, Explorer client) is enforced only here:
  - `minScale: 1` (controller.ts:1095, from commit f6eba721 of 2026-10-05: "The
  picture is framed at reading size").
  - The hard-coded `scale = 1` (layout-measure.ts:259, from c394d186 of
  2026-10-01).
  - The unit test "never shrinks the text to make the path fit"
  (layout-measure.test.ts:37).

  Manual zoom is not bound by it: `MIN_SCALE 0.05`, `MAX_SCALE 3`
  (pan-zoom.ts:15-16).

  **Each case:**
  - **First arrival with no stage:** the fit runs; it animates over 350 ms
  (pan-zoom.ts:78-117).
  - **First arrival with no subject** (root landing via index.ts:972-975, or
  `?dir=`): the fit runs, centred on the first card.
  - **New subject (Centre, search, World Map file):**
    1. `render()` captures the subject's title anchor if its card was visible in
  the old picture (368).
    2. `drawScene` starts the fit animation.
    3. `placeSubjectAnchor` (151-163, called at 384-386) cancels that animation
  before its first frame and sets `mapUserAdjusted`. The fit is discarded and
  the subject is held still.
    4. `recentreOn` and the search's `pinHit` then call `focusNode` →
  `focusElement`, which animates the card's centre to 40%/40% of the frame
  (controller.ts:670-681; index.ts:1166-1174, 610-629).
    - When the old picture is kept, `renderBranches` starts a move from the old
  pose (branch-renderer.ts:537-541). A fit started in the same render therefore
  measures the old pose, not the new one.
  - **Opening a directory inside the map:** `captureDirectoryChange` →
  `afterRender` translates so that the clicked label or box keeps its screen
  position. It sets `mapUserAdjusted = true`; there is no fit

  - **Opening a directory from the World Map** (`openThingInLocalMap`,

  ## 3. The 3D→2D return

  `changePerspective("2d")` (index.ts:757-812):
  1. It takes the 3D subject's screen anchor (773).
  2. It calls `renderCurrentView("show")` → `localView.show()` (1411;
  controller.ts:265-271). If a render is owed, `render()` → `drawScene` →
  `fitMapToPath`/`fitMapToContent`, which starts an animation only.
  3. It immediately calls `localView.placeSubjectAnchor(target, anchor3D)` when
  the anchor lies inside `#view-map` (782-787), and again after `ready` (791).

  `placeSubjectAnchor` cancels the fit animation, which has not yet moved
  anything. It translates the current transform so the subject's `.node-title`
  centre lands on the sphere's position, keeps k, and sets `mapUserAdjusted =
  mapHasInitialFit = true` (controller.ts:151-163).

  So the 2D transform is neither restored nor recomputed: it is the old 2D
  transform translated by the 3D anchor. `mapInitialTransform` still holds the
  discarded fit, which is why ⟲ recovers it.

  The behaviour is the documented rule "Perspective controls preserve the
  selected identity's screen position" (layer-3 doc line 64). It is locked in by
  local-map-branches.spec.ts:83-125 (within 3 px) and
  local-map-simplicity.spec.ts:145-147.

  `animatePerspective` only plays the visual bridge from captured snapshots; it
  does not set the camera (perspectiveTransition.ts:103-224).
