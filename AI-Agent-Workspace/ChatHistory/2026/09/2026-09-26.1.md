#### Circularity

I want to push on "totally unsolved," because I think it's *partly* solved and the unsolved part is narrower than it feels.

The circular thing was the old "heuristic oracles": regex-based expected edges grading a regex-based analyzer. You called that out correctly. But three oracles exist that don't share a mechanism with the analyzer:

1. **The compiler.** SCIP's edges come from a resolver whose correctness is validated by something we don't control: the program builds. That's independent. Where it went wrong in this repo wasn't the oracle; it was that SCIP's edge *definition* (every symbol reference, crate-root back-refs, cfg(test) modules) differs from ours, and the mismatch got papered over with thresholds like recall 0.05 instead of projecting SCIP's output into our definition first. Define "edge" precisely, project, then demand ~1.0.

2. **Mutation.** This one is the mission stated as a test. "What breaks if I change B?" has a ground truth: change B and see what breaks. Delete an export in B, run the build, collect the files that fail. That set is the true dependents. It's slow, but the Rosetta apps are tiny, and the devcontainer already has all eight toolchains. It's not circular because the oracle is the build system, not any parser. I'd be excited to make this the primary benchmark.

3. **Curated fixtures.** Your `csharp-reflection`, `webforms-appsettings`, `queue-worker` workspaces already are this: hand-authored code with known edges. That's the bioinformatics gold-standard approach, and it's the *only* oracle for dynamic patterns (reflection, DI containers, markup-to-code-behind), which is exactly your day-job code.

Rosetta parity is none of these. It's triangulation: if 7 of 8 languages agree and 1 doesn't, the 1 is probably wrong. It catches regressions; it doesn't establish truth. I overstated it as "the guardrail." It's *a* guardrail.

Where it's genuinely unsolved: dynamic dispatch in a large codebase you didn't write. No oracle but a human. I'd rather the tool say "this edge is inferred, confidence low" than pretend.

#### One file or many

You asked for the tradeoff straight, so:

| | One graph file | One file per source file |
|---|---|---|
| Reading the whole graph | one parse | 627 opens + parses |
| Git diff when one file changes | whole-file diff, merge conflicts | one small diff, reviewable in a PR |
| Browsable on GitHub | no | yes |
| Partial regeneration | no | yes (`--changed` already exists) |
| Consistency | atomic | needs a lint pass for cross-file invariants |
| Human-readable | no | yes |

The honest answer is that these aren't competitors. The many-file form is the *database*; the single file is an *index* over it. The repo already works this way without admitting it: `visualize` builds `explorer-data.json` (an index) by parsing all the markdown, and `inspect` and `lint` each re-parse the markdown independently. The fix isn't to replace markdown; it's to build the index **once**, cache it (gitignored), and have every consumer read the cache, rebuilding from markdown when stale.

Which means: **I was wrong to lean toward "generated facts move to JSON," and your parsimony argument is why.** If the index is derivable from the markdown, then the markdown must losslessly carry everything the picture needs. That's a constraint, and it's a good one. It's your own CAP-008 (the Explorer shows exactly what the Live Docs encode). If the picture ever needs something the markdown can't express, that's a signal to grow the format, not to fork the data. The generated region just needs a strict grammar (it nearly has one) and a round-trip test: `render(parse(doc)) === doc`. Then `parse.ts` shrinks from 616 lines to something small, and "markdown is a lightweight AST" stops being a slogan and becomes a property with a test.

One gentle note on "truer representation, translatable to many languages": today a Live Doc captures the *interface and wiring* of a file, not its *behavior*. #### The canvas

What you described is not a new feature bolted onto the side. It's the existing model, one level up. Look at the shape:

| Level | Node | "Exposes" | "Consumes" |
|---|---|---|---|
| Symbol | a function, class, route | — | references |
| File | a file | public symbols | imports |
| Folder | a directory | (aggregate) | (aggregate) |
| **System** | **a repo/app** | **endpoints** | **remote endpoints** |
| Zone | cloud, on-prem | — | — |

A system's public symbols are its endpoints: controller routes, WCF `OperationContract`s, stored procedures. Its dependencies are the remote endpoints it calls: `HttpClient` calls, WCF proxies, connection strings. Same two sections, same markdown file shape, same card with pins on the left and right. So your chain is drawable with the picture that already exists:

```
portal-ui ─HTTP→ payments-api ─WCF→ wcf-router ─WCF→ wcf-service ─SQL→ firm-db ─linked server→ warehouse-db
└──────── cloud ────────┘   IPSEC   └──────────────── on-prem ────────────────────────┘
```

The IPSEC tunnel is an edge crossing a zone membrane. That's the Membrane Map metaphor at system scale, and it fell out without trying.

**Where the inter-system edges come from.** Three tiers, and the picture should draw them differently (solid, dashed, dotted) rather than pretend they're equal:

1. **Observed from contracts.** Portal calls `GET /payments/{id}`; the API has `[HttpGet("payments/{id}")]`. Client proxy implements `IPaymentRouter`; the router service implements the same interface. Route and contract matching is heuristic but well-trodden.

You already built fixtures for exactly this within a single repo (`webforms-appsettings`, `spa-runtime-config`). Cross-repo needs one thing more: each system declares what it *answers to* (base URL, service name, database name) so a URL in A's config can resolve to B.
3. **Declared.** You draw it. The linked-server hop, a database whose schema isn't in source control, the fact that a tunnel exists at all. That's authored content at the system level, no different from Purpose and Notes on a file.

"True input/output shapes" are symbol-level detail on endpoint symbols: DTOs on a route, `DataContract`s on a WCF operation, parameters on a proc. Those become the pins. The canvas file itself is just a markdown file listing folders and what each answers to. In-paradigm, one primitive.
