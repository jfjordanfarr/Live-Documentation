## 2026 Development Trajectory: Dev Days 52–70

### What We're Building and Why

**Live Documentation** is a VS Code extension and CLI suite that generates deterministic, compiler-grade markdown documentation for every tracked file in a workspace. Each generated "Live Doc" contains authored preamble sections plus auto-generated `Public Symbols`, `Dependencies`, and `Observed Evidence` sections. Together, these form a markdown-as-AST graph that answers the question: _"For any given change in any given file, what other files will be impacted?"_

The guiding philosophy is **zero-LLM, zero-cloud, zero-cost**: the tool never touches an LLM, never sends code anywhere, never hallucinates. Users enrich generated docs with whatever AI tools they already use. The output is versionable markdown that can be regenerated locally, published to wikis, consumed by humans, copilots, and CI systems alike.

### The Arc of 2026: Three Phases

**Phase 1: The Great Simplification (Dev Days 52–57, Jan 6–13)**

2026 opened with a codebase that still carried the legacy of its original "Link-Aware Diagnostics" architecture: a SQLite database (`better-sqlite3`), a `GraphStore`, a `RippleAnalyzer`, LSIF/SCIP knowledge feed parsers, change event processors, acknowledgement persistence, and ~587 lines in `main.ts`.

## Full Capability Analysis: What the Extension Should Do

### The Regeneration Timing Problem

You've identified the core architecture question: **how does on-save regeneration work without drowning in requests?**

My benchmark reveals the constraint: even a zero-file `--changed` dry run takes **~12.4 seconds** because of `tsx` compilation overhead. A real single-file regeneration would take roughly the same. This means:

1. **On-save regeneration via CLI shelling is infeasible** — a developer saving 5 files in 10 seconds would queue 5 sequential 12+ second processes
2. **In-process generation (calling `generateLiveDocs()` directly from the server)** would eliminate the tsx startup cost but still involves glob discovery, git status parsing, polyglot adapter invocation, and file I/O per invocation
3. **The debounce-then-notify pattern is the right architectural instinct** — exactly what you alluded to

- Watch file saves via LSP's `documents.onDidSave` (already wired)
