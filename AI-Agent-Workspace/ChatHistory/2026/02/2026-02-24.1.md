## Workstream 1: Generator Pipeline — Directory Live Doc Generation

### What exists today

The generator in generator.ts iterates `targetFiles` (568 individual files), produces one Live Doc per source file, and prunes stale docs. There is **no concept of directory-as-artifact** anywhere in the pipeline. The `discoverTargetFiles()` function returns file paths only.

### What needs to be built

**1a. Directory discovery** — After discovering target files, collect the unique set of directories that contain at least one tracked file. This is trivial (`new Set(targetFiles.map(f => path.dirname(f)))`), but the recursion depth is the design question: do we generate a doc for every intermediate directory, or only leaf directories containing files?

**Recommendation**: Every directory that contains at least one tracked file, recursing upward to the workspace root. A directory like live-docs gets a doc, so does src, shared, packages, and the root. This matches the "so on and so forth all the way" vision.

**1b. Directory Live Doc rendering** — A new archetype (`"directory"`) with its own section template:

## Workstream 2: Explorer Graph — Directory Nodes

### What exists today

The Explorer graph in graph.ts builds `ExplorerNodePayload` for each file-level Live Doc. The Circuit Board already computes a `DirectoryNode` hierarchy in layoutUtils.ts — but this is a **client-side layout construct** built from file paths, not from directory Live Docs. It has `name`, `path`, `children`, and `nodes` but **no authored metadata, no purpose, no aggregate statistics**.

### What needs to be built

**2a. Serve directory Live Docs in the graph payload** — `buildExplorerGraph()` currently creates nodes only for files. It needs to also parse directory Live Docs and include them as a separate node type (or enrich the existing `DirectoryNode` hierarchy with metadata from the docs).

Two design options:

- **Option A**: Directory Live Docs become first-class `ExplorerNodePayload` entries (with `archetype: "directory"`). The Circuit Board and other views can reference them like any other node.
- **Option B**: Directory metadata is served as a sidecar dictionary (`Map<directoryPath, DirectoryMetadata>`) alongside the graph. The Circuit Board reads this dictionary when rendering.

**Recommendation**: Option B. Directories are not graph nodes in the dependency sense — they don't have symbols, they don't consume or produce dependencies. They're containers. Mixing them into the node array would pollute the Force Graph (568 + ~100 directory nodes), pollute statistics, and require special-casing everywhere. A sidecar dictionary keeps the existing abstractions clean.

**2b. Type extension** — Add to the Explorer shared types:

```typescript
export interface DirectoryMetadata {
  path: string;
  purpose?: string;
  notes?: string;
  fileCount: number;
  subdirectoryCount: number;
  archetypeCounts: Record<string, number>;
  totalPublicSymbols: number;
}
```

### Estimated effort: ~0.5 dev days

## Archetype & Directory Live Doc Analysis

### Current Layer 4 Archetypes — Canonical Sections

| Archetype          | Public Symbols                                                | Dependencies                        | Observed Evidence             | Targets                         | Supporting Fixtures | Re-Exported Anchors      |
| ------------------ | ------------------------------------------------------------- | ----------------------------------- | ----------------------------- | ------------------------------- | ------------------- | ------------------------ |
| **implementation** | Symbols with signatures, docs, type refs                      | Resolved links to sibling Live Docs | Test files covering this file | —                               | —                   | If barrel/re-export file |
| **test**           | _(usually empty)_                                             | Imports from implementation files   | —                             | Implementation files under test | Fixture files used  | —                        |
| **asset**          | _(empty)_                                                     | References parsed from JSON, etc.   | —                             | —                               | —                   | —                        |
| **stub**           | _(defined but never materialized — 0 files in the workspace)_ |

The key structural pattern is: every Live Doc has **Metadata → Authored (Purpose + Notes) → Generated sections**. The Generated sections are gated by the `archetype` discriminant inside generator.ts.

### Can a directory slot into an existing archetype?

**No, not cleanly.** The closest match is "implementation" since it has the richest section set, but the semantics are wrong at every level:

- **Public Symbols** — directories don't export symbols; they _contain_ files that do. The directory analog is a _table of contents_.
- **Dependencies** — for a file, this means "what I import." For a directory, the useful concept is "what do my children collectively import _from outside this directory_" — cross-boundary aggregate dependencies.
- **Observed Evidence** — for a file, this lists specific test files. For a directory, the useful concept is aggregate coverage statistics.

A barrel file (`index.ts`) is the closest existing analogy — it re-exports symbols from a directory's contents. But directory docs are a superset: they describe _all_ children regardless of what's re-exported, and they aggregate metrics that no single file can.

**Recommendation: a new `"directory"` archetype** — the archetype discriminant already drives section selection in `buildGeneratedSections()`, so adding a new branch is the clean path and costs essentially nothing in complexity.

### What's Computable Without New Analysis?

Everything above is derived from data the generator already collects:

- **Contents**: file discovery already enumerates all tracked files
- **Aggregate Dependencies**: `buildGeneratedSections()` already resolves dependencies per file — we just aggregate and filter by "crosses directory boundary"

- **Cohesion**: ratio of intra-directory edges to total edges — trivial arithmetic

### Design Question Refined

Given this analysis, the real design question is: **should the directory docs be generated in the same pass as file docs, or in a second pass?**

A **second pass** is cleaner because:

- File docs must exist first (the Contents section links to them)
- The `inbound` graph must be fully built before we can compute Aggregate Dependents
- Cohesion and Surface Area require the complete dependency graph

The generator already builds the complete `WorkspaceSymbolIndex` in a first pass before rendering, so adding a "directory aggregation pass" after the file pass is architecturally natural — mirroring how `buildLiveDocGraph` already does a two-phase parse-then-resolve.

The generator's file discovery is glob-based (`discoverTargetFiles` matches files, not directories), and every consumer of `codePath` — the graph builder, the parser, the orphan finder, the lint pipeline, the inspect pathfinder — assumes `codePath` resolves to a **file that exists on disk**. Specifically:

- **find-orphans.ts** find-orphans.ts on the `expectedCodePath`. A directory Live Doc with `Code Path: packages/shared/src/live-docs/` would pass (`fs.access` succeeds on directories), but then it would be confounded with the _directory_ rather than a _file_, producing ambiguous orphan detection.

- **report-precision.ts** report-precision.ts at `parsedDoc.sourcePath` to re-analyze it and compare symbols/dependencies against the generated doc. A directory has no symbols to analyze — `analyzeSourceFile()` would fail or return empty, and the precision pipeline would flag it as zero-precision.

- **The prune logic** in generator.ts builds a `preservedDocPaths` set from the file generation pass. Directory docs wouldn't be in that set — they'd be **pruned as stale** unless we modify the pruning logic.

### 2. The Naming Problem

Where does the directory Live Doc's markdown file _live_ in the mirror tree? The current convention is:

```
source path:    packages/shared/src/live-docs/analysis/coActivation.ts
Live Doc path:  .mdmd/layer-4/packages/shared/src/live-docs/analysis/coActivation.ts.mdmd.md
```

For a directory analysis, there are two options:

- **`analysis/.mdmd.md`** (a file named after the extension inside the directory) — works, but `.mdmd.md` as a filename is weird and would collide if there were ever a file literally named `.mdmd.md` in the source tree
- **`analysis.mdmd.md`** (a sibling file alongside the directory) — conflicts if there's a source file named `analysis` (unlikely but technically possible), and breaks the mirror-tree invariant where the Live Doc path structure matches the source path structure

The `composeLiveDocPath()` function in markdown.ts naively appends the extension: `path.join(root, baseLayer, sourcePath + extension)`. For `sourcePath = "packages/shared/src/live-docs/"`, this produces `".mdmd/layer-4/packages/shared/src/live-docs/.mdmd.md"` — a hidden file. For `sourcePath = "packages/shared/src/live-docs"` (no trailing slash), it produces `".mdmd/layer-4/packages/shared/src/live-docs.mdmd.md"` — a sibling file that sits _next to_ the directory rather than _inside_ it, breaking the expectation that `ls .mdmd/layer-4/packages/shared/src/` shows a directory `live-docs/` containing the child Live Docs.

### 3. Overlap with the System Layer (Layer 3)

This is the most intellectually honest concern. The **System Layer already produces aggregate cluster documents**. Its archetypes — `component`, `interaction`, `data-model`, `workflow`, `integration`, `testing` — describe precisely the kind of cross-file relational analysis we're proposing for directory docs. The system generator uses co-activation analysis and graph clustering to discover meaningful groups of files, materialises a markdown document per cluster with component paths, edge tuples, and statistical significance data.

The critical difference: system clusters are **semantically derived** (co-activation, inheritance, data flow), while directory docs would be **structurally derived** (filesystem hierarchy). These are different partitions of the same file set, and they will **frequently disagree**:

- A directory like live-docs may contain files that participate in 3 different system-layer clusters
- A system-layer "component" cluster may span files across 4 different directories

If we ship both, we're generating **two competing aggregate views** of the same workspace, with different grouping strategies, different edge representations, and potentially contradictory cohesion signals. A consumer (human or copilot) looking at the aggregate dependency picture for "the analysis module" might get different answers depending on whether they look at the directory doc or the system component doc.

### 4. The Metadata `Code Path` Problem

Every Live Doc has a `- Code Path: <workspace-relative-path>` metadata line. The parser uses this as the **primary key** for the graph:

```typescript

```

For files, this is unambiguous. For directories, what is the `Code Path`? Options:

- live-docs (trailing slash) — inconsistent with how every other code path is normalized (no trailing slashes anywhere)
- live-docs (no trailing slash) — ambiguous: is this a file named `live-docs` or a directory?

This ambiguity infects `graph.nodes.get(codePath)`, `resolveArtifactIdentifier()`, the inspect pathfinder's BFS, and every other Map lookup keyed by code path.

### 5. The `archetype` Type Union Surface Area

Adding `"directory"` to `LiveDocumentationArchetype` is a type-level change that ripples through:

- liveDocumentationConfig.ts — the union definition
- archetype.ts — `resolveArchetype()` never receives directories
- generator.ts — `buildGeneratedSections()` switch on archetype
- circuitView.ts — CSS classes by archetype
- graph.ts — node payload assembly
- The lint pipeline — evidence validation is gated by archetype
- The system layer — `includeInComponents()` filters by archetype
- Every test fixture with hardcoded archetype strings

Not catastrophic, but it's a wide blast radius for what's nominally a "new archetype."

### 6. Generation Ordering Dependency

Directory docs **require a second pass** because they aggregate data from file docs. This means:

- The generator must run file analysis first, then directory aggregation
- `--changed` mode becomes tricky: if a file changes, its parent directory docs also need regeneration, and their parent, recursively to the root — a change to one file could trigger O(depth) directory doc rewrites
- `--include` mode (explicit file subset) has no sensible meaning for directories — you'd need a separate `--include-dir` flag or automatic parent inclusion

### 7. Scaling / File Count Explosion

In a deeply nested project, the number of directories can be substantial. Our own workspace has ~568 tracked files. A rough count suggests ~150–200 unique directory paths. That's 150–200 new Live Docs files. For a monorepo with 5,000 files, you might see 800+ directory docs. Each directory doc triggers:

- File write (disk I/O during generation)
- Parse pass (during graph build for Explorer/inspect)
- Lint validation
- Git tracking (diff noise on every regeneration)

This is the kind of thing that feels fine at our scale but could become a pain point for large adopters — and the product roadmap explicitly mentions monorepo support.

### 8. Detail Panel Assumptions

The Explorer's detail panel currently fetches and renders the markdown of a Live Doc selected by node click. It assumes the content has `Public Symbols`, `Dependencies`, etc. A directory Live Doc with different section names (`Contents`, `Aggregate Dependencies`, `Surface Area`) would need either:

- Generic section rendering (already somewhat present), or
- Archetype-aware rendering in the detail panel (new code path)

The difficulties cluster around one core design assumption: **the system was designed around `codePath` as a file path that resolves to a parseable source artifact**. Directories violate this assumption at every layer:

## Answering Your Three Questions

### 1. "Open in Code" — What is it getting us?

Here's the complete truth:

- **The VS Code extension has zero integration with the Explorer.** No webview, no URI handler, no command registration. The Explorer is launched as a standalone CLI (`npm run live-docs:visualize`) that spawns an HTTP server and opens the system browser.

- **The `/open` endpoint calls `execFile('code', [absoluteCodePath])`** — it shells out to the `code` CLI command. This works _only_ if (a) VS Code is installed, (b) the `code` command is on PATH, and (c) the workspace is local. - **The VS Code extension API has `vscode.commands.executeCommand('vscode.open', uri)` and `vscode.window.showTextDocument()`** which are the _correct_ way to open files in VS Code. If the Explorer were a VS Code webview panel, it could use `postMessage` to the extension host. Alternatively, a `vscode://` URI scheme could trigger file opening from an external browser.

**Net assessment**: The `/open` endpoint is a development convenience that works only in one specific environment (local machine, VS Code installed, `code` on PATH). ## The Case Against the Server

Here's the ledger:

### What the server provides

| Capability           | Server                                 | Static Equivalent                                  | Gap Severity    |
| -------------------- | -------------------------------------- | -------------------------------------------------- | --------------- |
| Initial graph load   | `/graph` → JSON                        | `explorer-data.json` → JSON                        | **None**        |
| Detail panel content | `/details` → parsed sections           | Embedded `docs` dict in JSON                       | **None**        |
| Raw doc download     | `/doc` → markdown file                 | Embedded `docs` dict                               | **None**        |
| Local Map data       | `/local-map` → computed JSON           | Client-side from graph (already works)             | **None**        |
| Bundled related docs | `/bundled-docs` → lazy scan            | Pre-scanned in JSON                                | **None**        |
| Graph refresh        | `/graph?refresh=1` → re-parse all docs | Re-run `visualize:static` (~12s) + browser refresh | **Marginal**    |
| Open file in VS Code | `/open` → `execFile('code', ...)`      | No equivalent (silently fails in static)           | **Replaceable** |

### What "Open in VS Code" actually needs

The extension already exists. The _correct_ architecture is:

- Static site renders a `vscode://file/{absolute-path}:{line}` URI link
- Or: the extension registers a custom URI handler (`vscode://jfjordanfarr.live-documentation/open?path=...`)
- Or: a VS Code webview panel hosts the Explorer and uses `postMessage` to the extension host

None of these require an HTTP server.

### The refresh latency question

- **Server refresh**: ~2-3 seconds (graph re-parse only, no tsx startup, no file writes)
- **Static rebuild**: ~12 seconds (tsx startup + graph parse + 14MB JSON write + HTML copy)
- **Optimized static rebuild**: If we skip the HTML template (it doesn't change) and skip tsx startup by making it a compiled CLI, the cost drops to ~3-4 seconds (graph parse + JSON write)

The 12-second latency is noticeable in a tight edit→regenerate→visualize loop, but it's not fundamentally different from the ~6-second `npm run live-docs:generate` that precedes it. The workflow is already:

1. Edit source file
2. `npm run live-docs:generate` (~6s)
3. View in Explorer

Adding "4. `npm run live-docs:visualize:static` (~12s)" doesn't dramatically worsen this. And the static build could be easily integrated into the generate step itself with a `--explorer` flag.

### Your architectural insight: CLI outputs → static site inputs

You're describing a clean pipeline:

```
source files → live-docs:generate → .mdmd/layer-4/*.mdmd.md → live-docs:visualize:static → dist/explorer/
                                                                                              ├── index.html
                                                                                              ├── explorer-data.json
                                                                                              └── local-maps/ (optional)
```

The outputs of the generator (markdown files) are the inputs to the graph builder, which produces JSON, which drives the static HTML. Every stage is a pure function of its inputs. No runtime state, no long-lived process.

This is the right architecture. The server is an _optimization_ (keeps the graph in memory, avoids re-parsing) wrapped in an _environment assumption_ (VS Code, local machine, `code` on PATH) that doesn't hold for the distribution scenarios we've designed: GitHub Pages, Teams embeds, offline snapshots.

### Where the server _does_ still make sense

One legitimate defense of the server: **during active development of the Explorer itself**, having a hot-reloading server is convenient. But that's a developer-of-Live-Documentation concern, not an adopter concern. We could keep the server as an internal development tool while making the static build the canonical user-facing distribution.

### Verdict

- Already works in static mode (graph, details, local map, bundled docs)
- Doesn't work correctly anyway (open in VS Code — wrong API, fails in static, silently fails in containers)
- Can be replaced by composing existing CLI commands (`generate` + `visualize:static`)

1. You're already waiting ~6s for `generate` to run
2. The static build could be compiled (no tsx startup) to cut this significantly
3. A `--watch` mode on the static builder could use `fs.watch` to rebuild incrementally

## 1. The JSON/MD Boundary

The clean line is: **Markdown for things humans author and browse on GitHub; JSON for things machines produce and consume.**

| Artifact                      | Format                          | Rationale                                                                                 |
| ----------------------------- | ------------------------------- | ----------------------------------------------------------------------------------------- |
| Per-file Live Docs (layer-4)  | **Markdown**                    | Humans author Purpose/Notes; browsable on GitHub; copilot context fuel; versionable diffs |
| Explorer graph + symbol index | **JSON** (`explorer-data.json`) | Already JSON; purely machine-consumed; 14MB would be absurd as .md                        |
| Lint report                   | **JSON** (new)                  | Structured diagnostics; consumed by Explorer, CI, and future VS Code extension            |
| Directory aggregates          | **JSON** (new, if/when)         | No authoring surface; purely computed rollups; feed Explorer enrichment                   |
| System/Layer-3 views          | **Markdown**                    | Currently materialised as .md; serves architectural documentation browsing                |

The principle: if there is no `## Authored` block (no human writes into it), it has no business being Markdown. JSON is easier to version, faster to parse, and composable as pipeline input.

## 2. Markdown Materialisation Strategy

Current reality: `live-docs:generate` writes markdown into `{root}/{baseLayer}/` (our workspace: layer-4). These are **repo-committed** and that's correct — they carry authored content, show up in GitHub browse/search, and serve as copilot context.

For the **new computed artifacts** (lint report, directory aggregates), the strategy should be:

| Output                   | Location                             | Committed?              |
| ------------------------ | ------------------------------------ | ----------------------- |
| Per-file Live Docs       | `{root}/{baseLayer}/`                | Yes                     |
| Lint report JSON         | `{root}/.cache/lint-report.json`     | **No** (.gitignore'd)   |
| Explorer bundle          | explorer                             | **No** (build artifact) |
| Directory aggregate JSON | `{root}/.cache/directory-index.json` | **No**                  |

The `.cache/` convention inside the Live Docs root is platform-agnostic (no `os.tmpdir()` needed), co-located with the docs it describes, and trivially .gitignore'd with a single line. This avoids:

- Platform-specific temp directory paths (tmp, `%TEMP%`, `$TMPDIR`)
- XDG_CACHE_HOME complexity
- Files disappearing on reboot
- Confusion about where to find cached outputs

The cache is a **build-time intermediate**, not a distribution artifact. Any CLI that needs it rebuilds it if stale, or reads it if fresh (like a lockfile).

| Command                      | What it does now                                     |
| ---------------------------- | ---------------------------------------------------- |
| `live-docs:generate`         | Writes per-file markdown + optional System views     |

| `live-docs:visualize`        | Starts HTTP server                                   |
| `live-docs:visualize:static` | Builds static bundle to explorer                     |

## The Reframe: Live Documentation as Codebase Cartography

The primary value isn't the documentation. It's the **map**. The generated graph — symbols, dependencies, archetypes, evidence — is worth more than every authored Purpose section combined, because it's the thing that tells you where data flows, what breaks when you change something, and where the unmapped territory is.

## My Recommendation: Path A, Reimagined as "Map View"

Reasons:

1. **Different questions, different views.** The treemap answers "where is everything, how big is it, how does it cluster?" The Local Map answers "what flows into and out of this specific node?" 2. **Progressive disclosure solves the DOM problem.** A 2-level treemap with ~20 visible rectangles at any time is trivially fast. Drill-down is a clean animation. The full 568-node render never happens.

3. **Directory dependencies become natural.** Edges between directory rectangles, colored/weighted by aggregated connection count, give you the "coarse granularity" view you're describing — the thing that's missing today.

4. **Cluster mode is a drop-in.** If the grouping function is parameterized (directory hierarchy vs. co-activation cluster), the same layout engine handles both. You get the System Layer's semantic clustering surfaced spatially without needing Layer 3 markdown at all.

5. **Rename: "Map View"** (or "Overview"). "Circuit Board" was always a metaphor searching for a reason. "Map View" says what it does — it's the map you zoom into.

Here's the cross-reference synthesis — eight friction points between today's design proposals and the documented requirements, each framed as a decision boundary.

---

## 1. FROM/TO Pathfinding: Replacement vs. Addition

**Today's proposal**: Replace FROM/TO with impact tracing (ripple from a single origin).

**Documentation requires** (CAP-003, SC-LD-008, FR-LD5, US-9 §4):

- "traces dependency paths between arbitrary 'from' and 'to' artifacts" (CAP-003)
- "Local Map mode where maintainers can enter a From artifact and a To artifact" (CAP-003)
- "live-docs inspect MUST support --from/--to path discovery" (FR-LD5)
- Stream LV1-E: FROM/TO in Local Map is marked **COMPLETE** (shipped 2025-12-18)
- SC-LD-008 is a _success signal_ — its satisfaction is how we prove the system works

**Decision boundary**: FROM/TO can't be _replaced_ — it's a shipped capability, a functional requirement, a success criterion, and half of the "flagship CLI experience." Impact tracing can be _added_ as a complementary mode (single-origin fan-out vs. two-endpoint path), but the FROM/TO controls must remain. The practical question becomes: does impact tracing live in Local Map as a mode toggle, or is it a separate view state triggered when only `From` is set?

---

## 2. Detail Panel: Named Component or Described Function?

**Today's proposal**: Expandable center card replaces the 360px sidebar.

**Documentation requires** (CAP-008, SC-LD-007, REQ-V1, US-9 §1–2):

- "detail panel must surface the relevant Live Doc metadata" (CAP-008)
- "detail panel renders authored Live Doc sections read-only and loads within ≤500 ms" (REQ-V1)
- "selection state and detail panel persist" across view switches (US-9 §2)
- "detail panel lists public symbols with 'open in editor' affordances" (US-9 §1)

**Decision boundary**: The documentation names "detail panel" 6+ times across FRs, SCs, and acceptance scenarios. But every mention describes the same _function_: surface Live Doc metadata + provide "open in editor" + persist across views + render ≤500 ms. An expandable card satisfying all four functions could be argued to _be_ the detail panel in a different layout. The risk is the cross-view persistence requirement (US-9 §2) — if you switch from Local Map to Force Graph, the card metaphor changes dramatically. Either:

- **(A)** Keep a consistent detail mechanism across views (the card IS the panel, just not a sidebar), or
- **(B)** Amend the documentation to say "detail surfaces are view-specific" (Local Map uses card expansion, Force Graph uses popover, Circuit Board uses drill-down).

---

## 3. Circuit Board → Map View: Focus Mode ≠ Drill-Down

**Today's proposal**: Progressive-disclosure treemap — directory rectangles → drill into file cards.

**Documentation requires** ([US-9 §1](../../../.mdmd/layer-2/feature-specification.mdmd.md), FR-LD16):

- "Given a node on the circuit-board view, When focus mode activates, Then unrelated nodes hide" (US-9 §1)
- "merge views into a single UI, maintain state across views, expose 'open in editor', provide focus-mode" (FR-LD16)

**Decision boundary**: The documented "focus mode" _hides unrelated nodes at the same level_ — you click a file, its non-dependents fade. Progressive-disclosure drill-down _changes what level you're viewing_ — you click a directory, its children appear. These are different interactions. The proposal is an evolution beyond what's documented, but it doesn't _contradict_ focus mode — you could have both (drill into a directory, THEN focus-mode within it). The rename from "Circuit Board" to "Map View" is cosmetic and free. The progressive disclosure is new documented territory.

---

## 4. Force Graph: Today's Discussion ALIGNS

**Today**: User defended Force Graph as most valuable view; agent agreed.

**Documentation**: CAP-010 assigns Force Graph for brownfield docs ("Show Related Documentation" checkbox, dashed borders). REQ-B1 formalizes this. US-11 requires visibility toggle.

**Decision boundary**: None — the only open question is layering today's topological-value insight INTO the documentation. The docs currently frame Force Graph primarily as the brownfield integration surface (CAP-010), but today's analysis shows it serves a deeper role: _emergent topology discovery_ (clusters, coupling patterns, symmetry). The docs should evolve to acknowledge this dual role — Force Graph for topology AND brownfield, not just brownfield.

---

## 5. Authored Content: "Codebase Cartography" vs. "Authored Preamble"

**Today's proposal**: Map is the primary value; authored content is optional enrichment.

**Documentation requires** (CAP-001, Guiding Principle #3, US-1):

- "every tracked asset owns an authored preamble" (CAP-001)
- "humans curate authored notes and waivers with discipline" (GP #3)
- "Writers and Architects: documentation owners edit a concise authored block" (Persona)
- US-1 is P1 — Complete, meaning authored curation is a _shipped, first-priority_ capability

**Decision boundary**: The documentation doesn't actually say authored content is the _primary_ value either — it says it's an _owned_ value. Read carefully, CAP-001 says "every tracked asset owns an authored preamble" not "the preamble is the point." The real primary value statement is in the mission: _"the definitive answer to the question: 'What other files will be impacted by this change?'"_ — which IS the cartography framing. The reframe is compatible if stated carefully: **the map (dependency graph) is the primary value; authored annotations are first-class enrichment for the Writers/Architects persona, not optional but also not the raison d'être.**

---

## 6. Directory Docs and the 1:1 Invariant

**Today's proposal**: JSON sidecar for directory aggregates (not markdown).

**Documentation requires** (REQ-L1):

- "one-to-one Live Doc ↔ source relationships"

**Decision boundary**: COMPATIBLE. The 1:1 invariant applies to _Live Docs_ (markdown files in the base layer). A JSON sidecar is explicitly NOT a Live Doc — it's a computed cache artifact. The documentation's "tracked asset" language never mentions directories. As long as directory JSON files live in a `.cache/` folder (not the base layer), the invariant holds. This is clean.

---

## 7. Data Parity and Computed Aggregates

**Today's proposal**: Map View shows directory-level aggregates (edge sums, health coloring).

**Documentation requires** (CAP-008):

- "data parity with the headless Live Doc graph—no inferred edges or metadata beyond what Live Docs encode"

**Decision boundary**: This is the **sharpest disagreement**. Directory-level edge sums, health coloring, and cluster assignments are _computed_ metadata not present in any Live Doc. The data parity principle says the Explorer must show exactly what Live Docs encode — nothing more, nothing less. Three resolutions:

- **(A)** Directory JSON sidecars become an explicit data source alongside Live Docs, and we amend data parity to say "no metadata beyond what Live Docs AND directory manifests encode."
- **(B)** Aggregates are computed client-side on the fly (sum of children's edges is derivable from the graph — no new data source needed). This arguably satisfies data parity because the facts are all in the graph; the aggregation is just presentation math.
- **(C)** Acknowledge that pure data parity was always aspirational — Knowledge Sources view already computes islands, fan-out, and fan-in client-side without any Live Doc encoding those facts.

Option B is the cleanest: directory aggregates are _derived views_ of existing Live Doc facts, not new data. The principle's spirit — "CLI and UI see the same graph" — is preserved because the underlying edges are identical.

---

## 8. Impact Tracing: Genuinely New Territory

**Today's proposal**: Impact tracing as a Local Map visualization mode — single origin, ripple outward showing affected files.

**Documentation says**: Nothing. This capability doesn't exist in vision, roadmap, spec, or acceptance criteria. The descoped "reactive ripple diagnostics" ([Scope and Non Goals](../../../.mdmd/layer-1/link-aware-diagnostics-vision.mdmd.md)) was about _real-time change notifications_, not visualization.

**Decision boundary**: Impact tracing is net-new. The closest documented behavior is `live-docs inspect --from A` (CLI walking toward terminal roots), but the _visualization_ of that walk as an animated/highlighted ripple through Local Map columns is undocumented. This needs to be formally added — likely as an extension of CAP-003 or CAP-008, with its own acceptance scenario. The natural fit: when `From` is set but `To` is empty, Local Map enters impact-tracing mode (fan-out columns). When both are set, it enters pathfinding mode (existing FROM/TO). This unifies both capabilities under the same UI controls.

---

## Summary: What Needs to Change

| Proposal                 | Documentation Status                           | Required Action                                                     |
| ------------------------ | ---------------------------------------------- | ------------------------------------------------------------------- |
| Impact tracing           | **New** — not documented                       | Add to CAP-003/CAP-008 as `From`-only mode                          |
| FROM/TO replacement      | **Contradicted** — shipped success signal      | Keep FROM/TO; add impact tracing alongside                          |
| Detail panel → card      | **Tension** — named 6+ times                   | Redefine "detail panel" as view-specific detail surface             |
| Map View drill-down      | **Extension** — goes beyond focus mode         | Document drill-down as complementary to focus mode                  |
| Force Graph value        | **Aligned** — but underappreciated             | Expand CAP-010 to acknowledge topological discovery role            |
| Authored content reframe | **Compatible** — mission already says "impact" | Clarify: map is primary, authored content is first-class enrichment |
| Directory JSON sidecar   | **Compatible** — sidecars aren't Live Docs     | No doc change needed                                                |
| Data parity + aggregates | **Sharp tension** — CAP-008 says "no inferred" | Resolve via "aggregates are derived views, not new data"            |

The single hardest decision: **impact tracing and FROM/TO must coexist**, not compete. The cleanest design is a unified `From`/`To` control where setting only `From` triggers impact tracing and setting both triggers pathfinding — same controls, two modes, zero documented requirements violated.

Here's the precise answer to your question.

## How Path Selection Works Today

**Both implementations (CLI and Explorer) use standard BFS with a single `parents` map.** This means:

### CLI (pathfind.ts and pathfind-symbol.ts)

The `searchGraph()` function at pathfind.ts runs BFS with a `Map<string, string>` called `parents` — each node maps to **exactly one** parent. When BFS reaches the target, `reconstructPath()` walks the parent chain back to produce a single path.

When a node is first visited, it's marked in `visited` and its parent is recorded. If a different path to the same node is discovered later (at the same depth or deeper), it's **silently discarded** because `visited.has(neighbor)` returns true.

This means: **whichever neighbor BFS dequeues first wins**. The iteration order is determined by `Set` iteration over `graph.nodes.get(node)?.dependencies` (for outbound) or `graph.inbound.get(node)` (for inbound). JavaScript `Set` iterates in insertion order, which depends on the order Live Docs were parsed.

### Explorer (pathfind.ts client-side)

The `findPath()` function at client pathfind.ts uses the same pattern: BFS with a `Map<string, string>` parents map, first-visit-wins. It tries inbound direction first, then outbound — returning whichever succeeds first.

### Rendering

`showPathResult()` at index.ts takes the single `PathfindResult`, extracts the `nodeIds`, and passes them to `localView.setActivePath()`. The renderer at render.ts (`renderPathModeColumns`) creates one column per `nodeId` — a linear chain: FROM → Via 1 → Via 2 → TO.

**There is zero infrastructure for alternate paths. One path in, one path rendered.**

## What's Lost

The answer to "which path is chosen" is: **the one determined by JavaScript Set insertion order of the dependency edges when the graph was built.** This is essentially arbitrary from the user's perspective.

Consider a diamond dependency:

```
A → B → D
A → C → D
```

BFS from A to D: both B and C are at depth 1. Whichever's edge appeared first in the Set gets dequeued first. If B arrives at D first, path = A→B→D. C→D is never shown, despite being **equally valid and potentially more semantically meaningful**.

At 2+ hops, this gets worse. Consider:

```
A → B → E → D    (3 hops)
A → C → D        (2 hops, shortest)
A → F → G → D    (3 hops)
```

BFS correctly returns A→C→D (shortest). But A→B→E→D and A→F→G→D reveal different transitive dependency chains that might matter — especially if B or F have different semantic roles (one carries type information, one carries runtime behavior).

## Should We Show More Paths?

The mission is: _"What other files will be impacted by this change?"_

A single shortest path tells you **one** chain of impact. But real dependency graphs are denser than trees. The question isn't just "can A reach D?" but "through which intermediaries, and which symbols?"

Here's what I think the truthful answer looks like, in order of value:

### 1. All shortest paths (same hop count)

**High value, bounded cost.** A modified BFS that records all parents (not just the first) per node, then enumerates all shortest paths via backtracking. The number of shortest paths is bounded by the graph's branching factor at each depth — in practice, for the kinds of codebases Live Documentation targets, this is usually single digits.

This would let the Local Map show: "There are 3 equally-short paths from A to D. Here they are." The renderer could show them as a **merged DAG** (shared nodes in one column, divergent nodes side-by-side within a column) rather than as separate linear chains.

### 2. Near-miss paths (shortest+1)

**Medium value, higher cost.** After finding all shortest paths of length $k$, enumerate paths of length $k+1$. These often reveal an important intermediary that the shortest path "skips over." In practice, the shortest path between two files often goes through a shared interface/type file, while the +1 path goes through the actual implementation that uses that interface.

The risk: combinatorial growth. A +1 search on a 3-hop shortest path could yield dozens of 4-hop paths. Would need a cap (e.g., top 5 by some ranking heuristic like "how many of the intermediate nodes are unique to this path?").

### 3. Symbol-divergent paths (same file path, different symbol chains)

**Highest value per bit of new information, currently unavailable in the Explorer.** The CLI has `searchSymbolPath()` which tracks symbol transitions through the graph. But the Explorer's `findPath()` is file-level only — it doesn't use symbol edges at all. Two paths A→B→D that traverse different symbols through B are collapsed into one.

The pathfind-symbol.ts module exists in the CLI and does symbol-aware BFS with composite visited keys (`codePath#symbol`). This could be ported to the client-side pathfinder to reveal: "A reaches D through B, but through _two different symbol chains_ — one via `B.parseConfig` and another via `B.validateInput`."

The renderer change for all-shortest-paths is the smallest lift with the biggest payoff: the column structure already exists, the connection drawing already supports multi-hop with hop-indexed anchors, and the card factory already handles `hopIndex`. The key change is that a single hop column would contain **more than one card** when paths diverge at that depth.
