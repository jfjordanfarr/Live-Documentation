## The Three Views Have Three Distinct Jobs

### Local Map — "What does this file touch?"

The Local Map (screenshot 3) answers a **focused, file-centric question**: given `symbol-highlight.ts`, what are its inputs and outputs, at symbol granularity? It's the visual equivalent of `npm run live-docs:inspect -- --from symbol-highlight.ts`.

### Force Graph — "What's the shape of the whole dependency web?"

The Force Graph (screenshot 4) answers a **topological question**: which files cluster together? Where are the hubs? Where are the islands? Physics simulation reveals emergent structure — tightly-coupled modules pull together, loosely-coupled ones drift apart.

**Strengths**: Discovering unexpected coupling, spotting orphan nodes (the scattered dots at the periphery), identifying hub files that everything depends on (the dense core).

**Not suited for**: Locating a specific file (you're scanning 578 anonymous dots), understanding directory structure, or reading any detail about a node without hovering. It's a discovery tool, not a navigation tool.

### The Roadblock: `render()` Is a Full Teardown/Rebuild

**This is the design constraint that forces a modification to the vision.**

The current `render()` function ([circuitView.ts line ~340](packages/scripts/src/live-docs/explorer/client/views/circuitView.ts#L340)) does `circuitContainer.innerHTML = ""` and then rebuilds the entire DOM tree from scratch. Every call to `renderCurrentView()` (triggered by filter toggles, view switches, node selection) destroys all Circuit Board DOM elements and recreates them.

This matters because the progressive disclosure design has **two levels of state** that the current architecture doesn't distinguish:

1. **Structural state** — which directories are expanded/collapsed (new)
2. **Focus state** — which node is selected/hovered (existing)

In my diagrammed design, expanding a directory (State 1 → State 2) should be a **partial DOM update** — only the clicked directory tile gets replaced with its child tiles. But `render()` as written would nuke the entire treemap and rebuild it, losing pan/zoom position, expanded-directory state, and animation continuity.

**Implication**: The vision of smooth "click to expand" transitions requires `render()` to become state-aware rather than always doing a full rebuild. This is the same architecture the Local Map solved by extracting `state.ts` and `render.ts` as separate concerns. The Circuit Board needs the same decomposition.

However — and here's the design modification — **we should not attempt incremental DOM patching**. That's a complexity trap. Instead:

**Modified design**: `render()` continues to do a full rebuild, but it reads from a **`CircuitBoardState`** object that tracks which directories are expanded. The rebuild is fast (it was fast for 578 nodes — it'll be even faster with 30 directory tiles). The key change is that the `render()` function's output depends on `circuitBoardState.expandedDirectories`, and the pan/zoom transform is preserved across renders (it already is — `circuitTransform` is not reset by `render()`).

This means: no smooth CSS transitions for directory expand/collapse. Instead, the treemap layout changes instantly and then `animateCircuitTransform()` smoothly zooms to the newly expanded directory. This is architecturally clean and visually acceptable.

### The Second Constraint: Tile Sizing in Aggregated Mode

**This is the subtler design issue.**

In the current layout, tile size is determined bottom-up: measure each file card (260×168 px), compute the grid, sum up to the directory, sum up to the parent. This produces tiles sized by **content volume** — a directory with 14 files gets a big tile because it needs space for 14 cards.

In the aggregated view, we want tile size to reflect **architectural importance**. A directory with 3 files but 60 dependency edges (e.g., `server/src/features/live-docs/`) should be larger than a directory with 8 files but 4 edges (e.g., reporting).

The current `measureDirectoryTree()` can't express this because it sizes everything from file-grid metrics upward. We need a parallel sizing path: `measureDirectoryAggregate()` that returns a bounding box proportional to the aggregate score, using a squarified treemap algorithm rather than the existing flow layout.

**Modified design for tile sizing**: Use a classic squarified treemap (Bruls-Huizing-van Wijk) for the top-level aggregated layout, where each directory's weight is `totalDeps + totalSymbols` (or similar composite score). This replaces the current flow-layout-into-4:3-aspect-ratio algorithm for State 1 only. The existing flow layout continues to be used for State 2 (expanded directory showing individual files).

This means:

- layoutUtils.ts gains `computeSquarifiedLayout()` (~80 lines) — a standard algorithm with well-known implementations
- `measureDirectoryTree()` with `maxDepth=0` returns square weights instead of content-based dimensions
- The two layout algorithms coexist: squarified for directory-level, flow for file-level

### Additional Failure Modes Scraped from Context

1. **Deep nesting / single-directory dominance** (UC-085, UC-091, UC-092)
   External repos like BrainSimIII or a Unity project may have structures like `src/app/modules/feature/components/` where 90% of files live under one top-level directory. The aggregated view would show one giant tile and several tiny ones — defeating the purpose. **The plan needs recursive drill-down** (expanding a directory shows _sub-directories_ as aggregate tiles, not raw files) for directories exceeding some child-count threshold. Without this, the design solves our ~568-file workspace but breaks on larger codebases, which UC-091/UC-092 explicitly target.

2. **Connections across aggregation boundaries**
   If File A (in an expanded directory) depends on File B (inside a collapsed directory), what renders? Options: (a) draw connection to the collapsed directory tile, (b) draw nothing, (c) show a badge count ("3 outbound to shared"). The plan mentions Focus Mode dimming but doesn't address cross-boundary edge rendering. This is the single most likely source of user confusion.

3. **Test filter + aggregation interaction**
   `shouldCountNode()` includes test files in aggregate metrics, but `shouldRenderNode()` hides them when a directory is expanded. A directory tile might show "47 files, 8 symbols" in aggregate, then expand to reveal only 31 visible files — jarring mismatch. Either aggregate metrics should respect the active filter, or the tile should show "47 files (31 visible)".

4. **Expand state loss on view switching** (UC-060 plus existing `renderCurrentView()` behavior)
   The orchestrator in index.ts calls `render()` on every view switch. Since `render()` does full DOM teardown, the expand state must live _outside_ the DOM — in a `CircuitBoardState` object. The plan mentions this, but the risk is that `renderCurrentView()` calling `circuitView.render(nodes, state)` might not pass state through consistently. Must verify the wiring.

5. **Static bundle size regression** (UC-052)
   The squarified treemap algorithm (~80 lines), breadcrumb component, and aggregation logic add client-side JS to the static Explorer bundle. For GitHub Pages deployment, bundle size matters. This is likely negligible (~2-3KB gzipped) but worth a sanity check after implementation.

6. **Headless parity** (UC-046)
   The `live-docs:visualize` command produces a static HTML bundle. All new interactivity (expand/collapse, breadcrumbs, focus mode) is client-side JS, so headless generation isn't affected. But if we add server-side pre-rendering of aggregated metrics (e.g., embedding aggregate data in `explorer-data.json`), that changes the contract. The plan correctly avoids this — aggregation is computed client-side from existing node data.

7. **Performance ceiling on expand** (UC-087's original complaint)
   Expanding a directory with 200+ files still creates 200+ DOM nodes — the same saturation problem the aggregation was meant to solve. For our workspace (largest directory might be 50-60 files), this is fine. For UC-091/UC-092 targets, it's not. This reinforces failure mode #1: **nested aggregation** is needed for directories above a configurable child-count threshold.

### Verdict

The plan is **sound for our workspace** but has a **scalability gap** that UC-091 and UC-092 would expose. The fix is to make directory expansion recursive: clicking a large aggregate tile reveals its _sub-directory_ aggregates (not raw files) until a directory is small enough to show individual files. This is ~20 lines of additional logic in the expand handler and doesn't change the rest of the architecture.

The cross-boundary connection rendering (failure mode #2) is the design question most likely to produce a bad UX if punted. I'd recommend addressing it as a "badge count on collapsed tiles" approach — simple, informative, doesn't require SVG line routing.

## Why Progressive Zoom Feels Right But Is Tricky

Each zoom level compresses the parent into a thinner frame, and by level 5 you're looking through a telescope of nested borders with no usable space for content. The old Circuit Board _was_ this approach — everything nested in place — and it became "borderline useless" precisely because the nesting consumed all the visual budget.

So progressive zoom works for 2-3 levels but degrades at depth. The current "teleport with breadcrumb" works at arbitrary depth but loses spatial context. Neither is fully satisfying alone.

## Three Options

### Option A: Expand-in-Place with Dimmed Siblings ("Accordion Treemap")

The clicked directory tile grows to fill ~75% of the viewport. Its siblings shrink to thin labeled strips along one edge (right side or bottom), dimmed but still visible and clickable. The expanded directory shows its children (subdirectory tiles + uniform file cards). Clicking a sibling swaps which tile is expanded. Breadcrumb still works for going up.

```
┌──────────────────────────────────────────┬───────────┐
│                                          │ scripts   │ ← dimmed sibling strips
│   ┌─────────┐ ┌─────────┐ ┌────────┐    │ server    │
│   │shared/  │ │extension│ │ cli/   │    │           │
│   │  src    │ │  /src   │ │  src   │    │           │
│   │ 88files │ │ 1 file  │ │ 1 file │    │           │
│   └─────────┘ └─────────┘ └────────┘    │ tests     │
│                                          │           │
│   packages (expanded)                    │           │
└──────────────────────────────────────────┴───────────┘
```

**Pros:** Spatial anchoring without nesting depth problems. Siblings are always one click away. Understandable visual metaphor (accordion-like).

**Cons:** No cross-directory dependency visibility. Still a hard boundary between Circuit Board and Local Map. The dimmed strip region might feel wasted at leaf directories where all siblings are small.

### Option B: Unified View Continuum ("Semantic Zoom")

Circuit Board and Local Map merge into a single view with continuous zoom levels:

- **Level 1 — Directory tiles**: Squarified treemap of directories (current implementation)
- **Level 2 — File cards**: Uniform node cards in a grid within an expanded directory, with directory-level connection lines showing which sibling directories this one interacts with
- **Level 3 — File focus**: Click a file card and it transitions (CSS) to the center column of a 3-column layout. Its inbound dependencies appear left, outbound right — this IS the Local Map, reached via navigation rather than tab switch

The tab bar still exists but selecting "Local Map" simply jumps to Level 3 for the selected node. Selecting "Circuit Board" jumps to the directory level containing the selected node. They're bookmarks into the same continuum, not separate renderers.

```
Level 1 (directory tiles):
┌────────────┐ ┌────────────┐
│ shared/src │ │ scripts/   │
│  88 files  │ │  src       │
│  ──────→   │ │  78 files  │
│  (depends) │ │            │
└────────────┘ └────────────┘

Level 2 (file cards in shared/src):      [scripts/src dimmed strip →]
┌────────┐ ┌────────┐ ┌────────┐
│core.ts │ │parse.ts│ │types.ts│
│59 syms │ │ 5 syms │ │ 4 syms │
└────────┘ └────────┘ └────────┘
┌────────┐ ┌────────┐ ┌────────┐
│schema  │ │render  │ │discov. │
│ 8 syms │ │ 4 syms │ │ 3 syms │
└────────┘ └────────┘ └────────┘

Level 3 (file focus = Local Map):
    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │ types.ts │    │ core.ts  │    │ parse.ts │
    │ inbound  │ ←─ │ FOCUSED  │ ─→ │ outbound │
    │          │    │          │    │          │
    └──────────┘    └──────────┘    └──────────┘
```

**Pros:** Eliminates the artificial Circuit Board / Local Map boundary. A single navigation model from workspace overview to file detail. Cross-directory dependencies visible at Level 1/2 via aggregate connection lines between tiles. Most intellectually honest representation of the data — the views really are the same concept at different granularities.

**Cons:** Highest implementation effort. Requires rethinking the view management layer (currently tab-switched with separate renderers). CSS transitions between Level 2 and Level 3 are non-trivial (grid → 3-column with connection lines). Risk of over-engineering if the Level 2→3 transition doesn't feel natural.

### Option C: Two-Zone Layout with Directory Connections ("Practical Middle Ground")

Keep the current drill-down model but fix the three visual problems with focused changes:

1. **Files as uniform cards**: Files render as equal-sized node-card chips in a flow grid (not squarified). Directories continue as squarified tiles. Instantly distinguishable.
2. **Dimmed sibling bar**: When expanded, siblings appear as thin strips along the right edge (like Option A).
3. **Directory-level connections**: At Level 1/2, draw SVG lines between directory tiles showing aggregate dependency flow. Hovering a tile highlights which other tiles it depends on / is depended on by. The data already exists in `outboundDepCount` / `inboundDepCount`.

The Circuit Board and Local Map remain separate tabs but with a smoother handoff: clicking "Open in Local View" from a file card in Circuit Board animates the transition rather than hard-cutting.

**Pros:** Achievable incrementally. Each piece (uniform cards, dimmed siblings, directory connections) can land independently. Doesn't require rethinking the view architecture.

**Cons:** Doesn't resolve the fundamental "two views for one concept" tension. Directory connections at deep nesting levels (where siblings are far apart in the hierarchy) are hard to draw meaningfully.
