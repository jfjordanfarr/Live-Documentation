## Design Analysis: Bundle Edges in Browse Mode

### The fundamental tension

The treemap is a **space-filling layout** — every pixel is spoken for. Tiles represent proportional size within a directory. This is its strength (you see WHERE the code mass is) and its constraint (you can't just insert new tiles for remote directories without recomputing the entire squarify partition and breaking the user's spatial mental model).

The pin-active two-column layout solves the relational problem completely by **abandoning treemap geometry** and switching to a flow layout where cards from _any_ directory can appear, grouped by membrane ancestor bands. That's the right design for that mode.

The question is: what do we do in browse mode, where the geometry is locked?

### Cross-directory spanning: why bundle edges between tiles don't work

Your instinct is exactly right. Consider the user browsing membraneView. The treemap shows sibling tiles:

```
┌─────────────────────────────────────────┐
│  membraneView/                          │
│  ┌──────────┐ ┌──────────┐ ┌─────────┐ │
│  │browse-   │ │ index.ts │ │focal-   │ │
│  │renderer  │ │          │ │overlay  │ │
│  └──────────┘ └──────────┘ └─────────┘ │
│  ┌──────────┐ ┌──────────┐ ┌─────────┐ │
│  │pin-active│ │edge-     │ │svg-conn │ │
│  │renderer  │ │bundling  │ │ections  │ │
│  └──────────┘ └──────────┘ └─────────┘ │
└─────────────────────────────────────────┘
```

Drawing bundle edges between siblings here would show intra-directory dependencies (e.g., index.ts → browse-renderer.ts). But the **interesting** dependencies — browse-renderer.ts → `../../circuitView/aggregation`, focal-overlay.ts → `../connection-geometry` — point to directories that are _nowhere in the viewport_. You'd have edges flying off the edge of the treemap to... nothing. Or you'd need to add ghost tiles for those remote directories, which breaks squarify.

### The design that already exists (almost)

Looking at the code, the progressive disclosure model is already partially wired:

1. **Badges as hints** (browse-renderer.ts): Collapsed directory tiles show `15 out`, `8 in` badges. These ARE the browse-mode edge signal — they tell you "this directory has connectivity" without drawing a single line.

2. **Focal overlay as intermediate relational view** (index.ts): When a user clicks a file card (select, not pin), the focal overlay already draws SVG connections to other _visible_ nodes. This is the relational layer appearing on-demand within the spatial layout.

3. **Pin spectrum as full relational view**: Pinning symbols triggers the full membrane-band columns where remote directories are pulled in.

The missing piece isn't "draw edges between directory tiles." It's: **make the badges interactive so they bridge the user from spatial awareness to relational exploration.**

### Proposed interaction model

```
BROWSE MODE — SPATIAL LAYER
─────────────────────────────────────────
User sees:    Treemap tiles + metric badges
Interaction:  Click tile → drill in (navigate)
              Click file card → expand (show symbols)
Signal:       Badges tell you connectivity exists
              (files: 12, sym: 45, out: 15, in: 8)

         │
         │  Tap/click a badge (not the tile itself)
         ▼

BADGE POPOVER — RELATIONAL HINT
─────────────────────────────────────────
```

### Why this works

**No reflow**: Badge popovers float above the layout (absolutely positioned, like tooltips). The treemap geometry is untouched. No elements shift.

**No hover-dependent rendering**: The popover triggers on click/tap, not hover. Desktop users can hover for a tooltip preview ("15 outbound dependencies — click for details"), but the primary interaction is click. Mobile gets the same click path with zero hover dependency.

**Drill-in preserved**: Clicking the tile body drills in. Clicking the badge opens the popover. These are spatially distinct targets — the badges are small elements in the corner of collapsed tiles. This is the same pattern as "clicking a folder icon vs clicking folder text" in file explorers.

**Progressive disclosure**: Browse → Badge Popover → Pin-Active follows the principle of least surprise. Each step reveals more relational information, with each transition being local (popover appears near badge) or expected (pin-active is already established behavior).

**Mobile-friendly**: All interactions are tap-based. Long-press could be reserved for "quick peek" (show popover without requiring precise badge targeting on small tiles), but even without it, the model works with standard taps.

### What we should NOT do

1. **Draw bundle edges on the treemap in browse mode.** The original Gap 1 proposal had it right to disable these. The visual noise concern is real, AND the cross-directory spanning problem has no clean solution within squarify geometry.

2. **Hover-only edge reveal.** Causes reflow if membranes need to grow, unavailable on mobile, and ephemeral state means the user can't interact with the revealed information.

3. **Progressive membrane wrapping in browse mode.** Pin-active mode's membrane bands work because it abandons the treemap for a flow layout. Injecting flow elements into a squarify partition breaks the fundamental layout contract.

### Implementation delta from current state

This badge-popover approach is relatively lightweight:

- **Badge click handler** on collapsed directory badges (currently badges are static `<span>` elements) — add click handler that computes top-N dependency targets from `aggregates` + `graphData.links`
- **Popover DOM** — a floating `<div>` anchored near the badge, with a list of directory targets + edge counts. Dismissed on outside click or Escape.
- **Navigation integration** — clicking a target in the popover calls `onExpandDirectory` to navigate there
- **Pin integration** — a "Pin All" button in the popover that pins the directory's symbols, triggering the existing pin-active mode transition

Gap 3 (`expandedCards` persistence) and Gap 4 (dimming inconsistency) can proceed independently and are lower-risk.

## Verified On-Screen Behavior (Playwright Audit)

### What collapsed directory tiles have

- `membrane__label` + `membrane__metrics` only
- Whole tile is `role="button"`, single click handler → drill-in
- **No buttons, no pin elements** — badges are static `<span>` elements
- Size-based badge cutoff: `extension` (37×73) and `cli` (37×73) show zero badges; `server` (570×146) shows all 4 badges

### What collapsed file cards have

- Header row with filename + **"Pin all symbols"** button (always present, even collapsed)
- Symbol **count** summary ("3 symbols", "59 symbols") — no individual symbol names
- Path + directory
- **Single click → expand card in-place** (shows symbol rows with pin dots)
- **Pin All button clickable directly from collapsed card** — skips the expand step entirely

### The click-distance problem

From packages level to first SVG connection:

1. Click `server` tile → see `src` collapsed (click 1)
2. Click `src` tile → see `features`, `runtime`, `main.ts` (click 2)
3. Click `features` tile → see `live-docs`, `knowledge` (click 3)
4. Click `live-docs` tile → see file cards + subdirs (click 4)
5. Click Pin All on `generator.ts` card → pin-active mode with 12 cards, 42 SVG paths (click 5)

**5 clicks minimum** from a high-level collapsed tile to connections. The directory depth of this particular codebase amplifies the problem — live-docs is 7 levels deep as a membrane hierarchy.

### The transition surprise

Pin-active mode is a **complete layout replacement**: the treemap disappears entirely and a 3-column flow layout appears with membrane bands. The transition is instantaneous — clicking one pin dot or Pin All button triggers a full DOM rebuild. The "← Back to Browse" button returns to the treemap.

### Navigation is click-only — no breadcrumb in browse mode

- Single click on collapsed tile → drill in (expand directory, refocus treemap)
- Double-click on expanded membrane → collapse it (navigate up)
- No breadcrumb bar in browse mode — only in pin-active mode
- No keyboard navigation (Escape doesn't navigate up)
- Labels have `cursor: grab` (for panning), not clickable for navigation

### What Pin All actually does

Pin All on a 3-symbol file (`generator.ts`) → clean, manageable: 12 cards, 42 paths, 8 bands across 3 packages. Pin All on `main.ts` (2 symbols) → minimal: 2 cards, 1 path. The concern about 59-symbol files (`core.ts`) is valid — that would likely be overwhelming.

### Key "small surprises" discovered
