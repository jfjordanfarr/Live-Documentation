## Option A: Fix Phantom Edges — Global Symbol Collision Bug

### Problem Statement

The Explorer graph and the Live Doc generator both resolve type references (extends/implements) via a **global workspace-wide symbol index** without any file-proximity or language-scoping heuristic. When multiple files export the same symbol name (e.g., 7 Rosetta fixtures all export `Entry`), the resolver picks the **first non-barrel external match** — typically from a different language or a completely unrelated area of the codebase.

### Quantified Impact (from audit)

| Category                                                 | Bug Source                                              | Count                  | Example                                                                |
| -------------------------------------------------------- | ------------------------------------------------------- | ---------------------- | ---------------------------------------------------------------------- |
| `extends`/`implements` edges (detectInheritance)         | Regex on raw file content → global `createTypeResolver` | **4** of 5 are phantom | `models.ts → types.rs` (Entry), `java.typeref.test.ts → Repository.cs` |
| `dependency` edges (generator type-ref via liveDocGraph) | `resolveTypeToLiveDoc` → global `WorkspaceSymbolIndex`  | **5** cross-language   | `models.ts → Entry.java`, `processor.ts → ProcessorConfig.java`        |
| `type-reference` edges (explorer builder)                | Same global symbolIndex                                 | **2** cross-language   | `processor.ts → ProcessorConfig.java`                                  |
| **Generated Live Doc links** (Public Symbols section)    | `resolveTypeToLiveDoc` in rendering.ts                  | **5** cross-language   | TS `Record` extends `[Entry](../../../java/.../Entry.java.mdmd.md)`    |
| **Total phantom edges/links**                            |                                                         | **16**                 |                                                                        |

Only **1** of 5 `extends`/`implements` edges is legitimate (`LocalViewController implements LocalViewApi`).

### Root Causes (Two Distinct Bugs)

**Bug 1: `detectInheritance()` in graph.ts**

- Reads raw source file content and applies `class X extends Y` / `implements Y` regexes
- Matches inside template literal strings, test assertion strings, comments
- Feeds matches into `createTypeResolver()` which resolves globally
- This function is **almost entirely redundant**: the only legitimate edge it produces (`LocalViewController implements LocalViewApi`) is already present as a `dependency` edge from the parsed Live Doc metadata. The parsed metadata path in liveDocGraph.ts already handles type references via `symbolDocumentation.typeReferences` (liveDocGraph.ts).
- **However**, the parsed path creates `dependency`-kind edges, while `detectInheritance` creates `extends`/`implements`-kind edges that get distinct styling (pink/gold) in the Force Graph and Local Map. So removing it would lose the color distinction unless the edge kind is preserved through the parsed path.

**Bug 2: `resolveTypeToLiveDoc()` in rendering.ts**

- Uses `WorkspaceSymbolIndex` keyed purely by symbol name
- When `Entry` is exported by 7 different Rosetta fixtures, prefers the "first external non-barrel sorted by origin preference" — which is nondeterministic across languages
- This contaminates the **generated Live Doc markdown** itself (the `- Extends: [Entry](../../../java/...)` links), which then propagates into liveDocGraph.ts → graph edges → Explorer visualization
- The contaminated Live Docs are committed to the repo, so the damage persists across regeneration cycles unless fixed

### Proposed Fix Strategy

**Phase 1 — Delete `detectInheritance()` (~100 lines)**

The function is almost entirely phantom-producing. The parsed metadata path already handles legitimate cases. To preserve `extends`/`implements` edge styling:

- Modify liveDocGraph.ts to tag type-ref edges with their role (`extends`/`implements`/`type-reference`) in `rawDependencies`
- Modify `buildExplorerGraph()` to use that role as the link kind instead of the blanket `"dependency"` kind
- This shifts inheritance edge detection from "regex against raw source" to "parsed Live Doc metadata" — deterministic and already proven correct for the `LocalViewController` case

**Phase 2 — Add proximity scoping to `resolveTypeToLiveDoc()`**

When multiple files export the same symbol, prefer the one closest to the current file in the directory tree. The heuristic:

1. **Same directory** — highest priority (e.g., TS `models.ts` → TS types.ts for `Entry`)
2. **Same fixture/package** — next (same Rosetta language or same npm package)
3. **Same top-level area** — next (both in packages or both in tests)
4. **Global fallback** — existing behavior (only if no closer match)

This fix applies to both the generator (rendering.ts) and the Explorer builder (`createTypeResolver()` in graph.ts), since both use the same global-lookup pattern.

**Phase 3 — Regenerate & validate**

- Run `npm run live-docs:generate` to fix the 5 contaminated Live Docs
- Run `npm run live-docs:visualize` to rebuild the Explorer data
- Re-run the phantom edge audit script to confirm 0 phantoms
- Run `safe:commit` to validate everything

### Risks & Unknowns

- **Edge case: intentional cross-package type references.** The proximity heuristic could suppress a legitimate cross-package extends/implements where a symbol name collides. However, the current global behavior is strictly worse — it produces wrong results for all 7 Rosetta colliders. A proximity heuristic would be correct for all known cases.
- **The liveDocGraph.ts type-ref path already computes edges correctly** for resolved type references (the TS models.ts → TS types.ts dependency edge exists). The bug is only in the _styling_ — those edges render as grey "dependency" lines rather than pink/gold "extends"/"implements" lines. Preserving the styling requires threading the role through the edge metadata.
- **Non-fixture cross-language collisions**: The audit found the only production-code phantoms come from java.typeref.test.ts reading inline strings. Once `detectInheritance` is removed, those vanish. The `resolveTypeToLiveDoc` proximity fix prevents the remaining generator-level phantoms.
