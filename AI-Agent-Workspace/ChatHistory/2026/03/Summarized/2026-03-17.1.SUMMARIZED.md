## Turn 19 — Extended design discussion on view unification

**User** (L2518–L2536): Raises a deeper question: _"I guess I wonder why the old circuit board, with its nested directories, couldn't have those nested directories... expand... Is there a reason we can't progressively zoom in?"_ Then the crucial challenge: _"If we're going in on the unified Node Card representation... it begs the follow-up question: Why are the circuit board and the local map separate? Once you're zoomed in to a single file, why can't one seamlessly switch to seeing the inbound/outbound dependencies?"_

**Copilot** (L2538–L2680): Produces a thorough three-option analysis:

**Option A — Accordion Treemap**: Clicked directory grows to fill ~75% viewport, siblings shrink to labeled strips. Pros: spatial anchoring without nesting depth problems. Cons: no cross-directory dependency visibility.

**Option B — Unified View Continuum ("Semantic Zoom")**: Circuit Board and Local Map merge into a single view with continuous zoom levels. Level 1: directory tiles, Level 2: file cards in expanded directory with cross-directory connections, Level 3: click a file and it CSS-transitions to the Local Map's 3-column layout. Pros: eliminates the artificial view boundary. Cons: highest effort, requires rethinking view management.

**Option C — Two-Zone Layout ("Practical Middle Ground")**: (1) Files as uniform cards in flow grid, (2) dimmed sibling bar for spatial anchoring, (3) directory-level connection lines showing aggregate dependency flow. Pros: achievable incrementally, each piece shippable independently. Cons: doesn't resolve the fundamental "two views for one concept" tension.

Recommends **Option C now with Option B as the long-term direction.** Each Option C piece is a stepping stone toward the continuum.

## Technical Outcomes

**Circuit Board Monolith Decomposition**: The 741-line `circuitView.ts` was decomposed into 9 files under `circuitView/`, following the pure-function decomposition pattern established by the Local Map refactoring (18 files). The decomposition separates pure logic (testable in vitest node environment) from DOM construction (verified via Playwright):

| File             | Lines | Pure            | Tests |
| ---------------- | ----- | --------------- | ----- |
| state.ts         | 106   | Yes             | 21    |
| aggregation.ts   | 169   | Yes             | 22    |
| squarify.ts      | 179   | Yes             | 11    |
| directoryTile.ts | 66    | No (DOM)        | —     |
| breadcrumb.ts    | 50    | No (DOM)        | —     |
| index.ts         | 804   | No (controller) | —     |

**Two-Zone Layout**: At each drill-down level, the Circuit Board renders two visually distinct zones:

- **Top zone**: Squarified directory tiles (variable size proportional to aggregate dependency weight). Each tile shows file count, symbol count, cross-boundary dep counts (out/in), and dominant archetype badge.
- **Bottom zone**: Uniform 220×120px file cards in a CSS `flex-wrap` grid. Cards use the existing `.node-card` visual language with archetype, symbol count, and test coverage badges.

Zone height is computed using proportional weight-based splitting: `dirWeight / (dirWeight + fileWeight)`, clamped to `[160px, layoutHeight - 160px]` so neither zone can be squeezed below a usable minimum.

**Dimmed Sibling Strips**: When a directory is expanded, its peer directories appear as thin clickable strips along the right edge, showing directory name and file count. Clicking a sibling swaps the expanded directory without navigating upward. The strips provide spatial anchoring — landmarks that persist during drill-down.

**Squarified Treemap Algorithm**: Implementation of the Bruls-Huizing-van Wijk 2000 algorithm for proportional tile layout within an arbitrary rectangle. Works by greedily laying out tiles in rows, choosing between horizontal and vertical row orientation to minimize aspect ratio deviation from 1:1. Tile areas are precisely proportional to their input weights. 11 tests verify area proportionality, non-overlapping, bounds containment, and aspect ratio quality.

**Breadcrumb Navigation**: Zero-dependency breadcrumb builder creates a nav bar showing the directory drill-down path (e.g., `Root › .mdmd › layer-4 › packages › shared › src`). Each segment is a clickable button that collapses the view back to that level. Breadcrumbs appear when any directory is expanded and disappear at the root level.

**Single-Child Chain Collapsing**: When a directory has exactly one child directory (and no loose files), the chain is collapsed into a single tile with a joined display name using `/` separator (e.g., `shared/src` instead of separate `shared` and `src` tiles). This prevents the common pattern of deep nesting (`.mdmd/layer-4/packages/scripts/src/live-docs/explorer/client/`) from producing 8 single-tile drill-down levels.

**expandAndScrollToNode Enhancement**: Rewired to build the full ancestor chain from a target node to the root by walking up the hierarchy tree. This ensures that omnisearch selection, initial-focus node loading, and programmatic navigation all correctly expand the directory chain to reveal the target node with proper breadcrumb state.
