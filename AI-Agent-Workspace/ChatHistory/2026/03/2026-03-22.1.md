## The Rendering Reality

| View              | Rendering Tech                                            | Zoom/Pan Mechanism                                      |
| ----------------- | --------------------------------------------------------- | ------------------------------------------------------- |
| **Circuit Board** | Pure DOM (`document.createElement`, absolute positioning) | CSS `transform: matrix(k,0,0,k,x,y)` on a container div |
| **Local Map**     | Pure DOM (same pattern)                                   | CSS `translate() scale()` on a viewport wrapper         |
| **Force Graph**   | WebGL via `ForceGraph3D` (Three.js)                       | Library-managed camera (actual `<canvas>`)              |

The "canvas" references you see in the code are just variable name comments — index.ts says `// Size the layout canvas` but it's sizing a `<div>`. There is no `<canvas>` element in either the Circuit Board or Local Map. The zoom/pan is all CSS transforms on absolutely-positioned `<div>` elements.

## The 4K Problem

Since it's DOM, this is solvable — but the current layout hardcodes pixel dimensions:

```typescript
const layoutWidth = Math.max(viewportRect.width * 1.5, 1200);
const layoutHeight = Math.max(viewportRect.height * 1.2, 800);
```

On 4K, `viewportRect` reports the CSS pixel dimensions (not physical pixels), so the content is the same logical size — but the 1.5× multiplier creates a "virtual canvas" larger than the viewport, triggering the need to zoom out. The pan/zoom transform then scales everything down, making the tiles tiny. The fix would be to use viewport-fitting sizing (1.0× instead of 1.5×, or dynamically fit to the viewport like the Force Graph's auto-fit) and let the user zoom _in_ optionally rather than starting zoomed-out.

## The Membrane Concept

What you're describing — parent directories as nested enveloping rectangles at increasing sizes, with the active directory as the "center" — is a well-studied visualization pattern called a **zoomable treemap**. The key distinction from what we built:

| Current Design                                          | Membrane Design                                                                       |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Sibling directories in a strip on the **right edge**    | Sibling directories rendered as **adjacent rectangles at the same nesting level**     |
| Parent directory visible only in **breadcrumbs** (text) | Parent directory visible as a **background rectangle** surrounding the active content |
| Grandparents invisible                                  | Each ancestor visible as a progressively larger, dimmer, nested frame                 |
| Drill-down **replaces** content                         | Drill-down **zooms into** one rectangle while others shrink                           |

Because this is all DOM, the membrane effect is actually quite natural to implement:

1. **Nested `<div>` elements** — each directory level is a container div with a border/background color. When you expand a child, that child's div grows (via CSS transition) to fill ~80% of the parent's space, while siblings shrink to thin labeled strips (still in the same parent container, not displaced to a separate strip zone).

2. **CSS transitions** — the expansion/collapse can animate smoothly because these are DOM elements, not canvas-drawn rectangles. `transition: width 300ms ease, height 300ms ease` on the tiles.

3. **Ancestor visibility** — the grandparent's border and label remain visible as the outermost "membrane". Each ancestor is a nesting layer. Rather than a breadcrumb bar telling you textually where you are, the **visual nesting itself** is the navigation context.

4. **The active directory is always consistent size** — since the active content fills ~80% of whatever parent contains it, and the viewport zooms to frame it, the content you're working with stays at a comfortable reading size regardless of depth.

This design would be a much more natural fit for the DOM-based rendering we already have, and it aligns beautifully with the UC-094 unified view continuum direction from our last session. The "membrane" metaphor is essentially Option B (semantic zoom) but with the specific visual language of nested containment rather than view-tab switching.

The big architectural question: the current implementation tears down and rebuilds the DOM on every drill-down (`circuitContainer.innerHTML = ""`). The membrane approach requires persistent DOM elements that resize — the parent containers must _survive_ the drill-down, only their children change. That's a meaningful architectural shift from "re-render everything" to "mutate existing layout," but it's the _right_ direction if we want smooth transitions and spatial context preservation.

## C#: Namespaces ≠ Directories

C# is the most dangerous language for this assumption. In C#:

- A namespace can span multiple directories: `namespace MyApp.Services` can appear in `src/Services/AuthService.cs`, `src/Helpers/ServiceHelper.cs`, and `src/Legacy/OldService.cs` — three different directories, one namespace.
- A single file can declare types in multiple namespaces (rare but legal):
  ```csharp
  namespace MyApp.Models { public class User { } }
  namespace MyApp.DTOs { public class UserDto { } }
  ```
- The `global using` directive (C# 10+) creates project-wide implicit imports — functionally a "barrel" that lives in one file but applies everywhere.
- `InternalsVisibleTo` exposes internal members to specific assemblies, creating a visibility boundary that doesn't correspond to any directory.

The critical pattern: C# developers commonly organize by namespace rather than directory, and the compiler doesn't care if they match. A `GlobalUsings.cs` file at the project root is literally a barrel file whose "contents" span the entire project.

## Java: Packages ≈ Directories (Mostly)

Java is safer but not immune:

- By convention, `com.example.services` maps to `com/example/services/`. The compiler enforces this for public classes. So Java barrel files (which aren't really a Java idiom) would map to directories.
- **But**: a `package-info.java` file provides package-level Javadoc and annotations. It's not a re-export mechanism, but it IS a "file that represents a directory" — conceptually similar to a barrel.
- Inner classes and static imports can create cross-package binding that doesn't follow the directory tree, but these don't create barrel-like re-export patterns.

## Go: Already Solved

Go packages ARE directories. `package services` must live in one directory. There's no multi-directory namespace. Go is the cleanest case for the membrane model.

## Python: `__init__.py` Is Exactly a Barrel

Python's `__init__.py` is the purest barrel file in any language. It IS the directory. When you `import mypackage`, Python runs `mypackage/__init__.py`. Re-exports in `__init__.py` are the directory's public API. Perfect membrane alignment.

**Exception**: Python namespace packages (PEP 420) allow a package to span multiple directories without an `__init__.py`. Rare in practice but legally possible.

## The Actual Risk Matrix

| Language      | Barrel ≈ Directory?               | Risk to Membrane Model                                 |
| ------------- | --------------------------------- | ------------------------------------------------------ |
| TypeScript/JS | Yes (index.ts)                    | Low — barrel convention is directory-scoped            |
| Python        | Yes (`__init__.py`)               | Low (namespace packages are rare)                      |
| Go            | N/A (package = directory)         | None                                                   |
| Rust          | Mostly (`mod.rs` / `lib.rs`)      | Low                                                    |
| C             | N/A (no module system)            | None                                                   |
| Java          | Weak signal (`package-info.java`) | Low — packages are directories                         |
| **C#**        | **No**                            | **High — namespaces freely span directories**          |
| PowerShell    | Weak (`*.psd1` module manifests)  | Medium — manifests list explicit exports from anywhere |

## What This Means for the Membrane Model

The membrane model works beautifully when **the unit of public API aligns with the unit of filesystem containment**. That's true for TS, Python, Go, Rust, and mostly Java. It breaks for C# specifically.

But here's the thing: **Live Documentation already uses directories, not namespaces, as its organizational axis.** Every Live Doc is generated per file, filed under its directory path in layer-4. The dependency graph is built from file-level imports, not namespace membership. The membrane treemap would inherit this same axis.

So the question becomes: is the membrane model _wrong_ for C#, or is it _revealing_ something about C# codebases?

I'd argue it's revealing. If a C# project uses `namespace MyApp.Services` in three different directories, the membrane view would show three directories with connections between them — making it visually obvious that these files are coupled but organizationally scattered. That's a useful architectural signal: "these files claim to be one logical unit but are physically separated." The Force Graph would cluster them together (because they're tightly connected); the membrane would show them apart (because they're in different directories). The disagreement between the two views is the insight.

The `GlobalUsings.cs` case is trickier — it's a project-root barrel whose "contents" span the whole project. But `GlobalUsings.cs` doesn't create import edges in the dependency graph. It's a compiler directive, not a dependency. Our tree-sitter and SCIP adapters would see `using System.Linq;` as a framework reference, not an edge to another project file. So it wouldn't appear as a barrel in the graph at all.

## Net Assessment

The barrel-as-membrane metaphor is safe across all languages we currently support. The C# namespace-spanning case is real but doesn't break the model — it becomes an architectural insight surfaced by the visual disagreement between organizational containment (membrane) and functional coupling (Force Graph). The one language where we'd need explicit design accommodation is if we ever support a language with true multi-directory modules as a first-class concept (like Python namespace packages or C# when used in the "namespace directories don't match" antipattern), and even then, the membrane view would simply show the honest organizational truth while the Force Graph shows the coupling truth.

1. Track brace depth during symbol extraction
2. Maintain a stack of enclosing type names
3. Emit symbols with qualified names: `EventBus`, `EventBus.Options`, `EventBus.EventArgs`
4. In the membrane view, pins render hierarchically under their parent type

## The Hierarchy Function Is the Only Moving Part

The membrane map needs exactly one thing to build its nesting structure: a function that maps each file to a position in a tree. Currently that function is:

```
pathToHierarchy("src/Helpers/ServiceHelper.cs") → ["src", "Helpers", "ServiceHelper.cs"]
```

A namespace-based mode swaps in a different function:

```
namespaceToHierarchy("App.Services") → ["App", "Services"]
```

Everything downstream — pins, connections, edge bundling, zoom, rendering — is identical. The membrane containers just represent different things.

## What Each Mode Shows

| Concern                                                         | Directory Membrane               | Namespace Membrane                                               |
| --------------------------------------------------------------- | -------------------------------- | ---------------------------------------------------------------- |
| Container meaning                                               | Physical filesystem location     | Logical type grouping                                            |
| `ServiceHelper.cs` (in `Helpers/`, ns `App.Services`)           | Inside `Helpers/` membrane       | Inside `App.Services` membrane, next to `AuthService.cs`         |
| Partial class peers (`User.cs` + `User.g.cs` in different dirs) | Cross-membrane connection        | Same membrane — immediately visible as peers                     |
| Barrel files                                                    | Membrane boundary                | **No barrel concept** — the namespace IS the visibility boundary |
| Nested classes (`EventBus.Options`)                             | Hierarchical pins on a file node | Same                                                             |
| Files with no namespace (rare orphans)                          | Normal positioning               | Fallback: root membrane or `(global)`                            |

The namespace mode doesn't just make C# "work" — it shows C# developers what they already mentally picture. When a C# developer thinks about `App.Services`, they think of a container with `AuthService`, `ServiceHelper`, and `OldAuthService` in it, regardless of which directories those files physically inhabit.

## The Three-Axis Model

With this toggle, the full visualization suite becomes:

| View                         | Axis                            | What It Reveals                                   |
| ---------------------------- | ------------------------------- | ------------------------------------------------- |
| **Membrane Map (directory)** | Organizational — filesystem     | "Where do files physically live?"                 |
| **Membrane Map (namespace)** | Logical — type system grouping  | "How does the developer mentally organize types?" |
| **Force Graph**              | Topological — coupling strength | "What's the emergent shape?"                      |

And critically: **disagreement between the directory and namespace membranes is the most interesting signal.** If `ServiceHelper.cs` clusters with `AuthService.cs` in namespace mode but sits in a different membrane in directory mode, that's a file whose physical location doesn't match its logical role. That's actionable information — either the file is misplaced, or the namespace is wrong.

| Language      | Namespace = Directory?          | Toggle Benefit |
| ------------- | ------------------------------- | -------------- |
| TypeScript/JS | Yes (module path = file path)   | None           |
| Python        | Yes (package = directory)       | None           |
| Go            | Yes (enforced)                  | None           |
| Java          | Yes (enforced for public types) | Marginal       |
| Rust          | Mostly (mod = directory)        | Marginal       |
| **C#**        | **No**                          | **High**       |

## Implementation Overview: The Delta from Here to Membrane Map

Here is the overview-level abstract plan for what implementing the Membrane Map entails. This is the "what would the next dev day(s) look like?" roadmap.

### What Exists Today

The Explorer client code is approximately **17,400 lines** across 57 TypeScript files, plus **3,300 lines** of CSS:

| Module                                      | Lines  | Files | Purpose                                                                                  |
| ------------------------------------------- | ------ | ----- | ---------------------------------------------------------------------------------------- |
| **Local Map** (`views/localView/`)          | ~8,950 | 24    | 3-column symbol-level exploration, multi-hop pathfinding, connection drawing, pan/zoom   |
| **Circuit Board** (`views/circuitView/`)    | ~2,190 | 9     | Squarified treemap, directory aggregation, breadcrumb navigation, progressive disclosure |
| **Force Graph** (`views/forceGraphView.ts`) | ~1,060 | 1     | 3D force-directed graph (ForceGraph3D), related doc overlay                              |
| **Shared infra** (rest of `client/`)        | ~5,170 | 23    | Entry point, pathfinding, persistence, detail panel, omnisearch, data loading, download  |

### What Changes

The Membrane Map is **not a from-scratch rewrite** — it's a **synthesis**. The Circuit Board already has a squarified treemap layout engine and directory aggregation. The Local Map already has symbol-level pin rendering, connection geometry, multi-hop pathfinding, and pan/zoom. The Membrane Map welds them together onto one spatial coordinate system.

#### Phase 1 — Membrane Layout Engine (LD-1200)

**The single biggest new piece of code.** Neither the Circuit Board's `squarify.ts` nor the Local Map's `layout-math.ts` currently produces nested, recursively-sized rectangles that persist across zoom levels.

- **Input**: The existing `buildHierarchy()` from `layoutUtils.ts` already builds a tree of directories → files. Membrane Map needs a recursive squarified layout that assigns stable coordinates to every directory and file at every nesting level.
- **Key constraint**: Coordinates must be stable — zooming in doesn't reflow sibling membranes. This is fundamentally different from the current Circuit Board which tears down and rebuilds DOM on navigation.
- **Reusable**: `squarify.ts` (178 lines) is a clean, tested, pure-function squarify algorithm. It can be called recursively on each membrane's child list. The algorithm itself doesn't change; the orchestration layer that calls it recursively is new.
- **Output**: A `MembraneTile[]` tree structure with absolute pixel coordinates, suitable for direct DOM element positioning.
- **Estimated scope**: ~300-500 lines of new layout code.

#### Phase 2 — Browse Mode (LD-1201, replaces Circuit Board)

**Moderate effort, mostly adaptation.**

- Renders the membrane layout as nested `<div>` elements with border/background styling.
- File cards render as simple tiles (name, line count, connection count badge) — reuses aggregation metrics from `aggregation.ts`.
- No connection drawing, no symbol pins.
- Needs the persistent DOM pattern (elements resize/reposition, never destroyed) unlike the current Circuit Board's `innerHTML = ""` teardown.
- **Navigation**: Click a directory membrane to zoom in (CSS transform, not DOM rebuild). Breadcrumbs update. This replaces the Circuit Board's "expanded directory" pattern.
- **Reusable**: `directoryTile.ts` rendering patterns, `breadcrumb.ts` navigation, `aggregation.ts` metrics computation, `circuit.css` tile styling.
- **Estimated scope**: ~400-600 lines (view controller + renderer).

#### Phase 3 — Explore Mode (LD-1202, replaces Local Map)

**Heaviest adaptation phase.** This is where the Local Map's symbol-level rendering reattaches to the membrane substrate.

- When a user clicks a file card in Browse mode, that card becomes the **focal node**: it expands to full Local Map detail (symbol pins with inbound/outbound anchors).
- Connected nodes (in other membranes) render at reduced detail — name plus relevant pins only.
- Connections route from focal pins through membrane boundaries, using the existing `connection-geometry.ts` Bézier math.
- **Key complexity**: Connection routing must "punch through" nested membrane borders. This is geometrically new — current connections are either within-column (Local Map) or non-existent (Circuit Board). SVG paths need waypoints at each membrane boundary crossing.
- **Reusable**: `card-factory.ts` (symbol card DOM), `column-factory.ts` (symbol listing), `symbol-highlight.ts` (hover effects), `connection-geometry.ts` (Bézier computation), `runtime.ts` (anchor registry), `pan-zoom.ts`.
- **New**: Membrane boundary connection routing, reduced-detail card renderer, zoom-level-aware detail switching.
- **Estimated scope**: ~600-900 lines (the bulk of the work).

#### Phase 4 — Compare & Path Modes (LD-1205, LD-1206)

**Lower risk — these extend Explore mode.**

- **Compare mode**: Two focal nodes simultaneously. Both expand to full detail, connections between them are highlighted. The existing multi-pin architecture from Local Map supports this; the new piece is highlighting cross-membrane connections between two arbitrary focal points.
- **Path mode**: The existing `pathfind.ts` (748 lines) and Local Map path rendering already solve this. The question is whether path mode renders on the membrane substrate or retains the column layout. The architecture doc flags this as an open question — likely starts with column layout (reuse existing code) and migrates to membrane rendering later.
- **Estimated scope**: ~200-400 lines for Compare; Path mode may initially be a thin wrapper around existing pathfinding + column rendering.

#### Phase 5 — Edge Bundling (LD-1204)

**Medium complexity, significant visual impact.**

- When N connections cross the same membrane boundary, collapse them into one thick edge with a count badge.
- Expanding the membrane endpoint reveals individual connections.
- This is new code (no existing analog), but the connection count is already computed by `aggregation.ts`.
- **Estimated scope**: ~200-300 lines.

#### Phase 6 — Barrel-as-Membrane (LD-1203)

**Moderate, requires adapter awareness.**

- Detect barrel files (`index.ts`, `__init__.py`, `mod.rs`) and render them as membrane-edge nodes rather than interior cards.
- Connections from outside the membrane terminate at the membrane border (barrel pin) rather than routing interior.
- The detection logic is straightforward (filename pattern matching against known barrel names per language).
- **Estimated scope**: ~150-250 lines.

#### Phase 7 — C# Namespace Mode (LD-1207) & Nested Types (LD-1208)

**Two adapter-level enhancements.**

- **Namespace mode**: Swap the hierarchy function from `pathToHierarchy()` to `namespaceToHierarchy()`. The namespace data is already extracted by `extractCSharpNamespace()` — this is wiring, not extraction.
- **Nested types**: Modify `extractSymbols()` in the C# adapter to track brace depth and emit qualified names like `EventBus.Options`. Approximately 50-100 lines of adapter change.
- **Estimated scope**: ~100-200 lines total across adapter and Membrane Map hierarchy wiring.

#### Phase 8 — Integration, Testing, Phase-Out (LD-1209–LD-1213)

- Persistent DOM instead of teardown/rebuild (LD-1209)
- Zoom/pan via CSS transforms on the membrane root (LD-1210) — largely reuses `pan-zoom.ts`
- Integration tests (LD-1211) — test matrix: Browse/Explore/Compare/Path × small/medium/large workspace fixtures
- Deprecation: remove Circuit Board and Local Map views from tab bar (LD-1212) — only after feature parity is proven
- Update all guides and references (LD-1213) — a repeat of the documentation sweep done today, but replacing "planned successor" with "now shipping"

### Why This Ordering

The zipper puts the **hardest algorithmic problems first** (recursive layout, connection routing through nested rectangles) where they're cheapest to debug (pure functions, fast test cycles, no DOM). By Rung 6, the entire data pipeline is proven and the remaining work is rendering — which is tedious but not algorithmically risky.

Compare to the phase-based plan: Phase 3 (Explore mode) was flagged as "the hardest day" because it combines layout + connection routing + DOM in one shot. The zipper separates those concerns — connection routing through membranes is solved at Rung 5 as a pure math problem, long before any DOM rendering begins at Rung 7.

### Mapping to Dev Days

| Dev Day | Rungs            | End State                                                                                                                                           |
| ------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A**   | 1–3              | Layout engine + hierarchy + detail levels — all tested, zero DOM. A solid foundation that can be explored via logged output or temp visualizations. |
| **B**   | 4–6              | Edge bundling + connection geometry + state management — the complete data pipeline is proven correct.                                              |
| **C**   | 7–8              | Browse + Explore rendering — the Membrane Map is visually functional for the first time.                                                            |
| **D**   | 9–10             | Compare + Path modes + integration wiring — feature-complete.                                                                                       |
| **E**   | Phase-out + docs | Remove old views, update guides from "planned successor" to "now shipping."                                                                         |

The naming question (Browse/Explore/Compare/Path) can marinate through Dev Days A–B since those rungs don't touch user-facing labels — they're pure data types. By the time Rung 7 needs to render a mode picker, the names will have had time to settle.

### Structural Observations

**1. The "promoted" modules are a preparatory refactor, not a rewrite.**

Six modules move from `localView/` and one from `circuitView/` up to the `views/` level. All six are already clean, tested, and loosely coupled. The promotions are mechanical: move file, update import paths. During coexistence (before phase-out), both the old views and the new membrane view import from these promoted locations. TypeScript catches any broken imports at compile time. This refactor can and should happen as a standalone commit _before_ any Membrane Map code is written — it's low-risk and reduces future churn.

**2. `column-factory.ts` and `layout-math.ts` are _not_ promoted — they're obsolete.**

The column concept (Dependencies | Center | Dependents) is the fundamental abstraction that dissolves. The Membrane Map doesn't have columns; it has nested membranes with cards positioned by the layout engine. The column factory's _card-rendering_ logic is reusable (promoted as `card-factory.ts`), but the _column-assembly_ logic (`computeColumnCount`, `generateColumnLabel`, `computeGridTemplate`) has no Membrane Map equivalent. Same for `layout-math.ts` — its 508 lines of column counting and grid template math are specific to the 3-column/N-column paradigm. The recursive squarify layout replaces all of this.

**3. `subgraph-builder.ts` dissolves into the controller.**

The current subgraph builder constructs a `LocalSubgraph` — a flat list of nodes visible in the 3-column neighborhood. The Membrane Map doesn't partition nodes into subgraphs; the _entire_ membrane layout is always present, with detail levels controlling what renders. The neighbor-discovery logic (which nodes connect to the focal node?) is still needed but becomes a small function inside the controller or detail-levels module, not a standalone 233-line module.

**4. One thing in the existing structure that's mildly frustrating: layoutUtils.ts**

This file at views/layoutUtils.ts is a grab-bag — it builds the directory hierarchy tree, defines layout constants, runs the old flow-layout algorithm, _and_ exports types like `LayoutRect` and `DirectoryLayoutPlan`. The Membrane Map needs `buildHierarchy()` and `LayoutRect` but nothing else from it. During the Membrane Map work, I'd slim this file to just the hierarchy builder + shared types, extracting the Circuit Board–specific flow layout code into `circuitView/` (where it's only used). After phase-out, layoutUtils.ts becomes a thin hierarchy-building utility — which is all it should have been.

**5. types.ts at the client root needs a small update.**

The `ViewName` type currently reads `"circuit" | "map" | "graph" | "sources"`. The end state is `"membrane" | "graph" | "sources"`. During coexistence it'd temporarily be `"circuit" | "map" | "membrane" | "graph" | "sources"`. The `LocalMapTuning` interface inside `TuningConfig` would evolve into a `MembraneTuning` interface (same column-gap and hover-dim concepts, plus membrane-specific knobs like edge-bundling threshold).

**6. No changes outside `explorer/client/`.**

The server-side shared code (`explorer/shared/`), the build pipeline (visualize-static.ts), and the inspect CLI are all unaffected. The graph data model (`ExplorerGraphPayload`, `ExplorerNodePayload`, `ExplorerLinkPayload`) doesn't change — the Membrane Map is a new rendering layer over the same data.
