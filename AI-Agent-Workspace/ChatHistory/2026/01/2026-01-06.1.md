### How Thin Can the Extension Be?

The question cuts to the heart of the architecture:

| Capability | Where it lives today | Could be CLI-only? |

| Acknowledgement workflow | VS Code commands | ⚠️ Requires extension host |
| CodeLens annotations | Language server | ⚠️ Requires extension host |

**The extension's unique value** is providing *editor-time* feedback: diagnostics in the Problems panel, CodeLens overlays, quick fixes. But if the workflow is "run CLI, commit Live Docs, review in PR" (as it increasingly is), **the extension becomes optional**.

The thinnest possible extension would:
1. Expose a `live-docs:regenerate` command that shells out to the CLI
2. Expose a `live-docs:visualize` command that opens the browser
3. Provide diagnostic passthrough from the language server (for teams that want it)

The language server's main role becomes **hot-reload generation** during development — but even that could be a watch-mode CLI.

| `localOllamaBridge` | Ollama integration | **Keep** — needed for local LLM |
| `symbolBridge` | Server ↔ extension symbol communication | **Keep** — core to extension functioning |

### Thin Extension Proposal

The **thinnest viable extension** would:

1. **Register a language client** — connect to the language server
2. **Expose 3 commands**:
   - `liveDocumentation.regenerate` — shells out to `npm run live-docs:generate`
   - `liveDocumentation.visualize` — opens browser to `npm run live-docs:visualize`
   - `liveDocumentation.inspect` — runs `live-docs inspect` on current file
3. **Forward diagnostics** — pass-through from language server to Problems panel
4. **Provide CodeLens** (optional) — show Live Doc links inline

The language server would remain as the **hot-reload generation engine** during development, with the extension as a thin adapter.

## Question 2: Graph Edge Enrichment — Operational Concerns

You've identified the three-body problem of LLM-enriched graphs:

| Concern | Current State | Proposed Solution |
|---------|---------------|-------------------|
| **Retain useful** | Confidence calibration exists | Keep edges with `confidence >= threshold` |
| **Stop runaway spend** | No limits | **Rate limit + budget cap + explicit invocation** |
| **Prevent stale accumulation** | Provenance timestamps exist | **Source-based invalidation + TTL** |

### Proposed Model: Edge Lifecycle

```
┌─────────────────────────────────────────────────────────────────┐
│                        EDGE LIFECYCLE                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. CREATION                                                    │
│     - Deterministic analyzer finds edge → confidence: 1.0       │
│     - LLM extraction finds edge → confidence: 0.0-1.0          │
│     - All edges get: sourceHash, generatedAt, generatorId       │
│                                                                 │
│  2. VALIDATION                                                  │
│     - Confidence calibration (multi-sampling rejection)         │
│     - Corroboration bonus (multiple sources agree)              │
│     - Persist only if: calibratedConfidence >= threshold        │
│                                                                 │
│  3. INVALIDATION                                                │
│     - Source file changes → edges FROM that file marked stale   │
│     - Target file deleted → edges TO that file removed          │
│     - TTL expires → edge marked for re-validation               │
│                                                                 │
│  4. REGENERATION                                                │
│     - On next `live-docs:generate`:                             │
│       - Deterministic edges: always recomputed                  │
│       - LLM edges: recomputed ONLY if explicitly requested      │
│       - Stale edges: removed if not reconfirmed                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### Spend Controls

| Control | Implementation |
|---------|----------------|
| **Explicit invocation** | `--enrich` flag required; never automatic |
| **File-scope limit** | `--enrich --file <path>` enriches only one file |
| **Budget cap** | `live-docs.enrichBudget` setting (tokens/day or calls/day) |
| **Rate limit** | Minimum interval between enrichment runs |
| **Dry-run** | `--enrich --dry-run` shows what would be enriched without calling LLM |

### Stale Edge Prevention

| Trigger | Action |
|---------|--------|
| Source file changes (git diff) | Mark edges from that file as `stale: true` |
| Target file deleted | Remove edges pointing to it |
| Edge age > TTL (configurable, default 30 days) | Mark as `stale: true` |
| On `live-docs:generate` | Recompute deterministic edges; remove unconfirmed stale edges |
| On `live-docs:enrich` | Recompute LLM edges for stale sources only (unless `--full`) |

This means LLM enrichment is:
1. **Additive** on first run (discovers new edges)
2. **Surgical** on subsequent runs (only reprocesses changed files)
3. **Self-cleaning** (stale edges expire)

This is the question that separates "another documentation generator" from "documentation infrastructure."

### The Problem

A brownfield project has:
- README.md — Project overview
- `CONTRIBUTING.md` — Contribution guidelines
- `docs/architecture.md` — System design
- `docs/api/` — API reference (maybe generated by typedoc/doxygen)

- .github — Issue templates, workflows

They install Live Documentation. What happens?

### Option 1: Parallel Universe (Current Implicit Behavior)

Live Docs exist in `.live-documentation/source/`. Existing docs are ignored. Two documentation systems coexist awkwardly.

**Problem**: Maintainers now have two places to look. Neither is complete.

### Option 2: Migration/Import (Disrespectful)

Live Documentation tries to ingest existing docs, convert them to Live Doc format, replace the originals.

**Problem**: Destroys work. Loses structure. Introduces errors. Users hate it.

### Option 3: Bridge (The Right Answer)

Live Documentation **respects** existing documentation as first-class citizens of the documentation graph.

#### How It Would Work

1. **Discovery**: Live Docs generator discovers existing `.md` files outside the Live Doc tree
2. **Classification**: Each discovered doc gets an archetype:
   - README.md → `archetype: readme`
   - `docs/architecture.md` → `archetype: guide`
   - `docs/api/*.md` → `archetype: reference`
   - User-configurable patterns in .live-docs.config.json
3. **Linking**: When Live Docs reference existing docs (e.g., `[See architecture](../../docs/architecture.md)`), those links are preserved and traversable
4. **Inclusion**: `live-docs:visualize` and static exports include existing docs:
   - They appear in the graph with their own nodes
   - They're navigable in the Explorer
   - They're bundled in static exports
5. **Minimal Transformation**: For inclusion, we:
   - Parse frontmatter if present
   - Extract headings for anchor generation
   - Preserve content verbatim
   - Generate a thin metadata wrapper (not a full Live Doc)
