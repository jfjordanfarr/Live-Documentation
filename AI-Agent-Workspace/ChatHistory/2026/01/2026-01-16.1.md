## Feasibility Analysis: Multi-File Test Structure

The Live Docs `Observed Evidence` section populates via two mechanisms:
1. **Name matching**: `processor.test.ts` automatically backs processor.ts
2. **Explicit `Targets` links**: Test Live Docs can declare which files they test

A multi-file test structure would exercise **mechanism 2** — the edge-based detection where `integration.test.ts` → processor.ts proves coverage even without name matching.

### Proposed Structure Per Language

| Test File | Tests What | Edges Created |
|-----------|-----------|---------------|
| `processor.test.*` | `run()`, `summarize()` | test → processor, test → models |
| `models.test.*` | `createRecord()`, `validateConfig()` | test → models, test → types |

| Test File | Tests What | Edges Created |

| `processor.test.*` | Unit tests for processor | test → processor, test → models, test → types |
| `models.test.*` | Unit tests for models/helpers | test → models, test → helpers, test → types |
| `pipeline.test.*` | Integration test (no name match!) | test → processor, test → models |

**Total: 3 test files × 8 languages = 24 test files**

This structure:
- ✅ Has name-matched unit tests (`processor.test.ts` → processor.ts)
- ✅ Has non-name-matched integration test (`pipeline.test.ts` → processor.ts)
- ✅ Exercises edge-based test detection
- ✅ Covers all 5 implementation files via edges
- ✅ Keeps `helpers` and `types` tested indirectly (through models test)

## Oracle vs Heuristic/Adapter: Architecture Clarification

You're absolutely right that the terminology has become muddied. Here's the **de facto** situation:

### Original Intent

| Concept | Original Purpose | Key Characteristic |
|---------|-----------------|-------------------|
| **Oracle** | Compiler-backed ground truth | Uses real language tooling (TypeScript Compiler API, Python AST, etc.) to extract **authoritative** dependency edges |
| **Adapter** | Live Docs symbol/dependency extraction | Regex/heuristic-based extraction for **production use** during Live Doc generation |
| **Heuristic** | Fallback graph inference | Generic pattern matching for **benchmarking** when oracles aren't available |

### Current Reality

**Only TypeScript's oracle is truly compiler-backed** — it uses `import ts from "typescript"` and calls the TypeScript Compiler API (`ts.createProgram()`, `ts.resolveModuleName()`, etc.).

**All other "oracles" are actually sophisticated regex parsers:**
- **Java Oracle**: Regex on `import` statements + same-package reference patterns
- **Python Oracle**: Python AST via subprocess, but still essentially static analysis
- **C Oracle**: Regex on `#include` and function call patterns
- **Rust Oracle**: Regex on `use` and `mod` statements
- **Ruby Oracle**: Regex on `require` and `require_relative`
- **Go Oracle**: Regex on `import` blocks

### Why This Happened

From the 2025-12-16 chat history:

> *"The project adopted a Dual-mode accuracy validation strategy (AST comparison and self-similarity). This required building language-specific Polyglot Fixture Oracles (TypeScript, Python, C, Rust, Java, Ruby, C#)."*
>
> *"These oracles operate as the authoritative 'Golden Master' by extracting ground-truth dependency lists (expected.json) directly from compiler APIs **or reliable static parsers**."*

The key is **"or reliable static parsers"** — the oracles for non-TypeScript languages were built using regex-based static analysis because:
1. Integrating full compilers for 7+ languages is impractical
2. For well-structured fixtures with idiomatic code, regex can achieve near-perfect accuracy
3. The fixtures are curated specifically to be parseable by these patterns

### The Three Layers Now

| Layer | Files | Purpose | Method |
|-------|-------|---------|--------|
| **Oracles** | `packages/shared/src/testing/fixtureOracles/*.ts` | Generate expected.json (ground truth) | Language-specific regex (except TS which uses compiler) |
| **Adapters** | `packages/shared/src/live-docs/adapters/*.ts` | Extract symbols + dependencies for Live Docs | Language-specific regex |
| **Heuristics** | `packages/shared/src/inference/heuristics/*.ts` | Generate inferred.json for benchmark comparison | Language-specific regex (fallback inference) |

### The Muddy Part

**Oracles and Heuristics now do essentially the same thing** — regex-based extraction. The difference is:
- **Oracles** are "trusted" and write to expected.json
- **Heuristics** are "tested" and write to inferred.json

The benchmark measures: *How well do our heuristics match what the oracles would produce?*

For TypeScript, this is meaningful because the oracle has compiler-level precision. For other languages, it's essentially testing whether two regex implementations agree — which is less valuable.

### Should We Rename/Refactor?

Given this analysis, the "oracle" naming is somewhat aspirational for non-TypeScript languages. Options:

1. **Accept the terminology** — Oracles are "ground truth generators" even if they're regex-based
2. **Rename to "reference extractors"** — More accurate but breaks existing documentation
3. **Add real compiler oracles** — Use rust-analyzer, gopls, java LSP etc. (significant effort)
