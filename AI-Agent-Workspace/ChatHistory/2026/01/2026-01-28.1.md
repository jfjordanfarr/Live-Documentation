## Language Adapter Contract Analysis

Based on studying the C# and TypeScript adapters as "gold standards" (Newtonsoft.Json: **99.3%/99.3%**, OkHttp: **96.7%/96.0%**), here's what successful language adapters must do:

interface LanguageAdapter {

  }): Promise<SourceAnalysisResult | null>;

  symbols: PublicSymbolEntry[];     // What this file EXPORTS
  dependencies: DependencyEntry[];   // What this file IMPORTS
}

### The Three Key Detection Patterns Missing from Go

**1. Symbol→File Resolution (Critical for Recall)**

C# does this in csharp.dependencies.ts:
```typescript
// Resolves "MyNamespace.MyClass" to the file defining it
const pattern = `**/${simpleName}.cs`;
const matches = await glob(pattern, { cwd: workspaceRoot });
for (const candidate of matches) {
  const content = await readFileSafe(candidate);
  if (content.includes(`namespace ${namespacePrefix}`)) {
    return { specifier: relative, resolvedPath: relative, ... };
  }
}
```

Go equivalent would be:
- For `mux.Router` reference → Find file exporting `Router` in `github.com/gorilla/mux`

**2. Test→Implementation Detection**

- We skip `_test.go` files entirely: `if (absolutePath.endsWith("_test.go")) return null;`

**3. Same-Package Symbol References**

Go files in the same directory share a package namespace. When `bench_test.go` uses `NewRouter()`, it's a same-package call that should create an edge. We have no detection for this.

### Proposed Go Adapter Enhancements

1. **Don't skip test files** — Process them to detect test→impl dependencies
2. **Build package→files index** — Map each package directory to its constituent `.go` files
3. **Detect same-package symbol usage** — If file A calls `FunctionB()` and file B exports `FunctionB`, create edge A→B
4. **Use the SCIP pattern** — Build a symbol→defining-file map, then for each symbol reference, resolve to target

## The Visibility Model Mismatch

Our Live Documentation tooling is built around two core concepts:
1. **File-to-file relationships** — the primary, always-available unit
2. **Public Symbols** — the "interface" a file exposes that others can depend on

This model works beautifully for languages with **explicit module boundaries**:

| Language | Module Unit | Visibility Marker | File:Namespace |
|----------|-------------|-------------------|----------------|
| TypeScript | File | `export` keyword | 1:1 |
| C# | File/Type | `public`/`internal` | 1:1 |
| Java | File/Type | `public`/`package` | 1:1 |
| Rust | File/Crate | `pub` keyword | 1:1 |

But then we hit **package-scoped languages**:

| Language | Module Unit | Visibility Marker | File:Namespace |
|----------|-------------|-------------------|----------------|
| **Go** | Directory (package) | Capital letter | **N:1** |
| **Ruby** | Loose/global | None (by convention) | **N:global** |
| **Python** | Directory (package) | `_` prefix convention | **N:1** |
| **C** | Translation unit | Header exposure | **complex** |

## What "Public" Really Means

### Go's Two-Layer Visibility

Go has **two distinct visibility concepts**:

1. **Package-external visibility**: Capitalized identifiers (`Router`, `NewRouter`)
   - These are what external packages can import
   - Clear, mechanical rule
   
2. **Package-internal visibility**: Lowercase identifiers (`routeRegexp`, `newRequest`)
   - Visible to ALL files in the same directory/package
   - Invisible outside the package
   - **Not imports** — they're shared namespace

The problem: When `mux.go` uses `routeRegexp` from `regexp.go`, there's no import statement. They just... share a namespace. From a Live Documentation perspective, this IS a dependency, but it's **not mediated by a public symbol**.

### Ruby's Even Looser Model

Ruby essentially has:
1. **Method-level visibility**: `private`, `protected` (not relevant to our file-level analysis)
2. **Constant/Class visibility**: Effectively global unless namespaced by convention
3. **`require` relationships**: Pulls in entire files, not specific symbols

## Why C# Heuristic Works So Well

The C# heuristic achieves **99.3% precision** on Newtonsoft.Json (1346 TP, 10 FP) because C# has something Go fundamentally lacks: **explicit namespace imports via `using` directives**.

Looking at heuristics/csharp.ts, the key function is `disambiguateCSharpType()`:

```typescript
function disambiguateCSharpType(
  candidates: CSharpTypeDefinition[],
  namespaceName: string | null,
  usingNamespaces: Set<string>
): CSharpTypeDefinition | undefined {
  // 1. If only one type with this name exists → unambiguous
  if (candidates.length === 1) return candidates[0];
  
  // 2. Prefer types in the same namespace
  const sameNamespace = candidates.filter(c => c.namespaceName === namespaceName);
  if (sameNamespace.length === 1) return sameNamespace[0];
  
  // 3. Prefer types from imported namespaces (using directives)
  const importedMatches = candidates.filter(c => 
    usingNamespaces.has(c.namespaceName)
  );
  if (importedMatches.length === 1) return importedMatches[0];
}
```

This works because C# `using` statements are **import declarations** — they explicitly list which namespaces are in scope. The heuristic can match `SomeType` against `using Foo.Bar;` and know it refers to `Foo.Bar.SomeType`.

**Go lacks this mechanism entirely.** In Go, all files in a package share a namespace implicitly — there's no declaration of "I'm using symbols from `router.go`". The only explicit imports are for *other packages*, which live in separate directories.

### What Happened

On 2025-10-16, I wrote:
> "Tier 0: Tree-sitter/Native parsers (high confidence)"

But I immediately associated "tree-sitter" with the **native `node-tree-sitter` package**, which has C++ bindings. We had *just* experienced the pain of `better-sqlite3` native bindings — segfaults on Windows/Node 22, Electron ABI mismatches, the whole mess documented across 10/19, 10/22, 10/25, 10/26.

**The scarring from `better-sqlite3` made me gun-shy about *any* native bindings.** So tree-sitter stayed "aspirational" — mentioned 34 times in chat history, never implemented.

I genuinely did not know that:
1. https://www.npmjs.com/package/%40vscode/tree-sitter-wasm#%3A~%3Atext%3DFirst%2C%20build exists (Microsoft-maintained!)
2. It was already a year old when we started
3. It bundles **pre-built WASM grammars** — no native compilation, no ABI hell

| Concern | Reality |
|---------|---------|
| **Bundle size** | 22.1 MB for the full VS Code bundle. We'd only need ~2-5 MB for Go + Ruby grammars. |

### What Tree-sitter Gives Us

```
✅ Function/method declarations (with accurate start/end positions)
✅ Type/class/struct definitions
✅ Import/using statements (parsed, not resolved)
✅ Identifier usages (function calls, type references)
✅ Comment stripping (built into the AST — strings and comments are separate nodes)
✅ No regex false positives from "function" appearing in a string literal
```

### What Tree-sitter Does NOT Give Us

```
❌ Cross-file symbol resolution ("NewRouter in file A refers to definition in file B")
❌ Import path resolution ("import x from './foo'" → which actual file?)
❌ Type inference ("what type is this variable?")
❌ Namespace/module semantics
```

---

### The Real Question: Do We Need What Tree-sitter Doesn't Give?

**No.** Here's why:

Our current heuristics already do cross-file resolution via:
1. Build a symbol table: `{symbol name → defining file}`
2. Scan for symbol usages in other files
3. Match usages to definitions

The problem with our current approach is **step 1 and step 2 are unreliable** because regex can't distinguish:
- `NewRouter` in a comment vs. actual code
- `newRequest` as a local variable vs. a function call
- `func NewRouter()` vs. `// TODO: NewRouter should do X`

Tree-sitter makes **steps 1 and 2 trivially accurate**. Step 3 stays the same.

---

### The C# Question Specifically

You asked: *"Why not use tree-sitter for C# even when regex scores 99%?"*

**Because simpler is better.** Our C# heuristic is 326 lines of bespoke code that:
- Parses namespace declarations
- Extracts using directives
- Handles partial classes
- Disambiguates type names against namespaces

With tree-sitter, this becomes:
```typescript
const tree = parser.parse(source);
const types = tree.rootNode.descendantsOfType('class_declaration');
const usings = tree.rootNode.descendantsOfType('using_directive');
```

**50 lines, universal pattern, works for all languages.**

## Summary of Go Heuristic Fixes

### Problem 1: `localeCompare` sorting issue
**Root Cause**: The `resolveGoImportTargets` function used `localeCompare()` to sort files alphabetically before picking the first one. However, `localeCompare` is locale-dependent and in some locales, `_test.go` files sorted **before** regular `.go` files (underscore before period).

**Fix**: Created a `pickRepresentative()` helper that:
1. Filters to implementation files first (excluding `_test.go`)
