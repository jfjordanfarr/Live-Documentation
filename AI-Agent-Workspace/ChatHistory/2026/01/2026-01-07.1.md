GitHub Copilot: ## AI Boundary Analysis: Extension-Only vs. CLI-Available

### Option A: LLM Functionality Extension-Only

**Pros:**
- **Security posture**: NPM package can claim "no network calls, no LLM invocation, deterministic output" — powerful for enterprise adoption
- **Audit simplicity**: All LLM interactions flow through `vscode.lm`, which has its own consent/telemetry model
- **Liability containment**: If LLM generates bad code/advice, it's clearly in the "interactive IDE" context, not a CI pipeline
- **Dependency isolation**: No `ollama`/`openai` SDKs in `@live-documentation/shared`

**Cons:**
- CLI users can't get AI-enriched analysis without VS Code
- Duplicates effort if CLI eventually wants LLM features

### Option B: Move `localOllamaBridge` to Shared

**Pros:**
- **CLI parity**: `live-docs:inspect --enrich` could call local Ollama for semantic edge discovery
- **Headless automation**: CI could run LLM-assisted analysis (with explicit opt-in)
- **Single implementation**: One bridge, two consumers

**Cons:**
- **Security messaging complexity**: "The CLI is deterministic... unless you enable `--llm`"
- **Configuration sprawl**: Now CLI needs LLM provider config, API keys, etc.
- **Audit surface increases**: Every CLI invocation could potentially make network calls

### Recommendation

Given the vision docs emphasizing **"offline-first"**, **"no cloud dependencies"**, and the brownfield integration philosophy (**"bridge, don't replace"**), I'd recommend:

**Hybrid approach with clear boundaries:**
1. **Keep `localOllamaBridge` in extension** for now — preserves the "CLI = deterministic" guarantee
2. **Document the boundary explicitly** in Layer 3 architecture docs
3. **Defer CLI LLM** until there's a concrete user story that demands it (CAP-009 Task A: Graph Edge Enrichment is currently "explicit user invocation" which maps naturally to VS Code commands)
