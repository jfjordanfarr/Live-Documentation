## Architectural Assessment: Data Sharing Between Views

### Current Architecture

**Single source of truth**: `graphData: ExplorerGraphPayload`

```typescript
interface ExplorerGraphPayload {
  nodes: ExplorerNodePayload[];  // Live Docs (code-backed)
  links: ExplorerLinkPayload[];  // Dependency edges
  stats: ExplorerGraphStats;
}
```

**All four views consume the same `graphData`:**

| View | How it uses `graphData` |
|------|------------------------|
| **Force Graph** | Direct consumption — filters nodes/links per checkbox state, passes to ForceGraph3D |
| **Circuit Board** | Direct consumption — `graphData.nodes.filter(shouldRenderNode)` + builds directory tree |
| **Local Map** | Via `createLocalSubgraph()` — takes `graphData` + center node, builds neighbor subgraph |
| **Knowledge Sources** | Doesn't use graph data — shows bundled markdown tree separately |

**Key insight**: The architecture **already shares data correctly**. Each view receives the same `graphData` reference and applies its own filtering/transformation at render time.

### Why Related Docs Don't Belong in `graphData`

The `ExplorerNodePayload` type is designed for **Live Docs** (source-code-backed files):
- `codePath`, `codeRelativePath` — assumes a source file exists
- `docPath`, `docRelativePath` — assumes a Live Doc exists
- `archetype` — implementation/test/asset
- `dependencies`, `dependents` — code-level relationships
- `publicSymbols`, `symbolDocumentation` — code symbols

Related Documentation (bundled markdown) doesn't have:
- A backing source code file
- Public symbols or code dependencies
- A generated Live Doc

**Recommendation**: Keep `graphData` pure for Live Docs. Add a **parallel data structure** for related docs:

```typescript
// In startExplorer(), alongside graphData:
const relatedDocNodes: RelatedDocNode[] = buildRelatedDocNodes(bundledMarkdownPaths, bundledDocLinks);
const relatedDocLinks: RelatedDocLink[] = extractRelatedDocLinks(liveDocPaths, bundledMarkdown);

// Force Graph merges when checkbox is ON
function renderGraph(): void {
  const filteredNodes = graphData.nodes.filter(includeNode);
  const filteredLinks = graphData.links.filter(includeLink);
  
  if (state.filters.showRelatedDocs) {
    // Add related doc nodes with distinct type
    filteredNodes.push(...relatedDocNodes.map(toForceGraphNode));
    filteredLinks.push(...relatedDocLinks.map(toForceGraphLink));
  }
  
  forceGraphInstance.graphData({ nodes: filteredNodes, links: filteredLinks });
}
```

This approach:
- **Preserves type safety** — `ExplorerNodePayload` stays focused on Live Docs
- **Enables view-specific logic** — Circuit Board/Local Map ignore related docs (no code to show)
- **Aligns with strategic vision** — Force Graph is the "only viable venue" for brownfield docs

## Node ID Prefix: Pros & Cons

### Option A: Use `related:` prefix

**Pros:**
- ✅ **No ID collisions** — `related:README.md` vs `README.ts` are distinct
- ✅ **Easy type discrimination** — `if (id.startsWith("related:"))` is cheap
- ✅ **Self-documenting** — IDs clearly indicate node type

**Cons:**
- ⚠️ **Click handlers need prefix awareness** — When user clicks a markdown link in Detail Panel, we resolve the path to `related:path/to/file.md`
- ⚠️ **URL state needs adjustment** — If we put node ID in URL, it includes prefix

### Option B: Store related docs in separate map, use raw paths as IDs

**Pros:**
- ✅ **Simpler link interception** — `bundledMarkdown[path]` lookup works directly
- ✅ **No prefix stripping** — Paths are paths

**Cons:**
- ⚠️ **Possible collisions** — If a Live Doc has `id: "docs/README.md"` and we have bundled `docs/README.md`
- ⚠️ **Type discrimination requires map lookup** — `relatedDocNodesById.has(id)` vs `nodesById.has(id)`

### Recommendation: Option A with transparent handling

Use `related:` prefix for graph nodes, but hide this from user-facing code:

```typescript
const RELATED_PREFIX = "related:";

function toRelatedNodeId(path: string): string {
  return RELATED_PREFIX + path;
}

function fromRelatedNodeId(id: string): string | null {
  return id.startsWith(RELATED_PREFIX) ? id.slice(RELATED_PREFIX.length) : null;
}

function isRelatedDocId(id: string): boolean {
  return id.startsWith(RELATED_PREFIX);
}
```

**For link interception in Detail Panel**, the current `onBundledDocClick` callback already receives the raw path (not the node ID), so no change needed there.
