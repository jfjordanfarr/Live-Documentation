## Why Java Doesn't Have Symbol-to-Symbol Intelligence

### Root Cause

The Java adapter returns **`symbols: []`** (empty array) for all dependencies:

```typescript
// java.ts lines 248-253
.map((specifier) => ({
  specifier,
  resolvedPath: resolveJavaImport(specifier, sourceRoot, workspaceRoot),
  symbols: [],  // <-- ALWAYS EMPTY
  kind: "import"
}))
```

When the renderer encounters a dependency with no symbols, it falls back to a **whole-file link** (line 722-724 of rendering.ts):

```typescript
if (symbols.length === 0) {
  lines.push(`- [\`moduleLabel\`](${docRelative})`);
  continue;  // No anchor fragment = node-level pin to "Internals"
}
```

### TypeScript's Positive Control

TypeScript extracts actual symbol names from import statements:
```typescript
import { Reader, Writer } from './data/store';
// → symbols: ['Reader', 'Writer']
// → Links: store.ts.mdmd.md#symbol-reader, store.ts.mdmd.md#symbol-writer
```

### The Fix for Java

Java imports **do** contain extractable symbol information:
```java
import com.example.data.Reader;  // The class name IS the symbol
```

The class name `Reader` is the last segment of the fully-qualified import. We can extract it:

```typescript
// Fix: Extract class name as the imported symbol
const className = specifier.split('.').pop()!;
symbols: [className],  // → symbols: ['Reader']
```

This would enable:
- `App.java → Reader.java#symbol-reader` (symbol-to-symbol)
- Instead of `App.java → Reader.java` (node-to-node)

### The Fix for Rust

Rust is more nuanced:
- `mod math;` → imports the module itself → `symbols: ['math']` ✓
- `use crate::utils;` → imports the module → `symbols: ['utils']`
- `use crate::math::add;` → imports specific function → `symbols: ['add']`
- `use crate::math::{add, subtract};` → multiple imports → `symbols: ['add', 'subtract']`

## Proposed: Unified "Rosetta Stone" Program

### Program Shape: Data Report Pipeline

A minimal but meaningful program that exercises:
- **Entry point** that orchestrates the flow
- **Models** that define data structures
- **Processor** that transforms data (uses models)
- **Helpers** that provide utilities (used by processor)

```
┌─────────┐     ┌───────────┐     ┌─────────┐
│  main   │────▶│ processor │────▶│ helpers │
└────┬────┘     └─────┬─────┘     └─────────┘
     │                │
     ▼                ▼
┌─────────┐     ┌─────────┐
│ models  │◀────│         │
└─────────┘     └─────────┘
```

### Type-Safe Tier (Symbol-to-Symbol)

**Files:**
- `main.{ext}` - Entry point, imports `run()` from processor, `Report` from models
- `models.{ext}` - Defines `Record`, `Report` types
- `processor.{ext}` - `run()` function that uses `Record`, calls `format()` from helpers
- `helpers.{ext}` - `format()` and `validate()` utilities

**Expected Dependencies Graph:**
```
main ──[run]──▶ processor ──[format]──▶ helpers
  │                │
  └──[Report]──────┴──[Record]──▶ models
```

### Non-Type-Safe Tier (File-to-File)

Same structure but:
- No explicit type imports (just module imports)
- Symbol anchors only where language supports selective imports (Python `from X import Y`)

**Languages:**
- Python (can do symbol-level with `from X import Y`)
- Ruby (file-level `require_relative`)
- PowerShell (file-level dot-source)

test('all Rosetta variants produce equivalent dependency graphs', async () => {
  const manifest = loadRosettaManifest();
  
  for (const fixture of manifest.fixtures) {
    const graphs = await Promise.all(
      Object.entries(fixture.variants).map(async ([lang, path]) => ({
        lang,
        graph: await generateLiveDocGraph(path)
      }))
    );
    
    // All type-safe languages should have identical edge counts
    const typeSafe = graphs.filter(g => manifest.tiers['type-safe'].languages.includes(g.lang));
    const edgeCounts = typeSafe.map(g => g.graph.edges.length);
    expect(new Set(edgeCounts).size).toBe(1); // All same
    
    // Verify expected symbols appear in all type-safe variants
    for (const expected of fixture.expectedGraph.edges) {
      for (const { lang, graph } of typeSafe) {
        const edge = graph.edges.find(e => 
          e.from.includes(expected.from) && e.to.includes(expected.to)
        );
        expect(edge, `${lang}: missing ${expected.from}→${expected.to}`).toBeDefined();
      }
    }
  }
});

## Research Summary: Asset Connectivity Mechanism

### Current HTML/CSS Approach

The existing adapters use a **path-probing pattern**:

1. **Pattern extraction** - Regex extracts putative paths from attributes (`src`, `href`, `url()`)
2. **Path resolution** - `resolveResourcePath()` / `findDocumentRoot()` probe filesystem
3. **Dependency creation** - If file exists, create a `DependencyEntry` with `resolvedPath`

Key insight from html.ts:
```typescript
const { specifier, resolvedPath } = resolveResourcePath(rawPath, sourceDir, workspaceRoot);
if (seen.has(key)) return;
dependencies.push({
  specifier,
  resolvedPath,  // Only set if file actually exists
  symbols: [],
  kind: "import"
});
```

### How This Applies to JSON

For a `rosetta-manifest.json` adapter, we could:
1. Parse JSON and walk all string values
2. Check if string looks like a file path (contains `/`, ends with known extension)
3. Probe whether the path resolves to an existing file
4. Create dependencies for resolved paths
