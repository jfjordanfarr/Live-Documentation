## Why Java Doesn't Have Symbol-to-Symbol Intelligence

### Root Cause

The Java adapter returns **`symbols: []`** (empty array) for all dependencies:

```typescript
// java.ts lines 248-253
.map((specifier) => ({
  specifier,
  resolvedPath: resolveJavaImport(specifier, sourceRoot, workspaceRoot),
  symbols: [],  // <-- ALWAYS EMPTY
  kind: "import"
}))
```

When the renderer encounters a dependency with no symbols, it falls back to a **whole-file link** (line 722-724 of rendering.ts):

```typescript
if (symbols.length === 0) {
  lines.push(`- [\`moduleLabel\`](${docRelative})`);
  continue;  // No anchor fragment = node-level pin to "Internals"
}
```

### TypeScript's Positive Control

TypeScript extracts actual symbol names from import statements:
```typescript
import { Reader, Writer } from './data/store';
// → symbols: ['Reader', 'Writer']
// → Links: store.ts.mdmd.md#symbol-reader, store.ts.mdmd.md#symbol-writer
```

### The Fix for Java

Java imports **do** contain extractable symbol information:
```java
import com.example.data.Reader;  // The class name IS the symbol
```

The class name `Reader` is the last segment of the fully-qualified import. We can extract it:

```typescript
// Fix: Extract class name as the imported symbol
const className = specifier.split('.').pop()!;
symbols: [className],  // → symbols: ['Reader']
```

This would enable:
- `App.java → Reader.java#symbol-reader` (symbol-to-symbol)
- Instead of `App.java → Reader.java` (node-to-node)

### The Fix for Rust

Rust is more nuanced:
- `mod math;` → imports the module itself → `symbols: ['math']` ✓
- `use crate::utils;` → imports the module → `symbols: ['utils']`
- `use crate::math::add;` → imports specific function → `symbols: ['add']`
- `use crate::math::{add, subtract};` → multiple imports → `symbols: ['add', 'subtract']`
