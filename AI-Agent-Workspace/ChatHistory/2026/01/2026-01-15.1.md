### Commit 2: JSON Adapter

**Purpose**: Enable Live Docs for `.json` files to automatically detect and link to paths referenced within them.

**Design Philosophy**:

The JSON adapter differs from code adapters — it doesn't extract "public symbols" (JSON has no exports). Instead, it:
1. Extracts string values that look like file paths
2. Probes the filesystem to resolve them
3. Emits those as dependencies

This enables rosetta-manifest.json, fixtures.manifest.json, tsconfig.json, package.json to gain Live Doc connectivity.

**Implementation Strategy**:

```typescript
// packages/shared/src/live-docs/adapters/json.ts
export const jsonAdapter: LanguageAdapter = {
  id: "json-paths",
  extensions: [".json"],
  
  async analyze({ absolutePath, workspaceRoot }): Promise<SourceAnalysisResult | null> {
    const content = await fs.readFile(absolutePath, "utf8");
    let parsed: unknown;
    try {
      parsed = JSON.parse(content);
    } catch {
      return null; // Malformed JSON, skip
    }
    
    // Recursively walk JSON, collecting string values
    const candidates = extractPathCandidates(parsed);
    
    // Resolve each candidate relative to the JSON file's directory
    const dependencies = candidates
      .map(p => resolveJsonPath(p, absolutePath, workspaceRoot))
      .filter((d): d is DependencyEntry => d !== null);
    
    return { 
      symbols: [],     // JSON has no exported symbols
      dependencies 
    };
  }
};
```

**Path Detection Heuristics**:

| Pattern | Example | Resolution |
|---------|---------|------------|
| Relative path | `"./src/main.ts"` | Probe from JSON file's directory |
| Package-relative | `"src/main.ts"` | Probe from workspace root |
| URL | `"https://..."` | Skip (not local) |
| npm package | `"lodash"` | Skip (external) |
| Known keys | `"path"`, `"entry"`, `"file"` | Higher confidence |

**Architectural Improvement**:

Currently, JSON files get the `asset` archetype by default (per archetype.ts). The JSON adapter would populate their Dependencies section, making them first-class graph participants.

## 🚧 Decision Point: Go Package Structure

I've just created the Go Rosetta fixture, but I structured it with **Go's conventional package-per-directory** layout:

```
go/rosetta/
├── go.mod (module rosetta)
└── src/
    ├── main/main.go      (package main)
    ├── models/models.go  (package models)
    ├── processor/processor.go
    ├── helpers/helpers.go
    └── types/types.go
```

**The Problem**: This is different from other Rosetta fixtures (TypeScript, Rust, Python, etc.) which use **flat file structures**:

```
typescript/rosetta/
└── src/
    ├── main.ts
    ├── models.ts
    ├── processor.ts
    ├── helpers.ts
    └── types.ts
```

**Two Options**:

### Option A: Keep Go's Canonical Structure (Current)
- **Pro**: Follows Go's package conventions (each directory = one package)
- **Pro**: Go imports work correctly (`rosetta/src/models`)
- **Con**: Edge graph will have different paths (`src/main/main.go` vs main.ts)
- **Con**: Breaks "identical dependency graph shapes" validation rule from rosetta-manifest.json

### Option B: Flatten to Match Other Rosetta Fixtures
- Put all files in `src/` with naming like `types.go`, `models.go`, etc.
- Go doesn't naturally support this — all `.go` files in a directory must share the same `package` declaration
- Would require either:
  - All files declare `package rosetta` (non-idiomatic)
  - Or use `internal/` directory with relative imports (complex)

**My Recommendation**: **Option A** — Keep Go's canonical structure. 

Rationale:
1. The Rosetta Stone concept tests that our adapters **correctly handle each language's native import system**. Forcing Go into a non-idiomatic structure defeats that purpose.
2. The "identical graph shapes" rule in rosetta-manifest.json is about **node roles and edge relationships** (main→processor→models/helpers→types), not about matching file paths exactly.
3. The oracle and benchmark system already handle language-specific path differences.

**However**, this means:

## `fs.glob` Migration Attempt — December 2025

### What We Found
We tested Node 22's native `fs.glob` and `fs.globSync` APIs and discovered:

1. **They work** — both `fs.glob` (async) and `fs.globSync` exist in Node 22.14.0
2. **They're experimental** — the APIs emit `ExperimentalWarning` at runtime
3. **They could change** — experimental APIs aren't guaranteed to remain stable

### Decision
> Given our production/PCI-DSS security posture, using experimental APIs isn't appropriate.

We kept the `glob` package and instead accepted a Dependabot PR to update it from `^11.0.0` to `^11.0.2` for security patches.

### Current Status
The `fs.glob` API is still marked experimental in Node.js. According to the [Node.js documentation](https://nodejs.org/api/fs.html#fspromisesglobpattern-options), it was "Added in: v22.0.0" but remains experimental.

**Bottom line**: We should continue using the `glob` package until Node.js promotes `fs.glob` to stable. This is the correct security posture — we minimize dependencies where possible, but not at the cost of runtime stability.
