# Change over time: this repository's history in the structure layout

_A probe of October 16, 2026, by the root Claude Code agent (Fable 5.1), made for the owner's pick of that day ([Turn 2 of the day's record](../../../ChatHistory/2026/10/2026-10-16.1.record.md#turn-2)): "the rendering of change over time ... our \"declared layout\" (directory-oriented) 3D force graph will perform really nicely going snapshot by snapshot to show us the history of this repo", and their answers of [Turn 3](../../../ChatHistory/2026/10/2026-10-16.1.record.md#turn-3) to the ten questions the root put. The probe's page and its data are disposable and not committed; this record, its findings and its pictures are. Nothing in the product was changed for it. What the workspace had already said and what the field has done are in [the survey of the same day](../../../Research/2026-10-16-change-over-time.md); this record walks the scenarios on paper, as the World Map's plan did before its probes, and then looks._

## Brief

Regenerate a sample of this repository's commits with today's generator, one lens over every snapshot; derive one sequence of deltas from the graph indexes, with git's renames as the identity of a file across commits; build a disposable page over the Explorer's structure layout (the declared directory tree of hubs, 2026-10-14) with a scrubber along the bottom; feed the running simulation at each step rather than restart it; try the levers that keep the picture from wiggling; measure what a step costs in frames and what the sequence costs in memory; take pictures and a recording for the owner's eye. The probe is for the design doc that follows it, not a build of the feature.

What the owner decided before the probe (Turn 3): one generator over old snapshots ("The point is that Live Documentation, as it gets better and better, will be capable of producing a more and more accurate timeline reconstruction of its past"); renames by git's word ("Trust what git says"); the hubs as the skeleton, with the wiggle "to toy around with"; the simulation fed, not restarted; the headless twin and git as the oracle; a probe first, then the design doc in layer 3, then the build in gated commits. What they added: a timeline to scrub "along the bottom or something"; history machinery that "gets to work" once a view is created, finding a precomputed cache of the deltas or computing them for the first time, the timeline appearing when it is done or the processing shown as ongoing; and the question whether what is pinned could define a more useful temporal step than the commit, "only commits salient to the pinned items".

## The scenarios, walked on paper

Each names the situation, what the picture must do, what the sequence must carry for it, where it could go wrong, and whether this probe checks it or the design doc carries it.

1. **September 26 to 28 here.** Sixty-one commits in three days: the Copilot-era steering replaced by `AGENTS.md`, the inference path and the self-grading tools retired, `packages/server` renamed to `packages/generator`, five tree-sitter adapters landing one by one, the sample programs moved to `tests/integration/programs`, the grammar and the graph index, `packages/shared` renamed to `packages/engine` and `packages/scripts` to `packages/explorer`, the World Map. The picture must show three hubs sliding whole under new names, a hub of samples moving across the tree, hundreds of files dying in place in one step, and a run of births at one hub. The sequence must carry the renames git detects for the three package renames (7, 198 and 200 paths, measured on October 16) and the directory renames derived from them. It goes wrong if a hub's identity is its path: `directory:packages/shared` dies and `directory:packages/engine` is born, and two hundred files fly across the picture to a hub that starts at their centroid, which is where they already are, so the files hold still but the hub label changes; whether that reads as a rename to the eye is the question. The probe checks it: these commits are in the sample one by one.
2. **One file's life.** `forceGraphView.ts`: born under one package, renamed into another, growing symbols, its wires appearing and going. With the file pinned, the structure layout already draws its wires across steps, since references are drawn for retained files; the picture must show one sphere moving with its hub on the rename, growing, its wires changing, while the rest of the picture holds. The sequence must carry symbol counts per step and edge changes per step, and must let the page find the steps that touched one file, which is also what the owner's pinned-salient step needs. It goes wrong if a rename below git's similarity threshold is a death and a birth, which the picture must then show as such, honestly, rather than invent a slide. The probe checks it with one file pinned across the whole sample.
3. **A directory renamed whole.** `packages/shared` to `packages/engine`. A directory is renamed when, after the step, nothing is left under the old path and every surviving file of it stands under the new path at the same relative place; otherwise files slid individually and the hubs breathe. This is derived data the history command writes into the delta, not something the renderer infers, so that the CLI can say "renamed whole" in text too. It goes wrong on a split (half the files moved, half stayed), which must read as files leaving a hub that shrinks, and on a rename with a few deletions, which is still a rename of what survived. The probe checks the derivation against the three September renames, read by hand from git.
4. **A repository with ten thousand commits.** This repository changes a mean of 34 docs per commit that touches the mirror; a delta is a few kilobytes against a 439 KB snapshot. Ten thousand steps of ten kilobytes are a hundred megabytes of JSON, too much for a single file and too much to replay from the beginning on every seek, which is what Repo Visualizer does and what Gource avoids by rebuilding from a log offset. So the sequence needs keyframes, a whole snapshot every few hundred steps, with deltas between, and a seek is the nearest keyframe plus at most that many deltas; the page holds one snapshot's objects and the current chunk, never the whole history as objects. And the generation is hours of computation: the history command must run one process per commit (the V8 heap is capped at two or four gigabytes, and one process holding every snapshot would die), in a pool sized to the machine, resumable by a cache keyed by commit and lens, so that a second run computes only the new commits, which is also the owner's "precomputed cached shape of prior deltas". The probe measures this repository's numbers (bytes per step, time per commit, memory of the page) and the design doc scales them; the probe does not build keyframes.
5. **A repository without a committed mirror, such as TH04.** Under one lens the committed mirror is never read, so this is the ordinary case, not a special one: the command checks each commit out into a worktree, generates with today's rules and reads the index. What varies is the configuration: a repository without one gets the defaults, whose globs have been suffix-anywhere since 2026-10-15 and so read every layout the repository has had; this repository's own configuration is applied to every one of its commits for the same reason (a commit's own configuration would make a change of the tool look like a change of the code). The `.gitignore` is the commit's, so vendored trees ignored at that commit stay out. The probe applies today's configuration to every commit; the design doc states the rule.
6. **The 8 GB machine.** Two budgets. The page: one snapshot's spheres and labels (723 files and about a hundred hubs here) plus the sequence; this repository's whole history as deltas is a few megabytes, so the question is the renderer's own footprint, which the probe measures with the browser's heap size before and after loading and after fifty steps. The generator: one process per commit in a pool, and the pool's size bounded by memory, two on 8 GB; the probe's regeneration ran three at a time on the dev box and the design doc sets the rule. Neither budget wants localStorage, which is 5 MiB and synchronous; IndexedDB is the later home of a chunked sequence if a repository ever needs one, and never for state the docs must carry.
7. **The single file.** The Explorer's one-file export inlines everything, and a `file://` page cannot fetch its siblings, so the sequence is inlined or absent. For this repository a few megabytes inline is fine; for ten thousand commits it is not, and the single file must say what it carries: the whole sequence under a size the build sets, otherwise the latest window of steps with a line saying the rest needs the served bundle. The probe measures the bytes; the fork (window or nothing) is the design doc's and the owner's.
8. **A shallow clone.** `git rev-parse --is-shallow-repository` says so; the oldest commit available is a graft with no parent, and its "first step" would show every file born at once, which is an artifact of the clone and not of the code. The sequence must say where its knowledge begins and why, the scrubber's left edge must be marked as truncated, and the first snapshot is drawn as the beginning of what is known, not as a birth. The command reads history through the `git` executable (log, diff with rename detection, worktree), not by parsing `.git/` itself, since a `.git` can be a file pointing elsewhere in a worktree or a submodule and the executable knows every shape; the owner's "look in a `.git/`" is served, and no network is touched. The design doc carries it; the probe does not try a shallow clone.
9. **A link to a moment.** The address already carries the view, the perspective, the layout, the pins and the tuning; it gains the commit. Opening it loads the sequence, seeks to the commit (keyframe plus deltas) and draws that snapshot. A pin that does not exist at that commit is said so in the tray ("not yet born" or "already gone") and never dropped silently. The probe's page puts the step in its address so that a picture can be re-taken; the rest is the design doc's.
10. **The pinned-salient step (the owner's).** With a pin set, the scrubber's ticks are the steps whose delta touches a pinned file, a file under a pinned directory, or an edge of one; stepping by key moves to the next salient step with the quiet steps applied silently as a seek; the quiet ticks stay faint under the salient ones so the whole history stays in view. This is `git log -- <path>` on the graph, and it is cheap because the deltas are per step and keyed by file: the command writes, for each file, the steps that touched it, which scenario 2 needs as well. The probe tries it with one file pinned and reports how many of the sampled steps are salient to it.
11. **Where the computation happens, and when the timeline appears (the owner's).** The Explorer is a rendering of the docs and runs as a static page, which cannot read a repository's history; the computation is the generator's, through a history command, and the Explorer finds what the command produced and says so when nothing has. The one host where a view could start the computation is the VS Code panel the decisions log expects to return, which can run the command, show the commits done against the total, and reveal the timeline when the sequence is complete; the served bundle shows the timeline when it carries a sequence and otherwise one line saying how to compute it. The cache keyed by commit and lens makes the second run cheap, which is the owner's "locate the precomputed cached shape of prior deltas or computing them itself for the first time". The probe does not build this; the design doc puts it to the owner with this mapping, since it changes where their picture lives.
12. **The wiggle (the owner's).** Today a membership change reheats the simulation to full energy and every sphere stirs. The levers: a gentle reheat (a low alpha target rather than one), the hubs held fixed during a step and released after, a born file placed at its hub plus a small offset so that it does not erupt from the hub's centre, the velocity decay, and no simulation at all (pure placement at the hub, the forces left asleep). The probe tries three settings, today's full reheat, the gentle reheat with hubs held, and pure placement, and measures the mean and the greatest displacement of the spheres that did not change in the step, the frames a step takes to settle, and the frame rate while it does.
13. **The lens, named.** The owner's point about accuracy means a sequence must say which generator made it, so that a reader knows a shape is the tool's reading of that day; the cache is keyed by it and a new lens recomputes. The probe's sequence carries the generator's commit; the design doc makes it a rule.
14. **Time and sequence.** History is a graph, not a line. The mainline of the current branch (first parent) is the sequence; a merge is one step whose delta is the whole merge, its inner commits named on the step and not drawn one by one. The scrubber lays steps out by index, evenly, or by time, where the quiet stretches show as gaps and Gource's seconds-per-day applies; the owner's answer did not object to quiet stretches skipped. This repository's history is linear, so the probe lays its steps out by index and shows the date on each; the design doc carries merges.

## Method

1. **The sample.** 122 of this repository's 566 commits (`f7a75fa7`, 2025-10-16, to `6bcaa6bb`, 2026-10-16): every eighth commit across the whole history, every commit of September 26 to 28 (UTC) one by one, the first and the last. Each was checked out into a detached worktree and regenerated with the generator at `6bcaa6bb` and this repository's own `.live-docs.config.json`, into a fresh docs root, three worktrees at a time; the worktree's `index.json` was kept and the worktree removed. The timings are in the findings.
2. **The sequence.** A script of the probe's reads the indexes oldest to newest, interns every file path once, writes the first snapshot in full (files with symbol counts and archetypes; undirected file pairs with reference counts) and then one delta per step: files added, removed and renamed (git's `diff --name-status -M50%` between the two sampled commits, kept where both ends are in the snapshots), symbol counts changed, pairs added, removed and changed. The lens (the generator's commit) is written at the top.
3. **The page.** Disposable, built by a builder subagent from the Explorer's own pure modules (`spatialGraphOf` for the hubs and the containment links, `configureSpatialForces`, `spatialNodeRadius`) and the same 3D force library, with a scrubber along the bottom, play and pause, step by key, the commit's date and subject, a "what changed" list beside the picture, one pinned file whose wires are drawn, the three continuity settings of scenario 12, and the measurements of scenarios 4, 6 and 12 written to the console and gathered by a driver.
4. **The pictures and the recording.** Taken headlessly with Playwright at chosen steps (the first commit with code, the eve of September 27, the three package renames, the sample move, today), and a recording of the whole sample at one step per second; what the eye sees in motion is the evidence for continuity, as the Explorer rules say.

## What it found

The builder (a subagent on Opus 5.5 at high effort) first replayed every delta from the base and compared each step with the commit's own `index.json`: all 122 snapshots match on files, symbol counts, archetypes and pair counts, the last being 723 files and 1,676 pairs. The pinned file first exists at sampled step 32 (`8c2b5fc8`, 2026-02-23; its birth commit `0e8f034f` is not in the sample) and exists for 90 of the 121 steps. The container has no GPU, so Chromium rendered through SwiftShader at 42 to 85 ms a frame; the library ticks once per frame, so a measuring window of wall-clock seconds would have given each setting a different amount of simulation. The window therefore ends when the engine stops, at 180 ticks (three seconds at 60 frames a second), or at 15 s of wall clock, and settle is reported in ticks and in this machine's milliseconds. "Still" means no sphere moved more than 0.1 units in a tick. The heap is read with precise memory information and a forced garbage collection before each reading.

**The three settings as built.** A is the Explorer's update path as it is, `graphData` and `d3ReheatSimulation`, under which a renamed file or hub dies and is born again. B re-keys renamed files and hubs from `renamed` and `dirsRenamed` so that they keep their objects, places a born file at its hub plus the containment spring's rest length in a seeded random direction, holds every hub that stood before the step (`fx`, `fy`, `fz`) and releases them when the engine stops, and lets a hub new to the picture float in its first step. The library has no gentle reheat (below), so B's was built from the public API: the link and charge forces wrapped through `d3Force` to see a tenth of alpha, `d3AlphaMin` 0.1 and `d3AlphaDecay` 0.0456 so that the engine stops after exactly 50 ticks, and the library's centring force dropped, since it shifted every free sphere each tick against the held hubs (keeping it raised the mean file move over steps 2 to 12 from 21.5 to 31.3 units). C is B's re-keying and placement with `cooldownTicks(0)`, so the engine stops on the first frame without a tick.

**Scenario 4 and 6, the sequence's bytes and the heap.** 272,627 bytes: 99.6 KB is the interned path table, 297 bytes the base, 172 KB the deltas; the median delta is 646 bytes and the largest 10.2 KB (`d23a6f90`); 58 KB gzipped. The page's heap is about 6 MB before the sequence loads, 10 MB after the first picture, 16 to 17 MB through the middle and 18 to 19 MB at the end, so roughly 9 MB of renderer for 978 spheres and 2,653 lines. For scenario 4 this scales: a ten-thousand-commit history at this repository's median delta is about 6.5 MB of deltas before the path table, and the renderer's footprint is the snapshot's, not the history's.

**Scenario 10, the pinned-salient step.** 7 of the 90 steps where the pinned file exists are salient to it in the graph (32, 61, 63, 102, 103, 115, 116). Git shows its content changed in 10 of the sampled steps (those seven plus 33, 95 and 117), and `git log --follow` finds 14 commits on the file across the whole history: the graph misses the content-only changes, which touch neither its symbols nor its edges. A salient step by the graph is a change the map can show; a change git saw and the graph did not is the file's own business, and the design must decide whether the scrubber marks it too.

**What the library allows.** 3d-force-graph 1.80.0 over three-forcegraph 1.43.5 has no gentle reheat in its public API: `graphData()` always runs `stop().alpha(1)` in its deferred update, so every membership change is a full reheat whether or not `d3ReheatSimulation` is called, and that method also sets alpha to one. three-forcegraph has `d3AlphaTarget`, used for dragging, and 3d-force-graph does not expose it. The levers that exist are `d3AlphaDecay`, `d3AlphaMin` (the engine stops below it, only when it is above zero), `d3VelocityDecay`, `cooldownTicks`, `cooldownTime` (15,000 ms by default) and `d3Force` for replacing a force; B's gentleness is the alpha-scaling wrapper plus `d3AlphaMin`.

## Defects in the Explorer's modules, met while reusing them

1. **In the structure layout, reference wires drawn on demand are never positioned.** `pullingLinkForce` hands d3 only the containment links, so only their endpoints are resolved to node objects, and three-forcegraph skips a line whose endpoints have no coordinates. In the probe page 0 of 791 references resolved; their line objects sat at the origin with length one. In the built Explorer (`dist/explorer`, built 14:52 on October 16), hovering `.live-docs.config.json` in the structure layout gives two visible reference objects at the origin with length one and no wire on screen. `tests/e2e/force-graph-directories.spec.ts` checks each line's `visible` flag only, so it passes while nothing is drawn: a test that cannot fail.
2. **Link colours are dimmed five-fold.** `forceGraphView.ts` writes alphas (0.35, 0.5, 0.2, 0.025) and never sets `linkOpacity`, and the library multiplies them by its default of 0.2: containment shows at 0.07 and a revealed wire at 0.1.
3. **Every render rebuilds every line.** `spatialGraphOf` returns new link objects each time and the library binds render objects to data-object identity; that is the 65 to 88 ms per step measured here with about 2,650 links.
4. **The engine runs 15 s after every change.** The Explorer never sets `d3AlphaMin`, so the engine stops only at the library's fifteen-second cooldown, and `aria-busy` stays true that long.
5. **`NODE_COLORS` is not exported and has no `asset` colour**, so an asset falls back to grey; the page copied the table.
6. **The two cold-start filter defaults disagree**: `DEFAULT_SNAPSHOT` has `showAssets: true` and `getDefaultFilters` has it false; which governs was not checked.
7. **A hub's identity breaks over time.** A collapsed directory chain is identified by its deepest path, so a directory gaining or losing its only child changes the hub's id, a death and a birth for a hub that did not move.

## What this says

The shape the owner wanted holds. Fed rather than restarted, with a renamed file or hub keeping its object, a born file placed at its hub and the hubs held through the step, the structure layout carries this repository's history with the unchanged spheres moving a mean of under four units a step where today's update path moves them seventy-five and rebuilds the picture at every rename; the three package renames read as a name changing in place, which is what "slides whole" looks like when the hub already stood where its files were. The cost of a step is the data (about 6 ms) plus the library's rebuild of every line (65 to 88 ms, defect 3), and the sequence of 121 steps is a quarter of a megabyte: memory is a question of shape, as the brief said, and the shape is right.

Three things the probe settles for the design doc. First, the renderer must reach the simulation: the product's own force graph will need an alpha target or an equivalent of the wrapper the page built, since the library offers no gentle reheat, and the fifteen-second cooldown (defect 4) must go whether or not history is built. Second, held hubs are too still: a tree that never re-balances reads as growth only while it is small, so the design needs a release, a low-alpha relaxation of the hubs between steps or on a pause, measured as the page measured. Third, a hub's identity must be its path across time and not the collapsed chain's deepest member (defect 7), and a merge into an existing directory is a death the picture must show as such. Two findings are the product's today and not the history's: the on-demand wires of the structure layout are not drawn (defect 1), which a test with a geometric assertion must keep from returning, and the lines are a fifth as bright as written (defect 2), which is for the owner's eye.

What the probe did not settle: the pinned-salient step counted seven graph changes where git counted ten, so the scrubber's definition of "salient" is a design question (the graph's changes, git's, or both marked differently); the recording is of a software renderer on a paused clock, so the motion on a machine with a GPU, and the 8 GB machine, are still to be looked at; and names below depth two, the sample move's whole story, were never on screen.
