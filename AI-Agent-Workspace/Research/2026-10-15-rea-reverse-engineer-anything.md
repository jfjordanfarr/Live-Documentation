Everything quoted from REA's repository was read from its `main` branch on that date._

## What REA is

- **A local CLI and MCP server that connects a coding agent to reverse-engineering tools.** The repository is [morluto/rea](https://github.com/morluto/rea), "Reverse engineer anything with agents, from app behavior down to native binaries." The GitHub API, read on 2026-10-15, gives its creation date as 2026-04-14, its language as TypeScript, its licence as MIT, and 266,742 stars, 66,977 forks and 963 open issues. The npm package [`rea-agents`](https://www.npmjs.com/package/rea-agents) was first published on 2026-07-12 and stood at 6.5.0, published 2026-10-14, by the registry's own record. The README's milestone banner reads "250,000 GitHub stars".
- **Its pitch is a feature in someone else's app.** The README's first lines: "See a feature you like. Understand how it works, down to the binary level." and "See a feature in an app that you want in your own product? Ask your agent to investigate it with REA. It can inspect the app without its source code, explain how the feature works, show the evidence, and build a version for your project." ([README](https://github.com/morluto/rea/blob/main/README.md)). Its three showcases are two reconstructions and one trace: a DX-Ball sound-pan helper rebuilt in C that "passes 3,205 original-x86 cases and reproduces all 63 compiled function bytes", a PC-98 game's bullet-ring calculation, and Notion's clipboard bridge followed from the renderer through preload and IPC to the main process's `clipboard.write` ([the Notion case](https://rea.tools/showcase/notion/)).
- **What it reads.** The README's table: native binaries ("Pseudocode, assembly, strings, symbols, calls and references", through a bring-your-own Hopper, Ghidra or IDA), Go and Rust binaries' embedded build metadata, WebAssembly, EVM bytecode, SQLite files, Linux core dumps, JavaScript and Electron applications ("Modules, imports, source maps, routes, IPC and native add-on relationships"), websites through a Chrome-family browser, saved network captures, .NET assemblies ("Metadata, CIL instructions, declared native dependencies and build comparisons", needing no engine), Android packages and devices, Flutter apps, firmware, packet captures, logic-analyzer recordings, package inventories and process behaviour. "Static JavaScript and .NET inspection read the supplied files without running the application."
- **It runs locally, and is used through a model.** "Analysis runs locally, and results include the evidence and limitations behind each conclusion." Its FAQ: "REA analyzes targets locally. Your agent receives the tool results, and its model provider has its own data policy." Setup registers the MCP server with Claude Code, Codex, Cursor, Gemini CLI and others and installs a skill, the workflow instructions ([installation](https://github.com/morluto/rea/blob/main/docs/installation.md)); the CLI "uses the same application workflows and evidence contracts as REA's MCP server" ([CLI and Evidence](https://github.com/morluto/rea/blob/main/docs/cli.md)).
- **It stays out of source repositories by its own rule.** The skill it installs into the agent, [`reverse-engineer-anything`](https://github.com/morluto/rea/blob/main/.agents/skills/reverse-engineer-anything/SKILL.md) (its metadata says version 42), opens: "Use REA when a claim depends on a shipped binary or package, decompilation, passive application runtime evidence, or comparison with behavior not established by available source. For ordinary analysis of a complete source repository, use normal repository tools and do not run REA readiness or provider commands." Its one-line description ends "Skip REA for ordinary source-repository architecture analysis."
- **Its own architecture map is drawn by hand.** The README's "architecture map" is [a Mermaid file](https://github.com/morluto/rea/blob/main/docs/architecture.mermaid) of 168 lines kept beside the code, and the project's [AGENTS.md](https://github.com/morluto/rea/blob/main/AGENTS.md) tells contributors to "See docs/architecture.mermaid when changing composition." It is the kind of diagram Live Documentation exists to generate.

## How REA says what it knows

This is the part of REA nearest to Live Documentation's concerns, and the part the commentary does not describe.

- **A graph of the application, with closed vocabularies.** The [JavaScript Application Graph](https://github.com/morluto/rea/blob/main/docs/javascript-application-graph.md) is "REA's provider-neutral domain model for connecting shipped application bytes, JavaScript structure, Electron process boundaries, passive browser observations, and native add-ons", serialized "as RFC 8785 canonical JSON". Its node kinds: package, installer, artifact, ASAR entry, Electron main, preload, renderer and utility process code, asset, chunk, module, source map and original source module, BrowserWindow, frame, target, contextBridge API, IPC channel and handler, worker, endpoint, storage, native add-on and export, runtime script instance, and "an explicit `unknown` kind when classification is not justified". Its relations: `contains`, `loads`, `imports`, `maps_to`, `exposes`, `sends`, `invokes`, `handles`, `calls`, `persists_to`, `observed_as`, `changed_from`. "Provider names are deliberately absent from both vocabularies."
- **Every edge carries how it is known.** Each observation and edge carries "an authority, such as artifact bytes, AST analysis, static relationship inference, passive CDP runtime, and cross-layer reconciliation, native analysis, historical reference, or user assertion"; "an epistemic state: `observed`, `inferred`, `unknown`, or `unavailable`"; a confidence "independently bounded as exact, high, medium, low, or unknown"; a location "or an unavailable reason"; the extractor's name and version; "coverage status, truncation, omitted count, and named limits"; and limitations. The rules that bind them: "`static-relationship-inference` can only produce `inferred` facts"; "inferred facts require an explicit limitation"; "exact confidence is reserved for observations"; "An AST observation does not become a runtime fact, and a passive runtime fact does not prove which static module produced it." And the sentence that carries the design: "Unavailable values are represented explicitly rather than as missing fields, so absence of evidence cannot silently become evidence of absence."
- **Identity with a stated reach.** A node's identity is separate from its observations, under seven strategies that each name their "stability scope": a content digest holds for "globally exact bytes", a canonical path for "one artifact version", a runtime instance for "one capture only", and a structural fingerprint is an "explicit cross-version inference" that "never claim[s] exact cross-version identity".
- **The agent is told to keep the three apart.** The skill: "Every conclusion must distinguish observations, inferences, and unknowns. Cite Evidence IDs, preserve limitations and incomplete coverage, and never imply that static analysis observed execution." Its plan for a broad investigation ends with "a concise finding ledger linking each conclusion to Evidence IDs, confidence/evidence type, search boundary, and remaining unknowns", and, before finishing, "Mark each question as answered, partially answered, or unresolved based on its evidence". An open question is itself a record: `record_unknown` "to track unresolved questions in the user's investigation and name the authority or environment still required. Supply supporting and contradicting evidence IDs", and "Only qualifying observed evidence can verify a resolution" ([evidence workflows](https://github.com/morluto/rea/blob/main/.agents/skills/reverse-engineer-anything/references/evidence-workflows.md)). The rule behind the tools: "Missing coverage is unknown, not absence" and "Keep observed, derived, and inferred relationships distinct" ([tool design](https://github.com/morluto/rea/blob/main/docs/tool-design.md)).
- **The record is a ledger, not a document.** "The complete application Evidence can be hundreds of megabytes for a real application"; "a 334 MB Obsidian application Evidence file yields a summary view of about 10 KB", and the agent works "summary-first" over retained Evidence, paging modules and asking for views ([CLI and Evidence](https://github.com/morluto/rea/blob/main/docs/cli.md)). A feature trace starts from "one literal seed kind: node ID, route, string, API, IPC channel, module" and returns "the complete graph reachable in the selected direction"; a version comparison yields "a `changed_from` graph containing all compared nodes" ([application workflows](https://github.com/morluto/rea/blob/main/docs/javascript-application-workflows.md)). None of these documents describes a committed, human-readable artifact; the human-facing result is what the agent writes, as the showcase pages are. The Notion page says REA gave the starting points and the link from the clipboard member to its receiver "came from reading the wrappers" ([the Notion case](https://rea.tools/showcase/notion/)).
- **A correction to the week's summaries.** Search summaries of the week credited REA with named workflow stages and labels of "seen, inferred, or unknown". The sources use `observed`, `inferred`, `unknown` and `unavailable`, the README describes its flow in one paragraph, and the only numbered sequence is the skill's seven-step plan for a broad investigation.

## Where it stands beside Live Documentation

| | REA | Live Documentation |
| --- | --- | --- |
| Subject | A shipped artifact: a binary, a bundle, an assembly, a capture, a running process | A folder of source files |
| First reader | A coding agent, through MCP or CLI JSON | A person, through markdown, the Explorer and the CLI; agents read what a person exports ([direction.md](../Memory/direction.md), 2026-10-03) |
| Form of record | A session ledger and exported Evidence bundles, hundreds of megabytes for a real application, projected into views | One committed markdown file per source file, a derived index that is never committed, a static page |
| What an edge carries | Authority, epistemic state, bounded confidence, location, extractor, coverage, limitations | How it was observed: an import or type reference within a folder; `contract`, `configuration` or `declared` across a process boundary; an entry's reason and declarer ([the decisions log](../../.mdmd/layer-3/architectural-decisions.mdmd.md#openings-and-the-basis-of-an-edge-recorded-2026-09-28)) |
| What it says of what it could not see | An explicit `unknown` or `unavailable` fact with a limitation, and an unknown ledger | An unresolved import stays as an external dependency line ([openings](../../.mdmd/layer-3/openings.mdmd.md)); a reference that is not an import is absent, as the dead code sweep of 2026-10-08 found ([the vision](../../.mdmd/layer-1/vision.mdmd.md#where-this-stands)) |
| Correctness | Verification lanes against real engines; a reconstruction closes only under a "verifier whose authority is comparable to the original observation" ([obligation ledgers](https://github.com/morluto/rea/blob/main/docs/reconstruction-obligation-ledgers.md)) | Oracles that share no mechanism with the analyzer: a compiler's resolution, hand-verified fixtures, cross-language parity ([the vision](../../.mdmd/layer-1/vision.mdmd.md#correctness)) |
| Change over time | `changed_from` edges and comparison tools between two analyses | `git diff` of the mirror |
| A model | None inside REA; every use is through the agent's model provider | None: "It calls no model and makes no network requests" |
| Licence | MIT | MIT |

Two sentences written on different days by the two projects sit well together. REA's skill: "For ordinary analysis of a complete source repository, use normal repository tools." Live Documentation's vision: "Not an LLM tool. It calls no model and makes no network requests. Agents may read its output like anyone else."

## The agent's judgement

The owner's three questions, answered as a reading and not a decision.

**Is it related?** By subject, no: REA reads what a build produced, Live Documentation reads what a person wrote, and REA's own skill hands a source repository back to "normal repository tools". By instinct, yes, and closely: both hold that a map is only as good as the evidence written on each of its edges, that an inference must say it is one, and that a reader must be able to see where a fact came from. REA's `observed`, `inferred`, `unknown`, `unavailable` is the instinct of the vision's "Where an edge is inferred rather than observed, the map says so", of the basis on every cross-process edge, and of the `Entry` line's reason and declarer. REA states it more completely, on every edge, with "unavailable" as a value a reader can see.

**Is Live Documentation a layer of abstraction outside it?** Neither above it nor below it. They are two maps of the same kind of thing from different inputs, and neither contains the other: REA has no durable, person-facing, reviewable record, and Live Documentation has no reading of an artifact. If they ever met, it would be on the World Map, at a piece whose source is not in hand, a vendor's assembly or a database whose schema is not in source control, described from its artifact rather than declared by hand. That is a possible adapter and not a plan, and it would be judged like every adapter, against an oracle that shares no mechanism with it.

**Is it a fad?** The attention is a cycle, by the commentary's own reading and by the thread's "can't figure out what's this tool's purpose". The engineering under the attention is careful, and the parts that matter here, the evidence contract and the closed vocabularies, would be worth reading at a tenth of the stars. The framing that carried it, "see a feature you like ... build a version for your project", is the opposite pole from this project's purpose in the owner's words, "never letting understanding run away from you" ([direction.md](../Memory/direction.md), 2026-10-08), and it comes with the legal weather the thread names.

**What it suggests.** Each an open question, none decided:

1. **Say what an adapter could not see.** Today a reference the adapter cannot resolve is either an external dependency line or nothing. REA's rule, that absence of evidence must not silently become evidence of absence, has a form the grammar could carry: a computed `import(expression)`, a `require` of a variable, a reflection call, written on the doc as an unresolved reference with its line, so that the Knowledge Sources panel can say "this file has references the docs cannot follow" where it now says only what nothing reaches. The dead code sweep already named the gap. It sits within the markdown-is-canonical rule, and the compiler oracle, which records what the adapter dropped, can measure it.
2. **Say how each file was read.** The vision's status knows which adapters are compiler-backed and which are hand-written scanners; the reader of a doc, or of the panel, does not. One fact per doc, or one breakdown per bundle, would carry "the upper limit of scale is set by what the data can honestly support" to the person looking.
3. **An artifact as a subject, for the pieces with no source.** REA reads a .NET assembly's metadata and declared native dependencies with no engine. A piece of the owner's estate that is only a vendor's DLL could offer "what it exposes and what it stands on" from the artifact, where today it can only be declared. A later adapter, if ever; its oracle would be the compiler that built the artifact, when it is at hand.
4. **A skill as the plain-text door.** Apart from MCP, REA's whole agent-facing surface is one markdown file of instructions. The owner's rule is "plain text with the easiest-to-copy utilities" and exports rather than doors ([owner.md](../Memory/owner.md), 2026-10-08). A Live Documentation skill would be one page saying where the mirror is, what the grammar is and which commands answer which questions; cheap, in keeping, and not a server.

**Confirmations rather than ideas.** A feature trace from a seed is `inspect --from`; working summary-first over a huge ledger is what one doc per file already is; a version comparison is what a committed mirror gets from git and what a session ledger lacks; and REA's unknown ledger is a formal register of open questions, of the kind the earlier way of working here kept and the owner retired on 2026-09-27 with the rest of that scaffolding, so it is noted and not proposed.

**What not to take.** MCP as a door, which the owner set aside on 2026-10-08; the clone-a-feature framing; and reconstruction, a different purpose with its own legal weather.

## Addendum, 2026-10-15, after the owner's reply

The owner's reading of the relation ([Turn 6](../ChatHistory/2026/10/2026-10-15.1.record.md#turn-6)): "REA produces something code-like and then Live Documentation can render that something understandable to humans." The judgement above had looked at REA's own record, the evidence ledger, and not at what its engines emit: pseudocode and reconstructed C from a native binary, recovered modules from a bundle, decompiled Java from an APK, and, in its showcases, whole source repositories maintained by an agent. A folder of code-like files is Live Documentation's input, so the layer the owner named exists without any integration: the decompiler or the reconstruction runs outside, and Live Documentation reads the folder. "Neither above nor below" above is corrected to this: above the output, with nothing between.

Tried the same evening on REA's TH04 reconstruction repository ([the probe](../Probes/2026-10-15/live-docs-over-th04/README.md)): 941 docs and an Explorer bundle in ten seconds, cold. The picture was lopsided for reasons that are this project's own: the C adapter registers only `.c` and `.h`, so 349 C++ files and 172 headers got empty docs; root-relative includes do not resolve; a C++ `main` is not marked; the shipped globs carry no `*.hpp` or `*.inl`. The pipeline is real; the gaps it showed are ours. Where it thins: a stripped native binary decompiles to functions without files or names, so its map is a map of addresses until someone names them, which is the work REA's showcases show an agent doing; a bundle without source maps is a map of numbered modules. What Live Documentation adds that REA leaves to prose: the picture, the walk from the entry, what nothing reaches, and a committed mirror that diffs.
