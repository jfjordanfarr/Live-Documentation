Where two copies of one method read the same files they must agree; the Roslyn misses could only come from a difference in which files each read, and that is what they turned out to be (section 2). So the Roslyn number did not compare the analyzer with anything independent of it, and could not have told a right edge from a wrong one.

Two smaller measures appear in the agent's floor survey of 12-11: a "Self-Similarity" mode, the benchmark's default, that ran one TypeScript fixture of four edges ("100% across the board (4 TP, 0 FP, 0 FN)", agent, [2025-12-11.1.md](../../../ChatHistory/2025/12/2025-12-11.1.md), line 219; `git show 85e6b0a4:reports/test-report.self-similarity.md`), and rebuild stability. Neither bore on the owner's questions.

So, of the four: symbol, per-file and dependency precision compared the generator with itself; AST precision and recall compared a heuristic path the product did not ship with an answer key that was a compiler for TypeScript, a parser for Python, and for the other five languages a second scanner by the same hand, which for C#, Roslyn included, repeated the graded code's own regular expressions.

**What removing the 40 did to the measurement.** Recall went from 252 of 295 to 252 of 255; precision stayed at 98.8%. Nothing on the graded side changed: `inferred.json` is the file of 2025-11-08. Every one of the 40 removed edges was a miss, and no edge the heuristics had found was removed. That is not chance: the heuristics could only name files in their own input set, so "outside the scope" and "out of the analyzer's reach" were the same 40 edges. The whole gain of 13.4 points came from the answer key.

**Trimmed to the analyzer, or truly out of scope?** The removed edges can be recovered (`git show 85e6b0a4^:tests/integration/benchmarks/fixtures/csharp/roslyn-compilers/expected.json` against the same file at `85e6b0a4`), and the Roslyn files they name can be read at the pinned commit `fa2ab851`. This reader did both, fetching `LanguageVersion.cs` and the 26 in-scope source files read-only from GitHub into its scratchpad. What the evidence supports:

- The scope rule was not made up on the day. It was the fixture's own `materialization.include`, set in November. But it had never been applied to the key, and it was applied for the first time only after the gate failed, and only on the side that raised the score.
- Fourteen of the forty were edges _from_ files outside the declared scope: twelve from `CSharpExtensions.cs` (4), `CSharpParseOptions.cs` (3), `CSharpCompilationOptions.cs` (2), `GlobalSuppressions.cs` (2) and `CSharpFileSystemExtensions.cs` (1), and two from `LanguageVersion.cs`. Those are dependents outside the sample, and dropping them is defensible under any reading of "the sample".
- Twenty-six were edges _from_ files inside the scope to `LanguageVersion.cs`, all but one with the relation `imports`. The agent called them enum references; the slice report and the bearings (finding 9) call them "dependencies of in-scope files". **Most were not dependencies at all.** The oracle never indexed `enum`, so the enum `LanguageVersion` could not have produced them. Run over `LanguageVersion.cs`, the oracle's type pattern finds five "types": the three real classes `LanguageVersionExtensionsInternal`, `CSharpRequiredLanguageVersion` and `LanguageVersionFacts`, and two from its documentation comments, `methods` from "Default interface methods" and `ToString` from "Sealed record ToString" (the file's lines 135 and 187). Twenty-four of the twenty-six source files contain neither the enum's name nor any of the three class names, and each mentions `ToString`, a method name, which the oracle resolved to a comment. One (`DefiniteAssignment.cs`) constructs `CSharpRequiredLanguageVersion` three times, a real dependency, and is the one `uses` edge. One (`NullableWalker.cs`) compares values of the enum through `compilation.LanguageVersion`, a property declared in another file; whether a compiler would draw this edge is uncertain, and the oracle found it only through `ToString`.
- So the trim removed, among the 26, at least 24 false edges and at most 2 true ones. It was not done because they were false: nobody looked at them, and the rule that removed them would have removed true edges as readily. The key was wrong in a way no one checked, and the analyzer "missed" those edges only because it did not read the file holding the comment. The commit's account, "40 edges from parent directory files" (line 1862), was wrong about the 26, but the edges it dropped were mostly wrong too.
- The same artifact can live inside the scope: any comment in `FlowAnalysis` or `Utilities` that reads "class X", "struct X", "interface X" or "record X" makes X a type in both the key and the graded code, and both would then draw the same false edges and agree on them. This reader did not measure how many of the 255 edges that remain are of that kind.

What happened next supports the owner's scepticism about the number itself. Roslyn was swapped out on 2026-01-27 for Newtonsoft.Json, first scored at 99.1% "against the oracle" (commit `4def4c39`); once a compiler graded it, the January report finds "precision=0.703, recall=0.651" ([2026-01.md](../2026-01.md), question 1). Two copies of one regex agreeing is not a measure of either.
