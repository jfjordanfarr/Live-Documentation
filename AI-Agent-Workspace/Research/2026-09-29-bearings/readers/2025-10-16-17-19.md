### 3. Answers to the five questions

**Q1. What the project was at its founding, and what the owner wanted that no later month mentions.** It was a VS Code language server whose diagnostics in the Problems panel would give Copilot, working in agent mode, clues about context "just outside" its window (L5). The trigger was divergence between four layers of docs and code, and then between code files. Four wants carry no later mention that I know of:

- **Serving an agent mid-edit through the editor's own diagnostics channel.** The agent reads a warning because it is in the Problems list. That is a delivery mechanism, not a picture.
- **The ricochet problem** (L479): a doc edit flags the code, the code edit flags the doc, and so on. The owner wanted to break the loop "while also leveraging the fact of _some_ ricochet to our benefit when specifying software from docs". That is round-trip specification.
- **Riding on the IDE's language services instead of parsing** (L289, L1005). This is the most-repeated founding value, and it was later abandoned for tree-sitter and compilers. The spirit survives as "tree-sitter likely" and as compilers used as oracles.
- **Designing for bursts of agent edits**: debounce and back-off (L481, "How long do we back off waiting for new changes to arrive?"). This matters for the editor panel the vision will rebuild.

The diagnostics subsystem itself was deleted on 2026-02-18 (`6348820c`, "Remove diagnostics subsystem — 38 source files, 7,328 lines"). The LLM provider gate and `analyzeWithAI` went on 2026-02-17 (`15c708eb`).

**Q2. Where the rules were first spoken.** See section 4.

**Q3. Why "membrane".** My transcripts give the name once, in the owner's pasted instructions at 2025-10-19 L2688, and never define the word. `git log -S` puts its first commit at `ff9871a9` (2025-10-19 20:06). The only surrounding meaning is structural. The layers run "from most abstract/public to most concrete/internal" (L2682), and layer 4 is "a more human-readable C Header file, describing the programmatic surface" (2025-10-16 L11). My inference, not the owner's word: a membrane here means the surface that separates a unit's outside from its inside, and each layer is a surface over the one beneath.

A grep of the whole chat record finds "membrane" only as MDMD's name until 2026-03-22.1.md L242. There the owner, in their own turn (which starts at L240), speaks of directories "surrounding-like-a-membrane (parent)". That is where the Membrane Map's sense comes from. I found no passage tying the two together. So the record supports two separate uses that happen to share an image, containment behind a surface, rather than a line of descent. Only the owner can say what they meant in October; the four layers predate this repository ("I've previously described", 2025-10-16 L7).

**Q4. Does the founding idea deserve to come back?** My days do not include 2025-10-25; the heading question is not in them. What they do hold is that the owner **deferred** docs-to-code; they never rejected it. The sequence and its condition are explicit (2025-10-19 L2147): code-to-code first, until "really really satisfied with our ability to detect the true set of perturbances", "_then_ we work our way up to code-to-docs and docs-to-docs". The oracle-measured adapters of September are the closest the project has come to meeting that condition.

The owner also set constraints that any return must honour:

- no forced frontmatter or command-line registration (L1005);
- links inferred and rebuildable (L1005);
- noise cut down (L2);
- no endless ricochet (L479).

The prose reference report in ideas.md meets all four: the links are inferred from backticked names, the report is derived, and a report cannot ricochet. What it lacks is the reverse direction the founding asked for: given a code change, which prose names the changed symbol. My inference: if backticked names resolved into edges in the graph index, `inspect --direction inbound` from a file would answer the founding question with prose included. That makes the prose report the first step back rather than a side tool.

**Q5. Who the tool was for, and what success looked like.** It was for GitHub Copilot in agent mode (L5), and for "Copilot and myself" (L1217, 2025-10-17 L380 "It's just us."). Benchmarks were to be designed "for ease of interpretation by Github Copilot" (2025-10-17 L1104), and the tool was to be tuned by the agent "to meet your own contextual needs" (2025-10-19 L343). The user stories about technical writers, developers and leads are SpecKit template output written by the agent (spec.md at `f7a75fa7`), and so is the success criterion about "pilot teams" and "sprints". The owner waved that kind of thing off as "pomp and circumstance".

Success in the owner's own words meant:

- a "definitive answer" to what a change affects (2025-10-19 L2144, L2149);
- reproducible results (2025-10-16 L1273);
- outputs that could be confirmed "or falsif[ied]" against the true AST of known software (L1595);
- low barrier to entry for developer and user (L2339);
- no Copilot credits spent (2025-10-19 L2067);
- "the first project in which we get a VS Code Extension actually working in the Host Extension window" (L1613).

This agrees with the November finding that the agent was "the primary consumer". October shows it from line 5 of day one. September's "humans are the audience" is a reversal of the founding, not of a later drift.
