## The product roadmap

`.mdmd/layer-2/product-roadmap.mdmd.md@ae216cb5`, 573 lines, read whole.

### Origin of the roadmap

It arrived on 2025-10-21 in `ea84a251` ("docs: add architecture bridge docs") as a 32-line "Link-Aware Diagnostics Roadmap (Layer 2)" of four streams, ripple observability to auto-repair, all of the diagnostics product. The same day the owner had asked for "the MDMD crystallization of our vision (from top-down (based on full census of all chat history that begins with `jfjordanfarr:` and all spec docs from 001-link-aware-diagnostics/) and from bottom-up" ([2025-10-21.md](../../../ChatHistory/2025/10/2025-10-21.md), line 1854), and answered the agent's plan to "distill Layer‑1 vision → Layer‑2 roadmap so we have the authoritative “why/what”" with "EXACTLY. EXACTLY. We are completely and totally aligned." (line 1866; the agent's plan is line 1858). So the roadmap is the owner's layer 2, "requirements and roadmap" in their 2025-10-19 layering ([direction.md](../../../Memory/direction.md), line 62), written by the agent.

Forty-one commits touched it, arrival and retirement included, the last edit before September on 2026-03-23 (`git log --follow`). The streams that matter today arrived on these days: the Hosted Showcase on 2025-11-15 (`48ac509c`, "thread hosted showcase plan"), the visualization requirement and its accessibility criteria on 2025-11-21 (`053d111a`, "docs: vision for visualization surfaces"), the latency targets on 2025-11-09 (`86a74a76`), and brownfield on 2026-01-06 (`185977a2`). After February 2026 it was mostly struck through: LLM enrichment, diagnostics, docstring drift and the authoring bridge each carry a "Descoped" line and strikethrough text.

### Uncarried substance from the roadmap

Checked against `AI-Agent-Workspace/Memory/`, `.mdmd/layer-1` to `layer-3`, `README.md`, `AGENTS.md` and `SECURITY.md`, each with several phrasings (`hosted`, `showcase`, `Cloudflare`; `latency`, `ms`, `≤`; `interactions`; `preset`; `MCP`, `OpenAPI`, `JetBrains`; `brownfield`, `layer 4`, `first paragraph`, `semantic index`).

1. **The hosted showcase, and the owner's reason for it.** `product-roadmap.mdmd.md@ae216cb5`, lines 200 to 220 and 323 to 328: "a stateless Cloudflare (or equivalent) runner that clones public GitHub repositories, executes the existing Live Docs generator, and returns a downloadable bundle while preserving the offline-first guarantee" (line 202), public repositories only, the workspace deleted at once, a "Replay Locally" call to action on every response (line 220), and "positioning the hosted runner strictly as a marketing experience" (line 572). This one is the owner's, not the agent's. On 2025-11-15, after seeing Google's Code Wiki: "**We should plan for a future where we host a public-facing websitre on Cloudflare which can run our software against open source repos provided by the user, and we output the Live Documentation and even the sqlite DB which generated it, all at no cost to the user**" ([2025-11-15.md](../../../ChatHistory/2025/11/2025-11-15.md), line 379), and the reason: "The reason I think that we will need this is visibility. We are frankly building something superior to the paid competitors. It should be very easy for a prospective user of our software to give it a spin and see what it spits out." (line 381). The same session set a boundary: "I just want to make sure that your edits haven't permeated some subtle idea that this hosted component has absolutely anything to do with what users are downloading and using in their own development environments." (line 716). **Judgement:** the runner itself fits nothing today (the product makes no network call, and "Internet calls are things I really do want to do without if I can", [ideas.md](../../../Memory/ideas.md), line 20); but the want, a person trying the map on a public repository without installing anything, is a human-audience want that fits the new vision better than the old, and it came back on its own on 2026-09-28 as "a website with precomputed indexes for popular open source software" (same line). Neither the 2025 idea, its reason ("visibility", "give it a spin") nor its boundary is recorded now, so the September entry reads as new. Worth one dated line under that entry.

2. **Latency targets.** Lines 297 and 305: "CLI exports and diagnostics respond within target latency (≤2 s for repos under 10k files)" and a detail panel that "loads within ≤500 ms for repos under 5k files". No current document sets a size or a time the tool must meet; the one measurement kept is the 12 seconds of a `--changed` run in February ([architectural-decisions.mdmd.md](../../../../.mdmd/layer-3/architectural-decisions.mdmd.md), line 178), and the Membrane Map doc says only that "Large workspaces (1000+ files) require lazy rendering" ([membrane-map.mdmd.md](../../../../.mdmd/layer-3/membrane-map.mdmd.md), line 183). **Judgement:** the numbers were the agent's, never measured and never asked for by the owner that I found, and rightly not carried as targets. What is lost is the question they stood for: how large a folder or an estate the map must stay usable on. The owner's estate is the case that will answer it; it is not written down.

3. **"Within two interactions."** Line 302, the acceptance line for the merged view: it "loads a Live Doc file, expands its symbols, and highlights inbound/outbound edges while dimming unrelated nodes within two interactions." **Judgement:** the agent's criterion of 2025-11-21, and still a good one. The measure the agent proposed on 2026-09-29 for the Membrane Map, "the steps a set of questions with known answers takes" ([direction.md](../../../Memory/direction.md), line 93), is the same idea found again; the roadmap had it as a number. Not a loss of substance, but a before-and-after worth knowing (question 2 below).

4. **Brownfield docs belong to layers 1 to 3, never to the base layer, and their headings are searchable.** Lines 268 to 272 and 341 to 345: "brownfield docs conceptually map to Layers 1–3 (Vision, Requirements, Architecture) and never to the Base/Source layer (Layer 4)" (line 270), and optional indexing of "title, headings, first paragraph" so that "semantic search surfaces legacy context without mutating files" (line 271). The decisions log carries the principle, never rewrite, bridge by link, `bundleExclude` ([architectural-decisions.mdmd.md](../../../../.mdmd/layer-3/architectural-decisions.mdmd.md), lines 170 to 173), and the code draws related docs (the bundle's related-documentation downloads, [download.ts](../../../../packages/explorer/src/client/download.ts), line 75). The layer mapping and the search are in no current doc. **Judgement:** the search was the agent's and unbuilt; rightly dropped. The mapping is a small true rule that only matters if the owner points the tool at a repository with its own docs, which is the day-job case; low stakes.

5. **An external query surface for other tools.** Lines 175 and 314: "Offer MCP/OpenAPI surfaces so other IDE agents can consume the Live Doc graph", "with authentication disabled by default for local use". **Judgement:** rightly dropped with the agent audience. The owner's newer thought, the World Map as context for an agent ([ideas.md](../../../Memory/ideas.md), line 16), is recorded and does not need a server; the graph index is already the machine-readable surface.

Smaller, and dead with their systems: a public GitHub Pages site built from layer 1 with Astro (lines 182 to 186, 571); requirement handoff to Spec-Kit and issue trackers (188 to 192); staged adoption "Observe → Sustain" profiles (line 90); telemetry for the Explorer and the showcase (117 to 121, 206 to 220); "diagram presets" as an open question (line 564), the agent's; generative scaffolding from a doc's intent (156 to 160), which the vision's "Not a specification" and "Not an LLM tool" rule out ([vision.mdmd.md](../../../../.mdmd/layer-1/vision.mdmd.md), lines 74 and 77).

### Origin of the consolidation plan

Written on 2026-01-12 in `0d89e857` ("refactor: eliminate GraphStore infrastructure — Live Docs ARE the database"), edited on 2026-01-18 (`61c4b101`) and 2026-02-17 (`7befc770`, the LLM line struck), retired in `53ffb839`. Its closing note gives the occasion: it "was created after an attempted big-bang deletion revealed the scope of `changeProcessor.ts` integration" (line 137). The record of that day ([2026-01-12.1.md](../../../ChatHistory/2026/01/2026-01-12.1.md)) shows the owner's side of it, which the plan does not:

- The argument that removed SQLite was the owner's: two tools deciding separately what a code file is ("one would supposedly need _two separate configurations_ to determine what is and what is not a code file, no?", line 1481) and "Perhaps analysis of knock-on effects of edits should come as a result of analysis of the generated Live Documentation, no?" (line 1485). The phrase the decisions log quotes as the rationale, "Live Docs ARE the database", is the agent's summary of it: "The Live Docs on disk ARE the database" (line 1586, the agent's), then the commit subject.
- On the design: "I'm SO EXCITED to REDUCE the size of our codebase and doc set! When we get virtually equivalent functionality for less code, we are almost always going in the right direction. The simplest fully-functional implementation is very frequently the most correct." (line 2311).
- On the reverted deletion: "You hit a roadbump, and instead of stopping and asking questions, you reverted. I pushed back and you opted to flip the other direction. The correct path forward is a _dialogue_ against the newfound realizations, yeah?" (line 2502).
- On what change detection was still for: "We generate documentation proactively. There is no reason we shouldn't detect impacts proactively. That is a reasonable "bonus" to using the VS Code extension rather than just the NPM package." (line 2568); notices "_only_ on _breakages_ that are distinguishable as plausibly deleterious or unintended (namely, breakages across _polyglot_ bridges -- the unique benefit we bring to the table)" (line 2769); and "could detection of link breakages -- broken links between files (let's say that the user changes the name on a CSS file depended on by an HTML file) be **stateless**?" (line 2771).

### Uncarried substance from the consolidation plan

1. **Proactive notice of a severed link across languages.** The plan says only that "polyglot change detection remains useful but is not mission-critical" (line 17); the decisions log keeps the negative half, "in-editor polyglot change detection was not mission-critical" ([architectural-decisions.mdmd.md](../../../../.mdmd/layer-3/architectural-decisions.mdmd.md), line 195). The owner's positive half, quoted above (lines 2568, 2769 and 2771), is in no current doc: a stateless notice, raised only when a link between languages breaks, as the editor's bonus. **Judgement:** still meaningful. The editor panel is to be built fresh as a host of the Explorer "with a file watcher" ([vision.mdmd.md](../../../../.mdmd/layer-1/vision.mdmd.md), line 76), and a markup-to-script or configuration-to-service link that breaks is exactly what the estate's languages do not check for themselves. Whether anything reports it today I did not establish: `lint.ts` checks structure, authored sections, absolute links and islands ([lint.ts](../../../../scripts/live-docs/lint.ts), lines 216 to 301), not a dependency whose target has gone. It is the owner's call whether it belongs in the new product; it should at least be an open question rather than a closed "not mission-critical".
2. **Compare two searches before one replaces the other.** The risk table: "BFS traversal differs from RippleAnalyzer | Compare outputs in test harness before switching" (line 125). The agent's, and a method rather than a fact. **Judgement:** it applies now: the Explorer's own path search still stands beside the engine's, and the bearings note that the engine treats "both" as inbound when no target is given. Replacing the one with the other is the case this line was written for.
