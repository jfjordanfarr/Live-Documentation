## Why the static Explorer was wanted

The day's first chat began as a hunt for "loose ends". The owner named one in advance, the headless Local Map, and then, a turn later, proposed the static Explorer as a new one. Both came from the owner; the agent's contribution was to tie them together.

- **The owner's reasons, in one turn.** "I want the Live Documentation Explorer to be capable of working as a static site off of pure JSON data -- no node server required. Why? Because then, consumers of our software, potentially including ourselves, can host their own live documentation via Github Pages or other simple static site hosting services. Tantalizingly, this may even open the possibility (i.e. at my enterprise fullstack development day job) of serving these contents into a smart card in Microsoft Teams or something of that manner (embedding possibilities)." And a third reason, speed: "turning it into something flat that can be statically worked from gives us an opportunity to decouple potentially slow updates from the hopefully fast explorer. It would make writing changes _from_ the Explorer _to_ the documentation files more difficult, but it would make handling changes _from_ the live documentation _to_ the explorer potentially much easier (simple refreshes, perhaps not even page refreshes but a super basic refresh button in the UI which perhaps is sensitive to "dirtying" of the underlying JSON data from which it is built)." (owner, [2025-12-07.1.md](../../../ChatHistory/2025/12/2025-12-07.1.md), line 304). So three reasons: self-hosting on Pages, embedding at the day job, and decoupling slow generation from a fast viewer. Offline use and the network are not among them; the owner said nothing on this day about a CDN or about the page's network calls.
- **What the agent made of it.** It called the idea "a **superb architectural insight**" and claimed it "Solves the Headless JSON Problem Automatically" (agent, [2025-12-07.1.md](../../../ChatHistory/2025/12/2025-12-07.1.md), lines 306 and 317), because "The same JSON that powers the visual Explorer also powers:", first among them "LLM prompts (no image analysis needed)" (lines 318 and 319), and it listed "**Offline documentation**: Ship explorer + JSON with releases" among the enterprise uses (agent, line 345). Offline was the agent's word, not the owner's. Its first architecture kept the server: "Static Explorer is a **distribution format**, not a replacement architecture. The existing server (`npm run live-docs:visualize`) remains for local development" (agent, [2025-12-07.1.md](../../../ChatHistory/2025/12/2025-12-07.1.md), line 499). That two-mode arrangement lasted until the server was removed on 2026-03-10.
- **The owner took the pairing as the agent's.** "Very exciting!! Great! Okay, so what's say we get to work on the static site explorer and the headless JSON local map view simultaneously! They are, as you say, two sides of the same architectural coin!" (owner, [2025-12-07.1.md](../../../ChatHistory/2025/12/2025-12-07.1.md), line 609).
- **The owner asked that the docs not contradict each other.** "Try to be holistic though and ensure that we're not inadvertently declaring our intention to do two opposing things within the context of our #file:layer-1 #file:layer-2 and #file:001-link-aware-diagnostics docs, cumulatively." (owner, [2025-12-07.1.md](../../../ChatHistory/2025/12/2025-12-07.1.md), line 458). The agent found "**No contradictions found.**" and answered in requirement IDs (CAP-005, REQ-V1 and the like), then added ten tasks, LD-810 to LD-819 (agent, lines 488 and 584). Those schemes and files are gone.
- **The Markdown in the bundle was the owner's idea, and the showcase was its reason.** "Perhaps a naiive question on my part, but why not just bundle the documentation -- the markdown -- as part of the deliverables for the static site export? Is that silly relative to our architecture? (owner, [2025-12-07.1.md](../../../ChatHistory/2025/12/2025-12-07.1.md), line 1035). The hosted showcase, a site that takes a public repository and returns its docs, is in no current document; the vision says the tool makes no network requests, and a service that clones a stranger's repository would be a different product.

## Why the detail panel renders markdown

The markdown renderer was the agent's proposal, made while the static page could not reach the server's `/details` endpoint; the owner took it at once and then narrowed it.

- **The agent's reason.** Once the owner asked for the markdown in the bundle, the agent headed a section "The Detail Panel Becomes a Markdown Renderer" and proposed that it look up the doc in the static data and render it "(using a lightweight renderer like `marked`)" (agent, [2025-12-07.1.md](../../../ChatHistory/2025/12/2025-12-07.1.md), lines 1084 and 1087), because "The Live Doc *is* the canonical artifact" (line 1045). It then wrote its own instead: "**Add a markdown renderer** (lightweight, no dependencies)" (agent, line 1135). That is the origin of `markdown.ts`, a hand-written renderer with no library behind it.
- **The owner's reason: the old panel was ugly with raw links.** "As it should always have been. You'll see very obvious places where our visuals could have been profoundly improved by choosing to have the Detail Panel be a markdown renderer to begin with. There are mountains of naked markdown links, with their square brackets and hyphenated long file paths drifitng off. The amount of visual problems this would solve simultaneously would be, well, akin to the architectural two-birds-with-one-stone work we've been accruing throughout the day. This is a very Occam's Razor dev day." (owner, [2025-12-07.1.md](../../../ChatHistory/2025/12/2025-12-07.1.md), line 1101).
- **What the panel should offer, in static mode.** "In static mode, we shouldn't need to expose a button to allow the user to open that in their IDE" (line 1104); "It would be nice if there was an "Open in Circuit Board" button which would open to that node centered in the Circuit Board view, ensuring that any detail panel element can be viewed from any of our 3 visualization types in a simple and idiomatic way." (owner, line 1105). Every element reachable from every view is an early form of September's "at least two ways to do anything".
- **Markdown for the Authored section only; badges for the rest.** Shown the fully rendered panel, the owner was undecided ("I haven't decided yet whether I prefer the new format or the old", line 1616), and then set the rule: "I really should have specified that "Detail Panel as a Markdown renderer" should primarily apply just to the **Authored Content** section of the Live Documentation. That is genuinely all I meant by that. You previously had these genuinely wonderful, terse styles for the symbols as badges... it was unbelievably easy for me to tell what "Archetype" a given file was because it had a nice terse stylistic badge at the top. All that said, the fact that I can now see the descriptions and summaries on the public symbols, I'll readily admit that I'm pleased to have that information! I feel like there must be some kind of happy medium which lets us do more classical markdown rendering for the Authored Contnent, and then really slick, smart, well-styled... Metadata and Generated Content sections." (owner, [2025-12-07.1.md](../../../ChatHistory/2025/12/2025-12-07.1.md), line 2002).
- **The owner's rules for links in the panel.** "The Generated Content portions of the file should always produce hyperlinks to other Live Documentation files... But MarkDown links in the Authored content section could point **anywhree**. Therefore, we need a ruleset: If a Markdown link in an Authored Content section points to another live documentation file's path, we can do our classic Detail Panel focus on the linked file. If a MarkDown link in an Authored Content section points to an external website, we can keep this as an anchor tag and open a browser tab to the external website. **If a MarkDown link in an Authored Content section points to a file inside the workspace but _outside_ the Live Documentation files, we must create a hyperlink using a configured code repository URL prefix (static site mode) or open the file in VS Code (server mode)**." (owner, [2025-12-07.1.md](../../../ChatHistory/2025/12/2025-12-07.1.md), line 2004). Earlier, of links into the chat record: "links between the Live Documentation and chat history should indeed fail -- we'll have to think later about how we want to deal with those particular links" (owner, line 1789). That later thinking is the bearings' question 8, still open.
- **Colour in the panel.** "Would be nice if we could guarantee blue on top line, pink on bottom line for Dependencies section" (owner, line 2266), and badges for public symbols in place of "pure text styling and simple spaces in between them" (line 2265).
- **The owner caught a false "working".** After the agent reported the `<code>` tags fixed, the owner: "I don't see `<code>` styling inside them on several still (and this was true while I watched you with the playwright browser)."
