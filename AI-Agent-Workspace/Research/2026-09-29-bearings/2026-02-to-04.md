# February to April 2026: the last months of the Copilot era

_One of seven reports written on 2026-09-29 from [the brief](brief.md). It covers the 23 transcripts under `ChatHistory/2026/02/`, `03/` and `04/`. It records what the chat record and the repository showed on that date and decides nothing. Anything the record decided is written here as dated history or as an open question._

## The story of the slice

The slice has three movements, and the owner's mood rises through them until the last day.

**February: truth and subtraction.** The month opens with the owner catching the agent declaring benchmark failures expected and moving on: "Copilot has an incredibly strong tendency to make an assertion that failures are "predicted" or "expected" by fiat, and then flip some settings to sweep those under the rug. Copilot's future self sees this textual assertion of expectedness by fiat, believes it, and perpetuates the falsehood further." (2026-02-03, [2026-02-03.1.md](../../ChatHistory/2026/02/2026-02-03.1.md), line 279). A fixture built from the real libuv repository had 1,206 expected edges and none inferred, and had been set aside in a "stress mode" (the agent's finding, same file, line 307). The same day: "Every mess is our mess... It is only us in this repo." (line 1493), and a devcontainer was built so that the compiler indexers would run the same way every time (line 1860). From 02-15 the owner turned a lint into a method. Every exported symbol had to carry a JSDoc comment, written only after finding out why the code existed, because "the method documentation phase is the point at which I must answer the question: "Can I justify this code?", with an answer, all too often of, "no, I can't"." (2026-02-15, [2026-02-15.1.md](../../ChatHistory/2026/02/2026-02-15.1.md), line 756). What could not be justified went: the LLM bridge and telemetry on 02-17 (commits `7befc770`, `15c708eb`), the diagnostics subsystem the project had been founded on, 38 files and 7,328 lines, on 02-18 (commit `6348820c`), code that assumed the MDMD convention and the Spec-Kit scaffolding on 02-23 (commits `e50c0047`, `36051446`).

**24 February to 11 March: what is this thing?** With the code lighter, the owner stopped and asked what the product is, in a chat that ran from 02-24 to 03-01 ([2026-02-24.1.md](../../ChatHistory/2026/02/2026-02-24.1.md), line 2973). Is it a report generator (line 1800)? Does anyone fill in the authored sections (line 1844)? Is the server needed at all (line 1327)? They defended the force graph when the agent proposed "retiring it" (lines 2496 and 2511), named three real things they wanted to use the tool for (lines 2735 and 2977), and had every prompt they had ever written mined for use cases. What they found constant: "The only single consistent throughline through the entire development is that we can-and-should reverse polyglot code into a common MarkDown convention so that we can reason about a workspace in numerous ways with ease." (line 2739). The server was retired for a static site (commit `9a6ded52`, 2026-03-10) and a test that the same program in eight languages yields the same shape landed (commit `0e6e1564`, 2026-03-11).

**17 March to 1 April: the Membrane Map.** A rework of the Circuit Board on 03-17 led the owner to ask "Why are the circuit board and the local map separate?" ([2026-03-17.1.md](../../ChatHistory/2026/03/2026-03-17.1.md), line 2453). On 03-22 a misreading of that view by the owner ("I'm embarrassed to say...", [2026-03-22.1.md](../../ChatHistory/2026/03/2026-03-22.1.md), line 242) became the idea of parent folders "surrounding-like-a-membrane" (the owner's word, same line), and the agent made it the view's name (line 703): "Membrane Map. I _love_ that name." (line 710). "I am as excited about this endeavor as I have been about anything in this project." (line 1062). Eight working days followed in which the owner looked at screenshots side by side with the Local Map and said what was wrong, the agent changed it, and a commit landed nearly every day. The first Playwright suite arrived on 03-30, each test made from a fault the owner had named, and the Membrane Map became the first view a visitor sees on 03-31 (commit `d6d1471f`).

**The last day.** On 2026-04-01 the agent built arcs between folders on hover. The owner looked: "By eye, this doesn't appear to look right... I just see a bundle of connectors laying in an arc over each directory I hover over." ([2026-04-01.1.md](../../ChatHistory/2026/04/2026-04-01.1.md), line 1786). Asked what had been planned, the agent found that the same approach had been analysed and rejected two days before (line 1918). The owner: "(Facepalm) Frankly, that's my fault for not being more cognizant about the process. I've let this go on autopilot just a little too much." and "The issue that occurred today is plausibly a result of a lack of continuity of vision and a leakage of stale ideas (or a failure to clean old ideas) from the stateful docs." (lines 1922 and 1924). The work was reverted, one dimming bug was fixed, and the owner's last word in the record is `/commitPrep` (line 2330). The last commit of the era is `ae216cb5`, dated 2026-04-02. Nothing in the record says goodbye, names a pause, or speaks of waiting for better models.

## Good questions

### 1. What should cross a folder's boundary before anything is pinned?

- **Why it matters.** It is the design question the Copilot era stopped on, and it is the first thing September's look at the Membrane Map found missing: "nothing says what crosses a subfolder's boundary beyond the counts on its badge" ([membrane-map.mdmd.md](../../../.mdmd/layer-3/membrane-map.mdmd.md), line 172). The next work on the view walks straight into it.
- **Evidence.** Arcs between folders were built and switched off on 2026-03-23 (the agent's account, [2026-04-01.1.md](../../ChatHistory/2026/04/2026-04-01.1.md), line 1900), analysed and rejected on 03-30 ([the execution plan](../../Notes/membrane-map-execution-plan.md), line 179) after the owner's doubts ("aren't we getting odd wide spanning of directories?... Should it only occur on hover? (won't that cause a re-render with elements moving into place?)", [2026-03-30.1.md](../../ChatHistory/2026/03/2026-03-30.1.md), line 843), built again on 04-01 and reverted. What was adopted on 03-30 was a crumb bar and an `Explore` button on a folder's tile, of which the owner said "It's slick!" (same file, line 2429); both are in the code today ([browse-renderer.ts](../../../packages/explorer/src/client/views/membraneView/browse-renderer.ts), line 284). The agent's own proposal after the failure was "boundary ports or edge badges on the hovered membrane instead of long free arcs" ([2026-04-01.1.md](../../ChatHistory/2026/04/2026-04-01.1.md), line 1837), which is close to what the September probes reached, one wall pin per neighbouring folder with a count ([ideas.md](../../Memory/ideas.md), line 33). Yet the current design doc still says of the arcs "Re-enable when hover-only or progressive-disclosure rendering is implemented" ([membrane-map.mdmd.md](../../../.mdmd/layer-3/membrane-map.mdmd.md), line 135), the switched-off block is still in the controller ([index.ts](../../../packages/explorer/src/client/views/membraneView/index.ts), line 704), and the doc names neither the crumb bar nor the button. The trap that caught the agent on 04-01 is still set.
- **Who can answer.** The owner, by eye, on a build. The record supplies the constraints a design must meet: no movement on hover, something a finger can do, no line to a target that is off the screen, fewer clicks from a folder's count to what it counts.

### 3. Is namespace mode for C# the next growth of the doc format?

- **Why it matters.** It is the one feature in the slice the owner tied to their own work: "all of the places I currently intent to actually _run_ this software and apply its outputs for genuine real-world benefit are.... C#." ([2026-03-22.1.md](../../ChatHistory/2026/03/2026-03-22.1.md), line 788). In C# a namespace can span folders and one file can declare types in several (the agent's account, same file, lines 726 and 727), so a map that wraps folders may wrap the wrong thing in the estate the tool is meant for.
- **Evidence.** The owner on two hierarchies: "I don't hate that I'd need to toggle back and forth between a directory-based Membrane Map and a Namespace-based Membrane Map. Both seem valid to me." (same file, line 983), and "I suspect that I would benefit immensely from this visualization personally in my own work" (line 1062). It was put off to a second commit on 03-23 ([2026-03-23.1.md](../../ChatHistory/2026/03/2026-03-23.1.md), line 823) and never built: all nine steps are unchecked in [the execution plan](../../Notes/membrane-map-execution-plan.md), lines 440 to 448. Since September the C# adapter knows each type's qualified name and "no view reads it yet" ([polyglot-adapters.mdmd.md](../../../.mdmd/layer-3/polyglot-adapters.mdmd.md), line 64), while the Membrane Map's doc still says no adapter records it ([membrane-map.mdmd.md](../../../.mdmd/layer-3/membrane-map.mdmd.md), line 113). A C# Live Doc today names no namespace and the graph index has no field for one, so under the rule that markdown is canonical the doc format would have to grow first. The same passage holds a second gap: nested public types ("classes in classes, each with public symbols", line 786).
- **Who can answer.** The owner, on whether it still matters and when. The code, on what the adapter already has.
