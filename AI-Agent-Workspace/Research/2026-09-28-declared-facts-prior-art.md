## Grammars: what existing formats let a person declare, and where the declaration lives

Survey date: 2026-09-28. Every claim below cites the page it was read from, with the version or date the page states. Where the primary text could not be reached, the section says so and "Not found" records what was tried. Nothing here decides anything; it records what exists.

### 1. "What can be declared" about a system and a connection

#### C4 model and the Structurizr DSL

The C4 model names five abstractions: person, software system, container ("applications and data stores"), component, and code ([c4model.com/abstractions](https://c4model.com/abstractions)). It calls itself "Notation independent" and "Tooling independent", with core diagrams "system context, containers, components, and code" and supplementary "system landscape, dynamic, and deployment" ([c4model.com](https://c4model.com/)). The site carries no version number. A container is "an application or a data store. For example, a server-side web application, a client-side single-page application, a desktop application, a mobile app, a database schema, a folder on a file system, an Amazon Web Services S3 bucket, etc." ([container diagram](https://c4model.com/diagrams/container)). Its notation rules fix what an element and a line must carry ([notation](https://c4model.com/diagrams/notation)):

| On                      | Rule (quoted)                                                                                                                                 |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| element                 | "The type of every element should be explicitly specified (e.g. Person, Software System, Container or Component)."                            |
| element                 | "Every element should have a short description, to provide an 'at a glance' view of key responsibilities."                                    |
| container, component    | "Every container and component should have a technology explicitly specified."                                                                |
| line                    | "Every line should represent a unidirectional relationship."                                                                                  |
| line                    | "Every line should be labelled, the label being consistent with the direction and intent of the relationship (e.g. dependency or data flow)." |
| line between containers | "should have a technology/protocol explicitly labelled."                                                                                      |

Deployment is a separate diagram: it shows "how instances of software systems and/or containers in the static model are deployed on to the infrastructure within a given deployment environment", and a "deployment node represents where an instance of a software system/container is running" ([deployment diagram](https://c4model.com/diagrams/deployment)).

The Structurizr DSL is the textual grammar for C4 ([language reference](https://docs.structurizr.com/dsl/language), no version stated on the page). The `workspace` is "the top level language construct, and the wrapper for the model and views". What an element or relationship may carry:

| Construct | Declared fields (from the grammar) |
| --- | --- |
| `person`, `softwareSystem` | name, description, tags; children `description`, `tags`, `url`, `properties`, `perspectives`, relationships; software systems also `!docs`, `!adrs`, `group`, `container` |
| `container`, `component` | as above plus `technology` |
| `group <name>` | "a way to define a named grouping of elements, which will be rendered as a boundary around those elements. Groups can be nested." A component may instead state `group "Group Name"` inside itself |
| `A -> B [description] [technology] [tags]` | unidirectional; children `tags`, `url`, `properties`, `perspectives` |
| `properties { <name> <value> }` | free name/value pairs on elements, relationships and views |
| `perspectives { <name> <description> [value] }` | named perspectives with description, value and url, on elements or relationships |
| `deploymentEnvironment <name>` | contains `group`, `deploymentGroup`, `deploymentNode`, relationships |
| `deploymentNode <name> [description] [technology] [tags] [instances]` | nests deployment nodes, `infrastructureNode` ("load balancers, firewalls, DNS services, etc."), `softwareSystemInstance`, `containerInstance` (each with `healthCheck`) |
| `deploymentGroup <name>` | "Restricts the scope of relationship replication between instances" |
| `!docs <path>`, `!adrs <path> [type]` | Markdown or AsciiDoc attached to the workspace, a software system or a container; path "must be a relative path, located within the same directory as the parent file, or a subdirectory of it"; files imported "alphabetically according to the filename" ([docs](https://docs.structurizr.com/dsl/docs), [adrs](https://docs.structurizr.com/dsl/adrs)); ADR formats `adrtools`, `madr`, `log4brains` |
| `!include <file\|directory\|url>`, `workspace extends <file\|url>` | composition of DSL from other files |
| `views { ... autoLayout [tb\|bt\|lr\|rl] ... }` | views are declared apart from the model; styles, themes, terminology live here |

Default tags are fixed per type (`Element`, `Person`, `Software System`, `Container`, `Component`, `Relationship`, `Infrastructure Node`); user tags and `properties` are open.

#### ArchiMate 3.2 (The Open Group)

The specification is document C226, published 19 October 2022, ISBN 1-957866-02-4 ([publications.opengroup.org/c226](https://publications.opengroup.org/c226)). Its HTML text at pubs.opengroup.org redirects to an Open Group login (see Not found). The open primary sources used are The Open Group's reference card N221 (copyright 2022, [n221p.pdf](https://www.opengroup.org/sites/default/files/docs/downloads/n221p.pdf)) and the Model Exchange File Format schemas.

Element groups on the card: Motivation elements, Strategy layer, Business layer, Application layer, Technology layer (including physical elements Equipment, Facility, Distribution Network, Material), Implementation and Migration layer, and two Composite elements. Definitions that matter here (all quoted from N221):

| Concept               | Definition                                                                                                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Serving               | "Represents that an element provides its functionality to another element."                                                                                      |
| Composition           | "Represents that an element consists of one or more other concepts."                                                                                             |
| Aggregation           | "Represents that an element combines one or more other concepts."                                                                                                |
| Assignment            | "Represents the allocation of responsibility, performance of behavior, storage, or execution."                                                                   |
| Realization           | "Represents that an element plays a critical role in the creation, achievement, sustenance, or operation of a more abstract element."                            |
| Access                | "Represents the ability of behavior and active structure elements to observe or act upon passive structure elements."                                            |
| Flow                  | "Represents transfer from one element to another."                                                                                                               |
| Triggering            | "Represents a temporal or causal relationship between elements."                                                                                                 |
| Association           | "Represents an unspecified relationship, or one that is not represented by another ArchiMate relationship."                                                      |
| Junction              | "Used to connect relationships of the same type."                                                                                                                |
| Grouping              | "The grouping element aggregates or composes concepts that belong together based on some common characteristic."                                                 |
| Location              | "A location represents a conceptual or physical place or position where concepts are located (e.g., structure elements) or performed (e.g., behavior elements)." |
| Node                  | "Represents a computational or physical resource that hosts, manipulates, or interacts with other computational or physical resources."                          |
| Application Interface | "Represents a point of access where application services are made available to a user, another application component, or a node."                                |
| Technology Interface  | "Represents a point of access where technology services offered by a technology internal active structure element can be accessed."                              |
| Path                  | "Represents a link between two or more technology internal active structure elements, through which these elements can exchange data, energy, or material."      |

Layered Viewpoint. The specification text was not reachable; a vendor guide reproduces it and attributes it to ArchiMate 3.0.1 (secondary source, [Visual Paradigm user guide](https://www.visual-paradigm.com/support/documents/vpuserguide/4455/4456/86488_layeredviewp.html)): "There are two categories of layers, namely dedicated layers and service layers." "Each dedicated layer exposes, by means of the 'realization' relationship, a layer of services, which are further on 'serving' the next dedicated layer." "The order, number, or nature of these layers are not fixed." Serving is therefore the upward relationship between a service layer and the layer that uses it; the drawn order of layers is a convention of the viewpoint, not a rule of the language.

Properties. The exchange format's model schema ([archimate3_Model.xsd](https://www.opengroup.org/xsd/archimate/3.1/archimate3_Model.xsd)) has a root `model` ("a container for the elements, relationships, diagrams and organizations of the model") with `elements`, `relationships`, `organizations` (folder `item`s), `propertyDefinitions` and optional `metadata`; any element or relationship carries `properties`, each `property` pointing at a `propertyDefinitionRef` and holding a language-tagged `value`. Element types are an `xsi:type` enumeration (BusinessActor, ApplicationComponent, Node, Grouping, Location and the rest); relationship types are Composition, Aggregation, Assignment, Realization, Serving, Access, Influence, Triggering, Flow, Specialization, Association, plus AndJunction and OrJunction. So the vocabulary is fixed and properties are open, defined once per model and referenced by id.

#### FINOS CALM (Common Architecture Language Model)

CALM is "an open-source FINOS specification for defining software architectures in a standardized, version-controlled, machine-readable format" ([calm.finos.org](https://calm.finos.org/)); "By capturing architecture as code, CALM enables a consistent, version-controlled approach that aligns design intent with implementation" ([what is CALM](https://calm.finos.org/introduction/what-is-calm/)). Releases in the repository: 1.0-rc1, 1.0-rc2, 1.0, 1.1, 1.2 ([calm/release](https://github.com/finos/architecture-as-code/tree/main/calm/release)). Facts below are from the 1.2 schema (`$id` `https://calm.finos.org/release/1.2/meta/core.json`, [core.json](https://raw.githubusercontent.com/finos/architecture-as-code/main/calm/release/1.2/meta/core.json)) and the concept pages.

| Part                | What it declares                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| node                | required `unique-id`, `node-type`, `name`, `description`; optional `interfaces`, `controls`, `metadata`, `details` (`detailed-architecture`, `required-pattern`), `data-classification`, `run-as` ([nodes](https://calm.finos.org/core-concepts/nodes/))                                                                                                                                                                                                                                                                                                                                                                                              |
| `node-type`         | enum `actor`, `ecosystem`, `system`, `service`, `database`, `network`, `ldap`, `webclient`, `data-asset`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| relationship        | required `unique-id`, `relationship-type`; optional `description`, `protocol`, `metadata`, `controls`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `relationship-type` | one of `interacts` (actor + nodes), `connects` (source and destination, each a node plus interface ids), `deployed-in` (container + nodes), `composed-of` (container + nodes), `options` (decision objects)                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `protocol`          | enum `HTTP`, `HTTPS`, `FTP`, `SFTP`, `JDBC`, `WebSocket`, `SocketIO`, `LDAP`, `AMQP`, `TLS`, `mTLS`, `TCP`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| interface           | "a component that specifies how a node exposes its functionality to other nodes"; documented types `host-port-interface`, `hostname-interface`, `path-interface`, `oauth2-audience-interface`, `url-interface`, `rate-limit-interface`, `container-image-interface`, `port-interface` ([interfaces](https://calm.finos.org/core-concepts/interfaces/)); in the 1.2 schema an `interface-definition` has `unique-id`, `definition-url` ("URI of the external schema this interface configuration conforms to") and `config` ([interface.json](https://raw.githubusercontent.com/finos/architecture-as-code/main/calm/release/1.2/meta/interface.json)) |
| control             | "Controls model requirements for domains. For example, a security domain contains a series of control requirements."; a requirement "lays out what the control is and how it is expected to be enforced", a configuration is "the implementation of the requirement, how the requirement is fulfilled" ([controls](https://calm.finos.org/core-concepts/controls/)); each has `requirement-url` and a `config-url` or inline `config` ([control.json](https://raw.githubusercontent.com/finos/architecture-as-code/main/calm/release/1.0/meta/control.json))                                                                                          |
| metadata            | "Metadata is an arbitrary collection of objects that can be attached to nodes, relationships, or the entire architecture."; "Metadata objects can contain any properties" ([metadata](https://calm.finos.org/core-concepts/metadata/))                                                                                                                                                                                                                                                                                                                                                                                                                |
| architecture root   | `nodes`, `relationships`, `metadata`, `controls`, `flows`, `adrs` ("External links to ADRs (Architecture Decision Records) or similar documents ... These can be URLs or references to internal documentation.")                                                                                                                                                                                                                                                                                                                                                                                                                                      |

The relationship page describes the four core types: `interacts` "Defines an interaction between nodes, often representing a direct communication or service call."; `connects` "Illustrates a connection between interfaces, such as a network link or API call."; `deployed-in` "Indicates deployment relationships, showing where a node is hosted or run."; `composed-of` "Describes hierarchical relationships, showing how one node is composed of other sub-nodes." Interfaces are "not mandatory for defining a relationship between nodes but provide additional detail" ([relationships](https://calm.finos.org/core-concepts/relationships/)).

Patterns versus architectures: "Patterns describe architecture blueprints. Instead of listing a fixed set of components, a pattern prescribes: Which nodes (e.g., services, systems, databases) must exist. Which relationships connect those nodes." A pattern is JSON Schema (using `const`, `prefixItems`, `minItems`, `anyOf`); `calm generate` produces "a concrete architecture that conforms to the pattern's constraints" and `calm validate` "checks whether the target architecture has the required nodes/relationships and respects the pattern's constraints" ([patterns](https://calm.finos.org/core-concepts/patterns/)). The concept index also lists Standards, Flows, Timelines, Decorators ("Attach supplementary information like deployments, security context...") and Widgets ([core concepts](https://calm.finos.org/core-concepts/)).

#### Backstage software catalog

Nine entity kinds: Component, Template, API, Group, User, Resource, System, Domain, Location ([descriptor format](https://backstage.io/docs/features/software-catalog/descriptor-format)). Component requires `type`, `lifecycle`, `owner` and may state `system`, `subcomponentOf`, `providesApis`, `consumesApis`, `dependsOn`, `dependencyOf`; System requires `owner` (optional `domain`, `type`); Domain requires `owner` (optional `subdomainOf`). Common metadata: `name` (required), `namespace`, `title`, `description`, `labels`, `annotations`, `tags`, `links` ("A list of external hyperlinks related to the entity").

The three open fields are distinguished in the text:

| Field                  | Stated difference                                                                                                                                                                                                                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `metadata.labels`      | "optional key/value pairs of that are attached to the entity, and their use is identical to Kubernetes object labels"; for "references to other entities, and for information that is in one way or another classifying for the current entity"; key name part up to 63 characters; values follow entity-name rules |
| `metadata.annotations` | "An object with arbitrary non-identifying metadata attached to the entity, identical in use to Kubernetes object annotations"; used "mainly, but not limited, to reference into external systems"; values "can be of any length, but are limited to being strings"                                                  |
| `metadata.tags`        | "A list of single-valued strings, for example to classify catalog entities in various ways. This is different to the labels in metadata, as labels are key-value pairs."; each tag from `[a-z0-9:+#]` with hyphens, at most 63 characters                                                                           |

Relations are fixed pairs ([well-known relations](https://backstage.io/docs/features/software-catalog/well-known-relations)): `ownedBy`/`ownerOf` ("the owner is usually an organizational entity (User or Group), and the other entity can be anything"); `providesApi`/`apiProvidedBy` ("a component exposes an API - meaning that it hosts callable endpoints from which you can consume that API"); `consumesApi`/`apiConsumedBy` ("depends on endpoints of the API"); `dependsOn`/`dependencyOf` ("a general expression of being in need of that other entity for an entity to function"); `parentOf`/`childOf`; `memberOf`/`hasMember`; `partOf`/`hasPart` ("a component belongs to a larger component; a component, API or resource belongs to a system; that a system is grouped under a domain; or that a domain belongs to a larger domain").

#### SPDX 3.0.1 relationship types

A closed vocabulary of about sixty `from`/`to` types, several scoped by a lifecycle period ([RelationshipType](https://spdx.github.io/spdx-spec/v3.0.1/model/Core/Vocabularies/RelationshipType/)). Ones that overlap this design: `contains`, `dependsOn` ("during a LifecycleScopeType period"), `hasOptionalDependency`, `hasProvidedDependency` ("dependency is not in the distributed artifact"), `hasDynamicLink`, `hasStaticLink`, `configures` ("The from Element is a configuration applied to each to Element"), `generates`, `hasInput`, `hasOutput`, `hasHost`, `usesTool`, `hasDocumentation`, `hasTest`, `describes`, and `other` for anything outside the list.

#### SysML v2 ports and interfaces

OMG SysML 2.0 Part 1: Language Specification, formal/2026-03-02, March 2026 ([PDF](https://www.omg.org/spec/SysML/2.0/Language/PDF); the [specification page](https://www.omg.org/spec/SysML/2.0/) lists it as formal). Clause 7.12.1: "A port definition is a kind of occurrence definition (see 7.9) that defines a connection point to enable interactions between occurrences (most commonly parts)." "A port usage may be connected to one or more other port usages (see 7.14). Such connections enable interactions between the occurrences that own the ports. The features of the port usages ... specify what can be exchanged in such interactions." A port feature "may be directed, with one of the directions in, out, or inout". Clause 7.12.3: every port definition implies a conjugated one in which "in and out are reversed". Clause 7.14.1: "An interface definition is a kind of connection definition (see 7.13) whose ends are restricted to be port definitions (see 7.12)." "An interface is simply a connection all of whose ends are ports." Abstract syntax 8.3.12.5: "A PortDefinition defines a point at which external entities can connect to and interact with a system or part of a system." 8.3.14.2: "An InterfaceDefinition is a ConnectionDefinition all of whose ends are PortUsages".

The textual form, from 7.12.2 and 7.14.2 of the same document:

```
port def FuelingPort { attribute flowRate : Real; out fuelOut : Fuel; in fuelReturn : Fuel; }
part def FuelTank { port fuelOutPort : FuelingPort; }
interface def FuelingInterface { end fuelOutPort : FuelingPort; end fuelInPort : ~FuelingPort; }
interface fuelLine : FuelingInterface connect fuelTank.fuelingPort to engine.fuelingPort;
```

The release repository's training example writes the same shape with role binding: `interface : FuelInterface connect supplierPort ::> tankAssy.fuelTankPort to consumerPort ::> eng.engineFuelPort` ([Interface Example.sysml](https://raw.githubusercontent.com/Systems-Modeling/SysML-v2-Release/master/sysml/src/training/11.%20Interfaces/Interface%20Example.sysml)). So a "door" is a typed port with directed items, a definition is reused by many usages, and the wire is itself a typed thing whose ends must be ports.

#### UML stereotypes and tagged values

UML 2.5, formal/2015-03-01, March 2015 ([PDF](https://www.omg.org/spec/UML/2.5/PDF)); the current 2.5.1 is formal/17-12-05, December 2017 ([About UML 2.5.1](https://www.omg.org/spec/UML/2.5.1/About-UML)); the 2.5.1 PDF exceeded the fetch limit, so quotes are from 2.5. Clause 12.3.3.1: "A Profile is a restricted form of metamodel that can be used to extend UML, as described below. The primary extension construct is the Stereotype." Clause 12.3.3.4: "A Stereotype defines an extension for one or more metaclasses, and enables the use of specific terminology or notation in place of, or in addition to, the ones used for the extended metaclasses." Same clause: stereotype Properties "have traditionally been referred to as Tag Definitions. When a Stereotype is applied to a model element, the values of the Properties have traditionally been referred to as tagged values." Clause 12.3.3.3: "Stereotypes that are public members of a Profile may be applied to applicable model elements in Packages to which the Profile has been applied." Clause 12.4.9.1: "A stereotype defines how an existing metaclass may be extended". So the open key-value annotation is typed twice over: keys are declared in a profile, and the profile names which metaclasses may carry them.

#### Kubernetes labels versus annotations

Labels: "Labels are key/value pairs that are attached to objects such as Pods. Labels are intended to be used to specify identifying attributes of objects that are meaningful and relevant to users, but do not directly imply semantics to the core system." "Labels can be used to organize and to select subsets of objects." "Non-identifying information should be recorded using annotations." Key name segment "63 characters or less", optional prefix a DNS subdomain "not longer than 253 characters in total"; values "63 characters or less" ([labels](https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/)).

Annotations: "You can use Kubernetes annotations to attach arbitrary non-identifying metadata to objects." "In contrast, annotations are not used to identify and select objects. The metadata in an annotation can be small or large, structured or unstructured, and can include characters not permitted by labels." Listed uses include "Pointers to logging, monitoring, analytics, or audit repositories", "User or tool/system provenance information, such as URLs of related objects", and "Phone or pager numbers of persons responsible, or directory entries that specify where that information can be found, such as a team web site". "The total size of all annotations on a single object (keys and values combined) must not exceed 256 KiB." ([annotations](https://kubernetes.io/docs/concepts/overview/working-with-objects/annotations/)).

Recommended labels sit on top of the open system: "A common set of labels allows tools to work interoperably, describing objects in a common manner that all tools can understand." Keys: `app.kubernetes.io/name`, `instance`, `version`, `component` ("The component within the architecture"), `part-of` ("The name of a higher level application this one is part of"), `managed-by`; "These are recommended labels. They make it easier to manage applications but aren't required for any core tooling." ([common labels](https://kubernetes.io/docs/concepts/overview/working-with-objects/common-labels/)).

#### Azure and AWS resource tags

Azure ([tag resources](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/tag-resources), page dated 2025-09-15): "Each resource, resource group, and subscription can have a maximum of 50 tag name-value pairs." "The tag name has a limit of 512 characters and the tag value has a limit of 256 characters. For storage accounts, the tag name has a limit of 128 characters". Names cannot contain `< > % & \ ? /`. "Resources don't inherit the tags you apply to a resource group or a subscription." Tags cannot be applied to management groups. "Tags are stored as plain text. Do not add sensitive values to tags." Names are case-insensitive, values case-sensitive. Azure Policy is the enforcement layer: "Use Azure Policy to enforce tagging rules and conventions." Built-in definitions include "Require a tag on resources" (deny), "Require a tag and its value on resources" (deny), "Add a tag to resources" (modify), "Inherit a tag from the resource group" (modify) and "Inherit a tag from the subscription" (modify) ([tag policies](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/tag-policies), page dated 2025-09-15).

AWS ([tagging best practices](https://docs.aws.amazon.com/tag-editor/latest/userguide/best-practices-and-strats.html)): "Each resource can have a maximum of 50 user created tags."; keys beginning `aws:` are reserved and do not count; key "a minimum of 1 and a maximum of 128 Unicode characters"; value "a minimum of 0 and a maximum of 256 Unicode characters"; allowed characters "letters, numbers, spaces representable in UTF-8, and the following characters: _ . : / = + - @"; "Tag keys and values are case sensitive." Recommended naming: lowercase, hyphens, an organization prefix with a colon (`anycompany:cost-center`, `anycompany:environment-type`, `anycompany:application-id`). Enforcement through "tag policies using AWS Organizations". Groups: "With the AWS Resource Groups service, you can create groups of AWS resources based on one or more tags or portions of tags."

#### OpenTelemetry resource attributes

"A Resource is an immutable representation of the observed entity for which telemetry is being produced, expressed as Attributes." A process on Kubernetes "has a Pod name, it is in a namespace and possibly is part of a Deployment which also has a name. All three of these attributes can be included in the Resource." ([resource SDK](https://opentelemetry.io/docs/specs/otel/resource/sdk/)). Service attributes ([semconv service](https://opentelemetry.io/docs/specs/semconv/resource/service/)): `service.name` (Required) "Logical name of the service", which "MUST be the same for all instances of horizontally scaled services"; `service.version` (Recommended); `service.namespace` "A namespace for service.name", "for example the team name that owns a group of services"; `service.instance.id` "The string ID of the service instance"; "The triplet service.namespace,service.name,service.instance.id MUST be globally unique". Deployment ([deployment attributes](https://opentelemetry.io/docs/specs/semconv/registry/attributes/deployment/)): `deployment.environment.name` (Stable) "Name of the deployment environment (aka deployment tier)", well-known values `development`, `production`, `staging`, `test`; it "does not affect the uniqueness constraints defined through the service.namespace, service.name and service.instance.id resource attributes", so the same service in staging and production is the same service.

What such a template cannot state, read off the field lists above:

- Anything that is not an Azure resource type: `type` is "the namespace of the resource provider and the resource type", so an on-premises server, a partner's API or a SaaS tenant has no resource and no fields ([template syntax](https://learn.microsoft.com/en-us/azure/azure-resource-manager/templates/syntax)).
- Who owns a resource or what it is for: no typed field exists; the carriers are `tags` (free key-value, 50 per resource), `comments`, a `metadata` object that "Resource Manager ignores", or Bicep's `@description`.
- That one deployed thing calls another: `dependsOn` is deployment order and "isn't the right approach" for documenting interconnection; a role assignment states permission (principal, role, scope) and a private endpoint states a network path (subnet, remote resource, group id), and neither says a call is made, in which direction, or over which route.
- Which deployed instance corresponds to which folder of code: no field in the resource references read here links a site, a plan or an identity to a repository path.
- Environment as a first-class fact: the template carries it only as a tag value (the Azure tag page's own example is `Environment = Production`) or in the parameters that name the deployment.
- What the app reads from a connection string or app setting: the value is a string, may be hidden ("may contain sensitive information"), or is a Key Vault reference that resolves at run time; the address inside it is the only edge fact.

Group-level declaration exists in several forms: Structurizr `group` (nested, on the model, or set from inside an element), ArchiMate Grouping (an element that "aggregates or composes concepts"), Backstage System and Domain reached through `partOf`, CALM `composed-of` and `deployed-in` (a container plus a list of nodes), CycloneDX compositions (one `aggregate` for a list of assemblies or dependencies), Kubernetes selection by label (`part-of`), and cloud tags at resource-group or subscription level applied downward by policy because "Resources don't inherit the tags".

Layout: Structurizr and ArchiMate keep positions outside the model (a compiled JSON; a separate diagram schema); Threat Dragon keeps them inside the same file next to the facts; CALM, Backstage, CycloneDX, SPDX, Kubernetes, tags, OTel and IaC carry no positions at all; C4 and UML leave it to the tool.

Where the file lives: Backstage is the only grammar read here that says the declaration sits with the code in the code's own repository and names the file; Structurizr says the source is text the author stores where they choose, with docs and ADRs relative to it, and Lite reads it from a data directory; CALM says version-controlled and shows a registry, not a path; Threat Dragon and TMT store a model file locally or in a repository the tool is pointed at; Kubernetes and cloud tags live on the object itself; OTel attributes live in the running process; IaC declarations live in the template and describe only what the template deploys.

- Any typed link from an Azure resource to a source folder: the `Microsoft.Web/sites/sourcecontrols` child resource appears in the Key Vault page's example template but its reference page was not fetched.
- SysML v2 user-defined metadata (training folder "39. Metadata" exists; not read).

### The agent's judgement on the grammars

_Read by the agent on 2026-09-28, after the survey above. A judgement, not a decision; the owner's answer is the decision._

**What can be declared.** Every grammar that has survived in use pairs a small fixed vocabulary with an open key-value layer and keeps the two apart on purpose: Structurizr's types beside `properties` and `tags`, ArchiMate's types beside `propertyDefinitions`, CALM's node and relationship types beside `metadata`, Backstage's kinds and relations beside `labels`, `annotations` and `tags`, UML's metaclasses beside tagged values. Only cloud tags are open with nothing fixed, and they are then governed by policy. So the owner's lean towards "some kind of key-value tag annotation system" is the open half of what everyone does, and nobody does only that half. The fixed half the grammars agree on is short: a name and a description; a kind from a closed list; on an edge, its direction and its technology or protocol; a boundary or zone; a door; and, in two of them, a statement of what the document leaves out. The Live Docs already carry the name (the path), the kind where a manifest states it, the doors (the openings), the direction and the basis of an edge. What is left for a person is a kind for a folder without a manifest and for a piece with no folder at all (the Oracle database, a partner's API), the district (Structurizr's `group`, the threat model's trust boundary), the tunnel (an edge whose technology the C4 notation asks for on every line between containers), the edges no scan sees, and open properties. We would agree with that split and with keeping the fixed list that short.

The infrastructure-as-code lean checks out halfway, and the half that fails is instructive. A template states a resource's type, kind and sku, its identity, a role assignment (principal, role, scope), a private endpoint, app settings and connection strings, and diagnostic settings; it cannot state anything off the cloud, who owns a resource, what it is for, that one thing calls another (Microsoft's own page says `dependsOn` "isn't the right approach" for documenting interconnection), or which deployed instance is which folder of code. So the "difference between what can be inferred and what is salient" has a concrete shape: a template says what a resource may do, an identity with the Key Vault Secrets User role at a scope; the code and its configuration say what it does do, a call to that vault's address; and a person says what is true off the cloud and what things are for. The owner's example, an identity with only read permission into a resource, is a "may" edge and is statable in full from the template. That is a new edge kind for the docs, permission rather than call, and it is observed, not declared.

**Where it lives.** Backstage is the only grammar that says the declaration sits with the code, in the code's repository, under a named file, with a `Location` entity to aggregate many; Structurizr says the source is text kept where the author chooses, with docs and decision records relative to it, and keeps layout in a separate compiled file; CALM says version-controlled and shows a registry; the threat-modelling tools keep one model file per model with the drawing inside it. Read against this repository's shape, the Backstage answer is the one for a system: what a person declares about one system lives with that system's docs, in the configured root beside its code, so a snapshot of the system carries it. The Structurizr and CALM answer is the one for the estate: one file for the board that names its systems (folders or snapshots), its districts, its tunnels and the edges nothing scanned, kept wherever the board is kept, which for this repository would be the layer-3 place the owner guessed. Positions are outside both, per the tools section. We would agree with all three, and the choice that remains is only the names.

## Tool behaviour: who writes, what survives regeneration, what wins, what is left out

Surveyed 2026-09-28. Every claim below comes from a page fetched that day; the URL follows the claim. Vendor blog posts and community threads are labelled as such and were used only where no product documentation answered the question. Nothing here recommends or decides.

### 3. "Who writes it": a person by hand, or the tool writing positions back into a file a person also edits

#### Structurizr

The DSL is a text format a person writes: "The Structurizr DSL provides a way to define a software architecture model (based upon the C4 model) using a text-based domain specific language (DSL)" (https://docs.structurizr.com/dsl). A workspace is "the wrapper for: A software architecture model (elements and relationships). Views (that become rendered as diagrams)" plus documentation and decision records (https://docs.structurizr.com/workspaces).

Positions are kept out of the authored file on purpose: "Element x,y positions are not stored in the source of your workspace, such as your workspace definition when using the Structurizr DSL. This information is instead stored in a JSON version of your workspace, the schema for which can be found at on GitHub" (https://docs.structurizr.com/ui/diagrams/manual-layout).

In the Java model an `ElementView` holds `element`, `id`, `x` and `y`; `getX()` "Gets the horizontal position of the element when rendered", and a package-private `copyLayoutInformationFrom(ElementView source)` copies the coordinates (https://raw.githubusercontent.com/structurizr/java/master/structurizr-core/src/main/java/com/structurizr/view/ElementView.java). The public JSON schema repository (github.com/structurizr/json) returned 404 on 2026-09-28 for both blob and raw URLs, so the field list comes from the Java source.

Layout survives a regeneration by a merge step the docs spell out: "Parse your workspace source (DSL, Java, etc) and create an in-memory representation of your workspace", then "Load the current version of the workspace (e.g. load from Structurizr Lite, pull from the cloud service/an on-premises installation), extract the manual layout information, and merge it into the workspace created during step 1." Matching is by identity, not position: "For elements, the merging algorithm will attempt to match on element name, but will fallback to matching on the internal element ID to cater for situations where an element has been renamed." The failure mode is named: if "you rename an element and change the creation order... you may find that the element can't be matched, and manual layout information for that element will be lost" (https://docs.structurizr.com/ui/diagrams/manual-layout).

The CLI exposes the same step: "The `merge` command allows you to merge the layout information from one workspace into another", with `-workspace` (a "JSON/DSL file"), `-layout` ("The path or URL to the workspace JSON file that includes layout information"), optional `-view`, and `-output` (https://docs.structurizr.com/cli/merge). `push` merges by default: "-merge: Whether to merge layout information from the remote workspace (optional; defaults to `true`)" (https://docs.structurizr.com/cli/push).

What Structurizr Lite writes back when a person drags: "Structurizr Lite will write a JSON version of your workspace into your Structurizr Lite data directory to a file named `workspace.json` - this includes your workspace and the layout information for your diagrams." To publish hand-laid-out diagrams, "push the `workspace.json` file using the Structurizr CLI with `-merge false` to force your local diagram layout to be used"; for auto-laid-out ones, "just push the `workspace.dsl` file". Java users call `workspace.getViews().copyLayoutInformationFrom(liteWorkspace.getViews())` (https://docs.structurizr.com/lite/workflow).

"By default, auto-save is enabled, with a 5000ms interval"; "A value of `0` will disable auto-save"; with auto-sync, Lite "will pull a copy of your remote workspace upon startup and save it as `workspace.json`" and pushes it on shutdown (https://docs.structurizr.com/lite/usage). Lite "is only designed to be used by a single person, and has no collaboration features built-in"; concurrent use "may result in unexpected behaviour (workspace content corrupted, diagram layout lost, etc)" (https://docs.structurizr.com/lite).

The alternative is automatic layout, which removes the person from layout entirely. When it is enabled on a diagram, "This diagram is not editable because automatic layout is enabled" and "the diagram elements will be locked in place and cannot be moved"; Graphviz must be installed "if you are using the on-premises installation or Lite"; running auto-layout once by hand on a diagram without it enabled leaves elements "still movable manually after running auto-layout" (https://docs.structurizr.com/ui/diagrams/automatic-layout).

#### Structurizr for Java ComponentFinder

The one scanning path in Structurizr. The library "provides a facility to discover components in a Java codebase, via a combination of Apache Commons BCEL and JavaParser, using a pluggable and customisable set of matching and filtering rules"; fuller documentation is offered to Patreon supporters as early access (https://docs.structurizr.com/java/component).

The person supplies the container, the classes (for example a `.jar`), and strategies such as "Find all types that have been annotated with Spring's @Controller annotation" or "Find all types where the name ends Repository", each with a technology label; the finder returns components and the dependencies between them. What the docs list as still done by hand: "Exclude the CrashController", "Add inbound relationships to components from outside the web application container", "Add outbound relationships from components to elements outside", "Add component descriptions", "Add clickable hyperlinks from a component to the code" (https://docs.structurizr.com/java/component/introduction).

#### draw.io / diagrams.net

The picture and its data are one XML document. "Extras > Edit Diagram" shows the source, which begins and ends with `<mxGraphModel>` and contains "shapes, connectors, styles, and metadata in your diagram, and even which shape libraries are currently displayed" (https://www.drawio.com/docs/manual/advanced/diagram-source-edit/).

Any shape or connector can carry named properties through Edit Data: "Type the name in the text field that says _Enter Property Name_ and click _Add Property_", shown as "property names on the left, and values on the right" (https://www.drawio.com/doc/faq/shape-metadata).

The file can live in a repository: "Open your diagrams from, save and export them to your repositories on GitHub"; "Files on GitHub are limited to 1MB" (https://www.drawio.com/docs/integrations/github/). Positions are authored by dragging and persisted by the editor in the same file a person can also edit as XML.

#### Archi and coArchi

"Archi uses local file-based models and these can be shared and versioned using a Git-type workflow with the Collaboration plug-in" (https://www.archimatetool.com/faq/). The default is a "single .archimate XML file containing model and views" (https://github.com/archi-contribs/archi-grafico-plugin/wiki/GRAFICO-explained).

GRAFICO, which coArchi builds on, "is a way to persist an ArchiMate model in a bunch of XML files (one file per ArchiMate element or view)" so that "The resulting files can then be easily tracked and merge using almost any Version Control System (VCS) or Source Code Management (SCM) solutions like git" (https://github.com/archi-contribs/archi-grafico-plugin).

In a coArchi repository "Each file contains the description of a single object (element, relationship or view)"; on publish, "In case of conflicts (same concept changed and published by someone else) you'll see a windows helping you to fix them", and users are told not to use Git's own merge or pull requests (https://github.com/archimatetool/archi-modelrepository-plugin/wiki/Understand-the-Basics). coArchi2 is "a work in progress and there are some features that are not working or buggy" (https://github.com/archimatetool/archi-modelrepository-plugin2). Views, with their geometry, and model elements are versioned together as separate files.

#### IcePanel

A hosted model: "Organization > Team > Landscape > Version", with objects, connections, flows and share links under a version. A version is "a snapshot of a landscape's model"; `latest` is the live editable one, numbered versions are immutable, and every API path is version-scoped (https://developer.icepanel.io/core-concepts/overview). "Versions are static, and the diagrams and objects can't be edited or removed from your landscape"; versions are created by hand or weekly with "Auto version" (https://docs.icepanel.io/future-state-design/versioning).

Diagram and model are one store: "Adding an object to a diagram creates it in the model"; "You can think of diagrams as a visual representation of a model"; the delete key removes an object from the view only (https://docs.icepanel.io/core-features/diagramming). "Changing an object will update it everywhere it exists. This includes all diagrams, flows, and the model" (https://docs.icepanel.io/core-features/modelling).

Code is linked, not scanned: "Link your model objects to reality, such as code repos, branches, folders and files. When those links move, change names or get deleted, we'll notify you that the object may need to be updated in your IcePanel landscape" (https://docs.icepanel.io/integrations/code-repo-linking/azure-devops). Where diagram positions sit in the API is not stated in the overview.

#### Ilograph

A diagram is YAML with four top-level sections, "An array of resources (the resource tree)", perspectives, contexts and imports; there is no coordinate field. Layout is steered, not set: a `layout` object gives `compactness`, "A number from 0.1 to 1 indicating how compactly child resources are rendered", and `sizes`, where for `auto` "the layout engine automatically chooses on a per-perspective basis"; a perspective has an `orientation` of `leftToRight` or `topToBottom` (https://www.ilograph.com/docs/spec/).

#### D2, Mermaid, PlantUML

D2 has three engines: dagre, the default, "A fast, directed graph layout engine that produces layered/hierarchical layouts. Based on Graphviz's DOT algorithm"; ELK; and TALA, "a new layout engine designed specifically for software architecture diagrams". "Directions can only be set at a global level for all the layout engines except TALA" (https://d2lang.com/tour/layouts). Only TALA pins: "'top' and 'left' can be used to lock positions" and "'near' can be specified to be to another shape"; TALA "Has randomness. A small change to a label can cascade into an entirely different layout" (https://d2lang.com/tour/tala). Pins live in the source text, not in a side file.

Mermaid's syntax reference lists two algorithms, ELK and dagre, chosen with `layout:` in the diagram's metadata block ("You can specify the layout algorithm directly in the metadata section of your Mermaid diagram code"), for flowchart, state, class, entity relationship, requirement, use case and agentflow diagrams; no per-node position is documented (https://mermaid.js.org/intro/syntax-reference.html).

PlantUML: "PlantUML operates primarily as a generator, fabricating diagrams autonomously based on the input text", and "this convenience comes at a cost of limited control over the precise layout, a constraint when compared to tools that permit manual element positioning" (https://plantuml.com/faq).

#### Excalidraw

A file has `type`, `version`, `source`, `elements`, `appState` and `files`; each element carries `x`, `y`, `width`, `height` (https://docs.excalidraw.com/docs/codebase/json-schema). Arbitrary data rides on the element: "you can store `custom` data on each `element` in a `customData` object", typed `Record<string, any>` (https://docs.excalidraw.com/docs/@excalidraw/excalidraw/api/props/). Meaning and picture are one file; positions are authored by hand.

### 4. "How it is shared"

#### Structurizr sharing

Three visibilities. Private: "The workspace can be only accessed by signed in users who you have given access to using role-based access." Sharing link: "A sharing link can also be enabled/disabled for individual workspaces, which is a simple way to provide people with a read-only view of the diagrams and documentation in a workspace." Public: "The workspace is public on the web, and can be accessed by anybody without signing in" (https://docs.structurizr.com/cloud/workspace-visibility).

Four roles: owner; admin, "everything the owner can do, except deleting the workspace"; read/write, which "includes changing and saving the diagram layout, using the browser-based editor, plus uploading new versions of the workspace via the web API"; read-only, where "The API key/secret pair isn't accessible and diagrams are not editable" (https://docs.structurizr.com/cloud/role-based-access).

The on-premises installation is "a standalone version of Structurizr that can be run locally on your own infrastructure", a `.war` where by default "all data is stored on the local file system" (https://docs.structurizr.com/onpremises). It carries read/write and read-only roles, assignable by username, role name or a regular expression such as `^.*@example.com$`, or in the DSL with a `users { ... }` block (https://docs.structurizr.com/onpremises/role-based-access). A shared workspace is the whole workspace; nothing in these pages leaves parts out.

#### draw.io

Export formats: PNG, JPEG, WebP, SVG, GIF, PDF, HTML, XML, JSON, URL and .drawio. "You can choose to embed the diagram data in PNG, SVG, and PDF files so that they can be opened in the draw.io editor as the diagram", and "For a diagram that someone else might want to edit, use XML or one of the formats with _Include a copy of my diagram_ (PNG, SVG)" (https://www.drawio.com/doc/faq/export-diagram).

Publish as link: "The diagram data is embedded in the URL you just created" and "your diagram is not hosted anywhere"; the link is a static copy at publishing time; "This link is therefore always valid, and you can't revoke access to your diagram"; a "Selected Page" option limits the link to one page; "Very large diagrams may not be able to be loaded from a overly long URL" (https://www.drawio.com/docs/manual/export/publish-link/). Leaving parts out is by page selection or by editing a copy.

#### IcePanel sharing

A share link is "a read-only and up-to-date version of your design to be shared with a URL"; a link can be locked to a version so that "anyone who uses this link will always see the diagram exactly as it appears in this version"; "Only admins and editors in a landscape can create share links"; navigation can be restricted with "limit to this diagram"; "Password and SSO-protected links are only available on Growth and Isolation plans" (https://docs.icepanel.io/collaboration/sharing.md).

#### Backstage

"By default, Backstage endpoints are not protected, and all actions are available to anyone" (https://backstage.io/docs/permissions/overview). Per-entity read control exists as a permission: `catalog.entity.read` "is used to authorize actions that involve reading one or more entities from the catalog. If this permission is not authorized, it will appear that the entity does not exist in the catalog", in the frontend and in API responses (https://raw.githubusercontent.com/backstage/backstage/master/plugins/catalog-common/src/permissions.ts). Visibility is per entity only when an installation writes a policy; there is no in-entity flag.

#### OpenAPI: `x-internal` and Overlays

Extensions "are custom properties that start with `x-`" and "The extension value can be a primitive, an array, an object or `null`" (https://swagger.io/docs/specification/v3_0/openapi-extensions/, SmartBear's documentation of the specification; the specification's own clause could not be retrieved verbatim, see Not found).

Redocly's `remove-x-internal` decorator "Removes nodes that have a specific flag property. Nodes that don't have the flag property defined are not impacted"; the property name defaults to `x-internal` and is configurable with `internalFlagProperty`; it exists to "maintain them together but generate two sets of API docs from a single-source-of-truth", paired with `--remove-unused-components` (https://redocly.com/docs/cli/decorators/remove-x-internal). The guide bundles one root file twice, `internal@latest` untouched and `external@latest` with `remove-x-internal: on`, into two output files (https://redocly.com/docs/cli/guides/hide-apis).

The OpenAPI Initiative's Overlay Specification v1.0.0 (2024-10-17) generalises this. An Overlay "describes a set of changes to be applied or 'overlaid' onto an existing OpenAPI description", as an ordered list of Action Objects with a JSONPath `target`, an `update`, and `remove`, "A boolean value that indicates that the target object or array must be removed from the map or array it is contained in". Use cases "include updating descriptions, adding metadata to be consumed by another tool, or removing certain elements from an API description before sharing it with partners" (https://spec.openapis.org/overlay/v1.0.0.html). In both mechanisms the shared document does not say what was removed.

#### Terraform `sensitive`

"If you are outputting sensitive data such as a password or API key, use the `sensitive` argument to prevent Terraform from displaying the value in CLI output"; "Terraform stores the values of `sensitive` outputs in your state", and `terraform output -json` or `-raw` prints them in plain text (https://developer.hashicorp.com/terraform/language/values/outputs).

Plan output shows `~ password = (sensitive value)` and an output as `db_connect_string = <sensitive>`; "When you run Terraform commands with a local state file, Terraform stores the state as plain text, including variable values, even if you have flagged them as `sensitive`" (https://developer.hashicorp.com/terraform/tutorials/configuration-language/sensitive-variables). "Terraform still stores the values of sensitive variables in your state" (https://developer.hashicorp.com/terraform/language/values/variables). The redaction is in the rendering; the shared plan text shows a placeholder where a value was withheld.

#### CycloneDX

A BOM can declare its own incompleteness. `compositions[].aggregate` takes: `complete`, "The constituent parts are known and documented. The completeness of vulnerabilities expressed in a BOM may also be described"; `incomplete`, "The constituent parts are not known and undocumented"; `incomplete_first_party_only`, `incomplete_first_party_proprietary_only`, `incomplete_first_party_opensource_only`, `incomplete_third_party_only`, `incomplete_third_party_proprietary_only`, `incomplete_third_party_opensource_only`, each "Only ... components are known"; `unknown`, "The constituent parts are unknown"; `not_specified`, "The constituent parts completeness is not specified" (https://raw.githubusercontent.com/CycloneDX/specification/master/schema/bom-1.6.schema.json, version 1.6).

BOM-Link is a URN, `urn:cdx:serialNumber/version#bom-ref`, that lets one BOM "reference components, services, or vulnerabilities in BOMs from other systems or other BOMs" (https://cyclonedx.org/capabilities/bomlink/). Bom-ref values "SHOULD not start with the BOM-Link intro 'urn:cdx:'" (schema, same URL).

#### SBOM redaction guidance

CISA's draft 2025 Minimum Elements (published 2025-08-22, comments to 2025-10-03, https://www.cisa.gov/resources-tools/resources/2025-minimum-elements-software-bill-materials-sbom) says: "If an SBOM does not list all dependencies, the SBOM author must explicitly identify Known Unknowns"; "The default interpretation of the SBOM should be that the data is incomplete. The SBOM author should further distinguish between dependency information that is unknown to the SBOM author and that which is purposefully redacted. The SBOM author should have a process for recipients to ask about any redacted, security-related information. Organizations may consider an SBOM incomplete if essential dependencies are redacted. SBOM authors should indicate unknown or redacted components in a way that is distinguishable from unknown values for specific elements" (https://www.cisa.gov/sites/default/files/2025-08/2025_CISA_SBOM_Minimum_Elements.pdf, section "Known Unknowns (Major Update)").

A research paper, "Trustworthy and Confidential SBOM Exchange" (submitted 2025-09-16, revised 2026-03-12), proposes Petra so vendors can "compose and distribute redacted SBOM data using selective encryption" and consumers can "search redacted SBOMs for answers to specific security questions without revealing information they are not authorized to access" (https://arxiv.org/abs/2509.13217).

#### Microsoft Threat Modeling Tool

"Reports: Create HTML reports to share with others" via Report > Create Full Report; File offers "Share links (view and edit)" through OneDrive. Every element except a trust boundary has "Out of scope: If selected, the element is taken out of the threat-generation matrix (not recommended)" and "Reason for out of scope: Justification field to let users know why out of scope was selected" (https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-feature-overview, page dated 2017-08-17, last updated 2026-01-22). The exclusion stays in the model with its reason; the page does not say whether the report omits out-of-scope elements.

### 5. "What wins when a declaration contradicts a scan"

#### Discovered only, no override on the map

Azure Application Insights Application Map: "A map is produced by identifying the individual application components with their `roleName` or `name` property in recorded telemetry"; "Application map locates components by following HTTP dependency calls made between instrumented servers". The only override is upstream, in what is emitted: "This section provides examples to manually set or override cloud role names and change what appears on the application map", and "For current OpenTelemetry-based applications, set cloud role values with resource attributes".

Filters hide but do not add: "Node filters allow you to see only certain nodes in the application map and hide all other nodes"; "After a node or connector is removed from the view, a subsequent filter can't restore the item"; "The Copy link option encodes all current filter settings in the copied URL" (https://learn.microsoft.com/en-us/azure/azure-monitor/app/app-map, dated 2026-03-06). No adding, removing or moving of nodes or edges is described.

Datadog Service Map: "Nodes represent services exactly as instrumented in APM and match those in your Catalog"; "Edges represent aggregate calls from one service to another"; "New services or connections appear within moments of being instrumented and automatically age out if no corresponding traces are seen for 30 days"; grouping is by team or application (https://docs.datadoghq.com/tracing/services/services_map/). No manual edit of nodes or edges appears on that page. Declared facts live beside the map, not in it: Software Catalog definitions are YAML (`entity.datadog.yaml` or API) carrying owner, team, links, contacts, tier and lifecycle, while "with APM and USM data, you can automatically detect dependencies among components" (https://docs.datadoghq.com/software_catalog/service_definitions/).

Dynatrace Smartscape: "Smartscape Classic auto-discovery delivers a quick and efficient visualization of all the topological dependencies in your infrastructure, processes, and services" (https://docs.dynatrace.com/docs/discover-dynatrace/platform/smartscape). The built-in model "automatically detects more than a hundred entity types"; the extension point is "adding your own domain-related types and relationships" to "extend the built-in model" (https://docs.dynatrace.com/docs/extend-dynatrace/extend-topology).

Those additions are rules over data, not drawn edges: "Go to Settings > Topology model > Generic types", "Set Type name to a unique type name that will serve as the entity identifier", and "To extract a relationship between a given entity type and another entity type, we need to find a joined data stream" (https://docs.dynatrace.com/docs/extend-dynatrace/extend-topology/custom-topology). A GitHub project, "Smartscape Topology Builder", offers a GUI to "Draw edges between any two entities" but does so by feeding the engine through the Settings API, metric ingest or injected OTLP spans; its README says "Internal Dynatrace tooling. Not for distribution" and that edges take 5 to 15 minutes to appear (https://github.com/joshuadwood/smartscape-custom-topology). The pattern in all three: to change the map, change the evidence.

#### Declared only

Structurizr's model is the DSL a person wrote (Section 3), with the Java ComponentFinder as an opt-in scan whose gaps the person fills by hand. Archi's models are "local file-based" authored files. IcePanel's code links only "notify you that the object may need to be updated"; nothing is written into the model from code.

#### Hybrids

ServiceNow CMDB, Identification and Reconciliation Engine (IRE): identification rules "uniquely identify CIs based on CI attributes"; reconciliation rules "manage authorization and update priority between discovery sources" (https://www.servicenow.com/docs/r/servicenow-platform/configuration-management-database-cmdb/c_CMDBIdentifyandReconcile.html, Brazil release, updated 2026-09-10). Reconciliation is the "Process of reconciling CIs and CI attributes by allowing only designated authoritative data sources to write to the CMDB at the CI table and attribute level" (https://raw.githubusercontent.com/ServiceNow/ServiceNowDocs/australia/markdown/servicenow-platform/configuration-management-database-cmdb/c_CompsandProcessIDandReconcil.md).

"Static and dynamic reconciliation rules determine which discovery source is authorized to update which CI attributes", and "Data source rules prevent discovery sources from inserting new CIs for a specific class" while still trusting them for updates (https://raw.githubusercontent.com/ServiceNow/ServiceNowDocs/australia/markdown/servicenow-platform/configuration-management-database-cmdb/configuring-ire.md).

Staleness lets a lower source in: "Specify data refresh rules to determine if a CI is stale for a specific discovery source"; if the attributes named in the static rule were not updated by the source "within the specified Effective Duration" the CI is stale for that source and a lower-priority authorized source may update it; a duration of 0 (the default) makes it available immediately; "Data refresh rules have no impact when dynamic reconciliation rules are in effect" (https://raw.githubusercontent.com/ServiceNow/ServiceNowDocs/australia/markdown/servicenow-platform/configuration-management-database-cmdb/create-datasource-staleness-rule.md). "To help resolve conflicting attribute values, IRE uses timestamps" such as `last_discovered` (https://raw.githubusercontent.com/ServiceNow/ServiceNowDocs/australia/markdown/servicenow-platform/configuration-management-database-cmdb/ire.md).

A community article, not product documentation, gives the numbering: a lower number is a higher priority (ServiceNow at 100 over ServiceWatch at 200), and a lower-priority source's changes are "overridden in favor of the higher-priority source" and masked in the IRE response (https://www.servicenow.com/community/cmdb-articles/understanding-ire-reconciliation-rules/ta-p/3289239). The winner is chosen per attribute by a configured precedence, with age as the tie-breaker.

Backstage: an entity read from a location "gets stored verbatim"; "the processor might look at information in the `spec` field of the entity, and emit relations that correspond to those declarations"; "If relations are emitted, then they are put in a dedicated relations table to be picked up by the stitching process below"; stitching is "gathering all of the output from the previous steps and merging them into the final object which is what is visible from the catalog API" (https://backstage.io/docs/features/software-catalog/life-of-an-entity). The authored body is never rewritten; derived relations sit in a separate table and are merged at read time, so a declaration and a derivation coexist as different fields.

AWS Workload Discovery (formerly AWS Perspective): the discovery component "runs every 15 minutes as a container task", and a storage component "stores user preferences and saved architecture diagrams" through Amplify and S3 (https://raw.githubusercontent.com/aws-solutions/workload-discovery-on-aws/main/README.md). The changelog records "Export of diagrams to JSON" and "Export of diagrams to draw.io" in 2.1.0 (2023-09-21), a configurable discovery interval in 2.1.3 (2023-12-18), and "Export of diagrams to myApplications" and to SVG in 2.2.0 (2024-11-20) (https://raw.githubusercontent.com/aws-solutions/workload-discovery-on-aws/main/CHANGELOG.md).

The solution was discontinued on 2026-08-14 and the repository archived: "Workload Discovery on AWS is no longer available. We encourage customers to explore using Amazon CloudWatch Application Map and AWS DevOps Agent" (https://github.com/aws-solutions/workload-discovery-on-aws; the same notice replaces the implementation guide at https://docs.aws.amazon.com/solutions/latest/workload-discovery-on-aws/architecture-overview.html). What a saved diagram does when its resources change could not be verified (see Not found).

Multiplayer.app: on 2026-09-28 the system dashboard documentation page states the feature is no longer supported (https://www.multiplayer.app/docs/system-dashboard/). Earlier pages survive: release notes of 2025-01-10 describe platforms that "represent your actual software system, consisting of components... and their dependencies", with platform grouping and component filtering (https://www.multiplayer.app/docs/release-notes/release-notes-01-10-2025/); a blog post of 2024-11-26 says "auto-detected components and dependencies can be used to instantly generate your system map" (https://www.multiplayer.app/blog/no-more-whiteboards-multiplayer-auto-generates-architecture-diagrams/). Deletion is not honoured, hiding is: "create a layer named Deleted with the Visible checkbox unchecked" and assign shapes to it, otherwise a deleted component is treated as new and regenerated; the feature "must be used with Tailored Diagram templates and cannot be used with other types of diagrams" (https://www.cloudockit.com/auto-refreshed-diagrams/).

There's no opportunity to miss things, or add things that don't exist"; on change "Hava creates a new version and retains historical information"; exports are PDF, PNG, Visio, CSV and JSON (https://www.hava.io/features). The drift is announced, not resolved: "Note: Objects have changed outside of Terraform", and in refresh-only mode "This is a refresh-only plan, so Terraform will not take any actions to undo these"; the person then either applies the refresh to record reality in state or changes configuration and applies to restore it (https://developer.hashicorp.com/terraform/tutorials/state/resource-drift). CloudFormation drift detection: "A resource is considered to have drifted if any of its actual property values differ from the expected property values. This includes if the property or resource has been deleted"; expected values come from "the stack template and any values specified as template parameters". "CloudFormation only determines drift for property values that are explicitly set"; unsupported resource types get `NOT_CHECKED`; some values (Lambda code, IAM passwords) cannot be compared; equal-but-not-identical values (1024 MB versus 1 GB) are reported as drift; resolution is the person's, by updating resources or by import (https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-cfn-stack-drift.html). Detection changes nothing.

### What the tools say for the questions

Who owns layout: a person owns it in Structurizr (unless auto-layout is on), draw.io, Archi, IcePanel, Excalidraw, Cloudockit and Lucidscale; an engine owns it in Ilograph, D2 (except TALA pins), Mermaid, PlantUML, Hava and the three observability maps.

Where layout lives relative to meaning: two files in Structurizr (DSL for meaning, JSON for meaning plus x,y); one file in draw.io, Excalidraw, Archi's `.archimate` and Ilograph; one file per object in GRAFICO and coArchi; one hosted store in IcePanel; inside the source text for D2's TALA pins.

Structurizr is the only surveyed tool that carries layout across a regenerated model by an explicit merge with a documented matching rule (name, then ID) and a documented loss case. Cloudockit does the same for cloud diagrams by a per-shape unique ID, and refuses deletion in favour of hiding.

Who shows disagreement rather than choosing: Terraform ("Objects have changed outside of Terraform", refresh-only plans) and CloudFormation (drift statuses with expected versus actual per property) show the difference and act on nothing. Backstage keeps the authored `spec` verbatim and stores derived relations in a separate table, merged at read time, so both survive without a winner. Lattix keeps manual and extracted dependencies as different kinds.

Who chooses: ServiceNow, by a configured per-attribute precedence with a staleness clause, marking rejected updates. The observability maps and Hava do not admit a declaration at all: the map is the scan, and the only override is to change what is emitted or to edit an exported copy.

Sharing with parts left out: Structurizr and IcePanel share whole workspaces or diagrams, scoped by role, link, version or a single-diagram limit, and say nothing about omissions. Redocly's `remove-x-internal` and the OpenAPI Overlay `remove` action strip flagged or targeted nodes and leave no trace in the output. Terraform leaves a placeholder where a value was withheld. CycloneDX carries an explicit completeness enum (`compositions.aggregate`) and a cross-document link (BOM-Link). CISA's draft guidance asks that redacted and unknown be distinguishable and that a channel exist to ask about redactions. The Threat Modeling Tool records an out-of-scope flag with a reason in the model itself. draw.io's published link is a static, unrevokable copy of the selected page.

### The agent's judgement on tool behaviour

_Read by the agent on 2026-09-28, after the survey above. A judgement, not a decision; the owner's answer is the decision._

**Who writes it.** One tool in the field has a documented answer to a tool writing positions into something a person also edits, and the answer is that it does not: Structurizr keeps meaning in the authored DSL and layout in a JSON file the tool writes, and carries the layout across a regenerated model by matching elements on name and then on identity, with the loss case written down. Every tool that keeps meaning and picture in one file (draw.io, Archi, Excalidraw, IcePanel) has the tool own the whole file and the person edit through the tool. The engine-owned tools keep no positions at all. The Structurizr split is the one that fits this repository's rules: the generated region is the generator's, the authored region is the person's, and positions would be a third thing, written by the Explorer into a file of its own, keyed by the identity of the piece (a system's folder, or a declared system's name), so that regenerating the docs never touches them and moving a piece never touches the docs. We would agree with it; the choice it leaves is only whether that file is committed, which the field leaves to the author.

**How it is shared.** Sharing a whole workspace by role, link or version is the norm (Structurizr, IcePanel, draw.io's static link); leaving parts out exists only in API descriptions (Redocly's `remove-x-internal`, the OpenAPI Overlay) and in SBOMs (CycloneDX `compositions.aggregate`, CISA's Known Unknowns). The two camps differ in one thing: the API tools strip and leave no trace, the SBOM guidance says a recipient must be able to tell redacted from unknown. We would agree with the SBOM camp. The static bundle is already the draw.io kind of share, a copy that cannot be recalled; a trim at build time ("World Map only", "no Local Map", "no endpoints") should be stated in the bundle the way CycloneDX states completeness, and a piece with its endpoints withheld should say so rather than look like a piece with none. The Threat Modeling Tool's out-of-scope flag with a reason is the same idea per element, and an `internal` mark on an opening, the `x-internal` idea, is a declared fact the trim would respect.

**What wins.** The field splits three ways. The observability maps and Hava admit no declaration: the map is the scan, and to change it you change the evidence, which is the owner's "even better": fix the web.config. Structurizr, Archi and IcePanel admit no scan. Among the hybrids, ServiceNow chooses per attribute by a configured precedence with a staleness clause; Terraform, CloudFormation, Backstage and Lattix keep both sides and show the difference, or keep them as different kinds, and let nothing win silently. We would agree with the second group and not with ServiceNow's machinery: a declared edge carries `declared` as its basis beside `source`, `contract` and `configuration`, the scan's edge is never removed, and where the two name different targets the disagreement is drawn and reported as drift, which is the owner's nudge to clean up the configuration. Nothing needs a precedence table until someone asks for one.

"(reproduction)" marks a secondary page that quotes a specification this survey could not reach directly. Where a primary source could not be fetched, the section says so and the item is listed again under "Not found". This survey records what exists and decides nothing.

### A. Zooming between scales

**Shneiderman, 1996** (DRUM record of the technical report, https://drum.lib.umd.edu/handle/1903/5784).
- The Visual Information-Seeking Mantra: "Overview first, zoom and filter, then details-on-demand."
- The taxonomy crosses seven tasks (overview, zoom, filter, details-on-demand, relate, history, extract) with seven data types (1-, 2- and 3-dimensional, temporal, multi-dimensional, tree, network).
- The PDF behind the record is a scanned image, so the one-line task definitions are not quoted here.

**Furnas, 1986, generalized fisheye views** (CHI '86 paper, mirror at https://cspages.ucalgary.ca/~saul/581/exer.eps/4furnas86.pdf; record at https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/22627.22342).
- "In many contexts, humans often represent their own 'neighborhood' in great detail, yet only major landmarks further away."
- The problem stated: "Currently the most common viewing interface is simply a small window for looking into the structure, centered at some point." "As a result it is easy to get lost".
- "The fundamental motivation of a fisheye strategy is to provide a balance of local detail and global context."
- The formalism is a Degree of Interest function, "DOIfisheye (x|.=y) = API(x) - D(x,y)" (minus sign), where "the interest increases with a priori importance and decreases with distance".
- "A display of any desired size, n, can then be made by simply showing the n 'most interesting' points, as indicated by the DOI function."

**Pad++ and zoomable user interfaces.** Pad++ explores interfaces where "zooming is a fundamental part of the user's interaction with the computer (also known as multiscale interfaces)" (https://www.cs.umd.edu/hcil/pad++/; paper list at https://www.cs.umd.edu/hcil/pad++/papers/). From the 1996 JVLC paper:
- "The user controls where they look on this vast data surface by panning and zooming." (https://www.cs.umd.edu/hcil/pad++/papers/jvlc-96-pad/zoom-3.html)
- The reason for semantic zooming: "Instead of representing a page of text so small that it is unreadable, it might make more sense to present an abstraction of the text, perhaps just a title that is readable." (same page)
- Semantic zooming defined: objects "change not just their size but also their appearance when they are magnified"; "an object could appear as a point when small. As it grows, it could then in turn appear as a solid rectangle, then a labeled rectangle, then a page of text" (https://www.cs.umd.edu/hcil/pad++/papers/jvlc-96-pad/zoom-6.html).
- In the file-system demo, "both directories and files show their filenames as labels when the user is sufficiently close to be able to read them" (https://www.cs.umd.edu/hcil/pad++/papers/jvlc-96-pad/zoom-5.html).

**Bederson, 2011, "The promise of zoomable user interfaces"** (http://www.cs.umd.edu/~bederson/images/pubs_pdfs/2011_-_BIT_-_Promise_of_ZUIs.pdf). The paper "describes design guidelines, and offers a cautionary tale". The guidelines that bear on a zoom boundary:
- "Unless the data set is fundamentally spatial (e.g. maps), users probably do not want zooming as their primary interaction with the data."
- "Zooming works best when the objects can be recognised when they are zoomed out."
- Maintain aspect ratio: under semantic zooming "the small object must have the same aspect ratio", or "at least fit in the same box as the full object. Otherwise, nearby objects can end up overlapping when the user zooms out."
- Use meaningful layout: "If the user can predict where an object will be based on attributes that they are likely to be familiar with, then they can trim the search space."
- Use consistent layout: "Ideally, once an object is placed in space, it should not move. That way, the user can build up an internal map over time of where objects are." The paper notes this "is often in direct conflict with the previous one of meaningful layout."
- Use scannable layout: "In 2D, however, for any layout except for a grid, there is the potential for a much heavier load on short-term memory."
- Use breadth over depth: "when objects are placed at many different levels, the user would not know that the small objects exist (unless the space is carefully designed to indicate them), and they can get lost."
- Use small data sets: "ZUIs appear to work better for users when they have no more than about 100 screens worth of information."
- Simple and consistent navigation: "it must be difficult or impossible to get lost in Desert Fog"; existing tools "vary between single and double clicks to zoom in, how much the screen is zoomed per action, whether zooms scale by a fixed percentage or whether the target object fills the screen."
- On animated transitions (Klein and Bederson 2005, scrolling while reading, 0 to 500 ms): "Reading errors were reduced by 54% with 500 ms animations"; "when designed correctly, the benefits of simple animated navigational transitions can outweigh their costs. This supports the design decision to make zooming transitions use short animations."

**Semantic zoom in maps.**
- OpenStreetMap: "A zoom level is an integer that represents how much of the world is visible on a map"; the table pairs level 0 with "whole world", 10 with "metropolitan area", 16 with "street" and 18 with "some buildings, trees", running from 1:500 million at level 0 to 1:500 at level 20 (https://wiki.openstreetmap.org/wiki/Zoom_levels).
- Mapbox: "A zoom level determines how much of the world is visible on a map", 0 to 22; at low zoom "a small set of map tiles covers a large geographical area"; the Earth at 0, a continent at 3, large rivers at 6, buildings at 15 (https://docs.mapbox.com/help/glossary/zoom-level/).
- The mechanism that changes what is drawn is per layer: "minzoom: The minimum zoom level for the layer. At zoom levels less than the minzoom, the layer will be hidden"; "maxzoom: ... At zoom levels equal to or greater than the maxzoom, the layer will be hidden"; for several layer types "zoom-dependent expressions will be evaluated only at integer zoom levels" (https://docs.mapbox.com/style-spec/reference/layers/).

**C4 model** (https://c4model.com/introduction and https://c4model.com/diagrams/notation; the model calls itself "notation independent" at https://c4model.com/).
- "It's a way to create 'maps of your code', at various levels of detail, in the same way you would use something like Google Maps to zoom in and out of an area you are interested in."
- The container diagram "zooms into the software system in scope, showing the applications and data stores inside it"; the component diagram "zooms into an individual container, showing the components inside it"; the code diagram "can be used to zoom into an individual component".
- Rules that hold at every level: "The type of every element should be explicitly specified"; "Every element should have a short description, to provide an 'at a glance' view of key responsibilities"; "Every container and component should have a technology explicitly specified."
- Lines: "Every line should represent a unidirectional relationship"; "Every line should be labelled, the label being consistent with the direction and intent of the relationship"; container-to-container lines "should have a technology/protocol explicitly labelled".
- Legend and colour: "Every diagram should have a key/legend explaining the notation being used"; "make sure that any colour coding is consistent (within and across diagrams)"; "be careful of things like black and white printers, color blindness, etc."; "Every diagram should have a title describing the diagram type and scope."

**Structurizr navigation** (https://docs.structurizr.com/ui/diagrams/navigation).
- Elements that can be entered are "marked with a zoom-in symbol".
- "Double-clicking a software system will either take you to the System Context or Container diagram for that software system, if one exists."
- "Double-clicking a container will take you to the first Component diagram for that container, if one exists."
- "Press the Up/Down or Left/Right cursor keys to move to the previous/next diagram." "Press the Space key to open quick navigation."
- The zoom target is a separate diagram, not a magnified region of the same picture.

**IcePanel** (https://docs.icepanel.io/core-features/diagramming).
- Zooming is "Clicking the magnifying glass icon at the top-left of an object in a diagram."
- "By default, when you zoom into an object, you will land on the top diagram in the list of possible diagrams within that object."
- Per source diagram, a menu offers "Set as custom landing diagram" and "Remove custom landing diagram"; "If there are no nested objects, a blank diagram will be created at a lower level."
- The docs page describes no zoom-out gesture.
- Their stated reason (2023-09-05): "The hierarchical nature of the C4 model feels like it wants to be consumed using an interactive and zoomable interface so anyone can zoom in for more technical detail"; "Simple diagrams created at a high-level view can be a superpower to help bridge communication gaps between technical and non-technical team members." (https://icepanel.io/blog/how-to-create-interactive-zoomable-software-architecture-diagrams)

**Prezi.** The product presents slides "on a zoomable canvas" (https://prezi.com/). Its own guidance (https://prezi.com/blog/mastering-the-prezi-zoom/, 2016, updated 2019):
- One "infinite canvas"; "by zooming into the details from the birds-eye view of the big picture, you can help your audience understand their importance".
- "zoom out to show your audience how your ideas fit into a bigger picture".
- The warning: "there is such a thing as too much Prezi zoom"; a talk can feel "more like a rollercoaster ride than a speech".

What each source says changes at a zoom boundary, and what stays put:

| Source                    | Changes when zooming                                        | Stays constant                                  |
| ------------------------- | ----------------------------------------------------------- | ----------------------------------------------- |
| Furnas fisheye            | Which points clear the interest threshold                   | One structure; each point's a priori importance |
| Pad++ semantic zoom       | An object's representation (point, box, labelled box, text) | The object's place on the surface               |
| Bederson guidelines       | Representation, within the same box or aspect ratio         | Position ("should not move"); the zoom gesture  |
| Map zoom levels           | Which layers are drawn (minzoom, maxzoom)                   | Coordinates; geography                          |
| C4, Structurizr, IcePanel | The diagram: a separate one per level                       | The element entered; notation rules; the legend |
| Prezi                     | Camera framing                                              | The canvas and its contents                     |

### B. Motion along edges

**Vizceral (Netflix, open source 2016).**
- "vizceral is a component for displaying traffic data on a webgl canvas. If a graph of nodes and edges with data about traffic volume is provided, it will render a traffic graph animating the connection volume between nodes." "There are three levels of information, global, regional, and service-level, with clicking or double-clicking on a node bringing you one level deeper." (https://raw.githubusercontent.com/Netflix/vizceral/master/README.md)
- Volume is density, sampled: "since we are dealing with metric values that are too large to visualize 1:1 effectively, there is some level of sampling in the number of dots animated"; the aim is that "exact numbers stop being as important and relative information is much more actionable" (https://github.com/Netflix/vizceral/wiki).
- Each connection carries metrics of three types, "normal", "danger" and "warning", "the colors that are used for the nodes themselves"; "maxVolume" is "The maximum volume seen recently to relatively measure particle density"; notices on nodes and connections carry a severity (0 info, 1 warning, 2 error); "Any node can also contain nodes and connections. This is how we allow the drill-down functionality."; renderers are 'global' and 'region', with an 'ltrTree' layout option (https://github.com/Netflix/vizceral/wiki/How-to-Use).
- Default colours: colorTraffic.normal "rgb(186, 213, 237)", warning "rgb(268, 185, 73)" (sic), danger "rgb(184, 36, 36)" (https://github.com/Netflix/vizceral/wiki/Configuration).
- Netflix's one-line purpose: "Vizceral helps provide this at-a-glance intuition without needing to first build up a mental model of the system." (https://netflix.github.io/)
- No option to switch the particle animation off appears in the README or the wiki pages fetched. The August 2016 announcement post returned 403 (see "Not found").

**Kiali (Istio)** (https://kiali.io/docs/features/topology/).
- "Kiali offers several display options for the graph, including traffic animation."
- "For HTTP traffic, circles represent successful requests while red diamonds represent errors. The more dense the circles and diamonds the higher the request rate. The faster the animation the faster the response times. TCP traffic is represented by offset circles where the speed of the circles indicates the traffic speed."
- Colour is health: "The color of an edge between components represents the health of the requests between those components." "A node colored red or orange might need attention."
- The graph is flat and two-dimensional; the animation is a display option rather than always on.

**draw.io.**
- Flow animation is a connector style: "In the Style tab of the format panel, enable Flow Animation." "The connectors will now appear as if they have dashes moving from the source connection point to the target connection point." (https://www.drawio.com/doc/faq/connector-animate)
- SVG export keeps it: "Export your diagram to a SVG file to include the connector animation when you publish it in a web page"; animated GIF export loops it (same page).
- Settings: "The default Flow Duration is 500"; timing "Linear (default), Ease, Ease-in, Ease-out, Ease-in-out"; direction defaults to Normal, "flowing from the source to the target shape", with Reverse, Alternate and Alternate-Reverse (https://www.drawio.com/docs/manual/styles/connector-animation-styles/).
- The docs name the feature "Flow Animation"; the `flowAnimation=1` style string was not seen on the pages fetched.
- Viewer-side switch: "View > Animations", because "animations can be distracting when you are trying to draw and edit it. Animations also consume additional device resources and if there are many in a diagram, they may slow down the editor"; "This does not disable the flow animation style on the connectors, only the visual effect in your browser window" (https://www.drawio.com/docs/manual/styles/disable-animations/).

**Grafana Node Graph** (https://grafana.com/docs/grafana/latest/panels-visualizations/visualizations/node-graph/).
- Nodes carry "arc__" fields that "create the color circle around the node"; edges have thickness, colour and "the pattern of dashes and gaps".
- Layouts: layered ("a predictable and orderly layout"), force (for "500+" nodes) and grid.
- "Nodes that are not currently visible are hidden behind clickable markers that show an approximate number of hidden nodes."
- No animated edge or flow effect is mentioned.

**Mermaid flowcharts** (https://mermaid.js.org/syntax/flowchart.html). Direction keywords TB, TD, BT, RL, LR. Edge animation is per edge: "Once you have assigned an ID to an edge, you can turn on animations for that edge by defining the edge's properties" with `{ animate: true }`; "two animation speeds are supported: fast and slow"; or a classDef with a stroke-dasharray animation.

**React Flow** (https://reactflow.dev/examples/edges/animating-edges). "React Flow provides a simple built-in animation for the default edge type"; a custom edge can "animate an SVG element along a path using the animateMotion element". The `animated` boolean is an Edge property (https://reactflow.dev/api-reference/types/edge) and adds the class `.react-flow__edge.animated`, "Added to an Edge when its animated prop is true" (https://reactflow.dev/learn/customization/theming).

**Tversky, Morrison and Betrancourt, 2002, "Animation: can it facilitate?"** (https://hci.stanford.edu/courses/cs448b/papers/Tversky_AnimationFacilitate_IJHCS02.pdf).
- Congruence Principle: "the content and format of the graphic should correspond to the content and format of the concepts to be conveyed." From it, "animated graphics should be effective in portraying change over time. Yet the research on the efficacy of animated over static graphics is not encouraging."
- "In cases where animated graphics seem superior to static ones, scrutiny reveals lack of equivalence between animated and static graphics in content or procedures; the animated graphics convey more information or involve interactivity."
- Apprehension Principle: "graphics should be accurately perceived and appropriately conceived. Animations are often too complex or too fast to be accurately perceived." "Moreover, many continuous events are conceived of as sequences of discrete steps."
- "Animations may be more effective than comparable static graphics in situations other than conveying complex systems, for example, for real time reorientations in time and space."
- "Stopping, starting and replaying an animation can allow reinspection"; "Animations that allow close-ups, zooming, alternative perspectives, and control of speed are even more likely to facilitate perception and comprehension."

**Accessibility.**
- WCAG 2.2, 2.2.2 Pause, Stop, Hide (Level A): "For any moving, blinking or scrolling information that (1) starts automatically, (2) lasts more than five seconds, and (3) is presented in parallel with other content, there is a mechanism for the user to pause, stop, or hide it unless the movement, blinking, or scrolling is part of an activity where it is essential." (https://www.w3.org/TR/WCAG22/#pause-stop-hide)
- WCAG 2.2, 2.3.3 Animation from Interactions (Level AAA): "Motion animation triggered by interaction can be disabled, unless the animation is essential to the functionality or the information being conveyed." (same page)
- Understanding 2.3.3: "Some users experience distraction or nausea from animated content"; "Triggered reactions include nausea, migraine headaches, and potentially needing bed rest to recover." Essential means that removing it "would fundamentally change the information or functionality of the content, and information and functionality cannot be achieved in another way." "Another animation that is often non-essential is parallax scrolling." (https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)
- `prefers-reduced-motion` "is used to detect if a user has enabled a setting on their device to minimize the amount of non-essential motion", with values `no-preference` and `reduce`; the setting says "the user prefers an interface that removes, reduces, or replaces motion-based animations"; "Animations such as scaling or panning large objects can be vestibular motion triggers." (https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)

### C. Layering: side by side versus stacked "floors"

**ArchiMate layered viewpoint** (reproduction: https://www.visual-paradigm.com/support/documents/vpuserguide/4455/4456/86488_layeredviewp.html, which states it quotes the ArchiMate 3.0.1 specification; the Open Group's own pages redirect to a login, see "Not found").
- "There are two categories of layers, namely dedicated layers and service layers."
- "Each dedicated layer exposes, by means of the 'realization' relationship, a layer of services, which are further on 'serving' the next dedicated layer."
- "The order, number, or nature of these layers are not fixed, but in general a (more or less) complete and natural layering of an ArchiMate model should contain the succession of layers depicted in the example given below."
- "The main goal of the layered viewpoint is to provide an overview in one diagram."
- The vertical axis therefore reads as serving: a layer's services sit between it and the layer it serves. The example figure's top-to-bottom order could not be read from a fetched page.

**Sugiyama-style layered drawing and Graphviz dot.**
- dot makes "hierarchical or layered drawings of directed graphs"; "The layout algorithm aims edges in the same direction (top to bottom, or left to right) and then attempts to avoid edge crossings and reduce edge length." (https://graphviz.org/docs/layouts/dot/)
- The paper behind it (Gansner, Koutsofios, North and Vo, 1993, https://graphviz.org/documentation/TSE93.pdf) is "a four-pass algorithm" whose first pass "finds an optimal rank assignment". Its aesthetics: "A1. Expose hierarchical structure in the graph. In particular, aim edges in the same general direction if possible. This aids finding directed paths and highlights source and sink nodes." "A2. Avoid visual anomalies that do not convey information about the underlying graph. For example, avoid edge crossings and sharp bends." "A3. Keep edges short." "A4. Favor symmetry and balance."
- Here the vertical (or horizontal) axis means edge direction, that is, dependency order, and nothing else.
- `rankdir` "Sets direction of graph layout", default TB, with BT, LR and RL; "If rankdir="LR", and barring cycles, an edge T -> H; will go from left to right." (https://graphviz.org/docs/attrs/rankdir/)

**Switching the same model between stacked and side by side.** Every layered engine found exposes this as a direction option, not as a separate view:

| draw.io | Arrange > Layout > Vertical Flow or Horizontal Flow, "from top to bottom (Vertical) or left to right (Horizontal)"; ELK underneath; "Network Simplex (default)" layering | two menu items | none (https://www.drawio.com/docs/manual/layouts/flow-layouts/) |
| Mermaid flowchart | direction keyword | TB, TD, BT, RL, LR | declared per diagram (https://mermaid.js.org/syntax/flowchart.html) |
| Structurizr DSL | `autoLayout [tb|bt|lr|rl] [rankSeparation] [nodeSeparation]` | tb, bt, lr, rl | tb; rank separation 300 px (https://docs.structurizr.com/dsl/language) |

### D. Three-dimensional software maps and time

**CodeCity (Wettel and Lanza, 2007).**
- "The classes are represented as buildings in the city, while the packages are depicted as the districts in which the buildings reside", with "the visible properties of the city artifacts" depicting chosen metrics (https://wettel.github.io/codecity.html). The VISSOFT 2007 paper received the "Most Influential Paper" award at VISSOFT 2020 (https://wettel.github.io/).
- From the paper (https://wettel.github.io/download/Wettel07b-vissoft.pdf): "The height of the buildings represent their number of methods (NOM), while the width and length represents the number of attributes (NOA)." "The color saturation of the tiles is proportional to the nesting level of the corresponding packages."
- The intended reading: "a class with many methods but few attributes will be represented as a tall and thin building", while one with many attributes and few methods "will appear like a platform (or a 'parking lot')".

**CodeCity and evolution (Wettel and Lanza, WCRE 2008,** https://wettel.github.io/download/Wettel08d-wcre.pdf**).** Three techniques: "Age map to depict the age distribution", "Time travel to step through the system's history", and "Timeline to capture the entire evolution of a software artifact in a single view."
- Age map: "The age is an integer value representing the number of sampled versions that the artifact 'survived' up to that version. The color scheme ranges from light yellow for new-born classes/packages to dark blue for the oldest ones."
- Time travel keeps places fixed: "every artifact is assigned an individual real estate in the city, maintained throughout the entire evolution, i.e., if an artifact is removed from the system or does not yet exist in the system at a certain point in time, this is denoted by an empty space that cannot be occupied by other artifacts."
- Fine grain: methods are bricks stacked "in the order of their creation (i.e., older down, newer up). Removed methods are represented as empty spaces."

**The software city family.**
- Getaviz: "solve software engineering problems visually by exploring software artifacts in 2D, 3D, and virtual reality"; metaphors "Recursive Disk (2D and 3D), City, City Floors, City Bricks, and many more"; explored "via browser, HTC Vive, or Oculus Rift"; for "Java, Ruby, PHP, and C#"; uses named as "identifying and refactoring antipatterns, locating runtime bottlenecks, assessing software quality, and tracking changes across multiple versions"; it can "enrich these visualizations with evolutionary information from git and svn repositories" (https://github.com/softvis-research/Getaviz).
- JSCity: "Folders are districts and files are sub-districts"; "The buildings are functions; inner functions are represented as buildings on the top of their nested function/building"; "The Number Of Lines of Source (LOC) represents the height of the buildings/functions"; "The Number Of Variables (NOV) in a function correlates to the building's base size"; "Blue buildings denote named functions; green buildings are anonymous functions" (https://github.com/aserg-ufmg/JSCity).

**Gource.**
- "Software projects are displayed by Gource as an animated tree with the root directory of the project at its centre. Directories appear as branches with files as leaves. Developers can be seen working on the tree at the times they contributed to the project." (https://gource.io/)
- Time is a playback rate: "Seconds per day controls the amount of time Gource will take to display each day in the log file (10 seconds by default)"; `--realtime` sets one real day per day; idle stretches are skipped after 3 seconds unless `--disable-auto-skip` (https://github.com/acaudwell/Gource/wiki/Controls).
- Inactivity is decay: "By default, Gource 'expires' files which haven't been touched by a user in the 60 seconds", adjustable with `--file-idle-time` or disabled with 0 (same page).
- Space pauses; "While paused, you can still move the camera around and inspect the details of files and users"; the camera has "overview" and "track" modes; S cycles colour schemes (same page).

**code_swarm (Ogawa and Ma).**
- "an experiment in organic software visualization", GPL-3.0, with the TVCG 2009 paper as the requested citation (https://github.com/VIDILabs/code_swarm).
- The abstract: "In May of 2008, we published online a series of software visualization videos using a method called code_swarm. Shortly thereafter, we made the code open source and its popularity took off." The authors "designed for both developers and a casual audience" (https://www.ebi.ac.uk/europepmc/webservices/rest/search?query=EXT_ID:19834177&resultType=core&format=json).
- The often-repeated description (files flying toward the developer who commits them, inactive items fading) appears only in secondary sources and is not quoted here.

**Age or decay as a number: libyear** (https://libyear.com/).
- "A simple measure of software dependency freshness. It is a single number telling you how up-to-date your dependencies are."
- "If your system has a one year old dependency and a three year old dependency, then your whole system is four libyears old."
- "Rails 5.0.0 (June 2016) is 1 libyear behind 5.1.2 (June 2017)."
- Implementations are listed for dotnet, JavaScript, PHP, Python, Ruby, Java, Scala, Go, Rust and Common Lisp.

### What the UX standards say for the questions

- Across a zoom boundary, the cited work keeps the thing zoomed into and its place, and changes its representation. Furnas keeps one structure and drops far points below a threshold; Pad++ keeps the object's position and swaps its look from point to box to text; Bederson asks that the small form fit the same box and that "once an object is placed in space, it should not move"; map engines keep coordinates and hide or show layers by zoom level; C4 tools keep the element and open a separate diagram for its inside, reached by double-click (Structurizr) or a magnifier icon (IcePanel), with notation rules and a legend that hold at every level. Bederson also reports that short animated transitions (300 to 500 ms) helped in a controlled study and warns of "Desert Fog" and of inconsistent zoom gestures across tools.
- The animation in service maps is traffic, not dependency: Vizceral animates dots whose density is sampled volume and whose colour is normal, warning or danger; Kiali animates circles and diamonds whose density is request rate and whose speed is response time, as a display option. Two-dimensional diagram tools animate a dash pattern from source to target (draw.io, Mermaid, React Flow); draw.io ships a viewer-side switch and gives resource use and distraction while editing as the reasons; Mermaid and React Flow are off unless asked; Grafana's node graph does not animate. Tversky and colleagues find animation "not encouraging" for conveying complex systems, better for "real time reorientations in time and space", and helped by stopping, replaying and speed control; WCAG asks for a pause, stop or hide control for automatic motion over five seconds and, at AAA, for interaction-triggered motion to be disableable; `prefers-reduced-motion` is the browser signal. No fetched page reports a study of animated dependency edges specifically.
- Two vertical conventions exist. In ArchiMate the vertical axis means serving: each dedicated layer realizes services that serve the next layer, and the order is stated as customary rather than fixed. In Sugiyama-style layout (dot, ELK, draw.io, Mermaid, Structurizr autoLayout) the axis means edge direction only, chosen by a single option (TB, LR and so on), which is also the only form of "stacked versus side by side" found. Cloud vendors draw on-premises beside the cloud with the hybrid link as the wire; C4 nests deployment nodes to mean "runs inside"; Cloudcraft treats 3D and 2D as a projection toggle over one model.
- The 3D and time work encodes size metrics in height and footprint (methods and attributes in CodeCity, lines and variables in JSCity), category or nesting in colour, and age either as a colour ramp (light yellow new to dark blue old, with removed items leaving empty lots so places stay fixed) or as playback with decay (Gource expires idle files after 60 seconds by default). libyear reduces dependency staleness to one summed number that such a visual could draw from.
- On editing, Structurizr is the one tool found whose documentation states how manual positions survive a model change (stored apart from the source, merged by name then internal ID, lost on rename plus reorder or on a changed view key); draw.io keeps connectors routed after a shape moves; the game editors expose snapping as a master toggle over individually switchable modes with a configurable step.

### The agent's judgement on the UX standards

_Read by the agent on 2026-09-28, after the survey above. A judgement, not a decision; the owner's answer is the decision._

**Zooming between scales.** The rule is the same from Furnas in 1986 to IcePanel today: across a zoom boundary the thing and its place stay and only its representation changes. Pad++ swaps a point for a box for a label for a page at a fixed position; Bederson asks that the small form fit the same box, that "once an object is placed in space, it should not move", and reports that transitions of 300 to 500 milliseconds helped; the C4 tools open a separate diagram for the same element with the notation and the legend held constant. We would agree, and it sharpens the vision's sentence that a lid unfolds: the piece stays where the person put it, its box is the frame the Local Map fills, and the transition is a short animation rather than a cut. Bederson's caution that zooming should not be the primary interaction unless the data is spatial does not bite, because the board is spatial by construction: a person placed the pieces. His other caution does: one zoom gesture, the same everywhere, and no "Desert Fog" between the scales.

**Motion along edges.** Everything found that animates an edge animates traffic (Vizceral's dots are sampled volume, Kiali's speed is latency) or a bare dash pattern (draw.io, Mermaid, React Flow), and no study of animated dependency edges exists. Tversky and colleagues find animation "not encouraging" for conveying complex systems and helped by stopping, replaying and speed control; WCAG 2.2.2 requires a pause, stop or hide control for motion that starts by itself and lasts more than five seconds; `prefers-reduced-motion` is the browser's signal; draw.io names distraction while editing and device resources as the reasons for its viewer-side switch. We would agree with the owner's wish for the same gentle flow on the Local Map, with what the field adds: it is a viewer setting, it honours the reduced-motion preference, it pauses while a person drags, and because on these wires motion means direction and never volume, the dots are uniform and sparse so that nobody who has seen Vizceral reads density as traffic. On the Local Map the direction is already carried by the sides a wire enters and leaves, so the motion there is redundant encoding; that is allowed, and it is why the field's finding that animation adds feel rather than comprehension is not an argument against it.

**Floors versus side by side.** The vertical axis has two meanings in the field and they do not agree: in ArchiMate's layered viewpoint the order means serving, each layer's services serving the next, in an order the specification calls customary rather than fixed, and in Sugiyama-style layout it means edge direction and nothing else. The only "stacked versus side by side" switch anywhere is a layout-direction option, cloud vendors draw on-premises beside the cloud with the hybrid link as the wire, C4 nests deployment nodes to mean "runs inside", and no tool's documentation makes the vertical axis mean "governs". The pushback the owner invited follows from their own words: the board dropped the left-to-right law at the outer scale because a fixed axis with a meaning was "a mistake" there, and a floors law would put one back, with the field unable to agree what it means. What we would agree with is floors as an arrangement rather than a law: a district sits above another because a person put it there, the reading "this governs that" is theirs, and the tool offers the field's one switch, a one-click arrangement of districts side by side or stacked, after which pieces stay where they are. The cost the field names for stacking in three dimensions is occlusion; Cloudcraft's answer is a projection toggle, and the board's free orthographic camera is the same answer.

**Cruft and time.** CodeCity's age map runs light yellow for new to dark blue for old and keeps places fixed by leaving an empty lot where a thing was removed; Gource lets idle files fade; libyear reduces dependency staleness to one summed number of years behind. We would agree that the owner's vines have a number to grow from, libyear over lockfiles or an SBOM once those are read, and that CodeCity's empty lot is the rule to borrow when two snapshots of one system share a board.

**Editing on the map.** Structurizr is the one tool whose documentation says how hand positions survive a model change (kept apart from the source, matched by name then identity, lost on rename plus reorder), draw.io reroutes connectors after a shape moves, and the game editors expose snapping as a master toggle over individually switchable modes with a configurable step. We would agree with all three, and the last is the owner's "slider or checkbox" with a number attached.
