## The library

- The repository is [mattpocock/skills](https://github.com/mattpocock/skills), read in full at its commit of that morning, `b0618bc4` (2026-10-08, 09:44 +0100); every link below is pinned to it. Its README calls it "My agent skills that I use every day to do real engineering - not vibe coding", "small, easy to adapt, and composable", working "with any model", and sets it against GSD, BMAD and Spec-Kit, which "take away your control and make bugs in the process hard to resolve" ([README](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/README.md)).
- It names four failure modes and a fix for each: misalignment ("No-one knows exactly what they want", Thomas and Hunt), fixed by a grilling session; verbosity, fixed by a shared language (Evans's ubiquitous language), with the example "There's a problem with the materialization cascade" in place of a sentence; code that does not work, fixed by feedback loops and `/tdd`; and the ball of mud, fixed by designing deep modules and a periodic `/improve-codebase-architecture` survey ([README](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/README.md)).
- Skills split on who invokes them: user-invoked skills "orchestrate" and model-invoked skills "hold the reusable discipline"; "A user-invoked skill may invoke model-invoked skills, but never another user-invoked one." Installation is a Claude Code plugin (`claude plugin install mattpocock-skills@claude-plugins-official`) or editable copies through skills.sh, then `/setup-matt-pocock-skills` once per repository to choose an issue tracker (GitHub, GitLab, local files), triage labels and where docs go ([README](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/README.md)).
- The bar for changing a skill: an "Observed failure" in a real session, and a fit with the philosophy; "A hypothetical improvement ('it would be better if...') does not clear this part" ([SCOPE.md](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/SCOPE.md)). Two recorded rejections matter here: no cap on the number of questions, because "some plans need three questions, some need fifty" ([question-limits.md](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/.out-of-scope/question-limits.md)); and no routing through a harness's question tool, because "Structured pickers push the model towards multiple-choice questions with pre-baked answers, which is the opposite of what grilling is for: open questions you answer in your own words, one branch of the decision tree at a time" ([native-question-tool.md](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/.out-of-scope/native-question-tool.md)).

## Grilling: the primitive

- `grill-me` is seven lines: "Call the Skill tool with 'grilling'." `grill-with-docs` is the same with one word more: "Call the Skill tool twice, for 'grilling' and 'domain-modeling'." The interview itself is the model-invoked `grilling` skill, thirty lines ([grill-me](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/productivity/grill-me/SKILL.md), [grill-with-docs](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/grill-with-docs/SKILL.md), [grilling](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/productivity/grilling/SKILL.md)).
- Its whole method, from those thirty lines: "Interview the user relentlessly until you reach a shared understanding. Map this as a **design tree**: every decision branches into the decisions that hang off it." Work it in rounds: "The **frontier** is every decision whose prerequisites are already settled: the questions you can ask _now_ without guessing at answers you haven't heard yet. Ask the whole frontier in one round: number each question and give your recommended answer." "Word each question so 'yes' accepts your recommended answer." "A question whose answer depends on another question still open in this round belongs to a _later_ round, not this one." "Finding _facts_ is your job, never the user's. When a frontier question needs a fact from the environment (filesystem, tools, etc.), dispatch a sub-agent to find it; don't ask the user for anything you could look up yourself... The _decisions_ are the user's: put each to them and wait." "The session is done when the frontier is empty: every branch of the design tree visited, nothing left silently assumed. Do not act on it until the user confirms you have reached a shared understanding." ([grilling](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/productivity/grilling/SKILL.md))
- The format is a numbered, titled question, its body, then the recommendation alone on its own line, so that a person can "answer a round by number ('1 yes, 2 the second option, 3 no, here's why')". The docs page says "Thirteen questions typically land in about three rounds rather than thirteen" and admits the frontier's limit: "The agent chooses it by judgement; it does not compute it from a graph. So it can put two questions in one round and only later find that one answer should have changed the other. The only guard is to tell it." ([docs/productivity/grilling.md](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/docs/productivity/grilling.md))
- The failures its own page reports: a session that "ran out of questions and started building" (the confirmation gate exists for this); an agent that "answered its own questions instead of asking me", called "a bug in the run", most often when another skill runs grilling to resolve a ticket; and no async mode on purpose, since "a grilling session that nobody answers has produced the agent's opinion rather than yours" ([docs/productivity/grilling.md](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/docs/productivity/grilling.md)).

## Domain modeling: what "with docs" adds

- `domain-modeling` is "the *active* discipline: challenging terms, inventing edge-case scenarios, and writing the glossary and decisions down the moment they crystallise". During a session it does five things: challenge a term against the glossary ("Your glossary defines 'cancellation' as X, but you seem to mean Y. Which is it?"); sharpen fuzzy language; **discuss concrete scenarios** ("stress-test them with specific scenarios. Invent scenarios that probe edge cases and force the user to be precise about the boundaries between concepts"); **cross-reference with code** ("When the user states how something works, check whether the code agrees. If you find a contradiction, surface it"); and update `GLOSSARY.md` inline, a file that "should be totally devoid of implementation details" ([domain-modeling](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/domain-modeling/SKILL.md)).
- An ADR is offered only when three things hold: "Hard to reverse", "Surprising without context", "The result of a real trade-off". Its template is a title and "1-3 sentences: what's the context, what did we decide, and why", because "The value is in recording *that* a decision was made and *why*, not in filling out sections" ([ADR-FORMAT.md](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/domain-modeling/ADR-FORMAT.md)). The glossary is "opinionated": one word per concept with the others under `_Avoid_`, definitions of one or two sentences, and only terms "specific to this project's context" ([GLOSSARY-FORMAT.md](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/domain-modeling/GLOSSARY-FORMAT.md)). The page for `grill-with-docs` draws the line between the two outputs and what stays in conversation: glossary entries are written "the moment it resolves", ADRs for the decisions that meet the three tests, and "Everything else" remains "only in the context window you agreed it in" ([aihero.dev](https://www.aihero.dev/skills-grill-with-docs)).

## Wayfinder: the shape for work bigger than one session

- "A loose idea has arrived, too big for one agent session, and wrapped in fog: the way from here to the **destination** isn't visible yet. Wayfinding is about finding that way, not charging at the destination." The destination is named first, "the first act of charting", and "might be a spec to hand off and iterate on, a decision to lock before planning starts, or a change made in place" ([wayfinder](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/wayfinder/SKILL.md)).
- "Wayfinder is **planning** by default: each ticket resolves a decision, and the map is done when the way is clear, with nothing left to decide before someone goes and does the thing. The pull to just do the work is usually the signal you've reached the edge of the map and it's time to hand off." ([wayfinder](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/wayfinder/SKILL.md))
- The map is one issue, "an **index**, not a store", with four sections: Destination; Notes; Decisions so far, "one line per closed ticket, enough to judge relevance, then zoom the link for the detail the ticket holds"; Not yet specified; and Out of scope. Tickets are child issues, each one question "sized to one 100K token agent session", of four types: `research` (the agent alone, reading outside the working directory), `prototype` (with the human; "Use when 'how should it look' or 'how should it behave' is the key question"), `grilling` (with the human; "The default case"), and `task` (manual work that unblocks a decision, "the one type that _does_ rather than decides"). A ticket worked with a human "only resolves through that live exchange; the agent never stands in for the human's side of it". The frontier is "the open, unblocked, unclaimed children, the edge of the known"; blocking uses the tracker's native links so that the frontier is visible in the tracker's own UI ([wayfinder](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/wayfinder/SKILL.md)).
- The fog: "The map is _deliberately_ incomplete: don't chart what you can't yet see." The test between fog and ticket "is whether you can state the question precisely now, _not_ whether you can answer it now." Out of scope is "work you've consciously ruled out of _this_ effort" and "never graduates (the frontier stops at the destination)" ([wayfinder](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/wayfinder/SKILL.md)).
- Charting is one session: name the destination by grilling; grill again "**breadth-first** this time: fan out across the whole space rather than deep on any one thread, surfacing the open decisions and the first steps takeable now"; "If this surfaces no fog (the way to the destination is already clear, the whole journey small enough for one session), you don't need a map"; create the map and the tickets that can be specified, wire blocking in a second pass, fire the research subagents, stop. Working the map is "never ... more than one ticket per session, with the exception of research tickets" ([wayfinder](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/wayfinder/SKILL.md)).
- The trackers: GitHub, GitLab, or a local-markdown fallback. The docs page warns that "Local markdown puts the artifacts in your repo, which is not recommended, because material stored in the repo tends to persist by accident", and in the same paragraph that open-source maintainers, whose "public trackers fill up with agent-generated planning tickets", "often choose local markdown anyway" ([docs/engineering/wayfinder.md](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/docs/engineering/wayfinder.md)).
- Its reported failures: the agent "started writing production code in the middle of a wayfinder session", the most-reported one; "I charted 27 tickets, and by the time I got to the thirteenth, the rest no longer made sense", answered with a bounded destination and "prototype aggressively... Wayfinder is 'prototypemaxxing', not 'planmaxxing'"; "The grilling is exhausting. Every question is three paragraphs long", unfixed and laid to the current models; and a closed decision found wrong, where the agent "tends to design around the bad decision instead of challenging it, so you must steer it yourself" ([docs/engineering/wayfinder.md](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/docs/engineering/wayfinder.md)). Pocock's own framing of the fog, on the Latent Space page: "you can't quite decide everything right at the start" ([Latent Space](https://www.latent.space/p/wayfinder-skill)).

## The neighbours a map schedules

- `prototype`: "A prototype is **throwaway code that answers a question**. The question decides the shape." A logic question gets "a single shareable HTML file" that "a non-developer can drive"; a look question gets "several radically different UI variations on a single route". Six rules: throwaway and marked so; trivial to run; no persistence; no polish; surface the state after every action; and when done, fold the decision into the real code and keep the prototype "as a **primary source**" on a throwaway branch ([prototype](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/prototype/SKILL.md)).
- `research`: a background agent reads "**primary sources** (official docs, source code, specs, first-party APIs), not a secondary write-up of them" and writes "a single Markdown file, citing each claim's source", where the repository already keeps such notes ([research](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/research/SKILL.md)).
- `codebase-design`: a vocabulary (module, interface, implementation, depth, seam, adapter, leverage, locality) for deep modules, "a lot of behaviour behind a small interface, placed at a clean seam, testable through that interface"; the deletion test; "One adapter means a hypothetical seam. Two adapters means a real one." Its design-it-twice page spawns three or more sub-agents to produce "radically different" interfaces under different constraints, compared on depth, locality and seam placement, ending in an opinionated recommendation: "the user wants a strong read, not a menu" ([codebase-design](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/codebase-design/SKILL.md), [DESIGN-IT-TWICE.md](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/codebase-design/DESIGN-IT-TWICE.md)).
- `to-spec`: "no interview, just synthesis of what you've already discussed"; it sketches the test seams first ("The fewer seams across the codebase, the better - the ideal number is one"), checks them with the user, then writes a spec with no file paths or snippets, since "They may end up being outdated very quickly" ([to-spec](https://github.com/mattpocock/skills/blob/b0618bc436ad893b3c5e84e55fba86586d34a404/skills/engineering/to-spec/SKILL.md)).

## Where the library and this repository's conventions pull apart

- **The question format.** The library's rounds are marked with two emoji; this repository bans emoji in the UI, and the owner dislikes bureaucratic schemes. Numbered questions with a recommendation line keep the mechanics (answer by number; "yes" accepts) in plain words.
- **A glossary file.** The library writes `GLOSSARY.md` the moment a term resolves; the owner deferred naming on 2026-10-03 because "concretizing terms hasn't _yet_ borne more value than cost". A list of the words on trial with their candidates is the part of a glossary that can be kept without a rename.
- **ADR files.** The library's `docs/adr/` would be a second decisions log beside the layer-3 one, whose entries already meet the three tests.
- **"Plan, don't do".** The library keeps building out of a map; the owner has said "the designs and the walls we hit during them will primarily be the guide of this too" (2026-10-01). The library's own answer to that tension is the prototype ticket, which this repository has practised as probes since 2026-09-28.
- **Session size.** "One ticket per session" against the owner's "5 to 20 chats, probably interspersed with some other work" (2026-10-08): compatible, and a map is what makes the interspersing safe, since each chat reads the index and takes one question.
- **Fail early.** No ticket type in the library resolves to "this idea does not survive"; its closest tools are domain-modeling's invented scenarios and cross-reference with code, and the Out of scope section for what a resolution ruled out. The owner's aim of 2026-10-08, "fail ideas early for being unable to congeal with any permutation of adjustments to our software", is a test the library leaves to the interviewer's judgement.

## The agent's judgement

What would carry the World Map "from where we are now to where we want to be" is the library's shape with three adjustments, none of which the library forbids:

1. **A map in repository markdown, not on a tracker**, with a named destination, decisions as one-line pointers into direction.md and the decisions log, the fog as "Not yet specified", and an Out of scope list. It is the wayfinder map with this repository's system of record as the tracker, and the file the next chat reads first.
2. **A fixed set of scenarios every idea is walked through on paper before any code**: the owner's estate at work, this repository itself, two directories pointed at together with no board, a nested project, an imagined system, a board traded detached from its sources and a link shared from a hosted site, CI/CD files as a source, an SBOM found in a thing, the blank file, and an agent reading the board as text. This is domain-modeling's "invent scenarios that probe edge cases" made into a standard: an idea that cannot hold every scenario under some adjustment of the doc grammar, the board grammar, the join, the bundle, the Explorer, the CLI and the tests, without breaking a standing rule (markdown canonical; headless and UI as peers; a scan never hidden; orientation kept), fails early, and is written down as failed, with why.
3. **Prototype where talk cannot settle**, as probes, and research where a fact outside the repository is needed, as surveys here; both are already practised.

What it would not do: rename the views, start a glossary file or an ADR folder, or move decisions out of the record the owner reads.
