It extends [the survey of 2026-10-16](2026-10-16-change-over-time.md) and does not repeat it. The agent's report was read whole by the root agent and adopted as it stands, with this header and the reading at the end added; it records what the sources say on its date and decides nothing. Every claim has its URL beside it._

Method. Every URL below was read on 2026-10-17; push dates, star counts and tags come from the GitHub and GitLab APIs on that day. Primary sources (manuals, READMEs, source files, specifications) were preferred; two posts are used, one by the TFS product team (2009, kept in Microsoft's own archive) for TFS's rename model, and Mark Heath's (2011) only as an example of a Gource emitter. ## 1. What each version-control system exposes to a history reader

Letters follow the question: (a) the changes on a mainline with id, parents, date, author, message; (b) a working tree at a change; (c) renames and moves; (d) truncated local history.

**Git**
- (a) `git rev-list --first-parent`: "When finding commits to include, follow only the first parent commit upon seeing a merge commit."; `--reverse` reverses the output; `--parents` "Print also the parents of the commit"; placeholders `%H` "commit hash", `%P` "parent hashes", `%at` "author date, UNIX timestamp", `%an` "author name", `%s` "subject" (https://git-scm.com/docs/git-rev-list).
- (b) `git worktree add [--detach] <path> [<commit-ish>]`; `git worktree add -d <path>` "creates a new worktree with a detached HEAD"; removal by `git worktree remove` (https://git-scm.com/docs/git-worktree). `git archive` "Creates an archive of the specified format containing the tree structure for the named tree" (tar, zip, tar.gz, tgz), stamps files with "the commit time as recorded in the referenced commit object", and leaves out `export-ignore` paths (https://git-scm.com/docs/git-archive).
- (c) Inferred, never recorded (see the 2026-10-16 survey). `--name-status`: "Show only the name(s) and status of each changed file"; letters A, C, D, M, R, T, U, X, B; "Status letters C and R are always followed by a score (denoting the percentage of similarity between the source and target of the move or copy)"; "copied and renamed entries cannot appear if detection for those types is disabled" (https://git-scm.com/docs/git-diff). `git fast-export -M`/`-C`: "Perform move and/or copy detection ... and use it to generate rename and copy commands in the output dump"; the page states no default (https://git-scm.com/docs/git-fast-export).
- (d) `git rev-parse --is-shallow-repository`: "When the repository is shallow print "true", otherwise "false"." (https://git-scm.com/docs/git-rev-parse). `git clone --depth` makes "a history truncated to the specified number of commits", beside `--shallow-since` and `--shallow-exclude`; a partial clone with `--filter=blob:none` "will filter out all blobs (file contents) until needed by Git" (https://git-scm.com/docs/git-clone).

**Team Foundation Version Control (TFVC)**
- (a) `tf history itemspec [/version:versionspec] [/stopafter:number] [/recursive] [/user:username] [/format:(brief|detailed)] [/slotmode] [/itemmode] [/noprompt] ... [/sort:ascending,descending] [/collection:TeamProjectCollectionUrl]`; brief gives "ID number, changes made, user who made the changes, date, and comment", detailed adds "items changed, check-in notes, and check-in policy warnings"; no machine-readable format is offered (https://learn.microsoft.com/en-us/azure/devops/repos/tfvc/history-command). `tf changeset [changesetnumber | /latest] /noprompt`; "A changeset is a set of file and folder revisions that were committed to the Team Foundation version control server as part of the same check-in event"; its sample lists `$/baz/proj/buf.c Modified, Renamed` (https://learn.microsoft.com/en-us/azure/devops/repos/tfvc/changeset-command). In tf.exe 16.171 the commands sit under `tf vc help` (`tf vc history`, `tf vc changeset`, `tf vc get`, `tf vc merges`, ...) beside `tf git help` (https://learn.microsoft.com/en-us/azure/devops/repos/tfvc/help-command-team-foundation-version-control).
- (a, REST) `GET https://dev.azure.com/{organization}/{project}/_apis/tfvc/changesets` filters by `searchCriteria.fromId`, `toId`, `fromDate`, `toDate`, `itemPath`, `author`, `followRenames`; "Results are sorted by ID in descending order by default. Use id asc to sort by ID in ascending order."; `TfvcChangesetRef` has `changesetId`, `author`, `checkedInBy`, `createdDate`, `comment`, `commentTruncated`, `url` and no parent field (https://learn.microsoft.com/en-us/rest/api/azure/devops/tfvc/changesets/get-changesets?view=azure-devops-rest-7.1). `GET https://dev.azure.com/{organization}/_apis/tfvc/changesets/{id}/changes` returns `TfvcChange[]` (`changeType`, `item`, `mergeSources`, `newContent`, `pendingVersion`, `sourceServerItem`, `url`), paged by `$skip`, `$top`, `continuationToken`, under OAuth scope `vso.code` (https://learn.microsoft.com/en-us/rest/api/azure/devops/tfvc/changesets/get-changeset-changes?view=azure-devops-rest-7.1).
- (b) `tf get /v:15` "synchronizes the workspace to match the codebase as it existed when changeset 15 was created"; "Items that were added after that changeset are deleted from the workspace." (https://learn.microsoft.com/en-us/azure/devops/repos/tfvc/get-command). For `C<n>`: "If an item that's in scope wasn't modified in the specified changeset, the system takes the latest version of the item that occurred before the specified changeset"; other versionspecs are L (label), D (date), W (workspace), T (tip) (https://learn.microsoft.com/en-us/azure/devops/repos/tfvc/use-team-foundation-version-control-commands). REST `tfvc/items` takes `versionDescriptor.versionType=changeset` and `recursionLevel=full`, with "zipped content which is always returned as a download"; `TfvcItem` carries `isBranch`, `deletionId` and `version` ("Changeset version Id") (https://learn.microsoft.com/en-us/rest/api/azure/devops/tfvc/items/get?view=azure-devops-rest-7.1).
- (c) Recorded. `tf rename` (aliases `move`, `ren`) "changes the name or the path of a file or folder", taking effect at check-in (https://learn.microsoft.com/en-us/azure/devops/repos/tfvc/rename-command-team-foundation-version-control). The detailed history example shows, in one changeset, `rename $/SiteApp/Main/SolutionA/Project1/programBig.cs` and `delete, source rename $/SiteApp/Main/SolutionA/Project1/program3.cs;X15` (history-command, above). `VersionControlChangeType`: none, add, edit, encoding, rename, delete, undelete, branch, merge, lock, rollback, sourceRename, targetRename, property, all; `mergeSources` is the "List of merge sources in case of rename or branch creation"; `TfvcMergeSource.isRename` "Indicates if this a rename source. If false, it is a merge source." (get-changeset-changes, above).
- (d) The client keeps no history. A local workspace "caches the unmodified version of each of your files to enable you to edit, compare, and do other things without being connected to the server" and suits "fewer than 100,000 items" (https://learn.microsoft.com/en-us/azure/devops/repos/tfvc/decide-between-using-local-server-workspace); `tf history` reads a project collection, "presumed to be the one that contains the workspace that maps the current directory" (history-command). Truncation appears at migration: the Azure Repos importer can "migrate up to 180 days of history starting from the most recent changeset" (https://learn.microsoft.com/en-us/azure/devops/repos/git/import-from-tfvc).

**Subversion**
- (a, c) `svn log --xml --verbose`: `logentry` with a `revision` attribute and `author`, `date`, `paths`, `msg`; each `path` has `action` ("A)dd, D)elete, R)eplace or M)odify"), `kind` ("file", "dir", or "" "when repository was < 1.6 when committing"), optional `text-mods`, `prop-mods`, and an optional pair `copyfrom-path`, `copyfrom-rev` (https://svn.apache.org/repos/asf/subversion/trunk/subversion/svn/schema/log.rnc). R: "The item was replaced by a different one at the same location." (https://svnbook.red-bean.com/en/1.7/svn.ref.svn.c.log.html).
- (c) No move reaches the repository: `svn move` "is equivalent to an svn copy followed by svn delete" (https://svnbook.red-bean.com/en/1.7/svn.ref.svn.c.move.html); in 1.8, "Moves are recorded as such only within the working copy." and "The committed revision will show a copy and a delete, instead of a move." (https://subversion.apache.org/docs/release-notes/1.8.html).
- (b) `svn export [-r REV] URL[@PEGREV] [PATH]` "exports a clean directory tree from the repository specified by URL" "at revision REV if it is given" (https://svnbook.red-bean.com/en/1.7/svn.ref.svn.c.export.html). The dump format "is a serialized description of the actions required to (re)build a version history": `Node-action: {change | add | delete | replace}`, `Node-copyfrom-rev` with `Node-copyfrom-path` or neither, and "Version 3 format is a delta dump" (https://svn.apache.org/repos/asf/subversion/trunk/notes/dump-load-format.txt).
- (d) History is on the server: the `svn log` reference reads "Accesses Repository: Yes" (https://svnbook.red-bean.com/en/1.4/svn.ref.svn.c.log.html).

**Mercurial** (7.2, released 2026-01-29, https://www.mercurial-scm.org/)
- (a) Template keywords: `node` ("The changeset identification hash, as a 40 hexadecimal digit string"), `p1`, `p2`, `parents`, `date`, `author`, `desc`, `files`, `file_adds`, `file_dels`, `file_mods`, `file_copies` ("Files copied in this changeset with their sources") (https://mercurial-scm.org/help/topics/templating).
- (b) `hg archive -r` writes files, tar, tbz2, tgz, txz, uzip or zip (https://mercurial-scm.org/help/commands/archive); `hg export` prints "author, date, branch name (if non-default), changeset hash, parent(s) and commit comment", with `-g/--git` for git extended diffs (https://mercurial-scm.org/help/commands/export).
- (c) Recorded at commit: `hg rename` is "equivalent of copy + remove": "Mark dest as copies of sources; mark sources for deletion." (https://mercurial-scm.org/help/commands/rename); with `-A/--after` "the operation is recorded, but no copying is performed" (https://mercurial-scm.org/help/commands/copy); `hg log -f` follows "file history across copies and renames", else "File history is shown without following rename or copy history of files." (https://mercurial-scm.org/help/commands/log).

**Perforce, now P4** (pages headed "P4 CLI Documentation | 2026.1", with "Helix Core is now P4.")
- (a) `p4 changes` with `-s submitted`, `-l` full descriptions, `-t` time of day, `-m max` ("List only the highest numbered max changes"), `-r` ("earliest first instead of most recent first") (https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_changes.html); `p4 describe -s` gives "the changelist number, the changelist creator, the client workspace name, the date the changelist was created, and the changelist description" and the affected files without diffs (https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_describe.html); "p4 submit works atomically", and a renumbered changelist "is assigned the next number in the changelist sequence" (https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_submit.html).
- (b) `p4 sync //depot/proj1/...@21` takes "the revision of the file in the depot after changelist 21 was submitted"; the server keeps each workspace's "have list"; `-p` populates "but do not update the have list" (https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_sync.html). `p4 print` "writes the contents of a depot file to standard output" (https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_print.html); git-p4 relies on it: "Cloning or syncing does not require a p4 client; file contents are collected using p4 print." (https://git-scm.com/docs/git-p4).
- (c) Recorded: `p4 fstat` headAction is "one of add, edit, delete, branch, move/add, move/delete, integrate, import, purge, or archive", and `movedFile` is the "Name in depot of moved to/from file." (https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_fstat.html); "File history inherited by renaming (p4 move) is always displayed, regardless of whether the -i option is used" (https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_filelog.html); `p4 move -r` "performs a strict rename only" (https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_move.html).
- (d) History is on the server unless copied: `p4 clone` copies "the portion of its contents that you want to work with into your local server"; `-m` "Specifies the maximum number of revisions of each file to clone; a shallow clone." (https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_clone.html).

Silences:
- No Microsoft page read lists which `tf` commands work without the server, or describes reading TFVC history offline.
- The Mercurial pages read say nothing on shallow or narrow clones; the extension list fetched names neither.
- p4's tagged and JSON output modes were not checked.
- The `tf` pages read offer brief or detailed text only; the .NET client libraries were not read.

## 2. System-neutral formats for change over time

| Format or tool | Renames as renames | Structure inside files | Alive in 2026 |
| --- | --- | --- | --- |
| Gource custom log and readers | no: A, M, D only | no | yes (0.56, per the 2026-10-16 survey) |
| git fast-import stream | yes (`R`, `C`); git emits them only with `-M`/`-C` | no | yes |
| reposurgeon | as the stream carries them | no | yes (5.12, 2026-10-05) |
| git-tfs; git-svn | git-tfs: not described; git-svn: renamed directories untracked | no | git-tfs unmaintained; git-svn in git's manual |
| CodeCharta cc.json 2.0 | log parsers count renames | dependency lens, one snapshot | yes (2.1.0, 2026-10-05) |
| Hercules output | no field | shotness records (functions) | last push 2023-02-07 |
| SonarQube SCM provider | not a history format (blame) | no | yes (2026.1) |
| FAMIX/Moose, Hismo, FamixDiff | FamixDiff: add, delete, move, rename | yes, the model is structure | Moose 13 (2026-10-06) |
| GHTorrent | no file changes at all | no | domain now redirects elsewhere |
| Boa | RENAMED, MOVED, COPIED | ASTs; change kinds for program entities | compiler last push 2024-12-03 |
| Alitheia Core | copy-or-move entries | no | archived, last push 2014-01-13 |

- **Gource's native readers** (format in the 2026-10-16 survey): `src/formats` holds apache, bzr, custom, cvs-exp, cvs2cl, git, gitraw, hg, svn (https://api.github.com/repos/acaudwell/Gource/contents/src/formats). svn runs `svn log -r %s --xml --verbose --quiet`, passes the action letter through, never reads `copyfrom-path`, and for directories will "accept only deletes" (https://raw.githubusercontent.com/acaudwell/Gource/master/src/formats/svn.cpp); hg runs `hg log %s -r 0:tip --style '%s'` (https://raw.githubusercontent.com/acaudwell/Gource/master/src/formats/hg.cpp) with `file_copy = "{date|hgdate}|{author|person}|A|{name}\n"`, so a copy becomes an addition (https://raw.githubusercontent.com/acaudwell/Gource/master/data/gource.style); CVS uses `commit_action = (commit_state == "dead") ? "D" : "M";` (https://raw.githubusercontent.com/acaudwell/Gource/master/src/formats/cvs-exp.cpp); bzr passes `[AMDR]` through (https://raw.githubusercontent.com/acaudwell/Gource/master/src/formats/bzr.cpp).
- **git fast-import stream.** "fast-import reads a mixed command/data stream from standard input"; "Most end users want to use one of the existing frontend programs, which parses a specific type of foreign source"; a `commit` has `author`/`committer` with `<when>`, `from` ("the first ancestor of the new commit") and `merge` ("one additional ancestor commit"), then fileops `M`, `D`, `C` (copy), `R` ("Renames an existing file or subdirectory"), `deleteall`; date formats raw, raw-permissive, rfc2822, now; "the fast-import mark can also be the Perforce changeset number or the Subversion revision number" (https://git-scm.com/docs/git-fast-import).
- **Who else emits it.** Mercurial's extension list has `fastexport`, "export repositories as git fast-import stream" (https://mercurial-scm.org/help/extensions); hg-fast-export is "A mercurial to git converter using git-fast-import" (https://github.com/frej/fast-export); reposurgeon's VCS table runs `fossil export --git`, and notes Unity Version Control "Read-only. The cm fast-export command requires access to the repository server." and Software Heritage "Read-only; set up with 'swh-fast-export init'" (https://gitlab.com/esr/reposurgeon/-/raw/master/surgeon/vcs.go); fossil now says "Use "fossil git export" instead." (https://fossil-scm.org/home/help/export); git-p4: "Changesets from p4 are imported using Git fast-import." (https://git-scm.com/docs/git-p4). Not via the stream: p4-fusion writes through libgit2 and gives an integration "two parents" (https://github.com/salesforce/p4-fusion; pushed 2026-09-21, https://api.github.com/repos/salesforce/p4-fusion).
- **reposurgeon.** "it relies on being able to parse and emit the command streams created by git-fast-export and read by git-fast-import"; read-write "git, hg, bzr, brz, fossil, darcs, RCS, and SRC"; read-side "SCCS, CVS and svn, and for the Software Heritage archive"; Perforce only through repotool, which "can mirror a p4 repository as a local git repository"; svn's `svnadmin dump` "doesn't ship a git-fast-import stream", so "Reposurgeon contains an interpreter for this stream format"; git to Subversion "is very lossy", and "Fossil does not have separate committer and author fields" (https://gitlab.com/esr/reposurgeon/-/raw/master/repository-editing.adoc); tag 5.12 on 2026-10-05 (https://gitlab.com/api/v4/projects/esr%2Freposurgeon/repository/tags?per_page=3).
- **git-tfs and git-svn.** git-tfs, "A Git/TFS bridge, similar to git-svn": "This project is no more actively maintained because we are no more users of TFS."; no intermediate format is described (https://github.com/git-tfs/git-tfs; last push 2024-08-10, https://api.github.com/repos/git-tfs/git-tfs). git-svn: "Renamed and copied directories are not detected by Git and hence not tracked when committing to SVN"; it "cannot yet represent merge history that happened inside git back upstream" (https://git-scm.com/docs/git-svn).
- **CodeCharta.** "The cc.json 2.0 wire format: { meta, files, lenses }": `files` is "the identity layer", lenses are "additive analysis overlays joined to files by id", an id is "first 16 hex of sha-256(canonical tree path)", dependency edges are `fromId`/`toId` under `lenses.dependency.edges`, `meta.commitHash` is "an optional short git SHA", and nothing carries history, renames or deltas (https://raw.githubusercontent.com/MaibornWolff/codecharta/main/visualization/app/codeCharta/util/ccJson2Schema.json). 2.0.0 (2026-09-02) made it the default; 2.1.0 (2026-10-05) added the experimental `ccsh dependencyparser` (https://raw.githubusercontent.com/MaibornWolff/codecharta/main/analysis/CHANGELOG.md). The git parser reads `git -c core.quotepath=off log --numstat --raw --topo-order --reverse -m`, tracks renames (`number_of_renames`) and emits `temporal_coupling` edges ">=35%" (https://raw.githubusercontent.com/MaibornWolff/codecharta/main/analysis/analysers/parsers/GitLogParser/README.md); the SVN parser reads `svn log --verbose` (https://raw.githubusercontent.com/MaibornWolff/codecharta/main/analysis/analysers/parsers/SVNLogParser/README.md).
- **Hercules.** Protocol Buffers: `Metadata` (`hash`, `repository`, `begin_unix_time`, `end_unix_time`, `commits`, `run_time`), burndown matrices, couples, and `ShotnessRecord` (`type`, `name`, `file`, `counters`); no message carries renames (https://raw.githubusercontent.com/src-d/hercules/master/internal/pb/pb.proto); last push 2023-02-07 (https://api.github.com/repos/src-d/hercules).
- **SonarQube.** A blame seam, not a history format (section 4). 2026.1: "Git and SVN are supported by default"; "Team Foundation Version Control (TFVC) is not supported. Please convert your project to a Git repository."; "A full Git clone is required." (https://docs.sonarsource.com/sonarqube-server/2026.1/analyzing-source-code/scm-integration).
- **FAMIX and Moose.** "MSE is the default file format supported by Moose. It is a generic file format and can describe any model"; in JSON "A model is represented as a collection of entities"; neither mentions time (https://modularmoose.org/users/file-format). Moose 13 Stable, 2026-10-06 (https://api.github.com/repos/moosetechnology/Moose/releases/latest). Hismo (Gîrba and Ducasse, JSME 18(3), 2006): "In Hismo, we add time information as a layer on top of the snapshot information"; "Hismo can be built on top of any snapshot meta-model without interfering with the existing meta-model"; identity by name will "miss refactorings like renaming or moving", and "it is the responsibility of the implementation to determine how the identity is defined" (https://scg.unibe.ch/assets/archive/papers/Girb06aHismo.pdf). FamixDiff "Computes the list of changes (add/delete/move/rename) between two versions of the same system (in two models)", pushed 2026-05-19 (https://api.github.com/repos/moosetechnology/FamixDiff); in 2013 its matching was "based on exact match between all incoming and outgoing associations of the entity" (https://list.inf.unibe.ch/hyperkitty/list/moose-dev@list.inf.unibe.ch/message/SPWJPRYGLN3FHM27GQAUF4OLF463I53Q).
- **MSR datasets.** GHTorrent's 23 tables include `commits` (`id`, `sha`, `author_id`, `committer_id`, `project_id`, `created_at`) and `commit_parents` (`commit_id`, `parent_id`) and no table of changed files (https://raw.githubusercontent.com/gousiosg/github-mirror/master/sql/schema.sql); ghtorrent.org now redirects to an unrelated site. Boa's `ChangeKind` describes "the kind of change for an artifact or program entity/element": ADDED, DELETED, MODIFIED, RENAMED, MOVED ("moved to a different parent"), COPIED, MERGED, UNCHANGED (https://raw.githubusercontent.com/boalang/compiler/master/src/proto/shared.proto); `ChangedFile` has `change`, `kind`, `name`, per-parent `changes`, `previous_names` and an `ast` flag (https://raw.githubusercontent.com/boalang/compiler/master/src/proto/diff.proto; last push 2024-12-03, https://api.github.com/repos/boalang/compiler).
- **Alitheia Core (SQO-OSS).** `PathChangeType`: UNKNOWN, UNMODIFIED, ADDED, MODIFIED, REPLACED ("Path was deleted, then a new version was added in the same revision"), DELETED (https://raw.githubusercontent.com/istlab/Alitheia-Core/master/alitheia/core/src/main/java/eu/sqooss/service/tds/PathChangeType.java); `CommitCopyEntry`, "A commit entry representing a copy or a move (rename) operation", holds `fromPath`, `fromRev`, `toPath`, `toRev` (https://raw.githubusercontent.com/istlab/Alitheia-Core/master/alitheia/core/src/main/java/eu/sqooss/service/tds/CommitCopyEntry.java); archived, last push 2014-01-13 (https://api.github.com/repos/istlab/Alitheia-Core).

Silences:
- Gource's `addFile`, which interprets letters other than A, M, D, was not read.
- No source read says whether Unity's or Software Heritage's exporters emit `R` fileops.
- git-tfs's README says nothing on how TFVC renames, branches or merges map to git.
- cc.json 2.0 does not say what becomes of a renamed file's path-derived id.
- Software Heritage's data model page could not be loaded.

## 3. Deltas of a dependency graph over time

- **Repo Visualizer `history.json`** (schema only): top level `repo`, `generatedAt`, `totalCommits`, `firstCommit`, `lastCommit`, `exclude`, `commits`; a commit has `sha`, `shortSha`, `date`, `author`, `authorEmail`, `message`, `stats`, `changes` and no parents; a change has `path`, `added`, `removed`, `binary`, `status` (`isDeleted ? 'D' : 'M'`, so additions are written as M) (https://raw.githubusercontent.com/Jany-M/repo-visualizer/main/scripts/analyze.mjs), and `resolvedImports`, the touched file's whole resolved, de-duplicated target list, which replaces `imports` (https://raw.githubusercontent.com/Jany-M/repo-visualizer/main/scripts/importResolve.mjs). Edge removal is implied by replay, never stated.
- **Evolution Storyboards' input.** CCVisu "reads the input graph from a file in RSF (Relational Standard Format)" and "extracts the co-change graph from a CVS or SVN version repository"; the page gives no RSF grammar and no word on storyboards (https://ccvisu.sosy-lab.org/).
- **GEXF and Gephi.** GEXF "is a language for describing complex networks structures" (https://gexf.net/); 1.3 is the "Current recommended version since Mar. 2022" and added `timerepresentation` (interval or timestamp) and a slice mode (https://gexf.net/history.html); in `mode="dynamic"`, "The whole graph, each node, each edge and their respective data values may have time limits", with spells for repeated lifetimes (https://gexf.net/dynamics.html). Gephi cannot mix timestamps and intervals in one graph, and since 0.9.1 merges snapshot files (`mode="slice"`, `timerepresentation="timestamp"`, one graph-level timestamp each) into one timeline when node ids match across files (https://docs.gephi.org/desktop/User_Manual/Import_Dynamic_Data/); Gephi 0.11.3 shipped 2026-09-06 (https://api.github.com/repos/gephi/gephi/releases/latest).
- **GraphStream DGS.** "DGS is a file format allowing to store graphs and dynamic graphs in a textual human readable way"; header `DGS004`; events `an`, `cn`, `dn`, `ae`, `ce`, `de`, `cg`, `st` ("Allows to define a new step (clock tick)") and `cl` ("Clear the whole graph"); "all the events in one step can be considered occurring at the same time" (https://graphstream-project.org/doc/Advanced-Concepts/The-DGS-File-Format/); gs-core last push 2023-07-06 (https://api.github.com/repos/graphstream/gs-core).
- **Gephi graph streaming.** "a simple JSON-based format that can be used to post mutations to a graph (i.e. node and edge additions, removals and updates)", one object per line such as `{"an": {...}}`, `{"ae": {...}}` (https://python.igraph.org/en/main/api/igraph.remote.gephi.GephiGraphStreamer.html).
- **JSON Graph Format.** "A proposal for representing graph structures in JSON"; version 2 (January 2020), hypergraphs (January 2021); nothing on time or deltas (https://github.com/jsongraph/json-graph-specification).
- **NetworkX family.** NetworkX-Temporal 1.4.4 "extends the NetworkX library to dynamic graphs" as static, snapshot-based, event-based ("a sequence of edge-level events (interactions)") or unrolled graphs (https://networkx-temporal.readthedocs.io/en/latest/). - **NetLogo.** `nw:save` writes dl, gdf, gexf, gml, vna, and GraphML through `nw:save-graphml`; nothing on time (https://docs.netlogo.org/nw/save).
- **Deltas computed, not exchanged.** FamixDiff diffs two Famix models (section 2). GitHub's `GET /repos/{owner}/{repo}/dependency-graph/compare/{basehead}` "Gets the diff of the dependency changes between two commits", items with `change_type` `added` or `removed`, `manifest`, `ecosystem`, `name`, `version`, `scope`: package dependencies from manifests, for one pair of commits (https://docs.github.com/en/rest/dependency-graph/dependency-review).

## 5. TFVC's rename and branch model and a tree of directories

- **Renames: explicit, yes** (section 1). Since TFS 2010, renames are "Now implemented as a branch + delete behind the scenes (new name is branched from the old, then the old name is deleted)."; "We also added a new 'source rename' bit to identify items that were deleted because they were renamed."; "History will default to slot mode, that is, renames won't be followed automatically"; "an ItemID is unique to a path. Practically, this means that when an item is renamed, it effectively becomes a new item (because it has a new path)." (Matt Mitrik, TFS team, 2009-05-28, https://learn.microsoft.com/en-us/archive/blogs/mitrik/changing-to-slot-mode-in-tfs-2010-version-control). A 2010 commenter there asked for "something to link the 2" (old and new path) in the API; the 7.1 change object carries `mergeSources` with `isRename` (section 1).
- **Branches are paths.** "Unlike Git branches, which are repository scoped, TFVC branches are path scoped and not as lightweight."; "Main Only" "can be folder-based or with the main folder converted to a Branch" (https://learn.microsoft.com/en-us/azure/devops/repos/tfvc/branching-strategies-with-tfvc). `tf branch` "copies an item or set of items, including metadata and version control history, from one location to another" (https://learn.microsoft.com/en-us/azure/devops/repos/tfvc/branch-command). In a changeset a branch is the `branch` change type with `mergeSources` "in case of rename or branch creation"; `TfvcItem.isBranch` marks a branch (section 1).
- **Merges are per file.** "Merges in TFVC occur at the file level, not at the entire repository. Only a subset of changed files can be merged from one branch to another." (https://learn.microsoft.com/en-us/azure/devops/repos/git/import-from-tfvc). `tf merge` takes changeset ranges, and after a baseless merge "TFVC records the merge history and establishes a relationship between the folders and files" (https://learn.microsoft.com/en-us/azure/devops/repos/tfvc/merge-command). Merged items show combined types such as "merge, branch" and "merge, edit" (Mitrik, above).
- **No mainline in git's sense.** Changesets carry numbers and no parents, and the changes endpoint names a changeset by organization and id alone (section 1). "Git stores history as a snapshot of the repository in time, while TFVC records the discrete operations that occurred on a file."; "Change types in TFVC like rename, undelete, and rollback can't be expressed in Git."; Microsoft advises "we recommend not migrating your history" (https://learn.microsoft.com/en-us/azure/devops/repos/git/import-from-tfvc). A main line is a folder by convention (branching strategies, above).
- **Servers in use in 2026.** TFS 2018: Fixed policy, extended end 1/12/2028 PT (https://learn.microsoft.com/en-us/lifecycle/products/visual-studio-team-foundation-server-2018); Azure DevOps Server 2019: extended end 4/11/2029 (https://learn.microsoft.com/en-us/lifecycle/products/azure-devops-server-2019); 2020: mainstream ended 10/15/2025, extended end 10/9/2030 (https://learn.microsoft.com/en-us/lifecycle/products/azure-devops-server-2020); 2022: mainstream to 1/12/2028, extended to 1/12/2033 (https://learn.microsoft.com/en-us/lifecycle/products/azure-devops-server-2022); "Azure DevOps Server" without a year: Modern policy, in support since 12/9/2025 (https://learn.microsoft.com/en-us/lifecycle/products/azure-devops-server); its RC post: "we're removing the year from the name", with no word on TFVC (https://devblogs.microsoft.com/devops/announcing-the-new-azure-devops-server-rc-release/).
- **What each exposes.** REST versions: TFS 2018 RTW 4.0, Update 2 and 3 4.1, Server 2019 5.0, 2020 6.0, 2022 7.0, 2022.1 7.1, vNext 7.2 (https://learn.microsoft.com/en-us/rest/api/azure/devops/?view=azure-devops-rest-7.1); the changes endpoint's docs begin at 4.1 (get-changeset-changes, section 1). The current tf pages apply to "Azure DevOps Services | Azure DevOps Server | Azure DevOps Server 2022" and "Visual Studio 2019 | Visual Studio 2022", linking 2019, 2020 and TFS 2013 to 2018 versions (history-command, section 1); none describes local history. The cross-platform TEE-CLC: "This project is no longer maintained." (https://github.com/Microsoft/team-explorer-everywhere).

## 6. Precedents for a tool-minted format that became shared

**Gource's custom log.** Gource defines the line and writes it itself (2026-10-16 survey). The other emitters found are small converters, all for Gource: Tfs2Gource, "Small [windows] command line designed to export changesets from TFS for use in Gource", created 2013-05-21, last push 2014-04-07, one star (https://github.com/Mozketo/Tfs2Gource, https://api.github.com/repos/Mozketo/Tfs2Gource); Mark Heath's 2011 TFS code, which keeps changes whose type includes Edit, Add or Delete, maps them to M, A and D, and otherwise throws "Unsupported change type" (https://markheath.net/post/visualizing-tfs-repositories-with); MultiGource, "custom logs from many Git repos" (2012 to 2015, https://api.github.com/repos/frencil/multigource); Rource, "A Gource log generator from Git repositories" (2023, https://api.github.com/repos/AdamLeyshon/rource); clearcase2gource (section 4). No second reader of the format was found; with three letters, a rename or branch reaches it only as A, M and D.

**LSP's `TextDocumentContentChangeEvent`.** "An event describing a change to a text document. If only a text is provided it is considered to be the full content of the document."; the partial form has `range` ("The range of the document that changed.") and `text` ("The new text for the provided range."), `rangeLength` being deprecated; the whole form's `text` is "The new text of the whole document."; "The content changes describe single state changes to the document", applied in order (c1 moves S to S', c2 S' to S''), and the identifier's version "points to the version after all provided content changes have been applied" (https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.18/textDocument/didChange.md); "The version number of a document will increase after each change, including undo/redo. The number doesn't need to be consecutive." (https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/, which marks 3.18 current and 3.19 upcoming). Its reason to exist is "so a single Language Server can be re-used in multiple development tools" (https://microsoft.github.io/language-server-protocol/overviews/lsp/overview/); the implementors page lists about 400 servers and takes additions by pull request (https://microsoft.github.io/language-server-protocol/implementors/servers/).

**LSIF and SCIP.** LSIF's purpose "is to define a standard format for language servers or other programming tools to dump their knowledge about a workspace", a graph whose "edges represent the method and vertices are" documents, positions or results, "based on JSON as with the LSP"; "The 0.6.0 version of LSIF is currently under construction"; tools listed: `lsif-tsc`, `lsif-npm` (https://microsoft.github.io/language-server-protocol/specifications/lsif/0.6.0/specification/). SCIP is "a language-agnostic protocol for indexing source code" with its schema in `scip.proto` and indexers named for Java/Scala/Kotlin, TypeScript/JavaScript, Rust (rust-analyzer), C/C++, Ruby, Python, C#/VB, Dart, PHP and Debian packaging (https://github.com/sourcegraph/scip); v0.10.0 on 2026-09-03 (https://api.github.com/repos/sourcegraph/scip/releases/latest). Its design doc cites LSIF's "issues of development velocity, debugging, as well as indexer performance bottlenecks", picks Protobuf because "TLV format enables streaming reads and writes as well as merging by concatenation" and "Rules for maintaining forward and backward compatibility are easily understood", prefers documents to one graph and string ids to integer ids (whose off-by-one bugs "cause code navigation to fail repo-wide"), and expects "the number of SCIP producers to be much higher than the number of consumers" (https://raw.githubusercontent.com/sourcegraph/scip/main/docs/DESIGN.md). GitLab's code intelligence is "powered by LSIF", "does not natively support SCIP", and converts SCIP indexes with the SCIP CLI (https://docs.gitlab.com/user/project/code_intelligence/).

**git's fast-import stream** (added here). Written as git's contract for "frontend programs" (https://git-scm.com/docs/git-fast-import), it is now emitted by Mercurial's `fastexport`, fossil, Unity's `cm fast-export` and Software Heritage's `swh-fast-export`, and read and written by reposurgeon across eight systems (section 2); capabilities are negotiated by `feature` commands, which abort if unsupported (git-fast-import, above). **SWHID** (added here): identifiers from the Software Heritage archive, "officially adopted as ISO/IEC 18670:2025" on April 23, 2025, kept by "the SWHID core team" under a working group in public repositories (https://www.swhid.org/, https://github.com/swhid/specification).

Silences:
- No program other than Gource was found that reads the custom log.
- The LSP and LSIF pages give no adoption history over time, and the LSIF page carries no date.

## Read-across

- Agreement: systems that record moves (TFVC, Perforce, Mercurial) and models built for many systems (Trac's MOVE and COPY, Alitheia's copy-or-move entry, Boa's RENAMED, MOVED and COPIED, CodeCharta's RENAME with an old name, JetBrains' before and after revisions, the stream's `R` and `C`) all keep an old path beside a new one; the formats made for one viewer (Gource's log, Repo Visualizer's `history.json`) do not.
- Agreement: a rename survives a chain only if every link carries it; git emits `R` only with `-M`/`-C`, Subversion commits a copy and a delete, Gource's hg reader turns a copy into an addition, and Mark Heath's TFS converter keeps only changes whose type includes edit, add or delete.
- Agreement: of the five systems, history is local only for git, Mercurial and P4 personal servers; Subversion, TFVC and P4 servers hold it, and a TFVC workspace caches no history at all.
- Agreement: truncation shows differently in each: git answers `--is-shallow-repository`, `p4 clone -m` limits revisions per file, the Azure Repos importer stops at 180 days, and SonarQube needs a full git clone for blame.
- Disagreement on order: Trac and Alitheia require a total order (next, previous), which TFVC changesets, Subversion revisions and P4 changelists give; JetBrains, reposurgeon and the stream's `from`/`merge` require a DAG of parents; Gource and CodeCharta keep neither ids nor parents, only time.
- Disagreement on what crosses the seam: reposurgeon's extractor hands over each revision's whole manifest; Trac, Alitheia and the TFVC changes endpoint hand over change lists; Subversion's dump carries actions and, in version 3, content deltas; Gephi joins snapshots by id; DGS, Gephi streaming and DyNetX carry events only.
- Disagreement on identity: TFVC since 2010 identifies an item by its path and records a rename as branch plus delete; git infers by content similarity; CodeCharta 2.0 hashes the path; JetBrains equates commits by hash; Hismo leaves identity to the implementation.
- Disagreement on merges: git, Mercurial and the stream record merge parents for whole commits; TFVC merges per file, a subset at a time; p4-fusion turns a P4 integration into a second parent.
- Gap: structure inside files travels only in research or single-tool formats (Boa's ASTs, Hercules's shotness, FAMIX models and FamixDiff, CodeCharta's per-snapshot dependency lens); no VCS change format and no general dynamic-graph format read carries file-to-file dependency deltas per change.
- Observation: the shared formats found (the fast-import stream, LSP, SCIP, SWHID) each have a written specification in a public manual or repository and several producers; Gource's log has several producers, one reader and no rename type; GHTorrent's domain has lapsed and Alitheia Core is archived.

## The agent's reading for this project

_Read by the root agent on 2026-10-17 from the six sections above and the survey of the day before. A judgement for the owner to answer by exception, not a decision; the plan's C13 carries the outcome._

1. **The seam is small, and the field has drawn it three ways.** Gource and CodeCharta need only time-ordered file events; Trac and Alitheia need a total order of revisions; JetBrains, reposurgeon and the fast-import stream need a commit graph with parents. The history command needs the second with an eye on the third: an ordered list of changes on a mainline, each with its id, its date, its author, its message and, where the system has them, its parents; a working tree at a change; the renames between two changes; the files whose content changed between two changes; and where the local knowledge begins. Every system surveyed answers the first two: git by `rev-list --first-parent` and a worktree or archive, TFVC by changeset number and `tf get /version:C<n>` or the `tfvc/items` download, Subversion by revision and `svn export -r`, Mercurial by `hg log` and `hg archive -r`, P4 by `p4 changes` and `p4 sync @change`. So the seam is five operations with git as the first implementation, and a second system is a second implementation of the same five.
2. **A rename has a basis, as an edge does.** TFVC, Mercurial and P4 record renames; Subversion commits a copy and a delete that `copyfrom-path` makes legible; git infers them by similarity, which the owner chose to trust. The sequence should carry how each rename was known, recorded or inferred, the way a Live Doc's dependency line carries `contract` or `configuration` as its basis, so that a picture can say "renamed" and, on hover, "inferred at 50% similarity" where that is the truth. Nothing else in the sequence depends on the system.
3. **No shared format carries what the sequence carries, so it is minted here, and written down.** The nearest shared change format, git's fast-import stream, is emitted by Mercurial, fossil, Unity Version Control and Software Heritage and read by reposurgeon for eight systems, but it is a stream of file contents with rename and copy operations, far heavier than a graph's shape over time, and it carries nothing about dependencies. The general dynamic-graph formats (GEXF's intervals and slices, GraphStream's DGS events, DyNetX's plus-and-minus lines) carry node and edge events but know nothing of files, symbols or renames. The precedents that became shared (the stream, LSP, SCIP, SWHID) each had a written specification in a public place and several producers; so the sequence's format is specified in the decisions log when it lands, versioned by its `format` field, and its head names the system it was read from and the sampling rule. An export to GEXF or DGS for Gephi is not built unless a scenario asks for it, by the owner's rule that an agent's open question is not work until one does.
4. **TFVC later means a server, and the offline rule.** A TFVC workspace caches no history; `tf history` and the REST changesets both read the server, SonarQube 2026.1 declines TFVC outright, and Microsoft's own importer stops at 180 days of history. So a TFVC implementation of the seam can only be a call to the person's own server, which the tool never makes on its own: it would be the person's explicit act, with the server named and nothing cached beyond what they asked, and the sequence's head would say its source was a server and not a folder. TFS stays out of scope now, as the owner said on October 16, and this is the shape it would take if it came in. The on-premises servers the owner's estate could hold are supported into the 2030s (TFS 2018 to January 2028, Azure DevOps Server 2019 to 2029, 2020 to 2030, 2022 to 2033), with the changes endpoint documented from REST 4.1.
5. **TFVC has no mainline in git's sense, and its merges are per file.** Its changesets are a numbered total order with no parents; a branch is a folder; a merge is a change type on files. The seam's "mainline" is therefore the ordered changes of one folder's history, which is also what a folder-scoped scan wants, and a merge is a step whose delta is whatever the changeset changed; git's first-parent line is one case of that order, with parents carried where they exist.
6. **Identity by path, which TFVC chose in 2010, is what the sequence does for hubs already** (C6): a directory is its path across time and a rename of it is derived from its files' renames. For files the sequence keeps the system's word on identity, recorded or inferred, and shows a death and a birth where neither is given.
