### What stands from these, as the agent reads them

Not decisions; the owner's words above are the evidence, and today's words govern where they differ from older ones.

1. **The wish is ten months old and has kept its shape.** Many copies of the data behind the picture, one per commit, played as the evolution of a workspace (2025-12-19); the inflation and deflation of the universe seen in the force-directed graph (2026-09-27); a Gource-like timelapse in the 3D graph (2026-10-08); the declared-structure layout snapshot by snapshot (2026-10-16). What changed is the layout named, and that follows the 2026-10-14 structure layout's existence.
2. **A standing constraint from 2025-11-10 bears on where the sequence may live.** Nothing derived from local git history is written into the committed docs, because two clones' histories differ (shallow clones, different fetch depths) and the docs must be reproducible from source; no remote traversal and no authentication. The 2025-11-11 allowance is the other half: a view nothing permanent depends on may read local history. A timeline is such a view: the docs at each commit stay the truth, the sequence is derived from them and from `.git/`, and it is carried as data beside the bundle, never as lines in a Live Doc. Today's words reopen the reading of `.git/`, not the writing of its numbers into docs; the two are consistent.
3. **The place is the 3D graph, and the World Map keeps its own snapshot question.** The owner set the World Map apart on 2026-10-08; "two snapshots of one system on the board" (ideas.md, 2026-09-28) remains the World Map's version of time and is not this feature.
4. **The flyover is a different axis.** A system in action (2026-09-26) is behaviour within one state; the trajectory is one system across states. Both are the owner's wishes; only the second is picked.
5. **The prior art already in hand says two things the design will meet at once.** Keep each artifact's place (CodeCity's fixed real estate and empty lots; Bederson's rule), and let time be a playback rate with a pause and a free camera (Gource). Part 2 extends this.

### 1. How tools have shown a codebase changing over time

#### Gource (the owner's "gold standard")

What it is. "Gource is a visualization tool for source control repositories. The repository is displayed as a tree where the root of the repository is the centre, directories are branches and files are leaves. Contributors to the source code appear and disappear as they contribute to specific files and directories." (README, https://github.com/acaudwell/Gource/blob/master/README.md). "Gource includes built-in log generation support for Git, Mercurial, Bazaar and SVN" (https://gource.io/). Latest release on 2026-10-16: 0.56, "6 March 2026 Gource 0.56 has been released" (https://gource.io/); the ChangeLog already lists an unreleased 0.57 (https://github.com/acaudwell/Gource/blob/master/ChangeLog). Rendering is OpenGL and "requires a 3D accelerated video card" (README), but the tree itself is laid out in two dimensions: directory positions are `vec2` in `src/dirnode.cpp` (https://github.com/acaudwell/Gource/blob/master/src/dirnode.cpp).

The log it reads is an event log, not a series of snapshots. The custom format is pipe-delimited: "timestamp - An ISO 8601 or unix timestamp of when the update occurred. username - The name of the user who made the update. type - initial for the update type - (A)dded, (M)odified or (D)eleted. file - Path of the file updated. colour - A colour for the file in hex (FFFFFF) format. Optional." Example: `2010-06-03T05:39:55Z|andrew|A|src/main.cpp` (README; same text at https://github.com/acaudwell/Gource/wiki/Custom-Log-Format). Gource can write any supported VCS log out in this format with `--output-custom-log` (README), and it can be streamed live: "make a script that feeds custom log format entries into Gource via STDIN" (wiki Custom Log Format).

A rename does not exist in that format. There are only A, M and D. For git, Gource runs `git log --reverse --raw --encoding=UTF-8 --no-renames` (https://github.com/acaudwell/Gource/blob/master/src/formats/git.cpp), and the ChangeLog says why, at version 0.15: "Added --no-renames to the git log command as they don't display correctly." (ChangeLog). So a renamed file is a delete at the old path and an add at the new one. A pull request opened 2026-03-06 for Bazaar does the same on purpose: it "Splits rename entries into a **delete** of the old path and an **add** of the new path, matching how other VCS parsers handle renames" (https://github.com/acaudwell/Gource/pull/358). A user on issue #61 (2017-01-04) reports the wholesale case: "This also happens when a folder name has changed... Everything from this folder is then removed." (https://github.com/acaudwell/Gource/issues/61).

How the tree is built and held. The tree is a physics simulation. In `RDirNode::applyForces`, each directory is pulled toward its parent ("pull towards parent"), pushed outward along the grandparent-to-parent direction ("dirs should be pushed along the parent_parent to parent normal"), and repelled by siblings ("dirs should repulse from other dirs of this parent"), with a quadtree for neighbour forces (`src/dirnode.cpp`). A new directory starts at its parent's position offset by a hash of its path: `pos += normalise(normalise(parent->getPos() - parentP->getPos()) * 2.0f + vec2Hash(abspath));` (`setInitialPosition`, same file). Files are placed in rings around their directory (`updateFilePositions`). "Elasticity is a fun if somewhat pointless effect that controls how 'rubbery' directory branches behave" (https://github.com/acaudwell/Gource/wiki/Controls).

Files vanish by idleness, not only by deletion. "By default, Gource 'expires' files which haven't been touched by a user in the 60 seconds", turned off with `--file-idle-time 0` (wiki Controls). Issue #61's reporter saw "almost everything disappears with no reason" and the answer given was `--file-idle-time 0` (issue #61). Updates are deliberately delayed: "Gource doesn't actually apply updates immediately as they come up in the log, instead the user will move towards the area of the new files before adding them. This is easier to follow but it also means if you are using a small value for 'seconds-per-day', it can get quite far behind." (`--max-file-lag`, default 5 s; wiki Controls).

Time controls. "Seconds per day controls the amount of time Gource will take to display each day in the log file (10 seconds by default)"; "`--realtime` sets seconds-per-day to 60\*60\*24"; "Gource will advance to the next entry (after 3 seconds by default) if nothing is happening", with `--auto-skip-seconds` and `--disable-auto-skip`; "Use --start-position and --stop-position to specify the period of the project history to display. The argument is a fraction of the total length of the project history file" (wiki Controls). `--start-date`/`--stop-date`, `--loop`, `--time-scale` ("affects the movement speed of user avatars") and `--author-time` (new in 0.56) are in the README. Seeking: "You can seek to any point in the project using the time-line widget that appears along the bottom of the screen when the mouse passes over it. Mousing over the time-line shows the date at that position in the history file." Pause: "Pause the action by pressing **space**. While paused, you can still move the camera around and inspect the details of files and users." (wiki Controls). Keys: "(N) Jump forward in time to next log entry", "(<>) Adjust time scale / user avatar movement speed", "(+-) Adjust simulation speed", "(V) Toggle camera mode", "(T) Toggle display of directory tree edges" (README). There is no key for stepping backward.

What a seek does. `Gource::seekTo` calls `reset()` and then `commitlog->seekTo(percent)` (https://github.com/acaudwell/Gource/blob/master/src/gource.cpp); `reset()` deletes the root directory node, every file and every user and sets the clock to zero (same file), and the log seek is a byte offset, `percent * file_size` (https://github.com/acaudwell/Core/blob/master/seeklog.cpp). A seek therefore rebuilds the scene from that point in the log; the tree as it stood at that date is not reconstructed.

Camera. "**overview** - keeps the entire repository in view. **track** - follows the current active users or the selected user. The default mode is 'overview'." "As of 0.27, Gource will automatically rotate the view to make best use of the available screen space", disabled with `--disable-auto-rotate`; dragging pans or rotates and "will also disable automatic camera movement until you toggle the camera mode" (wiki Controls).

Long histories. The README warns: "For large projects, generating a log of the project history may take a long time... you may like to save a copy of the log for later use." `--max-files NUMBER`: "Set the maximum number of files or 0 for no limit. Excess files will be discarded." (README); in code, `addFile` returns nothing once `files.size() >= max_files` (`gource.cpp`). Commits are read into a queue capped at `commitqueue_max_size = 100` (`gource.cpp`). The docs give no measured limit in files, commits or memory; an open issue from 2018 reports leaks under AddressSanitizer (https://github.com/acaudwell/Gource/issues/150).

What it does not show. The README, wiki and site describe only the directory tree, files (coloured by extension, with a `--key` legend) and contributors; none of them mentions dependencies between files, file contents or line counts. An open pull request from 2025-09-30 proposes "Scale nodes by file size" (https://github.com/acaudwell/Gource/pull/351).

#### The other tools

- **code_swarm** (Ogawa and Ma; videos May 2008, TVCG 2009; already surveyed here on 2026-09-28). The sample configuration samples time by a fixed project interval per frame: "# Project time per frame MillisecondsPerFrame=21600000" (six hours), with "Optional Method instead of MillisecondsPerFrame #FramesPerDay=4" (https://github.com/VIDILabs/code_swarm/blob/master/data/sample.config). The original project page at michaelogawa.com/code_swarm now returns an unrelated site's "Page not found" (fetched 2026-10-16), so the visual description remains secondary.
- **Evolution Matrix** (Lanza, IWPSE 2001, https://scg.unibe.ch/archive/papers/Lanz01cEvolutionMatrix.pdf). Unit: class. "Each column of the matrix represents a version of the software, while each row represents the different versions of the same class." Added classes "are added at the bottom of the column of that version"; removed classes "leave empty space on the matrix". Time is sampled per release (case studies of "21 versions"). Nothing moves; it is a static small-multiples grid. Its stated limits: "The approach is not immune to name changes" and "the approach has worked for systems of nearly 100 classes."
- **Evolution Radar** (D'Ambros, Lanza, Lungu, IEEE TSE 35(5), 2009, https://doi.org/10.1109/tse.2009.17). Unit: files grouped into modules, placed by logical coupling, "the implicit dependency between software artifacts that have been changed together". The abstract does not say how time is navigated.
- **CVSscan line of work** (Voinea, Telea, van Wijk). The TU/e record "A Line Based Visualization of Code Evolution" (2005): "each file version is shown as a column and the horizontal axis shows time" (https://research.tue.nl/nl/publications/47bd7723-e631-422d-8104-320a61b61f9d). Unit: line of code within one file. The SoftVis 2005 CVSscan paper itself was not loaded.
- **Chronos** (Servant and Jones, VISSOFT 2013, https://doi.org/10.1109/vissoft.2013.6650547). Unit: an arbitrary slice of lines, "down to the line-level"; it "provides change history across all historical versions (i.e., it is not limited to a pairwise 'diff')" in "a zoom-able user interface".
- **CodeCity and time** (Wettel and Lanza, WCRE 2008): age map, time travel with fixed real estate, timeline; already surveyed here on 2026-09-28 (lines 735 to 739 of that survey).
- **git-of-theseus** (Erik Bernhardsson). Not an animation: stack plots of "the total number of lines in a repo broken down into cohorts by the year the code was added" and Kaplan-Meier survival curves (https://github.com/erikbern/git-of-theseus). It samples the first-parent chain at most once per `--interval`, "Min difference between commits to analyze (default: 604800s)", one week (https://github.com/erikbern/git-of-theseus/blob/master/git_of_theseus/analyze.py).
- **Hercules** (src-d). Burndown is "Exactly the same what git-of-theseus does but much faster"; "Granularity is the number of days each band in the stack consists of. Sampling is the frequency with which the burnout state is snapshotted." (https://github.com/src-d/hercules). Couples: files changed in the same commit. Last push to the repository 2023-02-07; last release v10.7.2, 2020-01-14 (GitHub API, read 2026-10-16).
- **GitHub Insights.** "You can see all commits made to a repository in the past year (excluding merge commits) in the Commit graph. The top graph shows commits for the entire year by week"; the code frequency graph shows "additions and deletions for each week"; "Certain contributor, commit, and code frequency insights are only available for repositories that have fewer than 10,000 commits." (https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/analyzing-changes-to-a-repositorys-content). The network graph "is a timeline of the most recent commits, and shows up to 100 of the most recently pushed-to branches... Use arrow keys or other keyboard shortcuts" (https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/understanding-connections-between-repositories). None of these shows files or structure.
- **Evolution Storyboards** (Beyer and Hassan, WCRE 2006, https://www.sosy-lab.org/research/pub/2006-WCRE.Animated_Visualization_of_Software_History_using_Evolution_Storyboards.pdf). The early tool that animates a dependency graph from version control: "a sequence of animated panels... one panel for each considered time period", each laid out by "an energy-based graph clustering algorithm" (CCVisu) over co-change graphs. Three samplings are compared: "a new panel after every 3 months", "after every 1000 dependencies", or "for each release", with the warning that under the latter two "the user is not aware of the amount of time that has elapsed between two panels". Stability: "the layout algorithm starts with the positions of the previous layout"; "For the first panel, the tool uses a random layout." Movement is shown, not hidden: a grey circle at the previous position and "a grey line from the previous position pt−1(a) to the current position pt(a)... animated by moving bubbles", restricted to a filtered set of nodes "to avoid clutter".
- **GEVOL** (Collberg, Kobourov, Nagra, Pitts, Wampler, SoftVis 2003): evolution of "call, inheritance, or flow graphs" per the Beck et al. survey (https://doi.org/10.2312/eurovisstar.20141174). The PDF on the author's site returned 404 (www2.cs.arizona.edu, 2026-10-16); not read.
- **Since 2023.** *Repo Visualizer* (Jany-M; repository created 2026-05-17, last push 2026-08-30, 12 stars on 2026-10-16) is the closest prior art found to the owner's idea: it "extracts the import graph between files at every commit, and renders the evolving structure as an animated force-directed network. Each top-level directory is a feature cluster, each file is a node sized by code churn, each import is an edge." Layout "wraps `d3-force` with cluster forces that pull each node toward its top-level directory's center on a ring. The simulation runs continuously and warm-restarts when nodes are added." State is "an incremental graph state: a `Map<path, node>` and a `Map<key, edge>`... Seeking backward replays from scratch up to the target." Keys: Space play/pause, Left/Right "Step backward / forward one commit", End "Jump to final state"; "For very large repos, you can limit to recent commits: `--max=300`" (https://github.com/Jany-M/repo-visualizer). *CodeCharta* (MaibornWolff, analysis release ana-2.1.0 on 2026-10-05) does not animate; its "Delta view" loads "two versions and compare[s] them. Green grew, red shrank" (https://github.com/MaibornWolff/codecharta).

### 2. Dynamic graph drawing and the reader's bearings

- **The mental map** (Misue, Eades, Lai, Sugiyama, J. Visual Languages and Computing 6(2), June 1995, https://doi.org/10.1006/jvlc.1995.1010). The publisher page returned 403 and no free copy was found, so the paper was not read. The Beck et al. survey summarizes it: "in order to preserve the mental map, their force-directed approach maintains the original horizontal and vertical ordering of nodes while reducing overlap; the initial layout, however, is not computed by the approach" (https://doi.org/10.2312/eurovisstar.20141174). Archambault and Purchase give the definition most experiments test, Coleman and Parker's: "the placement of existing nodes and edges should change as little as possible when a change is made to the graph" (https://eprints.gla.ac.uk/108356).
- **Online versus offline.** Beck, Burch, Diehl, Weiskopf (EuroVis STAR 2014, full text read): layouts "compute the individual node-link layouts of the animation only by considering past time steps (online) or both, past and future time steps (offline). In general, online approaches are more flexible... On the other hand, offline approaches allow for better optimizing the layout and maintaining the mental map because next changes are known." Offline's simplest form is to "aggregate the full sequence of graphs and to lay out only this so-called super-graph"; "However, adapting the layout gradually might be a better trade-off between preserving the mental map and individually readable layouts." Brandes and Wagner (1997) model it as "a readability model of the individual graphs and a stability model". Brandes and Mader (2012) "contrast layout stability to individual layout quality and conclude that only linking nodes of adjacent time steps provides better results than positioning nodes at or near fixed positions." Gorochowski et al. "use the concept of node age to preserve specifically the layout of old and stable graph structures."
- **Foresighted layout** (Diehl, Görg, Kerren, VisSym 2001, https://doi.org/10.2312/vissym/vissym01/175-184): "a generic algorithm which computes a Foresighted Layout for dynamically drawing these graphs while preserving the mental map... it takes a static graph drawing algorithm as a parameter. In other words, trees can be animated with a static tree layouter". The survey adds "Foresighted Layout with Tolerance" (Diehl and Görg 2002) and its extension to compound graphs with nested boxes (Pohl and Birke 2008).
- **The 2017 journal survey** (Beck et al., Computer Graphics Forum 36(1), online 2016-01-25, https://doi.org/10.1111/cgf.12791; abstract read, full text not loaded): "we identify the representation of time as the major distinguishing feature for dynamic graph visualizations: either graphs are represented as animated diagrams or as static charts based on a timeline. Evaluations of animated approaches focus on dynamic stability for preserving the viewer's mental map".
- **Empirical results on the mental map.** Archambault and Purchase, IJHCS 71(11), 2013: "To date, no experiment has found conclusive evidence that supports the effectiveness of the mental map in the comprehension of a dynamic graph series." (https://eprints.gla.ac.uk/108356). Their Graph Drawing 2012 experiment on orientation found the opposite for that task: "preserving the mental map for the tasks tested is significantly faster and produces fewer errors. As the number of targets increase, this result holds." (https://eprints.gla.ac.uk/78675). On memorability (2012): "no significant difference in terms of response time or error rate", but "qualitative data suggests that... preserving the mental map makes memorability tasks easier", with two helpful features: "interesting subgraphs that remain visible over time and interesting patterns in node movement. The former is supported by preserving the mental map while the latter is not." (https://eprints.gla.ac.uk/66915). The survey's verdict: "the role of the mental map is not yet clear, but at least there are indications that its role might have been overestimated in the literature."
- **Animation versus small multiples.** Archambault, Purchase, Pinaud (IEEE TVCG 17(4), 2011, https://doi.org/10.1109/tvcg.2010.78): "small multiples gave significantly faster performance than animation overall"; "small multiples had significantly more errors than animation for the tasks of determining sets of nodes or edges added to the graph during the same timeslice"; "Preserving the mental map under either the animation or the small multiples condition had little influence". The survey's synthesis: "timeline-based approaches seem to be preferable for tasks involving more than two time steps"; "animation tends to reveal more findings on adjacent time steps while small multiples foster the discovery of patterns lasting over longer periods"; "hybrid approaches mixing animation and timeline, under certain conditions, can produce better results" (Rufiange and McGuffin 2013).
- **Transitions.** "for the straightforward solution of just morphing one layout into the other, too many changes may happen at the same time to be traceable by the viewer." Marey's four phases: remove, translate as one object, move nodes individually, then show new nodes and edges (STAR). Heer and Robertson (TVCG 2007, https://doi.org/10.1109/tvcg.2007.70539): "animated transitions can significantly improve graphical perception." Bederson on placement ("once an object is placed in space, it should not move") and on 500 ms transitions is already surveyed here on 2026-09-28 (lines 570 to 576).
- **What force libraries do on add and remove.** d3-force: "If either x or y is NaN, the position is initialized in a phyllotaxis arrangement"; "If the specified array of nodes is modified... this method must be called again... the simulation does not make a defensive copy" (https://d3js.org/d3-force/simulation, source https://github.com/d3/d3/blob/main/docs/d3-force/simulation.md); d3-force-3d says the same for x, y, z (https://github.com/vasturiano/d3-force-3d). Position carries over only through object identity: D3's own temporal example keeps a `Map` of the old nodes and writes "Make a shallow copy to protect against mutation, while recycling old nodes to preserve position and velocity... `nodes = nodes.map(d => ({...old.get(d.id), ... d}))`", then `simulation.alpha(1).restart()` (https://observablehq.com/@d3/temporal-force-directed-graph, source via api.observablehq.com). 3d-force-graph's `graphData` "Can also be used to apply incremental updates" (https://github.com/vasturiano/3d-force-graph, tags to v1.80.1, last commit 2026-09-29); its dynamic example passes the same node objects back (`nodes: [...nodes, { id }]`, https://github.com/vasturiano/3d-force-graph/blob/master/example/dynamic/index.html). On every `graphData` change the engine does `.stop().alpha(1)// re-heat the simulation ... .nodes(state.graphData.nodes)` (https://github.com/vasturiano/three-forcegraph/blob/master/src/forcegraph-kapsule.js), so existing objects keep their x, y, z and the whole graph is reheated; new objects without positions start in the phyllotaxis.

Already said here: the 2026-09-28 survey (lines 570 to 576, Bederson); AGENTS.md's "Preserve orientation" rule is the workspace's own statement of the same concern.

Silences:
- None of the sources read gives a number for how much node movement a reader tolerates per step.
- The 1995 paper's own formal models were not read.
- The 3d-force-graph README does not state that positions survive `graphData`; it is inferred from its source and d3-force's docs.
- No study found tests the mental map in 3D or with a containment hierarchy fixed.

### 3. Identity across renames and moves

- **git infers renames; it records none.** The git FAQ: "Relying on explicit rename tracking makes it impossible to merge two trees that have done exactly the same thing, except one did it as a patch (create/delete)... By only relying on the ability to recreate this information when needed, Git aims to provide a more flexible way" (https://git.wiki.kernel.org/index.php/GitFaq, last modified 15 March 2019). `-M`: "If <n> is specified, it is a threshold on the similarity index (i.e. amount of addition/deletions compared to the file's size)... The default similarity index is 50%." (https://git-scm.com/docs/git-diff). diffcore-rename merges a D and an A pair into `R100 fileX file0` when "the contents of the deleted file fileX is similar enough" (https://git-scm.com/docs/gitdiffcore). `--follow`: "Continue listing the history of a file beyond renames (works only for a single file)." (https://git-scm.com/docs/git-log). `diff.renames` "Defaults to true" for porcelain only; `diff.renameLimit`: "The number of files to consider in the exhaustive portion of copy/rename detection... the default value is currently 1000" (https://git-scm.com/docs/git-config).
- **Directory renames** exist in git only at merge time: `merge.directoryRenames` decides "what happens at merge time to new files added to a directory on one side of history when that directory was renamed on the other side"; "Defaults to conflict." (https://git-scm.com/docs/git-config). Log and diff report a directory rename as per-file renames.
- **Tools.** Gource: rename is delete plus add, by design since 0.15 (section 1). Repo Visualizer: "`--no-renames` means renames always appear as 'D' on the old path and 'A' on the new path", adopted because combined paths such as "src/{Old => New}/file.css" broke parsing when directories were renamed (https://github.com/Jany-M/repo-visualizer/blob/main/scripts/analyze.mjs). Hercules detects renames itself: "RenameAnalysis improves TreeDiff's results by searching for changed blobs under different paths"; "CGit's default is 50%. Ours is 80% because 50% can be too computationally expensive", with a 60-second per-commit timeout (https://github.com/src-d/hercules/blob/master/internal/plumbing/renames.go). The Evolution Matrix: a renamed class "will be treated as a class which has been removed and a new class which has been added", and a "massive renaming of classes" shows as a growth leap (Lanza 2001).
- **Research on entity identity.** Kim, Pan, Whitehead (WCRE 2005, https://doi.org/10.1109/wcre.2005.33): "Most software evolution researchers use entity names, such as file names and function names, as entity identifiers... Unfortunately names change over time"; their function-level matcher's "accuracy is better than the average accuracy among human judges". Godfrey and Zou (TSE 2005, https://doi.org/10.1109/tse.2005.28) extend origin analysis to "merging and splitting of files and functions", using "how call relationships have changed".

What breaks on a wholesale directory rename, per the sources: in Gource, every file under the old directory is deleted and re-added elsewhere (issue #61); in the Evolution Matrix, the whole population turns over; in git, detection is per file and bounded by `diff.renameLimit` for the inexact part.

Already said here: the 2025-11-10 record (lines 2186 to 2192) retired git-derived churn metrics from the committed docs because two clones' local histories differ, and 2025-11-11 (lines 1530 to 1536) allowed "your own local, biased git history" for ephemeral views. Rename inference is one more place where two runs can disagree (different thresholds and limits); that is a reading of the sources, not a source.

Silences:
- No source found describes a visualization that tracks a directory's identity through its rename.
- git's docs do not say how `diff.renameLimit` interacts with very large directory moves beyond the sentence quoted.
- The Kim and Godfrey abstracts work at function level; neither addresses visual continuity.

### 5. Data size and memory in the browser

- **Events versus snapshots.** Gource stores an event log of A/M/D lines and replays it (section 1). Repo Visualizer stores per-commit `changes` with `resolvedImports` in one `history.json` and replays from scratch to seek backward (section 1). git itself is snapshots deduplicated by content, then delta-compressed on packing: "Git thinks of its data more like a series of snapshots of a miniature filesystem... if files have not changed, Git doesn't store the file again, just a link to the previous identical file" (https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F); "When Git packs objects, it looks for files that are named and sized similarly, and stores just the deltas from one version of the file to the next", and "the second version of the file is the one that is stored intact, whereas the original version is stored as a delta" (https://git-scm.com/book/en/v2/Git-Internals-Packfiles). Hercules's caveat on output size: "`hercules`' output for the Linux kernel in 'couples' mode is 1.5 GB and takes more than an hour / 180GB RAM to be parsed" in Python YAML, with Protocol Buffers as the advice, and "hibernation" to disk against out-of-memory (https://github.com/src-d/hercules).
- **JavaScript heap.** V8 blog, 2020-03-30: "V8 in Chrome already has a 2-GB or 4-GB limit on the size of the V8 heap (depending on how powerful the underlying device is), even on 64-bit architectures"; pointer compression "reduces V8 heap size up to 43%" and "Chrome's renderer process memory up to 20% on Desktop"; on real sites "tagged values occupy around 70% of the V8 heap" (https://v8.dev/blog/pointer-compression). V8 blog, 2019-06-25: `JSON.parse('…')` is "1.7× as fast" as an equivalent object literal in V8 and faster "in all major JavaScript engines"; "A good rule of thumb is to apply this technique for objects of 10 kB or larger" (https://v8.dev/blog/cost-of-javascript-2019). deck.gl's performance guide (last changed 2025-04-10): interactivity holds "up to about 1M (one million) data items", dropping to 10 to 20 FPS near 10M; "Chrome caps individual allocations at 1GB", so layers crash "somewhere between 10M and 100M items"; a JS array of objects will "take valuable CPU time to create, and significantly more memory to store than its binary form"; typed arrays can be "transferred directly" to workers "bypassing serialization and deserialization of JSON objects" (https://github.com/visgl/deck.gl/blob/master/docs/developer-guide/performance.md).
- **Typed arrays for graphs.** cosmos.gl takes positions and links as `Float32Array` (`setPointPositions`, `setLinks`), does "All the computations and drawing... on the GPU", handles "hundreds of thousands of points and links on modern hardware", and animates position changes by default (`transitionDuration: 800`) (https://github.com/cosmograph-org/cosmos, now cosmosgl/graph, pushed 2026-10-16).
- **localStorage.** "limited to 10 MiB of data maximum on all browsers. Browsers can store up to 5 MiB of local storage, and 5 MiB of session storage per origin." (https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria, source last changed 2026-01-05). "Both `sessionStorage` and `localStorage` in Web Storage are synchronous in nature... blocking the execution of other JavaScript code until the operation is completed"; "Asynchronous alternatives, such as IndexedDB, may be more suitable" (https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API). Values are UTF-16 strings (https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage).
- **IndexedDB, Cache API, OPFS quotas** (MDN, same page): Firefox best-effort is the smaller of "10% of the total disk size" or "10 GiB"; persistent up to "50% of the total disk size, capped at 8 TiB"; Chromium "up to 60% of the total disk size in both persistent and best-effort modes"; Safari browser apps "around 60% of total disk", other WebKit apps "around 15%"; over quota, writes fail "with a `QuotaExceededError` exception"; eviction under pressure is least-recently-used origin first, skipping persistent origins. The Storage Standard (Living Standard, updated 6 October 2026): "The storage quota of a storage shelf is an implementation-defined conservative estimate... It must not be a function of the available storage space on the device." (https://storage.spec.whatwg.org/).
- **file://.** "Modern browsers usually treat the origin of files loaded using the `file:///` scheme as opaque origins... if a file includes other files from the same folder (say), they are not assumed to come from the same origin, and may trigger CORS errors" (https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy). "Many browsers, including Firefox and Chrome, now treat all local files as having opaque origins (by default). As a result, loading a local file with included local resources will now result in CORS errors." (https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS/Errors/CORSRequestNotHttp, changed 2025-11-30). For modules: "if you try to load the HTML file locally (i.e., with a `file://` URL), you'll run into CORS errors due to JavaScript module security requirements" (https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules). Storage on an opaque origin is not covered by the quota page, which "assumes that data is always stored per origin".

Already said here: the owner's December 2025 idea to "write **many** copies of the raw underlying data which undergirds those visualizations" (`2026-10-09-owner-scenarios-mined.md` line 294); ideas.md, the bullet "The graph over time": "One state is already cheap: check a commit out into a worktree, run the generator, read its `index.json`. Nothing yet compares two graphs or draws the difference."

### 6. The directory tree as the stable skeleton

- **Gource** animates over containment, not connectivity: directories are branches held by parent attraction, outward push and sibling repulsion, and new directories start beside their parent at a path-hashed offset (section 1). Its docs give no rationale for choosing the tree beyond describing it.
- **CodeCity time travel** keeps containment fixed in space: "every artifact is assigned an individual real estate in the city, maintained throughout the entire evolution... denoted by an empty space that cannot be occupied by other artifacts" (already surveyed here on 2026-09-28, line 738).
- **EvoStreets** (Steinbrückner and Lewerentz, SoftVis 2010, https://doi.org/10.1145/1879211.1879239): "a new layout approach which explicitly takes the development history of software systems into account and makes history directly visible in the layouts. These layouts incrementally evolve in a very smooth and stable way during the development".
- **Stable treemaps.** Sondag, Speckmann, Verbeek (TVCG 24(1), 2018, https://doi.org/10.1109/tvcg.2017.2745140): "If the data changes, then a second important quality criterion is the stability of the treemap... Vernier, Sondag, Comba, Speckmann, Telea, Verbeek (CGF 39(3), 2020, https://doi.org/10.1111/cgf.13989) test "14 state-of-the-art rectangular treemapping algorithms" on "more than 2000 datasets" and find "the performance of treemapping algorithms depends on the characteristics of the datasets used".
- **Voronoi treemaps over time.** Tua, Minelli, Lanza, "Voronoi Evolving Treemaps" (VISSOFT 2021, https://doi.org/10.1109/vissoft52517.2021.00032): "able to display the complete evolution of a software system in terms of its hierarchical structure". - **Hierarchy plus dependency edges.** Holten's hierarchical edge bundles (TVCG 12(5), 2006, https://doi.org/10.1109/tvcg.2006.147) is static but takes the same shape: "We assume that the hierarchy is shown via a standard tree visualization method. ### Read-across

What the sources agree on:
- Version control yields events or snapshots, and visualizers re-derive state by replay. Gource replays an A/M/D log; Repo Visualizer replays per-commit changes and seeks backward by replaying from the start; Gource seeks by rebuilding from a log offset.
- A rename is, by default, a deletion and an addition. git infers renames by similarity (50% default, 80% in Hercules) and records none; Gource and Repo Visualizer turn inference off on purpose; the Evolution Matrix names this as a limitation.
- Stability is bought by reusing the previous positions: Beyer and Hassan seed each panel's layout with the last; D3's examples recycle node objects by id; 3d-force-graph keeps positions only when the same objects come back, and reheats the whole graph on each update.
- Containment-based layouts (Gource's tree, CodeCity's lots, EvoStreets, stable treemaps) are the field's usual way to keep places fixed over time, and they reserve or grow space rather than recompute it.
- Large data in the browser moves to typed arrays and binary formats (deck.gl, cosmos.gl); localStorage is small (5 MiB) and synchronous; IndexedDB quotas are large and implementation-defined; a `file://` page cannot load sibling files by `fetch` or modules in Firefox and Chrome by default.
- Sliders follow one keyboard grammar (arrows, Home, End, Page Up/Down) and should announce human-readable values; moving content longer than five seconds needs a pause.

Where they disagree:
- Whether preserving the mental map helps. Most comprehension experiments found no conclusive benefit (Archambault and Purchase 2013); orientation tasks did benefit (2012); memorability showed no measured difference but a perceived one.
- Animation versus small multiples: multiples are faster and better beyond two time steps; animation has fewer errors for "what was added in this step" tasks; hybrids can beat both.
- How to sample time: every commit (Repo Visualizer), continuous clock with idle skipping (Gource), fixed project time per frame (code_swarm), weekly (git-of-theseus, GitHub), or per release or per N changes (Beyer and Hassan, who warn the last two hide elapsed time).
- Offline (whole history known, supergraph or foresighted layout) versus online (past only) layout: offline preserves the map better; online is more flexible; Brandes and Mader found linking adjacent steps better than fixed positions.

What they leave open:
- How much movement per step a reader tolerates, in any number.
- Any study of mental-map preservation in 3D, or with a fixed containment skeleton plus moving dependency edges.
- Visual identity through a directory rename.
- Measured memory per node and edge for JSON graphs in today's engines, and whether IndexedDB offloading lowers a tab's resident memory.
- Practical limits of Gource itself on long histories.
- Whether a dependency-graph animation over git history has been evaluated with readers at all; the two found (Evolution Storyboards 2006, Repo Visualizer 2026) report no user study in the text read.

- **What regeneration costs.** Today's generator over a past tree checked out as a detached worktree, dry run, on this machine: 11.6 s over the tree of 2026-04-02 (661 files documented of 1,633 tracked), 15.6 s over the tree of 2025-12-19 (670 of 1,562), and 32.6 s over today's tree (723 documented, with the tracked-file listing and the entry index). Found on the way: the generator's `--workspace` option read neither the worktree's `.live-docs.config.json` nor this repository's and wrote the shipped default root (`.live-documentation/source/`), so a history command would have to read the configuration as it stood at each commit, or be given one.
- **How much changes per commit.** Over the last 120 commits that touched the mirror, a mean of 34 docs changed per commit and a maximum of 563 (a regeneration that touched every doc). A per-commit delta is small against 723 docs.
- **How big a snapshot is.** The derived graph today is 723 files, 3,861 edges and 2,614 public symbols. `index.json`, with every doc's symbols, authored text and edges, is 4.8 MB; the file ids with their edge targets alone, as JSON text, 439 KB; with the ids interned to integers, less again. ## Part 4. The agent's reading for this project

_Read by the root agent on 2026-10-16 from Parts 1 to 3. A judgement, not a decision; the owner's answers at the forks are the decisions, and the forks themselves are put in [the October 16 record](../ChatHistory/2026/10/2026-10-16.1.record.md#turn-2)._

1. **One lens over the whole history.** A committed mirror at a commit carries the generator of that day, and the adapters changed a great deal between 2026-09-27 and today (entries, C and C++ by the grammar, hidden files read). A sequence read from the committed docs would mix the tool's growth with the code's. Regenerating every commit with one generator version, at twelve to thirty seconds a commit here, keeps the lens constant, which is what "through its own lens" asks; the committed mirror is a shortcut only where the generator is the same. Both ways the docs stay the per-commit truth and the sequence is derived.
2. **Events, derived once, kept as deltas.** The field replays events (Gource, Repo Visualizer) and pays for it with a seek that rebuilds from the start; git keeps snapshots and packs deltas. A base graph with per-commit deltas (files born, dead, renamed, resized; edges added and removed), ids interned, materialized one snapshot at a time, seeks either way without replay and fits inline in the single file. Here a whole history would be a few megabytes against about 250 MB of full snapshots as JSON.
3. **A rename is a move, read from git, said honestly.** Gource and Repo Visualizer drop renames and pay with directories that vanish and reappear; git's inference at its default threshold found the three September renames here whole. A file below the threshold is a death and a birth, and the picture should say so rather than invent continuity. This is the cousin of the 2025-11-10 constraint: inference differs by threshold and by clone, so the sequence is derived data beside the bundle and never a line in a Live Doc.
4. **Hold the tree; move only what changed.** The structure layout's hubs are the skeleton the field keeps still (CodeCity's lots, Gource's branches, EvoStreets); a file is born at its hub, dies in place, and slides to its new hub on a rename; hub volumes breathe with exposed surface; no re-layout per snapshot. The connections layout is not the timeline's first home, because every edge change would move everything. The mental-map evidence is mixed, but the orientation task, which is what a scrubber asks of a reader, is the one where preserved positions measured faster with fewer errors.
5. **Feed the running simulation; never restart it.** The renderer already keeps node objects by id and has an update path with no warm-up; the library reheats on every data change and seeds a new object in a phyllotaxis unless its position is set, so a born file must be placed at its hub before the update, as a new hub already is at its members' centroid. A step is then a small reheat, not the hundred-tick warm-up that costs two to six seconds.
6. **Time as commits, with a clock beside them.** Step by commit as the unit of truth (every commit is cheap as a delta), with Gource's seconds-per-day for playing and a skip over quiet stretches, and what changed in the step shown beside the picture (GraphDiaries, Evolution Storyboards): the commit's message and the files and edges that changed, since animation's one measured strength is "what was added in this step".
7. **The control follows the slider grammar** (arrows, Home, End, Page Up and Down, a spoken value as date and commit) with a pause by WCAG; the address carries the commit, so a link shares a moment, by the readable-link rule.
8. **Memory is a question of shape before place.** Deltas and interned ids keep a whole history in a few megabytes of heap; typed arrays if a repository's history outgrows that; IndexedDB only if measured necessary; never localStorage, which is 5 MiB and synchronous. The `file://` origin rule means the single file inlines the sequence; a served bundle may fetch eras.
9. **Headless first, as always.** A history command in the generator produces the sequence, reading the configuration as it stood at each commit or given one; `inspect` answers "at commit X" and "between X and Y" in text and JSON; the oracle is git itself (a file's birth, death and renames by `git log --diff-filter` and `-M`) and this repository's own September renames read by hand as an expectation. Nothing grades itself.
10. **Out of scope now:** TFS, whose history lives on a server rather than in the folder; the 2D Local Map; the World Map's two-snapshot board; the flyover of a system in action; a user study.
