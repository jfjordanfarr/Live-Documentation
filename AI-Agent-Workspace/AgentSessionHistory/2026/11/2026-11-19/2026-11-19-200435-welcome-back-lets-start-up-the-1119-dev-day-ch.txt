  - **Bytes alone:** the TypeScript parse, the exported symbols with their doc
  comments, the raw import specifiers, the binary sniff, and the
  path-and-configuration part of the archetype.
  - **The rest of that commit's tree:**
    - the index pass (the symbol index, and the entry index from every
  manifest);
    - resolving dependencies against the files on disk;
    - re-exported symbols, which read the providers;
    - DOM and route inference;
    - every language adapter, which is given the file and symbol indexes, and
  several of which mix reading facts with resolving them;
    - Cited By, the authored block from the commit's own docs, whether linked
  documents exist, and the graph read back from all the docs.
  - **What of October 19 exists in the code:** the extraction-versus-resolution
  boundary is a principle, not a seam. Only caches that live for one run exist.
  There is no saved form of unresolved facts and no store across runs. The
  October 19 prototype saved nothing and was removed. The history's per-commit
  process can reuse nothing across commits today.

  ## The three shapes
  **(i) Write only what is read.**
  - **Saves.** Writes fall from 521 GB to 11 GB (98%), and most of the 17 to 28
  s of tree writing at late commits goes. Early commits gain little. At the
  head's rate the line's writes are about 3.6 to 5.6 of the rebuild's 22
  processor-hours.
  - **Needs.** The tree writer leaves out what `exclude` names, using
  discovery's own matcher. The check that a linked document exists must ask the
  commit's file listing, not the disk. Otherwise the markdown under the excluded
  folder must still be written: 51 GB, because records are large.
  - **Cost.** Small. It touches `git.ts` and `summarizeChange.ts`, which are
  both in the lens key, so it rides with the owed rebuild.
  - **Risk.** A future reader of excluded files would silently see less. The
  oracle comparison guards against that.

  **(ii) Move one tree from commit to commit.**
  - **Saves.** Writes fall to 2.6 GB alone. After (i), only 0.35 to 0.7 GB of 11
  GB remains to save, about 2% of the original writes.
  - **Needs.** Each process must take a contiguous run of the line in order.
  Today the pool hands commits to whichever process frees first, so neighbours
  land in different processes. Contiguous runs lose load balancing, since late
  commits cost three to five times early ones.
  - **Risk.**
    - The generator's own writes must be cleaned between commits.
    - Either git checkout's rules for names, links and case replace the careful
  tree writer's, or the difference-applying code must be written anew.
    - A leftover from the previous commit could silently enter a summary.
  - **Verdict.** Do not build.

  **(iii) Analyse each distinct version once.**
  - **Ceiling.** Large: 977,305 file-moments rest on 7,203 versions.
  - **The time it can reach.** The index pass plus per-file analysis is 75% of
  the generator. How much of that is reading facts, as against resolving them,
  starting up, loading grammars, or the 2.5 s pause October 19 found after the
  PowerShell adapter, is unmeasured.
  - **Cost.** Large: a saved form of every adapter's unresolved facts, a store
  keyed by version and code identity, and a second pass that resolves only from
  those facts. The far end, reading from git's object store with no tree, also
  replaces the disk access every adapter uses.
  - **Risk.** A cached fact that secretly depended on its neighbours, which
  October 19 found twice.
  - **Verdict.** Do not build it until the index pass is broken down. If it
  turns out to be a fixed cost per process, there is a cheaper fix: the pause
  alone is about 50 processor-minutes across the line.

  **How they compose.** (i) composes with both (ii) and (iii); (iii) with no
  tree on disk would make (i) and (ii) unnecessary.

  - **In isolation**, two parses of the 23 KB `powershell-ast.ps1` take about
  120 ms. The next event-loop turn then takes 11–13 s, all of it one V8 worker
  thread's processor time, with 0 ms on the main thread.
  - **Under `--liftoff-only`** that turn takes 2 ms.
  - **Under `--no-liftoff`** the same 10.8 s lands on the main thread inside the
  parse instead.
  - **It is not our patch:** the engine's patched grammar and the bundled
  `@vscode/tree-sitter-wasm` grammar behave the same.
  - **It is not** a garbage collection, a file read, the grammar's load, or
  anything in the adapter's JavaScript.
  - **The C++ grammar** shows a smaller pause of the same kind, 0.5–1.2 s.
  - **Liftoff alone parses PowerShell about 2× slower** (20 parses: 609 ms
  against 326 ms). At this repository's 17 PowerShell files that is a few tens
  of milliseconds.

  **Across a history rebuild** of 1,224 per-commit processes, the pause costs
  about **1.7–3.7 processor-hours of the 22**.

  ### 3. Work done twice

  - **Every TypeScript and JavaScript file is parsed twice:** once in the index
  pass (2.0–2.7 s) and again in `analyzeSourceFile` (1.0–1.9 s). Providers are
  parsed a third time inside `augmentWithReExportedSymbols`. Parsing each file
  once would save about 1.0–1.9 s of main-thread time, 5–10% of a Liftoff-only
  generation. It needs either keeping every AST alive between the passes (memory
  not measured) or the extraction seam that does not exist yet.
  - **Adapters run in both passes,** but most keep their own facts within the
  process. At the head their second pass cost 0.15 s in all.
  - **Reads.** At the head, 944 of the 2,213 paths read were read more than once
  (3,561 calls in all): every TypeScript file twice, C# files and C headers
  three times, some JSON four times. In a writing run every existing Live Doc is
  also read twice. All reading together is 0.2 s of the index pass and 0.5–0.9
  s of the analysis pass, so a read cache would save well under a second.

  ### 4. How it grows with files

  Under Liftoff-only, the index pass took 4.25, 4.34 and 4.72 s at 534, 858 and
  1,091 files. Its TypeScript parse took 2.04, 2.29 and 2.65 s, about 30% growth
  for twice the files.

  - **Fixed per process:** the TurboFan pauses, 5–11 s, paid whenever a
  PowerShell (or C++) file is parsed at all, whatever the file count. Also
  grammar loading (under 0.4 s for all grammars) and a memory baseline of about
  200 MB.
  - **Grows with files:** both TypeScript parses, and the analysis pass's
  resolution and composition. The analysis pass ran 4.7–7.1 s, too noisy under
  this load to give a slope.

  ### 5. Memory

  | Peak resident memory, dry run | Early | Middle | Head |
  | --- | ---: | ---: | ---: |
  | Default flags | 424 MB | 385 MB | 403 MB |
  | Liftoff-only | 224 MB | 232 MB | 253 MB |

  - **Writing runs** at the head, with the profiler running, peaked at 497–510
  MB.
  - **Most of the default figure is the TurboFan compile.**
  - **Per file:** roughly 50 KB above a baseline of about 200 MB. That is a
  slope from three points under load, so treat it as rough. At that rate even
  20,000 files would stay near 1.2 GB, comfortable on an 8 GB machine.

  ### 6. What follows

  1. **A plain waste, removable with identical results: turn off the WebAssembly
  optimizing tier.**
     - **How:** `--liftoff-only` or `--no-wasm-tier-up` on the processes the
  tool forks, `NODE_OPTIONS` for the CLI, or `v8.setFlagsFromString` before the
  first grammar loads.
     - **Why results stay identical:** it changes only how V8 compiles the
  grammar's machine code, never what the parser produces.
     - **What it saves:** 5–11 s of wall time, 7–17 processor-seconds and
  150–200 MB of memory per process; about 2–4 processor-hours of a rebuild.
     - **What it costs:** one line and a comment saying why.
     - **Before landing, check** that `--no-wasm-tier-up` gives the same relief,
  since only `--liftoff-only` was measured. Also check that a repository heavy
  in PowerShell or C++ parses fast enough on Liftoff alone.
     - **Do this first.**
  2. **Parsing each TypeScript file once** would save about 1–2 s of the roughly
  14 s left per process. It costs either AST memory or the extraction seam. Not
  worth doing on its own.
  3. **A store of per-version results** could reach at most about 4–5 s of a
  10–14 s process: the parses and extraction. It cannot reach discovery,
  resolution, composition, Cited By or process start. It needs the full seam
  between extracting a file's facts and resolving them, and it carries October's
  risk of a cached fact that secretly depends on its neighbours. **Don't build
  it now.** Remove the pause, write only what is read (shape (i) of the
  history-rebuild probe), then measure a rebuild again.
  4. **Don't build** a read cache, or an AST cache between the passes before its
  memory is measured.

  ### What was not measured

  - **Machine and repetitions.** Nothing was measured on an idle machine, and
  each configuration in the final set ran once.
  - **WebAssembly flags.** Neither `--no-wasm-tier-up` nor
  `--wasm-dynamic-tiering` was tried.
  - **The pause's internals.** I did not find which WebAssembly function is
  compiled (likely the generated lexer), or why the main thread blocks on that
  compile.
  - **AST-cache memory** was not measured.
  - **Writing runs at old commits** were not possible: today's graph reader
  rejects their committed docs.
  - **The history's own `summarizeChange` process** was not run. Process start
  and the text store are outside these figures.
  - **No browser** was needed.

  ### 1. Why the main thread waits

  - **The function:** `--trace-wasm-compilation-times` names function #3 of the
  PowerShell grammar. Its body is 377,471 bytes; TurboFan took 9.7 s and 167 MB
  of compiler memory (75 MB at peak). It is almost certainly the generated
  lexer, `ts_lex`, but I could not confirm the name because the module has no
  names. The bundled grammar behaves the same.
  - **What the main thread does:** `strace` shows it in one futex wait of 6.98
  s, with no processor time, released when the compiling thread finishes.
  - **The cause, in Node 22's source:**
    - Each time the libuv loop returns, Node calls `DrainTasks`, which waits
  until every background worker task is done.
    - V8's optimizing compile job is one of those tasks.
    - The promise from a WebAssembly compile is settled by a V8 task that does
  not keep the loop alive. So the code awaiting the grammar's load is resumed
  inside that drain; its first parses make the lexer hot, and its next `await`
  drops back into the drain, which then waits for the whole compile.
    - This is the same stall as nodejs/node#36616.
    - Node 24.0.0 (nodejs/node#58047) only waits for user-blocking tasks. That
  change was not backported to 22.
  - **Experiments that confirm it:**
    - With the timer held, the slowest turn of the event loop across 40 parses
  fell from 8.6 s to 2 ms.
    - Under the `tsx` command, which holds standard input open, there was no
  stall either.
    - With the timer held, the 40 parses finished in 0.7 s, but the process
  ended at 7.9 s, and at 12.2 s even with `process.exit()`. This is why the wait
  at the end cannot be removed on Node 22.

  ### The rule (`document.ts`)
  - **One rule for every value from a source file.** `writeValue` writes it in
  the slot's plain form, the form the format always wrote, wherever that reads
  back as the value. Anywhere else it writes a JSON string. `takeValue` is the
  inverse.
  - **Telling the forms apart.** No plain form starts with `"`, so the first
  character decides. The reader refuses a quoted value that the plain form could
  carry, so each value has exactly one form.
  - **Reading lines.** One cursor reads each line left to right, and every value
  delimits itself. All the per-line patterns (`` `([^`]+)` ``, `[^)]+`, the
  `split(", ")` / `split("; ")`) are gone.
  - **Links are URL references.** The composer percent-encodes what a URL or a
  markdown target can't hold: `%`, `&`, `#`, `?`, `(`, `)`, `<`, `>`, `\`,
  spaces, controls, U+2028/9. That is `encodeLinkPath`, applied through `linkTo`
  in `compose.ts`. `graph.ts`'s `resolveDocLink` decodes the path before the
  first `#`.
  - **Docstring lines.** A line the reader would take for structure gets a
  backslash in front (`escapeBody` / `unescapeBodyLine`). That covers a heading
  outside a fence, any `<!-- LIVE-DOC:` marker, and a fence no later line
  closes.
  - **Line endings.** A line ends at LF or CRLF alike, in the `Reader` and in
  `authoredBlockOf`.

  |---|---|
  | Key `{"a\nb":1}` | `#### "a\nb" {#symbol-ab}` |
  | Key with CRLF | `#### "a\r\nb"` |
