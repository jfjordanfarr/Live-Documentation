## What was built

1. **Each summary read once, each text read once.** Until now a run read, unzipped and parsed every summary at its start to find which were damaged, and again to build the sequence, and read every text twice. Now the start asks only whether each summary stands (`absentFromCache`); whether a summary reads, and whether the texts it names are in the store as the text of their hash, is found where the sequence reads it (`deriveSequence`). A damaged one is summarized again and the sequence read again; a changed text is removed first, so that the new summary writes it. The texts the sequence names are read once, held to their hashes, and kept for the words and the check at the head.
2. **Going on from the sequence the last run wrote.** Below.
3. **The steps' git words asked early.** `changesBetween` is unchanged (it lives in `git.ts`, which keys the lens). It is now asked for every new step before any summary is read, eight at a time, while the command's process is small: the earlier measurement put 12 of the 17 s of 1,333 calls on starting processes from a large heap. One git process for all the steps (`git diff-tree --stdin`) would need new git code whose answer must be shown equal to `git diff`'s at every pair; with the run going on from the last sequence, a warm run asks git for its new steps alone, so that was not built.
4. **The check at the head from git's object store.** `committedLiveDocGraph` in `headCheck.ts` lists the head's tree, reads the docs under the base layer by one `git cat-file --batch`, follows a link among them through the commit's own listing as the tree writer does (`followLink`, imported from `git.ts` unchanged), and parses each as `readLiveDocGraph` does. Before, the head's whole tree was written for this. A name a disk would fold into another's is now read under its own name; the generator writes no such names. _(Corrected 2026-11-20 by the review below: the generator mirrors source names, so such docs can stand, and the summaries' side leaves them out; a link among the docs alone was not enough to follow a link.)_
5. **`--rederive`** derives every step, whatever the last run wrote.

## Going on from the written sequence: the key, and why it is enough

The root's ruling: reuse a written sequence's steps only under the same lens key, the same configuration, the same code that reads summaries into a sequence (given an identity), and when the stored commits are exactly a prefix of today's line.

What was built, and where it is stricter or simpler than the ruling:
- **The record.** `<root>/history/history-resume.json` is written after `history.json`: its SHA-256 (so that a record never describes a sequence it was not written with, whatever stopped a run between the two files), the key, each text's hash by its id, the place of the change that first named each text (so that a damaged text found later can be mended by summarizing that change again), and the entries the trees did not hold (for `unwritten.txt`).
- **The key.** The lens's key; `sequenceCodeIdentity`, a hash of every file of the two packages but the tests (keyed or not), the lock, the version and the runtime's Unicode, the commit left out; and the whole configuration. The ruling asks for the configuration the reading reads (the bundle's exclusions and the docs root); the whole configuration is simpler and never wrong, at the cost of a whole derivation after an edit of a part the reading does not read.
- **The line.** Every change of the written sequence, its base and each step, must be the first of today's sampled changes as this run would write it: id, parents, date, author where the sequence carries authors, subject. That holds the sampling and `--no-authors` too. The whole written sequence must be a prefix, not just its first steps: a sequence that stopped short of today's line has strings in its tables, under ids, that a whole derivation would not hold or would hold under others, so the bytes would differ.
- **One more guard.** The written sequence's last moment, replayed as a reader replays it, must be the shape and rows of its last change's summary read afresh: what that step was held to when it was written. Otherwise the run says so and derives every step.
- **Why the bytes are the same.** The written sequence's tables are the writer's interners in order; its keyframes and the deltas written after depend on the moment's content and the tables alone (a keyframe is encoded in path order and sorted by id, and every string it names is already in the tables). `sequence.test.ts` builds a sequence whole and in two parts read back from JSON, stopped on either side of a keyframe, and holds the bytes equal; it went red with the keyframes dropped and with a table reordered. The integration test grows a scripted repository by a commit and holds the run that goes on to a `--rederive` run byte for byte, sequence and words; it went red with the prefix check taken out, where the replay guard caught the rewritten line instead.
- **What a continuing run does not look at, a trade.** It does not read the summaries of the written steps, so a damaged old summary is found and summarized again at the next whole derivation (`--rederive`, or any change of the key), not at once. The sequence already written stays right meanwhile: it was made when those summaries read, each step held to its summary, and the record holds it to its own hash. Every text is still read and held to its hash at every run, so a damaged text is mended at once; the integration test that removes and changes texts is kept unchanged, and runs in the gate (pending the lane).

## The root's two questions on the record, settled

- **An uncommitted edit moves the key.** `sequenceCodeIdentity` hashes the same `modified` half the lens does, for the files it counts: `checkoutOf` reads `git status` over the two packages and hashes the working bytes, or the absence, of every changed file the rule counts. `generator-identity.test.ts` holds it over a fixture checkout: an uncommitted edit of a history module moves it (twice, to two values) while the lens's key stays; committing moves it; a test, a file outside the packages and a commit of neither leave it. With `modified` left out of the identity the case went red at the uncommitted edit.
- **A half-written pair derives whole.** `history.json` and the record are each written to `<name>.<pid>.partial` and renamed into place (`writeInPlace`), the record after the sequence; a run's start removes any `.partial` a stopped run left. The integration case removes the record beside a sequence (as a run stopped between the two leaves it), and then puts an earlier run's record beside the newer sequence (as the next run would find it): each run says it was not gone on from, with the reason, and writes the same bytes. With the hash check taken out, the second went red.

## Milestone 2, drafted and not built: workers that live across commits and keep their tree

Notes, not product code: nothing of this is under `packages/`. The drafts are in [`drafts/`](drafts/), named `.ts.draft` so that no type check or test run picks them up; a successor builds from them. None of them has been compiled or run. The root's reading of each is given beside the builder's.

**What the generator writes into a tree, and reads back from it** (read in `generator.ts` and `summarizeChange.ts`, not traced): it reads the committed doc of each file before rewriting it (`readFileIfExists`, for the authored block and `generatedAt`; `summarizeChange.ts` reads every committed doc first, for whether its authored block can be read at all); it writes a doc where its rendering differs (`fs.writeFile`, the folders made with it), removes a doc its reader refuses that holds no words (`removeRefusedDoc`), prunes stale docs and the folders they leave empty (`pruneStaleLiveDocs`, `cleanupEmptyParents`), and writes `<root>/index.json` (`writeLiveDocGraph`). All of it lies under the configuration's root, which `treeOptions` already hands the tree writer as `docsRoot` (`docsRootWithin` gives `.mdmd` here, not the base layer). The task file lies in the scratch folder beside the tree, not in it. So a tree left as the last commit's regeneration is not the next commit's committed docs, and the docs root must be put right every time.

**[`drafts/git-tree-forward.ts.draft`](drafts/git-tree-forward.ts.draft): the tree brought forward** (for `git.ts`).
- `writeStoredTree` split, its rules unchanged, into `planTree` (the listing's rules: every refusal that does not ask the disk, links followed through the listing, an excluded picture marked empty) and `writePlan` (each entry placed by asking the disk, the blobs written), which also returns what it wrote.
- `bringTreeForward` compares the new change's plan with what was actually written for the old one, not git's word between the two commits: an entry is kept only where its mode, blob and emptiness are the same; every other entry of the old tree is removed, and every folder no entry of the new plan lies in, deepest first; the docs root is removed whole; then the new and changed entries are written in the tree's order, the disk asked before each as for a tree written anew. The root's reading: better than the brief's `git diff-tree`, since it makes the tree's own rules the single source and covers what the summarizing wrote (a link whose target changed, a picture written empty, the docs root). Keep it.
- Where the disk refuses an entry, or a folder that should be empty is not, it gives up and the caller writes the tree anew: a tree written anew settles two names a disk takes for one by the tree's order, and a tree brought forward could settle them otherwise, since the name already standing may be the later one.
- **The docs root rewritten whole** each time: about a seventh of the tree at this repository's head (1,115 of 7,962 files, 5 MB). Fine as the first form, and the next thing to narrow. To narrow it, the worker must know which docs the generator changed against the committed ones: the generator's result names each doc with its change (`files`: unchanged, updated or created), the pruned ones (`deletedFiles`) and the index; a doc `removeRefusedDoc` removed, and the folders `cleanupEmptyParents` removed, are not in it. With that list, only those paths and the commit's own changes under the docs root need putting right.

**[`drafts/git-repository-bring-to.ts.draft`](drafts/git-repository-bring-to.ts.draft): the seam** (for `git.ts` and `versionControl.ts`). `WorkingTree.bringTo(change, directory, options)` moves the tree's folder to a new name, removes its index, reads the new change's index beside the new name, and brings the tree forward, or writes it anew where bringing it forward gives up; `WorkingTree.broughtForward` says which.
- **Why the folder is renamed for every change:** so that no file's absolute path at one change is its path at another. That ends two stale-state entries at once (section 7 of [the speed record](../history-rebuild-speed/README.md)): the Rust adapter's `packageCache`, stale wherever a path is reused, and the path-keyed, modification-time-guarded `factsCache` of six adapters, which would serve a file's old facts wherever a rewritten file kept its time on a coarse clock.
- **What it costs:** a rename within one file system is one call, whatever the folder holds. What could hold the old path open: nothing of the worker's own between tasks (its streams are closed once a summary is written; its working folder is the command's, never the tree); on Windows a scanner or an indexer holding a handle in the folder makes a rename fail (`EPERM`, `EBUSY`), where the tree should then be written anew in a fresh folder, which the draft does not yet do. What remembers a path across the rename on purpose: nothing. The adapters' caches keep the old paths, never met again, until the worker is replaced, which bounds their memory (below).

**[`drafts/summarize-worker.ts.draft`](drafts/summarize-worker.ts.draft): the worker** (for `summarizeChange.ts`, which stays the summarizing entry the lens keys). Started once with `--worker <repository> <folder>`, it opens the repository itself and writes its own trees, so that the command's one main thread no longer writes every tree (the first limit the speed record found). For each task: the tree's git variables cleared, the tree written or brought forward, the new tree's variables set, the change summarized, and a report sent over the channel with the warnings, the entries left out, whether the tree was brought forward, how many files the generator failed on, and the process's peak memory since it began (what a lane of the pool holds, rather than one task's).

**[`drafts/regenerate-pool.ts.draft`](drafts/regenerate-pool.ts.draft): the pool** (for `regenerate.ts`). Runs of consecutive changes, about four to a worker, so that a worker's next change differs little from its last and the dearer end of the line still spreads over every worker; no change started after the deadline; a worker replaced after 100 tasks (a number to set from the memory measured over a long run, not yet measured), and after any task in which the generator failed a file. `RegenerationContext` gains `repository`, the top level the workers open; the guard test's reviewed list of its members must say why it cannot change a summary unkeyed.

- **Nothing writes to a parsed tree.** No code of the engine or the generator assigns to a `SourceFile` or a node, binds or transforms one, or keys a cache by one; the visitors collect into local arrays. TypeScript's own lazy caches are written: `lineMap` (by `getLineAndCharacterOfPosition`, `coreUtils.ts:169`, a function of the text) and `modifierFlagsCache` (by `ts.getModifiers`, `coreUtils.ts:149,160`, a function of the node's modifiers); `jsDocCache` is not reached on our paths. Each is the same whichever reader fills it first, so a shared tree is safe.
- **The three parse sites:** `sourceAnalysis.ts:91` (the analysis pass), `discovery.ts:391` (the index pass; another builder's file tonight, not edited here) and `dependencies.ts:548`, a third parse of every file behind an `export *`, repeated for each file that re-exports it. The only other parse is `adapters/json.ts:324–326`, a tsconfig's, private to its call. No adapter is handed a `SourceFile`.
- **The name.** No reader uses `sourceFile.fileName`, so a tree remembered from another commit's folder gives the same results; the parser reads the name only for `.d.ts` (the ambient flag), the script kind being passed explicitly. A memo keyed by the text, the script kind and whether the name ends in `.d.ts` is enough.
- **What a change would touch:** the three parse sites, a line each; a small module for the memo (beside `inferScriptKind` in `symbolExtraction.ts`, or its own); and either the memo threaded through `buildWorkspaceIndexes`, `analyzeSourceFile` and `gatherExportedSymbolsFromFile`, or a module-level memo the worker empties of what the last task did not use. All of it keys the lens. Within one commit it halves the parses even without workers.
- **Not measured:** what a worker's memo would hold. One commit's parses at the head are about 1,000 files, 9 MB of text; a parsed tree is commonly ten to twenty times its text, so 90 to 180 MB a worker, carried across a task, to be measured.
- **`git check-ignore` in a history tree** (`discovery.ts` and `tooling/gitIgnored.ts`, another builder's files tonight, not edited): every file of the tree is tracked when discovery walks the sources, so its answer is known to be none. What I would change there: an option the summarizing process passes through `generateLiveDocs` to discovery saying every file its walk finds is tracked, by which `keptByGitAndConfiguration` skips `gitIgnored` and `gitIgnoresCase` (which reads the clone's own `core.ignorecase` through the tree's `GIT_DIR`). Not checked: whether the documents' discovery runs before or after the docs are written.
