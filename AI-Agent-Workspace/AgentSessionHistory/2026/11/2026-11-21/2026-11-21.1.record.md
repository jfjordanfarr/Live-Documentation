| Compact binary of our own | 0.15 s, 2.2 s | 1.0 s, 351 MB | 2.83 MB | No |
| Indexed text, one fact per line | 0.08 s, 15.7 s | 0.6 s, then 1.7 GB for the whole map | 3.98 MB | Yes: `zcat`, `grep`, `diff` |
| SQLite | 1.6 s, 5.0 s | 7.2 s, 819 MB | 6.19 MB | Yes: any SQLite tool |
| HDF5 | 0.8 s, 2.6 s, after 6.7 s to load its library | 1.5 s, 395 MB | 8.82 MB | Yes: HDF5 tools |

- **JSON is out.** At 50k files it needs 26 seconds and 1.3 GB before it can answer anything.
- **HDF5 is out.** It writes different bytes every time for the same facts, and its library adds 5.6 MB to every saved page.
- **SQLite is the best on the command line and the worst in a page.** Read from disk by Node it gives the fastest first answer of any format, in the least memory. Written inside a page at 50k it takes 854 MB and over two minutes. Since you want both surfaces from one design, I count it out.

## The two that remain

- **Compact binary.** A table of contents, the connections as plain arrays of numbers, each string stored once, each section compressed separately. It is the only format whose numbers stay in proportion at 50k, and it has the smallest saved page. The cost is that nobody can read it without our reader.
- **Indexed text.** One fact per line, sorted by path, in compressed chunks with a small index. For example, one line lists the 632 files that depend on `Globals.cs`, so `grep` answers "what depends on this". It answers a first question as fast as the binary. Loading the whole map is slow and memory-hungry, but that was measured with the simplest possible reader, so it is not yet a fair comparison.

## Your decision

1. **Binary as the stored form, text exported on demand (my lean).** Fastest and lightest on a weak machine. You run one command or press one button when you want something to `grep`.
2. **Indexed text as the stored form.** Always readable with ordinary tools, about 40% larger, slower to load a whole map. How much slower is what the next leg measures.

I lean to the first because your stated priority is running "on absolute garbage", and you already expected Markdown to be an export. Which matters more to you: the speed and memory, or never needing our tool to read the facts?
